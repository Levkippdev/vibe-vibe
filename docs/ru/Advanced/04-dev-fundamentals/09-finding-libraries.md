# 4.9 Хватит изобретать велосипед

> **Цель раздела**: освоить самые используемые библиотеки экосистемы Node.js, научиться быстро находить подходящий инструмент и тратить время на бизнес-логику.

Сяомин хотел добавить в приложение бесконечный скролл, открыл Claude Code и сказал: «Помоги написать реализацию бесконечного скролла».

Claude Code немедленно начал писать код. Сидящий рядом сеньор увидел это и быстро остановил: «Стой! Уверен, что хочешь, чтобы он это написал?»

Сяомин в недоумении: «AI может написать — почему не позволить?»

Сеньор сказал: «Написать может, но это наименее эффективный подход. Если вы на React, `SWR` или `TanStack Query` уже обрабатывают бесконечный скролл, кэширование, ревалидацию, повтор ошибок, оптимистичные обновления... Если позволить AI писать, понадобится сотни строк только на edge cases — и это без production-тестов. Зрелые библиотеки надёжнее».

«Ценность AI не в том, чтобы помочь изобретать велосипед, — продолжил сеньор, — а в том, чтобы помочь найти правильное колесо и научить его использовать».

## Реальные проблемы проекта и решения

Прежде чем углубиться, посмотрим, с какими проблемами столкнулся реальный full-stack проект на Next.js и какие библиотеки их решили:

### Проблема 1: Данные юзеров меняются часто, рефетчить каждый раз слишком медленно

**Проблема**: На странице списка юзеров каждый возврат требует перезагрузки — ужасный опыт. Плюс несколько компонентов запрашивают один endpoint, тратя трафик.

**Решение**: `swr` — автоматически кэширует результаты запросов, компоненты делят одни данные, автоматическая ревалидация держит данные свежими.

### Проблема 2: Логика валидации форм разбросана, изменение в одном месте требует правок в нескольких файлах

**Проблема**: Валидация на frontend, валидация на backend — логики несогласованы, баги множатся.

**Решение**: `zod` — определяете схему один раз, разделяете между frontend и backend, типобезопасность, изменение в одном месте применяется везде.

### Проблема 3: Аутентификация юзера требует работы с сессиями, cookies, шифрованием паролей... слишком сложно

**Проблема**: Самописная auth-система занимает недели только на безопасность — и всё равно может быть ненадёжной.

**Решение**: `better-auth` — готовое решение аутентификации из коробки, поддерживает несколько способов логина, все вопросы security закрыты за вас.

### Проблема 4: Писать SQL для запросов к базе муторно и ошибкоопасно

**Проблема**: Ручной SQL легко испортить, без подсказок типов, смена структуры таблицы требует глобального поиска и замены.

**Решение**: `drizzle-orm` — типобезопасный ORM, интеллектуальное автодополнение при написании запросов, ошибки компиляции при смене структуры таблиц.

### Проблема 5: Контент, загруженный юзерами, может содержать злонамеренные скрипты

**Проблема**: Введённый юзером Markdown или HTML может содержать XSS-код атак.

**Решение**: `sanitize-html` + `rehype-sanitize` — автоматическая очистка опасного контента с сохранением безопасного форматирования.

### Проблема 6: Управление состоянием формы слишком сложное, каждое поле требует тонны кода

**Проблема**: Контролируемые компоненты писать муторно: валидация, сообщения об ошибках, состояния отправки... код разрастается.

**Решение**: `react-hook-form` — управление формами через Hooks, на 70% меньше кода, производительность тоже лучше.

### Проблема 7: Никто не знает, когда production-процессы падают

**Проблема**: При смерти Node.js-процесса сайт лежит, и перезапускать нужно вручную.

**Решение**: `pm2` — автоперезапуск, балансировка нагрузки, управление логами — всё одной командой.

### Проблема 8: Вывод логов слишком медленный, влияет на производительность

**Проблема**: `console.log` блокирует event loop при высокой конкурентности.

**Решение**: `pino` — асинхронное логирование, в 10+ раз быстрее `console.log`.

### Проблема 9: Drag-and-drop сортировка требует обработки кучи edge cases

**Проблема**: Drag-and-drop задействует события мыши, touch-события, анимации, детект коллизий... самописная версия — минимум сотни строк.

**Решение**: `@dnd-kit/core` — профессиональная библиотека drag-and-drop: доступность, поддержка touch, анимации — всё включено.

### Проблема 10: Картинки нужно сжимать до загрузки, иначе они слишком большие

**Проблема**: Загруженные юзерами фото часто по несколько МБ — серверный трафик не выдерживает.

**Решение**: `browser-image-compression` — сжатие картинок в браузере, минус 80% трафика.

---

**Видите?** Каждая решает конкретную проблему. Ни одна — «использование ради использования»: все по схеме «встретил проблему → нашёл библиотеку → решил проблему».

Это норма современной web-разработки — **дело не в том, можете ли вы написать, а в том, знаете ли вы, что решение уже есть**.

## Почему не изобретать велосипед?

В эпоху AI-ассистированной разработки у многих заблуждение: **«раз AI может помочь написать — почему бы не написать самому?»**

Правда в том:

1. **«Колёса», написанные AI, качеством ниже зрелых библиотек**:
   - Зрелые библиотеки протестированы в production миллионы раз; AI-код тестировали только вы
   - У зрелых библиотек полная обработка edge cases; AI-код может пропустить 90% edge case'ов
   - Зрелые библиотеки постоянно поддерживаются и обновляются по security; проблемы AI-кода чинить вам одним

2. **Стоимость поддержки куда выше воображения**:
   - Думаете, написали — и всё? Обновления зависимостей, security-уязвимости, новые требования... всё на вас
   - У зрелых библиотек есть сообщество, помогающее решать эти вопросы; у вашего кода есть только вы

3. **Реальная ценность AI — помочь вам выбирать и интегрировать библиотеки**:
   - Найти самую подходящую библиотеку
   - Читать документацию библиотеки
   - Написать корректный интеграционный код
   - Обработать особые случаи

::: tip Ценность разработчика в эпоху AI

Ваша ценность — не в «способности заставить AI писать код», а в «способности выбирать решения, собирать их и решать проблемы». Заставлять AI изобретать велосипеды — наименее эффективное поведение.

:::

## Шпаргалка частых библиотек Node.js

Ниже — самые используемые библиотеки экосистемы Node.js, организованные по категориям. Полный список — в [awesome-nodejs](https://github.com/sindresorhus/awesome-nodejs).

### Web-фреймворки

**Когда нужны**: когда нужно обрабатывать HTTP-запросы, роутинг, middleware. Для простого скрипта достаточно встроенного модуля `http` Node.js. Но для web-приложений и API-сервисов фреймворки экономят 90% бойлерплейта (матчинг роутов, парсинг запросов, обработка ошибок, управление middleware...).

- **[Fastify](https://github.com/fastify/fastify)** — высокопроизводительный web-фреймворк
  **Сценарий**: API-сервисы с высокой конкурентностью, в 2–3 раза быстрее Express

- **[Express](https://github.com/expressjs/express)** — самый популярный web-фреймворк
  **Сценарий**: Общие web-приложения, самая полная экосистема, легче всего искать ресурсы, предпочитаем командами

- **[Hono](https://github.com/honojs/hono)** — легковесный современный фреймворк
  **Сценарий**: Нужен deploy в несколько рантаймов — Cloudflare Workers, Deno, Bun

- **[Next.js](https://github.com/vercel/next.js)** — React full-stack фреймворк (рекомендуется в этом туториале)
  **Сценарий**: React-приложения, где нужны SSR, роутинг и API в одном решении

- **[Nest](https://github.com/nestjs/nest)** — enterprise-фреймворк
  **Сценарий**: Крупные проекты, где нужны dependency injection, модульная архитектура и полные engineering-решения

- **[Koa](https://github.com/koajs/koa)** — новое творение команды Express
  **Сценарий**: Предпочитаете стиль async/await, нужен более гибкий контроль middleware

### Базы данных: ORM/ODM

**Когда нужны**: когда нужно взаимодействовать с базой в коде. Ручной SQL ошибкоопасен, без подсказок типов, при смене схемы требует глобального поиска и замены. ORM позволяют писать запросы на TypeScript с IntelliSense, и компилятор ловит смены схемы.

- **[Drizzle](https://github.com/drizzle-team/drizzle-orm)** — типобезопасный ORM (рекомендуется в туториале)
  **Проблема**: Ручной SQL ошибкоопасен, без подсказок типов, при смене схемы требуется глобальный поиск и замена.
  **Решение**: Определяете схему на TypeScript, получаете IntelliSense для запросов, компилятор ловит смены схемы.
  **Почему не писать самому**: Вывод типов, query builder, управление миграциями, пул соединений... на реализацию самому ушли бы тысячи строк кода.

- **[Prisma](https://github.com/prisma/prisma)** — самый функционально полный ORM
  **Сценарий**: Нужны визуальное управление базой, автогенерация типов и полный набор migration-инструментов

- **[TypeORM](https://github.com/typeorm/typeorm)** — зарекомендовавший себя ORM
  **Сценарий**: Нужен традиционный ORM с поддержкой нескольких баз (MySQL, PostgreSQL, SQLite и др.)

- **[Mongoose](https://github.com/Automattic/mongoose)** — MongoDB ODM
  **Сценарий**: Выбор №1 при работе с MongoDB — валидация схем и построение запросов

- **[Sequelize](https://github.com/sequelize/sequelize)** — мультибазовый ORM
  **Сценарий**: Нужно переключаться между несколькими SQL-базами

- **[Knex](https://github.com/knex/knex)** — SQL query builder
  **Сценарий**: Не нужен полный ORM, нужна только типобезопасная сборка запросов

### Драйверы баз данных

**Когда нужны**: когда не хотите ORM и нужно исполнять SQL напрямую. Или когда ORM под капотом используют эти драйверы. Если нужны максимальная производительность или сложный нативный SQL — драйверы уместнее.

- **[node-postgres](https://github.com/brianc/node-postgres)** — клиент PostgreSQL
  **Сценарий**: Прямая работа с PostgreSQL без абстракции ORM

- **[ioredis](https://github.com/luin/ioredis)** — клиент Redis
  **Сценарий**: Кэширование, хранение сессий, очереди сообщений — лучше по производительности и функциям, чем официальный клиент

- **[mongodb](https://github.com/mongodb/node-mongodb-native)** — драйвер MongoDB
  **Сценарий**: Не нужен Mongoose, нужны более низкоуровневые операции с MongoDB

- **[mysql2](https://github.com/sidorares/node-mysql2)** — клиент MySQL
  **Сценарий**: Работа с MySQL/MariaDB с поддержкой Promise и Prepared Statements

### Валидация данных

**Когда нужна**: когда нужно валидировать ввод юзеров, параметры API-запросов или конфиг-файлы. Без валидации плохие данные ломают приложение или создают security-уязвимости. Самописная логика валидации, разбросанная по коду, ведёт к рассинхрону frontend-backend — смена одного поля требует правок в нескольких файлах.

- **[Zod](https://github.com/colinhacks/zod)** — TypeScript-first валидация схем (рекомендуется в туториале)
  **Проблема**: Валидируем один раз на frontend, один раз на backend, с несогласованной логикой — баги бесконечны. Смена одного поля требует правок в нескольких файлах.
  **Решение**: Схема определяется один раз, разделяется между frontend и backend, типобезопасность, изменение в одном месте применяется везде.
  **Почему не писать самому**: Правила валидации, сообщения об ошибках, вывод типов... сотни строк кода без типобезопасности.

- **[Joi](https://github.com/sideway/joi)** — мощная библиотека валидации
  **Сценарий**: Нужны сложные правила валидации (условная валидация, зависимые поля)

- **[Yup](https://github.com/jquense/yup)** — простая и лёгкая в использовании
  **Сценарий**: Использование с React Hook Form, чистый синтаксис

- **[ajv](https://github.com/ajv-validator/ajv)** — самый быстрый валидатор JSON Schema
  **Сценарий**: Нужно валидировать большие объёмы данных, производительность — приоритет №1

### Аутентификация и авторизация

**Когда нужна**: когда нужен логин юзеров и управление правами. Самописная auth-система требует обработки шифрования паролей, управления сессиями, безопасности cookies, защиты от CSRF, интеграции OAuth... Только security-вопроса занимают недели — и всё равно может быть ненадёжно.

- **[Better Auth](https://github.com/better-auth/better-auth)** — современная библиотека аутентификации (рекомендуется в туториале)
  **Проблема**: Самописная auth-система занимает недели только на security — и всё равно может быть ненадёжной. Шифрование паролей, сессии, cookies, CSRF... каждый — мина.
  **Решение**: Готовая аутентификация из коробки с несколькими способами логина (email, OAuth, magic links), security-вопросы закрыты за вас.
  **Почему не писать самому**: Хэширование паролей, соли, управление сессиями, refresh токенов, защита от CSRF... тысячи строк кода и с высокой вероятностью — security-уязвимости.

- **[Passport](https://github.com/jaredhanson/passport)** — зарекомендовавшее auth-middleware
  **Сценарий**: Нужна поддержка 500+ стратегий логина (OAuth, SAML и др.)

- **[Auth.js](https://github.com/nextauthjs/next-auth)** — auth-решение для Next.js
  **Сценарий**: Next.js-проектам нужна быстрая интеграция OAuth

- **[CASL](https://github.com/stalniy/casl)** — библиотека управления правами
  **Сценарий**: Нужен гранулярный контроль прав (RBAC, ABAC)

- **[node-casbin](https://github.com/casbin/node-casbin)** — библиотека контроля доступа
  **Сценарий**: Нужны сложные модели контроля доступа (ACL, RBAC, ABAC)

### HTTP-клиенты

**Когда нужны**: когда нужно вызывать внешние API с серверной стороны. Встроенный модуль `http` Node.js слишком низкоуровневый — приходится вручную обрабатывать тела запросов, парсинг ответов, повтор ошибок... Эти библиотеки берут это на себя.

- **[undici](https://github.com/nodejs/undici)** — официальный высокопроизводительный HTTP-клиент Node.js
  **Сценарий**: Нужна максимальная производительность; встроенный `fetch` Node.js 18+ построен на нём

- **[axios](https://github.com/axios/axios)** — самый популярный HTTP-клиент
  **Сценарий**: Общие HTTP-запросы, перехватчики, автотрансформации, хорошая браузерная совместимость

- **[got](https://github.com/sindresorhus/got)** — улучшенный HTTP-интерфейс
  **Сценарий**: Нужны продвинутые функции — retry, кэширование, hooks

- **[node-fetch](https://github.com/node-fetch/node-fetch)** — реализация Fetch API
  **Сценарий**: Хотите использовать браузерный `fetch` API в Node.js (встроен в Node.js 18+)

### Запросы данных в React (важно)

::: tip Зачем нужна отдельная библиотека запросов данных?

Можно подумать: «это же просто `fetch` — зачем библиотека?» Но запросы данных включают: кэширование, ревалидацию, повтор ошибок, оптимистичные обновления, обработку race conditions, офлайн-поддержку... Самописная реализация — сотни строк кода, и всё равно может быть ненадёжной.
:::

- **[SWR](https://github.com/vercel/swr)** — библиотека запросов данных на React Hooks от Vercel (используется в проектах туториала)
  - Автоматическое кэширование, ревалидация
  - Real-time обновления, оптимистичные обновления
  - Легковесная (~5KB)
  - Хороша для простых сценариев

- **[TanStack Query](https://github.com/TanStack/query)** — самая мощная библиотека запросов данных
  - Мощное управление кэшем
  - Бесконечный скролл, пагинация
  - Офлайн-поддержка
  - Отладка через DevTools
  - Хороша для сложных сценариев

**Сравнение**:
- SWR: простая, легковесная, достаточная (рекомендуется новичкам)
- TanStack Query: функционально богатая, хороша для сложных приложений

### UI и интеракции в React

**Когда нужны**: при работе со сложными UI-интеракциями (формы, drag-and-drop, анимации, безопасность контента). Самописная реализация требует обработки массы edge cases — зрелые библиотеки надёжнее.

- **[React Hook Form](https://github.com/react-hook-form/react-hook-form)** — управление состоянием форм
  **Проблема**: Контролируемые компоненты мучительны — каждому полю нужны `value`, `onChange`, валидация, сообщения об ошибках, состояние отправки... код взрывается.
  **Решение**: Hooks управляют формой, сокращая код на 70% и улучшая производительность (меньше ре-рендеров).
  **Почему не писать самому**: Валидация форм, обработка ошибок, состояния отправки, зависимости полей, динамические формы... минимум сотни строк кода, легко внести проблемы производительности.

- **[@dnd-kit/core](https://github.com/clauderic/dnd-kit)** — библиотека drag-and-drop
  **Проблема**: Drag-and-drop задействует события мыши, touch-события, анимации, детект коллизий... минимум сотни строк, плюс обработка edge cases.
  **Решение**: Профессиональная библиотека drag-and-drop с доступностью, поддержкой touch и анимациями — всё через гибкий, лёгкий в использовании API.
  **Почему не писать самому**: Слишком много edge cases — мультитач, навигация с клавиатуры, screen reader'ы, оптимизация производительности... самописная версия легко покрывает только 10% сценариев.

- **[sanitize-html](https://github.com/apostrophecms/sanitize-html)** — санитизация HTML-контента
  **Проблема**: Markdown или HTML, отправленные юзером, могут содержать XSS-код атак (теги `<script>`, события `onerror` и т.п.).
  **Решение**: Автоматическая очистка опасного контента с сохранением безопасного форматирования (вроде `<b>`, `<a>` и др.).
  **Почему не писать самому**: Векторов XSS-атак масса — не только `<script>`, но и обработчики событий, протокол `javascript:`, CSS-инъекции... легко упустить вектор при самописной реализации.

- **[browser-image-compression](https://github.com/Donaldcwl/browser-image-compression)** — сжатие изображений в браузере
  **Проблема**: Загруженные юзерами фото часто по несколько МБ — серверный трафик перегружен, загрузки медленные.
  **Решение**: Сжатие картинок в браузере, минус 80% трафика, быстрее загрузка, меньше нагрузка на сервер.
  **Почему не писать самому**: Сжатие изображений затрагивает Canvas API, сохранение EXIF, поддержку нескольких форматов, Worker-потоки... минимум сотни строк кода, и качество не гарантировано.

### Логирование

**Когда нужно**: когда нужно отслеживать проблемы в production. `console.log` блокирует event loop при высокой конкурентности, без уровней логов, без структурированного вывода, без ротации логов. Профессиональные библиотеки логирования улучшают производительность и поддерживаемость.

- **[pino](https://github.com/pinojs/pino)** — экстремально быстрая библиотека логирования (рекомендуется)
  **Проблема**: `console.log` блокирует event loop при высокой конкурентности, влияя на производительность.
  **Решение**: Асинхронное логирование, в 10+ раз быстрее `console.log`, поддержка структурированного вывода.
  **Почему не писать самому**: Асинхронная запись, ротация логов, форматирование, оптимизация производительности... минимум сотни строк кода — и не факт, что быстро.

- **[winston](https://github.com/winstonjs/winston)** — мультитранспортная асинхронная библиотека логирования
  **Сценарий**: Нужно одновременно выводить в файлы, базы, удалённые сервисы

- **[consola](https://github.com/unjs/consola)** — элегантное консольное логирование
  **Сценарий**: Dev-окружению нужен красивый вывод логов

- **[debug](https://github.com/debug-js/debug)** — легковесная утилита отладки
  **Сценарий**: Нужно переключать debug-логи по модулям

  **Сценарий**: Подсчёт хэшей файлов или данных

### Генераторы статических сайтов

**Когда нужны**: когда нужно строить сайты документации, блоги или маркетинговые страницы. Статические сайты быстрые, безопасные и легко деплоятся. Эти генераторы позволяют писать контент на Markdown и автоматически генерируют красивые сайты.

- **[VitePress](https://github.com/vuejs/vitepress)** — генератор статических сайтов на Vue (используется в этом туториале)
  **Сценарий**: Построение сайтов документации, на базе Vite, быстрый, красивые темы

- **[Astro](https://github.com/withastro/astro)** — современный генератор статических сайтов
  **Сценарий**: Нужна экстремальная производительность, поддержка нескольких фреймворков (React, Vue, Svelte)

- **[Docusaurus](https://github.com/facebook/docusaurus)** — генератор сайтов документации на React
  **Сценарий**: Построение продуктовой документации, функционально полный, от Facebook

- **[Hexo](https://github.com/hexojs/hexo)** — блог-фреймворк
  **Сценарий**: Быстрое создание личных блогов, богатые темы

### CMS (системы управления контентом)

**Когда нужны**: когда нужно позволить нетехническим людям управлять контентом сайта. Самописная админка занимает недели и даже месяцы; эти CMS-решения дают интерфейс управления контентом из коробки.

- **[Strapi](https://github.com/strapi/strapi)** — headless CMS
  **Сценарий**: Нужен гибкий backend управления контентом с выдачей контента через API

- **[Ghost](https://github.com/TryGhost/Ghost)** — блог-платформа
  **Сценарий**: Профессиональная платформа блогинга и публикации, отличный редактор

- **[KeystoneJS](https://github.com/keystonejs/keystone)** — платформа CMS и web-приложений
  **Сценарий**: Быстрое построение data-driven приложений и админок

### Менеджеры пакетов

**Когда нужны**: когда нужно устанавливать и управлять npm-пакетами. npm — дефолтный менеджер пакетов, но есть более быстрые и экономные к диску альтернативы.

- **[pnpm](https://pnpm.io)** — экономный к диску менеджер пакетов (рекомендуется в этом туториале)
  **Сценарий**: Экономия диска (hard links для общих зависимостей), быстрая установка

- **[npm](https://docs.npmjs.com/about-npm)** — дефолтный менеджер пакетов
  **Сценарий**: Идёт с Node.js, лучшая совместимость

- **[yarn](https://yarnpkg.com)** — альтернативный менеджер пакетов
  **Сценарий**: Нужна офлайн-установка, детерминированное разрешение зависимостей

- **[bun](https://bun.sh)** — all-in-one инструментарий
  **Сценарий**: Нужна экстремальная скорость, интегрирует runtime, бандлер и фреймворк тестов

## Как оценивать библиотеку?

Найдя библиотеки-кандидаты, прогоните их по чек-листу быстрой оценки:

### Чек-лист быстрой оценки

- ✅ **GitHub stars > 1000** (говорит о базе юзеров)
- ✅ **Обновлялась за последние 6 месяцев** (говорит о поддержке)
- ✅ **Issues получают быстрые ответы** (говорит об ответственных авторах)
- ✅ **Полная документация и примеры**
- ✅ **Поддержка TypeScript** (если используете TS)
- ⚠️ **Разумное количество зависимостей** (слишком много зависимостей = потенциальный риск)
- ⚠️ **Разумный размер пакета** (проверьте через bundlephobia)
- ⚠️ **Дружелюбная лицензия** (MIT/Apache 2.0 и т.п.)

### Пусть Claude Code поможет оценить

Отправьте README и package.json библиотеки в Claude Code и спросите:

```
Подходит ли эта библиотека для моего проекта? Есть ли лучшие альтернативы?
Пожалуйста, оцени по следующим углам:
1. Статус поддержки
2. Активность сообщества
3. Качество документации
4. Производительность
5. Есть ли лучшие альтернативы?
```

Claude Code даст детальный анализ и рекомендации.

## Когда всё-таки можно «изобретать велосипед»?

Рассматривать самописную реализацию стоит только в этих ситуациях:

1. **Существующие решения не отвечают вашим потребностям** (но сначала убедитесь, что вы действительно всё обыскали)
2. **Цели обучения** (но не используйте в production)
3. **Экстремальная оптимизация производительности** (но сначала профилируйте, не оптимизируйте преждевременно)
4. **Слишком тяжёлые зависимости** (простая функция, тянущая 100 МБ зависимостей, того не стоит)
