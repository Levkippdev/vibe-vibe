# Глава 4: Основы разработки, которые нужно знать

![img](/images/Advanced/mlkzwcw8-aa8ae9e1ebb5251a.jpg)

## Предисловие

Прежде чем вы начнёте писать код, наставник говорит: есть ключевые основы разработки, которые нужно понять заранее. Эти концепции не научат кодить напрямую, но помогут понять, как код на самом деле работает в интернете.

### Три состояния работы кода

Наставник сначала объясняет «жизненные состояния» кода: **Dev (разработка), Build и Production**.

Режим Dev — как черновик документа: после сохранения кода браузер обновляется сам, отлаживать проще. Режим Build — как вёрстка и печать черновика в книгу: код сжимается и оптимизируется. Режим Production симулирует реальное deploy-окружение, запуская собранную версию.

Понимание этих трёх состояний спасает от массы путаницы: например, почему ваши правки кода «не работают» (возможно, вы не в том режиме) или почему другие не видят вашу локальную демку (Dev-режим не подходит для показа).

### Выбор tech stack

Решения о tech stack принимаются после финализации PRD. Наставник говорит: «Сначала пойми, что строить, потом решай, чем строить».

Технологий так много, что новички застревают в передумывании. Но есть простая рамка решений: full-stack Next.js (AI-friendly, зрелая экосистема, лёгкий deploy); Vite — только если проект чисто frontend; для базы — PostgreSQL (реляционная + JSONB + pgvector, сильная расширяемость).

**Два способа хостить PostgreSQL**: Supabase и Neon — оба облачных сервиса managed PostgreSQL, но с разным назначением. **Supabase** даёт полную backend-платформу (аутентификация, storage, real-time подписки) — отлично для быстрой разработки; **Neon** сфокусирован именно на базе, легковесен и поддерживает serverless-архитектуру — лучше, когда нужна большая кастомизация backend. Хотите сфокусироваться на бизнес-логике — выбирайте Supabase; нужна гибкость контроля — Neon.

PostgreSQL поддерживает дополнительную функциональность через расширения вроде `JSONB` (хранение JSON-данных) и `pgvector` (векторный поиск, требует отдельной установки расширения).

Ключевая идея — «уяснить требования → оценить сложность → выбрать минимально жизнеспособное решение», оставляя место будущему расширению без overengineering. В эпоху AI чем единообразнее ваш tech stack, тем точнее AI понимает контекст — и тем выше эффективность разработки.

### Базовые кирпичики программирования

Наставник говорит: прежде чем писать код, нужно понять, из чего код состоит. Как перед написанием статьи нужно знать слова, у программирования есть свой «базовый алфавит» — **переменные**, **функции**, **условия** и **циклы**. Все языки программирования, как бы ни различался их синтаксис, строятся на этих четырёх концепциях. Переменные хранят данные, функции инкапсулируют переиспользуемую логику, условия позволяют программам реагировать по-разному на разные ситуации, циклы дают программам обрабатывать повторяющиеся задачи партиями. Эти четыре концепции — фундамент **Turing-полноты**: любая вычислимая проблема решается их комбинациями.

### Связь PRD и технической документации

После 5 итераций PRD, когда продуктовый план в основном финализирован, наставник напоминает: помимо бизнес-логики нужно задокументировать и конкретный план технической реализации — это **техническая документация**.

Многие путают PRD с техдокументацией, но их роли весьма ясны:

**PRD (документ продуктовых требований)** отвечает на вопрос «что строить»:

- Кто целевые юзеры?
- Какие ключевые функции?
- Как юзеры будут взаимодействовать?
- Как обрабатывать edge cases?

**Техническая документация** отвечает на вопрос «как строить»:

- Какой tech stack использовать? (Next.js + PostgreSQL)
- Как спроектировать схему БД? (таблица юзеров, постов, комментариев)
- Как определить API-интерфейсы? (`/api/auth`, `/api/posts`)
- Как интегрировать сторонние сервисы? (AI API, карты)
- Каков план deploy? (EdgeOne, Vercel, облачный сервер)

Наставник говорит: «На вашей стадии не нужно упираться в формат. Можно объединить техдокументацию и PRD в один документ и называть просто **проектной документацией** — так удобнее сверяться. Но чётко различайте продуктовое мышление и технические решения».

### Основы API и HTTP

Видя ваше любопытство, наставник объясняет принципы **взаимодействия frontend и backend**. Он говорит: **HTTP** — как дистанционная система инструкций: браузер отправляет стандартизированные инструкции серверу, сервер их обрабатывает и возвращает результат. Каждая инструкция содержит четыре части: **метод запроса** (GET/POST/PUT/DELETE и др. — какую операцию выполнить), **URL** (адрес ресурса), **Headers** (метаданные вроде аутентификации) и **Body** (отправляемые данные). Понимание этих четырёх частей помогает быстрее ставить диагнозы: `401` — не аутентифицирован (нужно залогиниться), `403` — запрещено (залогинен, но нет прав), `404` — ресурса нет (неверный адрес или удалён). AI поможет с деталями, но только понимание основ позволяет эффективно troubleshot'ить.

### Концепция разделения frontend и backend

Изучая HTTP-коммуникацию, наставник сначала объясняет концепции **frontend** и **backend**.

**Frontend** — интерфейс, который юзеры видят и с которым взаимодействуют: код, работающий в браузере. Кнопки, поля ввода, картинки и текст на странице — всё это рендерит frontend. Когда вы кликаете кнопку или печатаете, отвечает frontend-код.

**Backend** — код на сервере, обрабатывающий данные и логику. Юзеры его не видят, но он обрабатывает запросы frontend: запрашивает базу, проверяет личность, вызывает другие сервисы. Закончив обработку, backend возвращает результат frontend, который показывает его юзеру.

Раньше frontend и backend были отдельными проектами на разных языках, поддерживаемыми разными командами. Теперь с **full-stack фреймворком вроде Next.js** оба кода живут в одном проекте на одном языке (JavaScript/TypeScript), но ответственности не изменились: frontend — «представление», backend — «обработка».

Планируя функции, вы сталкиваетесь с двумя вопросами, которые нужно продумать заранее: юзер-система — это аутентификация; карта — внешние API. Наставник напоминает: не пихайте весь код в один файл — разбивайте функциональность на модули вроде `auth` (аутентификация), `api` (интерфейсы) и `components` (компоненты). Это **модульное мышление** — ключ к поддерживаемости проекта в долгую.

### Форматы конфиг-файлов

Пока вы пишете техдокументацию и настраиваете проект, вы сталкиваетесь со странными форматами конфиг-файлов вроде **JSON** и **YAML**.

**JSON** — строго структурированный способ выражения данных. Фигурные скобки `{}` для объектов, квадратные `[]` для массивов, данные организованы парами «ключ: значение». JSON — **лингва франка цифровой эпохи**, универсальный язык общения разных языков программирования и систем.

**YAML** — более дружелюбный к человеку конфиг-формат. Без скобок — иерархия выражается отступами, писать лаконичнее. Многие конфиги (например, часть CI/CD) в формате YAML.

Оказывается, для AI эти чётко структурированные форматы — «мануалы», которые он предпочитает читать больше всего, в сравнении со свободным естественным языком.

### Интеграция API на практике

Вы хотите интегрировать AI-способности или сервисы вроде карт. Наставник говорит: интеграция внешнего API — это шесть шагов: получить креденшелы, выбрать SDK, настроить переменные окружения, написать минимальный тест, архивировать справочную документацию, обработать частые ошибки.

Наставник даёт конкретное предупреждение: **всегда храните API Key в файле переменных окружения `.env`**, а не хардкодьте в код. Переменные окружения — как «firewall» между вашим кодом и секретами.

Для AI-приложений наставник рекомендует **Vercel AI SDK**. Он даёт пакет `@ai-sdk/openai-compatible`, подключающийся к любому провайдеру, совместимому с форматом OpenAI API. Нужно выучить одну API-спецификацию, менять `baseURL`, API Key и имя модели — и можно вызывать мейнстримные большие модели мира.

Когда тесты пройдут — сохраните официальную документацию. В следующий раз, прося AI собрать функцию, просто скормите ему доки — код будет точнее.

### Проектный мануал README.md

Код — не только для машин: его читают люди и AI. Вы узнаёте, что нужно написать **README.md**. Это не избыточная информация, а «мануал» проекта. Там ясно задокументировано, как запускать проект (`pnpm dev`), как настраивать переменные окружения и логика ключевых функций. После этого любой сможет стартовать, просто прочитав документацию.

README.md — как «парадная дверь» проекта, обычно включает: обзор проекта, quick start, переменные окружения, ключевые функции, tech stack и гайд по контрибуции.

### Не изобретайте велосипед

Освоив основы, вы думаете: раз можно всё написать самому, зачем библиотеки? Наставник останавливает: в мире разработки почти для каждой задачи есть зрелое решение. Ценность AI — не «писать код за вас», а «помогать находить правильные колёса и учить их использовать». В Node.js-экосистеме десятки тысяч библиотек: SWR для запросов данных, Zod для валидации, Better Auth для аутентификации, Drizzle для операций с базой... Умение искать библиотеки и оценивать их качество — ключевой навык, отличающий «пишу всё сам» от «собираю зрелые решения».
