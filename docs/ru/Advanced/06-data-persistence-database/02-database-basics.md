# 6.2 Основы баз данных

> **Цели обучения**: освоить ключевые концепции реляционных баз — таблицы, строки, колонки, primary keys, foreign keys, типы отношений и механизмы ограничений.

---

## Food-стартап Сяохун

Сяохун — человек действия. Она заметила, что кампусные платформы доставки еды берут чрезмерные комиссии и предлагают мало ресторанов, и решила построить собственную кампусную платформу доставки — обслуживающую только её университет, с курьерами-студентами и комиссией вдвое ниже Meituan.

Сначала она расписала данные, которыми нужно управлять:

- **Студенты-юзеры**: кто пользуется платформой? Телефон, ник, адрес общежития
- **Кампусные мерчанты**: столовые, бабл-ти, фруктовые — у каждого название, рейтинг, часы работы
- **Позиции меню**: что продаёт каждый ресторан, сколько стоит, есть ли фото
- **Записи заказов**: кто что купил в каком магазине, сколько заплатил, текущий статус
- **Детали заказа**: какие конкретно блюда в каждом заказе, по сколько каждого

Сяохун сначала думала об Excel — в универе она вела им расписания и бюджет, привычно.

Но быстро поняла: один заказ может содержать три блюда из разных категорий, а одно блюдо может появиться в сотнях заказов. Эти отношения образуют паутину, которую структура Excel «одна строка — одна запись» не потянет. Она попробовала запихнуть несколько названий блюд в одну ячейку через запятые — запрашивать и анализировать стало кошмаром.

Ей нужен был инструмент, способный управлять «отношениями между данными» — это **реляционная база данных**.

Слово «реляционная» — ключевое. Оно не значит, что база помогает управлять межличностными отношениями; оно значит, что она отлично управляет **отношениями между данными»: юзер-заказ, заказ-блюдо, мерчант-блюдо. Эти отношения трудно выразить в Excel, но нативно поддерживаются реляционными базами.

## Таблицы: «листы» в 100 раз мощнее Excel

**Таблицу** в базе данных можно сначала понять как «супер-лист Excel». Если вы пользовались Excel, у вас уже отличная отправная точка для понимания таблиц баз.

Вот что схоже:

| Концепция Excel | Концепция базы | Описание |
|-------------|----------------|-------------|
| Лист Worksheet | Таблица | Одна таблица на тип данных, например `users` хранит всех юзеров |
| Строка данных | Строка (также запись) | Конкретный юзер, конкретный заказ |
| Заголовки колонок | Колонка (также поле) | Атрибуты данных, например `phone`, `address` |

А вот отличия — именно в них базы сияют, и чего Excel никогда не сможет:

**Строгие типы данных.** В Excel колонка может смешивать текст и числа — никто не помешает написать «очень старый» в колонке «возраст». Базы этого не позволят: колонка типа `integer` принимает только целые; попытка вставить текст — база отклоняет наотрез. Кажется «неудобным», но именно это гарантирует качество данных. Представьте платформу доставки Сяохун: если колонку «цена» контаминировать текстом, checkout провалится. Строгая типизация базы предотвращает это у самого источника.

**Механизмы ограничений.** Базы могут принуждать правила: телефоны не дублируются (UNIQUE), ники не пустые (NOT NULL), ID юзера заказа обязан указывать на реально существующего юзера (FOREIGN KEY). Данные, нарушающие правила, не записываются — грязные данные блокируются у источника. Когда эти правила установлены, любой, пишущий данные любым способом, обязан им следовать — в отличие от Excel, где каждый может произвольно менять любую ячейку.

**Отношения между таблицами.** Это ключевая способность базы и причина названия «реляционная». Несколько таблиц могут устанавливать отношения через «внешние ключи», затем использовать операции SQL JOIN для извлечения связанных данных одним запросом. Например, «найти все заказы Сяохун и блюда в каждом заказе» — один SQL-оператор решает. В Excel вы бы прыгали между листами, вручную матчя ID — крайне неэффективно.

**Конкурентная безопасность.** Когда 100 юзеров размещают заказы одновременно, базы используют транзакции и блокировки, гарантируя корректную запись каждого заказа — без перезаписей и потерь. Эксель этого не умеет: одновременное редактирование двумя людьми одного файла ведёт в лучшем случае к конфликтам, в худшем — к потере правок.

## Primary Keys: ID-карта каждой строки

В реальном мире у каждого есть номер паспорта — уникальный по стране — используемый во всех системах для идентификации «кто вы». Открытие банковского счёта требует его, регистрация в больнице требует, покупка билетов на поезд требует — все системы используют этот номер для подтверждения «вы — это вы».

Базы работают так же. Каждая таблица нуждается в **primary key** для уникальной идентификации каждой строки данных. Как номер паспорта идентифицирует человека, primary key идентифицирует запись.

Правила primary key просты — всего три:

- **Уникальность**: никакие две строки не могут иметь одинаковое значение primary key (как никто не может делить номер паспорта)
- **Не null**: каждая строка обязана иметь значение primary key (у каждого обязан быть паспорт)
- **Неизменность**: однажды назначенный — не меняется (вы не меняете паспорт каждые несколько дней)

На практике primary key обычно использует колонку `id`. Современный PostgreSQL рекомендует `bigint generated always as identity` — «использовать большое целое как ID, автоматически генерируемое базой с инкрементом на 1» (стандартнее и безопаснее старого `serial`):

```sql
CREATE TABLE users (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  phone text   NOT NULL
);
```

> В Drizzle ORM запись `serial('id').primaryKey()` тоже отлично работает — AI-генерируемый код обычно использует обе формы. Ключевой принцип: пусть база сама назначает ID, чтобы вам не нужно было об этом думать.

Вы можете спросить: телефоны тоже уникальны — почему не использовать их как primary key?

Причина в том, что телефоны имеют «бизнес-значение» — юзеры могут сменить номер. Когда primary key референсится другими таблицами (например, таблица заказов хранит `user_id`), смена primary key означает обновление везде, где он референсится — эффект ряби. Поэтому индустриальная best practice: **использовать бессмысленный автоинкрементный ID как primary key** — просто, стабильно, эффективно.

## Foreign Keys: нить между таблицами

Если primary key — «кто я», то foreign key — «с кем я связан».

**Foreign key** — это колонка одной таблицы, указывающая на primary key другой таблицы. Её назначение — устанавливать отношения между таблицами, гарантируя, что референсируемые данные реально существуют.

Пример: таблица `orders` Сяохун имеет колонку `user_id`, чьё значение обязано быть реально существующим `id` из таблицы `users`. Это foreign key. Через этот `user_id` можно проследить от заказа к юзеру, сделавшему его: «Кто сделал этот заказ? `user_id` — 42, смотрю id=42 в `users` — а, это Сяохун».

```sql
CREATE TABLE orders (
  id          serial PRIMARY KEY,
  user_id     integer REFERENCES users(id),  -- foreign key pointing to users.id
  amount      real    NOT NULL,
  status      text    DEFAULT 'pending_payment'
);
```

Foreign keys дают три выгоды:

**Гарантия согласованности данных.** Нельзя создать заказ для несуществующего юзера. Если в `users` нет юзера с id=999, вставка заказа с `user_id=999` в `orders` провалится немедленно. Это «referential integrity»: на что вы ссылаетесь, обязано реально существовать; ссылаться на несуществующего юзера нельзя.

**Установление отношений.** Через `user_id` можно проследить от заказа к его юзеру или от юзера ко всем его заказам. Отношения между данными становятся ясными и запрашиваемыми.

**Каскадные операции (цепные реакции).** При удалении юзера что происходит с его заказами? База может автоматически удалить все его заказы (cascade delete) или предотвратить удаление (не позволять, если существуют связанные заказы). Это поведение конфигурируется при создании таблицы.

::: warning Колонки foreign keys обязаны быть проиндексированы
PostgreSQL **не** создаёт индексы на колонках foreign keys автоматически. Если в `orders` 100 000 строк, запрос «все заказы конкретного юзера» без индекса на `user_id` вызывает полное сканирование таблицы — листание от первой строки до последней, как поиск в книге без оглавления — в 100+ раз медленнее. Поэтому каждая колонка foreign key нуждается в ручном индексе. Тема детально разбирается в разделе 6.4.
:::

> Можно кликать связи во вкладке «Relationship Diagram» компонента выше для просмотра конкретных методов ассоциации foreign keys.

## Типы отношений: разбор

Отношения между таблицами базы сводятся всего к трём типам. Поняв эти три, вы сможете читать любой дизайн баз.

### Один-ко-многим (1:N) — самый частый

Один юзер может сделать много заказов, но каждый заказ принадлежит только одному юзеру. Это один-ко-многим.

```
users (1) ──→ orders (N)
  id              user_id → users.id
```

Реализация интуитивна: добавьте колонку foreign key на стороне «многих». `user_id` в таблице `orders`, указывающий на `users.id`, устанавливает отношение один-ко-многим.

Один-ко-многим — самый частый тип отношений; в любом приложении вы найдёте бесчисленные примеры:

- У одного мерчанта много блюд (мерчант → блюдо)
- Один автор пишет много статей (автор → статья)
- В одном классе много студентов (класс → студент)
- Один юзер публикует много апдейтов (юзер → апдейт)

Тест прост: спросите себя «Может ли один A иметь много B? Принадлежит ли один B только одному A?» Если оба «да» — это один-ко-многим.

### Многие-ко-многим (M:N) — требует junction-таблицу

Один заказ содержит много блюд, и одно блюдо появляется во многих заказах. Эта «многосторонность с обеих сторон» — отношение многие-ко-многим.

Многие-ко-многим нельзя выразить одним foreign key — потому что foreign key может указывать только на одну запись, а не на несколько одновременно. Решение — добавить **junction-таблицу**, разбив многие-ко-многим на два один-ко-многим:

```
orders (M) ←─ order_items ─→ dishes (N)
  id            order_id        id
                dish_id
                quantity
```

`order_items` — junction-таблица. Каждая строка записывает «какой заказ купил какое блюдо и сколько». У одного заказа несколько строк в `order_items` (заказано несколько блюд), и у одного блюда тоже несколько строк (заказано в нескольких заказах).

Junction-таблица — не просто «коннектор»: она может хранить атрибуты самих отношений. Например, `quantity` (количество) — атрибут «отношения между заказом и блюдом»: он принадлежит ни заказу, ни блюду — только этой конкретной связи.

Ещё примеры многие-ко-многим:

- Студент ↔ Курс (junction: записи зачисления, можно хранить оценки)
- Юзер ↔ Тег (junction: теги юзера, можно хранить время пометки)
- Статья ↔ Категория (junction: связь статья-категория)

### Один-к-одному (1:1) — разбиение больших таблиц

Один юзер соответствует одному детальному профилю. Почему не поместить их в одну таблицу?

Представьте: таблица `users` имеет 500 000 юзеров. При каждом логине система запрашивает `users` для верификации. Если таблицу набить редко используемыми полями вроде URL аватара, bio, настроек предпочтений, списка адресов — таблица становится «тяжёлой» и скорость запросов деградирует.

Решение — выделить редко используемые поля в другую таблицу:

```sql
CREATE TABLE profiles (
  id       serial PRIMARY KEY,
  user_id  integer UNIQUE REFERENCES users(id),  -- UNIQUE enforces one-to-one
  avatar   text,
  bio      text
);
```

Ключ — ограничение **UNIQUE** на `user_id`. Без него у одного юзера могло бы быть несколько профилей — стало бы один-ко-многим. С UNIQUE база гарантирует, что каждый `user_id` появляется только раз — строгое один-к-одному.

Один-к-одному на практике реже, но полезен в этих сценариях:

- Базовая инфа юзера ↔ Детальный профиль юзера (разбиение больших таблиц)
- Заказ ↔ Инвойс (не у каждого заказа есть инвойс)
- Сотрудник ↔ Рабочее место (один сотрудник — одно место)

## Целостность данных: почему ограничения важны

База без ограничений — как склад без правил: свалить можно что угодно, хаос неизбежен. Сегодня вставили юзера с «возрастом -5», завтра товар с «ценой null», послезавтра приложение падает в странных местах, и вы не догадываетесь, что это проблема данных.

**Ограничения** — правила, автоматически принуждаемые базой. При каждой записи данных база проверяет эти правила — несоответствующие данные отклоняются наотрез, даже не сохраняясь. Это как security в аэропорту: кем бы вы ни были и откуда бы ни летели — багаж через рентген, запрещённое перехватывается.

| Ограничение | Назначение | Аналогия из реальной жизни |
|-----------|---------|-------------------|
| PRIMARY KEY | Уникально идентифицирует каждую строку | Паспорт, уникален по стране |
| FOREIGN KEY | Гарантирует существование референсируемых данных | Получатель на посылке обязан быть реальным человеком |
| NOT NULL | Обязательное поле | Обязательные поля формы, пустым не отправить |
| UNIQUE | Дубликаты не разрешены | Телефон нельзя зарегистрировать дважды |
| CHECK | Валидация кастомных условий | Возраст > 0, рейтинг 1–5 |
| DEFAULT | Автозаполнение дефолтом | Статус заказа по умолчанию «pending payment» |

> Во вкладке «Constraint Demo» компонента выше можно видеть сравнения корректного и нарушающего для каждого типа ограничения.

Вы можете подумать: зачем ограничения на уровне базы, если я могу валидировать в коде?

Три причины:

**Код может иметь баги, но ограничения базы — последняя линия обороны.** Ваша логика валидации может быть неверной, пропустить граничное условие или иметь `if` без знака равенства — всё это пропускает грязные данные. Ограничения базы таких ошибок не делают; они беспристрастный вратарь.

**У данных несколько точек входа.** У вашего приложения есть API-эндпоинты, админ-панели, скрипты миграции, задачи по расписанию... каждая может писать данные. Вы не можете идеально реализовать логику валидации в каждой точке входа. А ограничения базы достаточно определить раз — они защищают все точки входа.

**Чистка грязных данных крайне дорога.** Представьте десятки тысяч заказов с `user_id`, указывающим на несуществующих юзеров — как это чинить? Удалить эти заказы? А деньги юзеров? Заменить `user_id` на дефолтного юзера? Данные искажаются. Профилактика всегда дешевле лечения.

## Краткий справочник типов данных

Каждая колонка обязана указывать тип данных. Выберете правильно — эффективное хранение и быстрые запросы; ошибётесь — потеря места или потеря данных.

Частые типы данных PostgreSQL:

| Тип | Назначение | Пример | Заметки |
|------|---------|---------|-------|
| `bigint` / `serial` | Primary key ID | 1, 2, 3... | `bigint` безопаснее, `serial` достаточен |
| `text` | Текст переменной длины | 'Hello World' | Всегда `text`, никогда `varchar(n)` |
| `integer` | Целое | 42, -1, 0 | Максимум 2,1 млрд, используйте если достаточно |
| `boolean` | Истина/ложь | true / false | — |
| `timestamptz` | Дата и время | '2024-01-15 09:30:00+08' | С таймзоной, **никогда** `timestamp` |
| `jsonb` | Структурированный JSON | '{"tags":["vip"]}' | Можно строить GIN-индексы для быстрых запросов |
| `numeric(10,2)` | Точный decimal | 99.99 | Обязателен для денег, никогда `real` |
| `uuid` | Глобальный уникальный идентификатор | 'a1b2c3d4-...' | Част в распределённых системах |

> Во вкладке «Data Types» компонента выше можно смотреть синтаксис Drizzle ORM для каждого типа.

::: warning Три частые ловушки типов

1. **`real` / `float` для денег**: у плавающей точки проблемы точности (0.1 + 0.2 ≠ 0.3). Деньги — только `numeric` или `integer` (единица: центы)
2. **`timestamp` для времени**: timestamp без таймзоны создаёт двусмысленность между серверами. Всегда `timestamptz`
3. **`varchar(255)` для строк**: в PostgreSQL `text` и `varchar` идентичны по производительности; `varchar(n)` лишь добавляет лимит длины с нулевой выгодой по производительности
:::

## SQLite vs PostgreSQL

| | SQLite | PostgreSQL |
|--|--------|------------|
| Позиционирование | Файловая база, zero config | Полный сервер баз данных |
| Хранение | Один файл `.db` | Отдельный процесс сервиса базы |
| Конкурентность | Один писатель, много читателей, малый масштаб | Высококонкурентные чтение/запись, production-ready |
| Типы данных | Свободные (только 5 реальных типов) | Строгие и богатые (50+ типов) |
| Поддержка JSON | Базовая | Мощный тип `jsonb` |
| Сценарии | Локальная разработка, embedded, прототипирование | Production, командная коллаборация, высокая конкурентность |
| Рекомендация туториала | Хорош для обучения и быстрого старта | Рекомендуется для реальных проектов, Supabase даёт free tier |

::: tip Совет по выбору
Если вы используете облачные сервисы вроде Supabase или Neon — вы получаете PostgreSQL напрямую, решать нечего. Для локальной разработки и быстрой валидации SQLite вполне достаточен — Drizzle ORM поддерживает бесшовное переключение между обоими.
:::

## Пусть AI поможет спроектировать схему

Поняв эти концепции, вы можете использовать такие промпты, чтобы AI спроектировал вашу базу:

```
Я строю [описание приложения], пожалуйста, помоги мне спроектировать схему базы данных.

Требования:
1. Используй PostgreSQL + Drizzle ORM
2. Перечисли все таблицы, поля, типы, ограничения
3. Аннотируй отношения между таблицами (один-ко-многим/многие-ко-многим)
4. У каждой таблицы обязаны быть id, created_at, updated_at
5. Используй китайские комментарии, объясняющие назначение каждого поля
```

AI сгенерирует полный код Drizzle-схемы, который можно скопировать прямо в проект.

---

::: tip Ключевые выводы раздела

- **Таблица** = контейнер для одного типа данных; строки — записи, колонки — атрибуты
- **Primary key** = уникальный ID каждой строки, используйте автоинкремент `serial`
- **Foreign key** = нить, соединяющая таблицы, гарантирует referential integrity
- **Три типа отношений**: один-ко-многим (самый частый), многие-ко-многим (нужна junction-таблица), один-к-одному (разбивает большие таблицы)
- **Ограничения** = стражи правил на уровне базы, финальная оборона поверх валидации кода
- **Типы данных** = выберите правильно для эффективного хранения и быстрых запросов
:::
