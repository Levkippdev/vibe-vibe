# Глава 6: Персистентность данных и базы данных

![img](/images/Advanced/mlkzzu32-0a305624d07171b4.jpg)



## Предисловие

Интерфейс уже отполирован, но вы упёрлись в неловкую проблему: при каждом обновлении страницы заполненные формы и сгенерированные беседы исчезают в воздухе.

Наставник объясняет: это происходит потому, что данные браузера по умолчанию хранятся во временной **памяти**. Чтобы данные выживали после закрытия или обновления страницы, нужна **персистентность данных**.

Он sternно напоминает: **Данные — фундамент всего бизнеса**. Frontend-код можно переписать, уродливый UI — рескиннуть, но если данные юзеров в базе потеряны или испорчены — ваш продукт закончен. Поэтому backend-разработка часто требует больше строгости, чем frontend-работа: вы охраняете душу продукта.



### Хранение в JSON-файлах

Персистентность не всегда требует сразу сложного софта. Простейший подход использует формат **JSON**, знакомый вам по конфиг-файлам: данные хранятся как `.json`-файлы. Каждая запись чата или профиль юзера — по сути просто текст. Сохранили в файл на диск, прочитали позже — и готово. Это мгновенно раскрывает суть «баз данных»: **ничего больше, чем эффективное чтение и запись файлов на диск**.



### Реляционные базы данных

JSON-файлы просты, но они становятся болезненно медленными, когда нужно найти «всех юзеров старше 20, живущих в Пекине» — пришлось бы сканировать весь файл. Входят **реляционные базы данных**. «Реляционность» — не про личные отношения; это про таблицы, связанные общими полями — таблица Users, связанная с таблицей Orders через `user_id`, например. Наставник просит представить это как **супер-Excel**, ухватив несколько ключевых концепций:

- **Table**: лист Excel, например таблица `Users`.
- **Row**: одна строка таблицы, представляющая конкретную запись (например, юзер Zhang San).
- **Column**: заголовки, определяющие, какие атрибуты у данных есть (имя, возраст, email).
- **Primary Key**: уникальный ID каждой строки (обычно `id`), абсолютно неповторимый.
- **Foreign Key**: нити, связывающие с другими таблицами. Записав `user_id` в таблицу `Orders`, можно проследить, какой юзер сделал заказ.

**Как судить о спроектированных AI структурах таблиц?** Новички часто не могут разглядеть изъяны схемы с первого взгляда. Наставник учит **«методу кросс-валидации AI»** (разговорно «перекрёстная переплавка»): **AI #1** проектирует вашу схему, затем этот код отправляется **AI #2** или **AI #3** с вопросом: *«Как senior-архитектор баз данных, на основе моего PRD и реальных бизнес-сценариев — здорова ли эта схема? Какие потенциальные ловушки производительности или логические пробелы существуют?»* После двух раундов таких «спаррингов лево-право» обычно получается устойчивая модель базы данных.



### Drizzle Schema

SQL — стандартный язык операций с базами; этот туториал использует **Drizzle ORM**. ORM позволяют управлять базами знакомым кодом TypeScript вместо ручного SQL. Drizzle использует TypeScript для определения схем — структуры таблиц, колонки и типы, — которые AI генерирует автоматически из документов PRD.

Например, если PRD гласит «один юзер может публиковать много статей», AI добавит поле `posts` в таблицу `User` и внешний ключ `authorId` в таблицу `Post`. **Ваша работа — ревью, корректен ли сгенерированный AI код.**

Наставник говорит: «Дизайн базы держится на понимании бизнес-отношений. AI берёт на себя техническую реализацию, но "каковы отношения между юзерами и заказами" — требует вашей бизнес-проницательности».

Чтобы понять результат работы AI, наставник построчно разбирает сниппет кода:

```typescript
// src/db/schema.ts
import { pgTable, serial, text, timestamp, integer } from 'drizzle-orm/pg-core'

export const users = pgTable('users', {
  id: serial('id').primaryKey(),           // Auto-increment primary key
  email: text('email').notNull().unique(),  // Required and unique
  name: text('name'),                       // Optional field (no .notNull())
  createdAt: timestamp('created_at').defaultNow(),
})

// Relationship example
export const posts = pgTable('posts', {
  id: serial('id').primaryKey(),
  title: text('title').notNull(),
  authorId: integer('author_id').references(() => users.id), // Foreign key reference
})
```

- **`pgTable`**: определяет структуру таблицы PostgreSQL
- **Типы**: `serial` (автоинкрементное целое), `text` (текст — всегда text, никогда varchar), `boolean`, `timestamptz` (timestamp с таймзоной), `integer`, `numeric` (точный decimal — обязателен для денег)
- **Опциональные поля**: поля без `.notNull()` по умолчанию опциональны
- **`.unique()`**: принуждает уникальность значений
- **`.references()`**: определяет отношения внешних ключей между таблицами



### Операции с базой

Освоение операций с базой требует понимания трёх ключевых концепций.

**CRUD-операции**: даже не пиша SQL, нужно усвоить **CRUD** (Create, Read, Update, Delete). Это фундамент всех операций с базой и ваш ключевой словарь для указаний AI по управлению данными.

**Транзакции — гарантия целостности данных**: наставник добавляет ключевую концепцию: «Некоторые операции затрагивают несколько изменений в базе, которые обязаны исполняться пачкой. Возьмём перевод денег: списали со счёта A, добавили на счёт B. Если списание прошло, а добавление провалилось — ваши данные испорчены». **Транзакция** упаковывает несколько операций в атомарную единицу «всё или ничего». Критично для финансовой, заказной и другой ключевой бизнес-логики.

**Индексы — ускорение запросов**: наставник продолжает: «С ростом данных вы можете столкнуться с замедлением запросов. Поиск email среди миллионов юзеров без индекса заставляет базу сканировать строку за строкой». **Индекс** работает как оглавление книги. Без него — полное сканирование таблицы; с ним — прямое попадание, ускорение в десятки-тысячи раз. Но индексы не бесплатны: они потребляют дополнительное место и замедляют запись, так как индексы должны обновляться при изменении данных. Обычно индексы строятся только на «часто запрашиваемых полях» вроде `email` или `created_at`. **Критично: PostgreSQL НЕ индексирует колонки внешних ключей автоматически** — это самая частая ловушка производительности, добавляйте их вручную.

AI знает, когда нужны транзакции и какие поля заслуживают индексов. Усвоение этих концепций улучшает вашу коммуникацию с AI.



### Целостность и валидация данных

«Данные сохранены, — спрашивает наставник, — но сохранены ли они правильно?»

Он приводит примеры: email введён как `hello` (невалидный формат), возраст `-5` (вне диапазона), заказы ссылаются на несуществующие ID юзеров (referential integrity). **Валидация данных предотвращает эти сценарии**.

Наставник объясняет, что у валидации **три линии обороны**:

**Первая линия: ограничения базы**. Определения схем с `.notNull()`, `.unique()`, `.references()` — ограничения уровня базы. Это «железные законы»: даже с багами в коде база отклоняет нарушения.

**Вторая линия: валидация backend API**. При обработке запросов AI автоматически добавляет логику валидации — форматы email, длины паролей, диапазоны enum и т.д. Это перехватывает ошибки до их попадания в базу.

**Третья линия: валидация форм на frontend**. Браузер проверяет до отправки. `<input type="email">` автовалидирует формат email; HTML5-атрибуты вроде `required`, `min`, `max` дают базовые проверки.

Наставник предупреждает: **каждая линия служит своей цели**. Ограничения базы — финальная страховочная сетка, валидация backend — главная оборона, валидация frontend — улучшение UX (быстрая обратная связь без сетевых ожиданий). Никогда не пропускайте защиту backend и базы только потому, что есть frontend-валидация — юзеры могут вызывать API напрямую, минуя UI.

AI знает, какая валидация принадлежит каждому слою. Запомнив «defense in depth», вы получаете направление при коллаборации с AI.



### Бэкап данных

«Прежде любого технического обсуждения, — говорит наставник серьёзно, — **осознание бэкапа данных**. Данные — душа вашего продукта; бэкапы — базовая линия разработки. Многие пренебрегают этим до удара коллапса базы, обнаруживая, что все данные юзеров исчезли — катастрофический исход.

**Автоматические бэкапы — не опция, а обязательство**. Ваша стратегия требует: автоматические бэкапы (ежедневно), бэкапы в нескольких местах (облако + локально), регулярные recovery-учения (проверка целостности бэкапов). Слишком многие делают бэкапы, ни разу не тестируя, и находят испорченные файлы только тогда, когда нужно восстановление.

Учения по disaster recovery важны не меньше самих бэкапов. Без практики вы не знаете, работают ли бэкапы на самом деле».



### Выбор базы данных

Для hands-on практики вы будете использовать **SQLite** — легковесную файловую базу, не требующую установки, идеальную для разработки и тестирования. Но для будущей масштабируемости наставник рекомендует **PostgreSQL**.

**Варианты хостинга PostgreSQL**: Supabase и Neon — популярные managed PostgreSQL-облака с разным позиционированием.

**Supabase** — полный BaaS (Backend as a Service): PostgreSQL плюс Auth, Storage, Realtime-подписки, Edge Functions и др. Идеально для быстрой валидации MVP без сложности backend.

**Neon** сфокусирован чисто на базе, предоставляя serverless PostgreSQL с автомасштабированием — подходит под кастомные требования backend.

Однако наставник советует: этот туториал рекомендует стандартный PostgreSQL вместо любого BaaS lock-in. Стандартный PostgreSQL углубляет понимание ключевых концепций баз, снижает стоимость миграции и оставляет будущие варианты хостинга открытыми — Supabase, Neon, Railway или self-hosted. Вы осваиваете саму базу, а не конкретную сервисную платформу. Этот «распакованный» образ мышления особенно важен в эпоху AI.

Почему PostgreSQL? Один убедительный пример: **backend OpenAI ChatGPT работает на PostgreSQL**. Они поддерживают 800 миллионов юзеров одним PostgreSQL-primary, обрабатывая миллионы запросов в секунду. Если PostgreSQL тянет ChatGPT — вам его хватит с запасом.

Любопытно, что такое «primary»? Кратко: **primary-replica и high availability** означает, что production-окружения обычно имеют один **primary** (записи) и несколько **replica** (чтения), с автоматической синхронизацией. Это распределяет нагрузку чтения и гарантирует, что replica примут эстафету при падении primary — базовая высокая доступность. Это операционные вопросы; для разработки достаточно одной базы, а managed-платформы берут остальное на себя.

Помимо одобрения топовой AI-компании, у PostgreSQL есть две неотразимые фичи для AI-разработчиков:

1. **Поддержка JSONB**: хоть она и реляционная, она хранит JSON как NoSQL (гибкая схема, лёгкий доступ, но меньше реляционных ограничений). Скидывайте AI-сгенерированные, структурно неопределённые сложные данные напрямую — правила (SQL) плюс гибкость (NoSQL).
2. **pgvector (векторный поиск)**: killer-фича эпохи AI. Хранит и запрашивает «векторные данные» — векторы, это числа, в которые AI конвертирует текст, измеряя «насколько похожи два фрагмента». Это включает **долговременную память AI** (RAG, Retrieval-Augmented Generation — позволяя AI ссылаться на сохранённые материалы при ответах). Выбор PostgreSQL прокладывает дорогу будущему вашего AI-приложения.



### Практические ловушки

**Dev- и production-базы**. Наставник объясняет: профессиональные команды держат отдельные базы — dev для тестов, production для реальных юзеров. Разделение — best practice, но **на старте допустимо использовать одну базу для быстрого старта** — разрабатывайте прямо на облачной базе, избегая хассла миграции при деплое. **Как только появятся реальные юзеры — строго разделяйте окружения**, предотвращая загрязнение данных и security-риски.

**Маркировка данных**: при общей базе как отличить тестовые данные от реальных? Два подхода: ручная чистка перед запуском или добавление поля `isTest`/`isDev` с пометкой dev-данных `true` и фильтрацией их в production-запросах. Дёшево и безопасно.

**Чистка тестовых данных**: при удалении тестовых данных скажите AI «удали все тестовые данные» — он сгенерирует что-то вроде `DELETE FROM users WHERE isTest = true`. Вы понимаете: удаляются только помеченные тестовые данные. **В этом назначение поля `isTest`** — предохранительный затвор, гарантирующий, что удаляются только тестовые данные, никогда — реальные.

**Connection URL**: вы часто увидите `Error: Invalid URL`. Наставник объясняет: подключение к базе — как отправка письма, формат должен быть точным: `postgresql://username:password@host:port/database`. Любая ошибка в пунктуации или спецсимволы в пароле (требующие escaping) ведут к провалу.


## После этой главы

Наставник напоминает: **после завершения главы вернитесь к технической документации главы 4 и изучите модели данных AI**.

Теперь вы можете читать эти структуры таблиц, отношения и индексы. Если дизайн AI имеет проблемы — вы их заметите; если нет — используйте уверенно. Освоение этого знания — не для самостоятельного проектирования баз, а для **понимания дизайнов AI и знания, что они делают**.

**Когда нужны корректировки**:

- Запросы замедлились → Попросите AI добавить индексы
- Несогласованность данных → Попросите AI проверить транзакции
- Нужны новые функции → Попросите AI расширить схему

Большую часть времени дизайны AI надёжны. Нужно лишь уметь их читать и знать, как просить AI об оптимизациях.
