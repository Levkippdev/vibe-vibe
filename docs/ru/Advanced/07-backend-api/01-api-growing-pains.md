# 7.1 Одного API больше не хватает

> **Цель раздела**: понять реальные вызовы, возникающие при переходе приложения от «работает» к «юзабельно», и научиться коммуницировать эти требования AI.

---

## Дилемма страницы фильма Сяомина

Проект «Личный Douban» Сяомина продолжается из главы 6. Дизайн базы завершён — пять таблиц: `movies`, `directors`, `tags`, `movie_tags` и `ratings`. Отношения расписаны, ограничения на месте. По CRUD-паттернам из 7.0 у него работают базовые операции — добавление фильмов, просмотр списка, редактирование, удаление. Всё работает.

Сяомин в восторге. Он решает, что backend практически готов, и начинает строить реальные страницы.

Первая — страница деталей фильма. Он открывает Douban: страница фильма показывает название, год, постер, имя режиссёра, список актёров, рейтинг юзеров, теги и синопсис. В его базе эта информация разбросана по четырём-пяти таблицам.

Какой подход самый интуитивный? Frontend делает пять запросов:

1. `GET /api/movies/1` → базовая информация фильма
2. `GET /api/directors/5` → информация режиссёра
3. `GET /api/movies/1/tags` → список тегов
4. `GET /api/movies/1/ratings` → рейтинги
5. `GET /api/movies/1/actors` → список актёров

Работает. Но когда Сяомин открывает страницу, опыт ужасен: сначала появляется название фильма, через полсекунды выскакивает имя режиссёра, ещё через момент — теги, рейтинг грузится последним. Юзер видит «прыгающую» страницу, как деталь за деталью.

Хуже: пять запросов — пять сетевых round trip'ов. Каждый занимает минимум десятки миллисекунд плюс время обработки сервера. Юзер ждёт несколько сотен миллисекунд полной страницы. При плохой сети (скажем, в метро) один запрос может упереться в timeout — и страница неполная: название есть, режиссёра нет, рейтинг есть, тегов нет.

Ветеран-разработчик глядит и спрашивает: «Сначала разберись: как эта страница рендерится?»

### Первый вопрос: этой странице вообще нужен API?

Это вопрос, который упускают многие новички. В Next.js компоненты страниц (`page.tsx`) по умолчанию работают на сервере и могут **запрашивать базу напрямую** — без API round trip.

Если страница фильма Сяомина — Server Component (а по умолчанию это так), он может вызвать запросы Drizzle прямо в компоненте, взять данные из всех пяти таблиц разом и отрендерить HTML в браузер. Весь процесс — ноль сетевых round trip'ов «frontend отправил запрос → backend вернул»: данные уже на сервере.

Так для кого API Routes? Два сценария:

- **Когда frontend нужна динамическая интеракция** — юзер кликает «В избранное», и frontend должен сказать backend «хочу в избранное». Эти юзер-триггеренные write-операции нуждаются в способе вызвать backend-логику
- **Внешние потребители** — если старый Ван захочет использовать данные Сяомина для мини-программы, ему нужен вызываемый HTTP-интерфейс

Страница деталей Сяомина — «показать данные при открытии», без интеракций юзера. Ветеран говорит: «Для страницы деталей просто запрашивай базу прямо в Server Component. API Route писать не нужно».

::: tip Server Actions: write-операции без написания интерфейсов

Вы можете заметить, что AI-сгенерированные фичи «в избранное», «лайк» или «отправка формы» не имеют файлов `app/api/xxx/route.ts`. Вместо них — функция с директивой `"use server"`, которую frontend вызывает напрямую.

Server Actions позволяют frontend вызывать серверную функцию напрямую, без ручного определения API-роутов или написания `fetch`-запросов. Для простых write-операций «юзер кликнул → backend обработал → вернул результат» они чище, чем API Routes.

Не нужно указывать, какой подход использовать. Claude Code с загруженным Skill `next-best-practices` решит сам: отображение страниц — прямые запросы к базе через Server Component, простые write-операции — Server Actions, интерфейсы для внешних потребителей — Route Handlers. Не удивляйтесь, не увидев `route.ts` в коде: AI, вероятно, выбрал более подходящий способ.
:::

Однако у списка фильмов Сяомина есть фильтрация, сортировка и пагинация — это юзер-триггеренные интеракции, где frontend должен динамически запрашивать разные данные по действиям юзера. Этот сценарий действительно нуждается в API.

Так что обсуждаемые далее пагинация, фильтрация и сортировка относятся к **сценариям, нуждающимся в API** — где frontend динамически запрашивает данные по действиям юзера.

Но даже в API-сценариях проблема «одна страница — пять запросов» остаётся. Например, когда Сяомин позже добавит на страницу фильма «избранное» и «комментарии», она станет интерактивной страницей на клиенте, берущей данные через API. Как тогда организовать структуру данных?

## Вложенная vs плоская: два подхода к организации данных

Допустим, frontend нужны данные фильма и режиссёра. Backend может вернуть это двумя способами:

### Вложенная структура

Встроить связанные данные «внутрь» основного объекта, вернув всю информацию разом:

<details>
<summary>Как выглядит вложенный ответ? Развернуть</summary>

```json
{
  "id": 1,
  "title": "Spirited Away",
  "year": 2001,
  "director": {
    "id": 5,
    "name": "Hayao Miyazaki",
    "nationality": "Japanese"
  },
  "tags": ["Animation", "Fantasy", "Adventure"],
  "rating": {
    "average": 9.4,
    "count": 2156
  }
}
```

Frontend может напрямую взять `movie.director.name` для имени режиссёра и `movie.rating.average` для рейтинга — без второго и третьего запросов. Все данные приходят разом.

</details>

### Плоская структура

Вернуть только ID связанных данных; frontend подгружает больше при необходимости:

<details>
<summary>Как выглядит плоский ответ? Развернуть</summary>

```json
{
  "id": 1,
  "title": "Spirited Away",
  "year": 2001,
  "directorId": 5,
  "tagIds": [1, 3, 7],
  "averageRating": 9.4
}
```

Получив `directorId: 5`, для отображения имени режиссёра frontend обязан вызвать `GET /api/directors/5`. Для имён тегов — запросить таблицу тегов с `tagIds`.

</details>

### Как выбирать?

Это не выбор «или-или» — всё зависит от сценария:

| Сценарий | Рекомендуемая структура | Причина |
|----------|----------------------|--------|
| Страница деталей фильма | Вложенная | Страница показывает полную информацию; выдача всего разом экономит frontend'у множество ходок |
| Страница списка фильмов | Плоская (или слегка вложенная) | Списку нужны только название, год, постер; полная инфа режиссёра и все теги жгут трафик |
| Таблицы админ-панелей | Плоская | В таблицах только ключевые поля на строку; детали грузятся по клику |
| Результаты поиска | Плоская + минимальная вложенность | Поиску нужны название и рейтинг, но не полные биографии режиссёров |

Практический критерий: **после получения данных, нужно ли frontend'у делать дополнительные запросы для рендера страницы?** Если да — интерфейс возвращает недостаточно; вложите больше связанных данных. Если frontend может рендерить напрямую с полученным — самое оно.

Сяомин переделал API деталей фильма во вложенную структуру, возвращая всю информацию одним запросом. Страница перешла от «сборки деталей» к «одним выстрелом» — быстрее загрузка, лучше опыт.

Разговаривая с AI, просто описывайте потребности:

> «API деталей фильма должен возвращать информацию режиссёра, список тегов и средний рейтинг одновременно, вложенной структурой — все данные одним запросом. API списка фильмов возвращает только название, год, URL постера и средний рейтинг».

## 500 записей разом — страница зависает

С проблемой деталей справившись, Сяомин берётся за список фильмов главной страницы.

Сначала фильмов было всего с десяток: `GET /api/movies` возвращал массив, frontend циклом рендерил их за миллисекунды. Гладкий опыт.

Потом Сяомин провёл выходные, внося каждый просмотренный фильм — больше 500. Открытие главной снова: браузер крутится несколько секунд до отображения. Он открыл dev tools: API вернул massive JSON с 500+ записями, несколько сотен KB данных. Frontend отрендерил 500+ карточек фильмов, тысячи DOM-узлов — браузер завис.

Это как прийти в библиотеку и попросить библиотекаря «вынеси все свои книги — я посмотрю». Библиотекарь полдня таскает десятки тысяч книг — вы физически не можете их просмотреть. Нормальный подход: «Сначала sci-fi, по 20 за раз, следующую партию — когда закончу».

Это **пагинация**.

### Offset-пагинация: режим перелистывания

Самый частый метод — **offset-пагинация**: сказать backend «пропусти первые N записей, дай следующие M».

Запрос: `GET /api/movies?page=3&limit=20`

Значение: страница 3, по 20 на страницу. Backend пропускает первые 40 (страницы 1 и 2), возвращая записи 41–60.

Преимущество — **простота и интуитивность**. Frontend может напрямую показать навигацию по номерам страниц: «Стр. 1, Стр. 2, Стр. 3...». Юзеры кликают любую страницу для прыжка. Пагинация-бары внизу результатов поиска Taobao и JD.com используют этот подход.

Недостаток — **глубже — медленнее**. При исполнении `OFFSET 10000 LIMIT 20` база обязана просканировать первые 10 000 записей (хотя не возвращать их), прежде чем взять ваши 20. Как найти книгу № 500 в библиотеке: библиотекарь считает от 1-й до 500-й, потом протягивает следующие 20. Каждый раз счёт с начала — глубже страница, медленнее.

Эта тема разбиралась в главе 6, разделе 6.3 (ловушки OFFSET). Для 500 фильмов Сяомина offset-пагинация полностью достаточна — проблемы производительности начинаются с десятков тысяч записей.

### Cursor-пагинация: режим закладки

Другой подход — **cursor-пагинация**: без номеров страниц, только «закладки».

Запрос: `GET /api/movies?cursor=eyJpZCI6NDB9&limit=20`

Значение: от записи после последней выданной ранее — дай ещё 20. `cursor` — закодированный маркер позиции последней записи предыдущей страницы.

Это как закладка в библиотеке. Следующий раз — старт с закладки, без счёта с начала. Насколько бы глубоко ни зашли — скорость константна: база читает прямо от закладки, не сканируя предыдущие записи.

Недостаток — **нельзя прыгать по страницам**. Только «дальше, дальше» страница за страницей; напрямую на 50-ю не прыгнуть. Поэтому социальные ленты (Weibo, Moments, TikTok) используют infinite scroll вместо пагинации — они на cursor-пагинации.

### Как выбирать?

| Сценарий | Рекомендация | Причина |
|----------|---------------------|--------|
| Таблицы админ-панелей | Offset | Нужна навигация по страницам, объём данных обычно умеренный |
| Результаты поиска товаров | Offset | Юзеры ожидают пагинацию, нужен прыжок на конкретные страницы |
| Социальная лента / списки комментариев | Cursor | Infinite scroll, большой объём, прыжки не нужны |
| Объём данных < 10 000 | Offset | Просто и достаточно, производительность не проблема |
| Объём данных > 100 000 | Cursor | Offset замедляется с глубиной |

В коллекции Сяомина всего несколько сотен названий — offset более чем достаточно.

Скажите AI:

> «Добавь пагинацию в API списка фильмов через offset/limit, по умолчанию 20 на страницу. Включи total count и total pages в ответ для навигации frontend'а».

### Что должен включать пагинированный ответ?

Вернуть просто данные недостаточно — frontend ещё должен знать «сколько всего», «на какой я странице», «есть ли следующая» — иначе непонятно, сколько кнопок страниц показывать и дизейблить ли «следующую».

Хороший пагинированный ответ выглядит так:

<details>
<summary>Пример пагинированного ответа</summary>

```json
{
  "success": true,
  "data": [
    { "id": 1, "title": "Spirited Away", "year": 2001, "rating": 9.4 },
    { "id": 2, "title": "My Neighbor Totoro", "year": 1988, "rating": 9.2 },
    { "id": 3, "title": "Castle in the Sky", "year": 1986, "rating": 9.1 }
  ],
  "meta": {
    "total": 500,
    "page": 1,
    "limit": 20,
    "totalPages": 25
  }
}
```

Инфо `meta` говорит frontend: 500 записей всего, сейчас страница 1, по 20 на страницу, 25 страниц. Frontend рендерит бар пагинации соответственно и дизейблит «следующую» на последней странице.

</details>

::: tip Cursor-ответы чуть отличаются
Cursor-пагинация не возвращает `total` и `totalPages` (подсчёт total сам требует полного сканирования — медленно). Вместо этого возвращается `nextCursor`. Frontend использует его для запроса следующей страницы; если `nextCursor` пуст — записей больше нет.
:::

## Хочется фильтровать по тегу и сортировать по рейтингу

Пагинация решена — у Сяомина новые требования.

Друг тестирует и говорит: «Список может показывать только анимацию? Не хочу листать 500 фильмов ради поиска». Другой друг: «Можешь сортировать по рейтингу сверху? Хочу видеть самые высоко оценённые».

Сяомин ломает голову: создавать новый API под каждое условие фильтра? `GET /api/movies/animation` — анимация, `GET /api/movies/top-rated` — высокорейтинговые? А если нужен и фильтр по тегу, И сортировка по рейтингу? Ещё `GET /api/movies/animation/top-rated`? Комбинаторный взрыв интерфейсов неуправляем.

Ветеран говорит: «Не создавай новые интерфейсы. Один list API с комбинациями query-параметров».

### Искусство комбинаций query-параметров

`GET /api/movies?tag=Animation&sort=rating&order=desc&page=1&limit=20`

Один запрос выражает: «Дай фильмы с тегом "Animation", отсортированные по рейтингу от высокого к низкому, страница 1, по 20».

Query-параметры прекрасны тем, что **свободно комбинируются**, как Lego:

- Только сортировка, без фильтра? `GET /api/movies?sort=rating&order=desc`
- Только фильтр, без сортировки? `GET /api/movies?tag=Animation`
- Фильтр по нескольким тегам? `GET /api/movies?tag=Animation&tag=Japanese`
- Ничего не передано? `GET /api/movies` возвращает все данные в дефолтном порядке (с пагинацией)

Только один интерфейс; frontend конструирует разные параметры по действиям юзера. Юзер выбрал «Animation» в панели фильтров — frontend добавляет `tag=Animation`; юзер кликнул «Сортировать по рейтингу» — frontend добавляет `sort=rating&order=desc`. Код интерфейса не меняется — все комбинации поддерживаются автоматически.

### Частые дизайны query-параметров

| Параметр | Назначение | Пример |
|-----------|---------|---------|
| `page` / `limit` | Пагинация | `?page=2&limit=20` |
| `sort` / `order` | Сортировка | `?sort=rating&order=desc` |
| `tag` / `genre` | Фильтр по категории | `?tag=Sci-Fi` |
| `year` | Фильтр по году | `?year=2024` или `?yearFrom=2020&yearTo=2024` |
| `q` / `search` | Поиск по ключевому слову | `?q=Spirited Away` |
| `minRating` | Минимальный рейтинг | `?minRating=8` |

Все эти параметры должны быть **опциональными**. Не переданы — используются дефолты: без фильтра, сортировка по времени создания по убыванию, страница 1 по 20. Это гибкость без поломки существующих вызовов.

::: warning Поиск и фильтр — разные вещи
**Фильтр** — точное совпадение: «тег равен Animation», «год равен 2024». **Поиск** — нечёткое совпадение: «название содержит "Spirited Away"». Можно комбинировать, но реализуются по-разному. Фильтры — WHERE-условия базы; поиск может потребовать full-text-индексов.

Для коллекции Сяомина достаточно простого поиска `LIKE '%keyword%'`. При росте данных до сотен тысяч может понадобиться full-text-поиск PostgreSQL — но это потом: сначала работающее, потом оптимизация.
:::

Скажите AI:

> «API списка фильмов поддерживает опциональные query-параметры: tag (фильтр по тегу), year (фильтр по году), q (поиск по названию), sort (поле сортировки, поддерживает rating/year/createdAt), order (asc или desc). Все параметры опциональны; без них — все данные в дефолтном порядке».

## Путь эволюции API Сяомина

Оглянем, как API списка фильмов Сяомина эволюционировал шаг за шагом:

| Этап | API | Проблема |
|-------|-----|---------|
| V1 | `GET /api/movies` → все 500 записей | Страница зависает |
| V2 | `GET /api/movies?page=1&limit=20` → пагинация | Нужные фильмы не найти |
| V3 | `GET /api/movies?tag=Animation&sort=rating&order=desc&page=1&limit=20` | Достаточно! |

Каждая эволюция двигалась реальными потребностями — не спроектирована Сяомином заранее, а обнаружена в использовании и усилена. Это норма дизайна API: стартуйте с простейшей версии, итерируйте при проблемах. Не нужно сразу проектировать «идеальный» API.

## Шаблоны промптов для общения с AI

Совместите изученные концепции, чтобы описать полное API-требование одним абзацем:

**При дизайне API с нуля:**

> «Помоги мне спроектировать два API: список фильмов и детали. List API поддерживает пагинацию (offset/limit, дефолт 20 на страницу), фильтр по тегу, сортировку по рейтингу или году и включает total count и total pages в ответе. Detail API возвращает информацию фильма с вложенной инфой режиссёра, списком тегов и средним рейтингом. Все ответы в формате `{ success, data, error }`».

**При добавлении фич в существующий API:**

> «Текущий `GET /api/movies` возвращает только все данные. Добавь пагинацию и фильтрацию. Пагинация — query-параметры page и limit; фильтрация — tag и year; сортировка — sort и order. Все новые параметры опциональны: без них поведение как раньше, backwards-совместимо».

**При самостоятельном ревью AI:**

> «Проверь существующий API списка фильмов на проблемы: 1) Поддерживает ли пагинацию? 2) Валидируются ли типы query-параметров (например, page — положительное целое)? 3) Ограничены ли поля сортировки разрешёнными значениями (чтобы юзеры не передавали произвольные имена колонок)?»

- **`next-best-practices`** — файловые конвенции Next.js, границы RSC, async API, обработка роутов, метаданные

Эти Skills обычно встроены в Claude Code. Они автоматически загружаются при работе с React или Next.js, помогая избегать частых ловушек производительности.
