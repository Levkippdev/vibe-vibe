# 7.2 Когда API ломаются

> **Цель раздела**: понять самые частые типы проблем после деплоя API — грязные данные, дубликаты отправки, обработка ошибок, истощение ресурсов — и как описывать эти проблемы AI, чтобы он помог их починить.

---

## Приложение Сяомина выходит в свет

«Личный Douban» Сяомина наконец завершён. Список фильмов с пагинацией, фильтрацией и сортировкой. Страница деталей возвращает все данные одним вызовом API. Опыт плавный. Он шерит ссылку в чат друзей — пусть все пробуют.

Первые три дня — всё спокойно.

На четвёртый день начинаются проблемы.

## В базе появляется фильм с пустым названием

Сяомин открывает Drizzle Studio проверить данные и находит странную запись: название пустое, год 0, ID режиссёра указывает на несуществующего режиссёра. Он в недоумении — на frontend явно есть валидация ввода. Кнопка «Отправить» дизейблится при пустом названии, поле года принимает только числа. Как такие данные могли отправиться?

Он спрашивает друга, тот говорит: «Я протестировал твой API напрямую через Postman, без параметров — и всё равно успешно».

Тогда Сяомин осознаёт: **frontend-валидация останавливает только «нормальных» юзеров**. Любой может обойти frontend: открыть dev tools браузера и отправить запросы напрямую, использовать Postman или curl для вызова API, даже написать скрипт для батч-вызовов. Ограничения ввода frontend, дизейблинг кнопок, проверки формата против этих способов бесполезны.

Это как торговый центр с охранником у входа, напоминающим «пожалуйста, через главный вход». Но если кто-то зашёл через боковую дверь, чёрный ход или даже влез в окно — охранник не остановит. Настоящая проверка безопасности — внутри: каждая касса проверяет вашу личность и право покупки.

**Frontend-валидация — для UX** (мгновенный фидбек, сообщение юзеру «название не может быть пустым» без ожидания ответа сервера), **backend-валидация — для security данных** (охрана нижней линии: откуда бы запрос ни пришёл, грязные данные не войдут в базу). Обе незаменимы.

### Zod — библиотека валидации, которую использует AI

Когда вы говорите AI «добавь валидацию параметров в API», он скорее всего использует **Zod**. Zod — самая популярная библиотека валидации в TypeScript-экосистеме. Не нужно учить её синтаксис — достаточно знать три вещи:

- **Что делает**: определяет правила «каким должен быть» (например, название — строка 1–100 символов, год — целое 1888–2030), затем автоматически валидирует входящие данные
- **Что происходит при провале валидации**: возвращает конкретные сообщения об ошибках frontend'у — какое поле неверно и почему
- **Почему вместо рукописных if-else**: Zod объединяет правила валидации и типы TypeScript — определили правила, типы выведены автоматически. Не нужно писать дважды. Плюс формат ошибок Zod консистентен, что удобно для обработки на frontend

<details>
<summary>Любопытно, как выглядит Zod? Развернуть; можно пропустить</summary>

```typescript
import { z } from 'zod'

// Правила: название — строка 1-100 символов, год — целое 1888-2030
const createMovieSchema = z.object({
  title: z.string().min(1, 'Title cannot be empty').max(100, 'Title too long'),
  year: z.number().int('Year must be integer').min(1888, 'Year cannot be earlier than 1888').max(2030),
  directorId: z.number().int().positive('Director ID must be positive integer'),
})

// Использование в API
export async function POST(request: Request) {
  const body = await request.json()
  const result = createMovieSchema.safeParse(body)

  if (!result.success) {
    // Валидация провалена: 400 с конкретным сообщением
    return Response.json(
      { success: false, error: { message: result.error.issues[0].message } },
      { status: 400 }
    )
  }

  // result.data — провалидированные безопасные данные, тип выведен автоматически
  const newMovie = await db.insert(movies).values(result.data).returning()
  return Response.json({ success: true, data: newMovie[0] })
}
```

Обратите внимание на метод `safeParse` — он не бросает исключение при провале валидации, а возвращает объект с `success` и `error`, позволяя решить, как обрабатывать. Это контролируемее, чем `try-catch`.

</details>

### Насколько строгой должна быть валидация?

Сяомин спрашивает ветерана: «Мне нужно добавить кучу правил на каждое поле?»

Ветеран: «Зависит от сценария. Ключевой принцип — **не доверять внешнему вводу, но и не перевалидировать**».

| Обязательно валидировать | Причина |
|---------------|--------|
| Обязательные поля не пустые | Пустые данные в базе вызывают каскад проблем ниже по потоку |
| Лимиты длины строк | Чтобы кто-то не передал строку на 10 МБ, взорвав память |
| Лимиты диапазона чисел | Рейтинг не бывает -1 или 999, год — 3000 |
| Валидация enum-значений | Статус — только «draft»/«published»/«archived», не произвольные строки |
| Существование foreign key | directorId обязан указывать на реального режиссёра (ограничения базы тоже заблокируют, но ранняя валидация даёт дружелюбнее ошибки) |

| Не нужно перевалидировать | Причина |
|--------------------------|--------|
| Внутренние вызовы сервисов | Ваш frontend вызывает ваш backend, формат данных под вашим контролем, базовой валидации достаточно |
| Поля с ограничениями базы | Если база уже имеет UNIQUE — не нужно проверять «есть ли дубль» в коде |

Скажите AI:

> «Добавь Zod-валидацию параметров во все POST и PATCH эндпоинты. Обязательные поля не пустые, строки с разумными лимитами длины, числа с разумными диапазонами. При провале — 400 с конкретным сообщением в формате `{ success: false, error: { message: '...' } }`».

## Один и тот же фильм добавлен 10 раз

Друг пишет Сяомину: «Кликнул кнопку добавления, сеть притормозила, я кликнул ещё несколько раз. Теперь "Spirited Away" появляется 10 раз...»

Сяомин открывает базу — точно: у фильма 10 идентичных записей, различаются только ID.

Классика: **дублирующая отправка**. Юзер не специально — сетевая задержка заставила подумать, что первый клик не сработал, и он кликнул ещё. Каждый клик отправил POST-запрос, и backend послушно создал 10 записей.

### Frontend блокирует один слой, backend ловит другой

**Слой frontend** — немедленно дизейблить кнопку после клика, показывать «Отправка...», восстанавливать по возврату запроса. Это блокирует 90% дубликатов. Но не все случаи: юзер рефрешит страницу и отправляет снова, авто-ретраи после timeout сети, кто-то дёргает API скриптом.

**Слой backend** — сделать API **идемпотентным**.

Идемпотентность — математическая концепция, но на бытовых примерах понятна легко:

- **Кнопки лифта** идемпотентны. Нажали «3-й этаж» — лифт едет на 3-й. Тревожно нажали ещё 5 раз — лифт всё равно едет на 3-й, не на 5 разных третьих этажей.
- **Выключатели света** идемпотентны. Свет уже горит, нажали ещё — остаётся гореть, не становится «дважды ярким».
- **Автоматы с напитками** не идемпотентны. Монету — одна бутылка, две монеты — две.

Для API:
- `GET` естественно идемпотентен — запрос одного ресурса сколько угодно раз даёт один результат, база не меняется
- `DELETE` тоже идемпотентен — удаление одной записи: первый раз успешно, второй — «уже не существует», состояние базы неизменно
- `POST` (создание) по умолчанию НЕ идемпотентен — каждый вызов создаёт новую запись, в чём и проблема Сяомина

### Как сделать create-API идемпотентным?

Несколько подходов — выбирайте по сценарию:

**Подход 1: Уникальное ограничение базы.** Если бизнес-логика «одинаковые название + год» не должны дублироваться — добавьте композитное unique constraint на уровне базы. При второй вставке дубля база отклонит с ошибкой, backend поймает её и вернёт 409 (conflict).

Простейший подход, подходит сценариям с естественными уникальными идентификаторами. Но не у всех данных они есть — например, комментарии: один юзер может спокойно оставить два разных комментария на один фильм.

**Подход 2: Idempotency Key.** Frontend генерирует уникальный ID запроса (например, UUID) при каждой отправке и кладёт его в header запроса. Backend, получив запрос, сначала проверяет, обработан ли этот ID — если да, возвращает предыдущий результат; нет — исполняет обычно.

Самый универсальный подход, подходит любому сценарию. Платёжные API почти все так делают — дважды списать юзера из-за сетевых ретраев точно не хочется.

**Подход 3: Дедупликация frontend + страховочная сетка backend.** Frontend дизейблит кнопку + backend добавляет unique constraint — двойная страховка. Для большинства сценариев достаточно.

Для приложения Сяомина достаточен подход 1 — один и тот же фильм (то же название + год) не должен вводиться дважды.

Скажите AI:

> «Добавь композитное unique constraint на title + year для таблицы movies. Если API добавления встречает дубль, верни 409 с сообщением "Этот фильм уже существует" вместо 500. Также дизейбль кнопку добавления на frontend после клика и восстанавливай по возврату запроса».

## Все ошибки показывают «Что-то пошло не так»

Друг даёт ещё фидбек: «Добавил фильм с неверным годом — на странице "Что-то пошло не так". Ищу несуществующий фильм — "Что-то пошло не так". Твой сервер упал — тоже "Что-то пошло не так". Это моя проблема или твоя? Мне ретраить или менять ввод?»

Сяомин проверяет код — вся обработка ошибок API выглядит так:

```
catch (error) {
  return Response.json({ error: 'Something went wrong' }, { status: 500 })
}
```

Какая бы ни была ошибка — неверные параметры, нет данных, база упала — всё возвращает 500 и «Что-то пошло не так». Frontend получает это и может показать только generic-ошибку. Юзер понятия не имеет, что случилось и что делать.

### HTTP-статус-коды: система классификации ошибок

Вы точно видели «404 страница не найдена» — кликнули по протухшей ссылке, опечатались в URL — браузер показывает 404. HTTP-статус-коды — эта система классификации, 404 лишь один из них. Не нужно заучивать все — достаточно знать самые частые:

| Статус | Значение | Когда использовать | Что должен видеть юзер |
|-------------|---------|-------------|----------------------|
| **200** | Успех | Запрос обработан нормально | Обычный показ данных |
| **201** | Создано | POST создал новый ресурс | «Успешно добавлено!» |
| **400** | Bad Request | Провал валидации параметров, неверный формат | «Название не может быть пустым» (конкретное сообщение) |
| **404** | Not Found | Запрошенный ID фильма не существует | «Не могу найти этот фильм» |
| **409** | Conflict | Дублирующее добавление того же фильма | «Этот фильм уже существует» |
| **429** | Too Many Requests | Слишком много запросов за короткое время | «Слишком часто, попробуйте позже» |
| **500** | Server Error | Баг кода, база упала | «Сервис временно недоступен, попробуйте позже» |

Ключевой принцип: **серия 400 — «проблема твоя (вызывающего)», серия 500 — «проблема моя (сервера)»**.

Это различие критично — оно определяет, как обрабатывать на frontend:

- **Серия 400**: юзер может исправить сам. Показывайте конкретные сообщения, ведите юзера к правильному вводу. «Название не может быть пустым» — юзер заполняет название и отправляет снова.
- **Серия 500**: юзер ничего не может — только ждать. Просто «Сервис временно недоступен, попробуйте позже». **Не показывайте юзерам внутренние детали ошибок** — «PostgreSQL connection refused at 10.0.0.5:5432» юзеру бесполезно и может раскрыть внутреннюю архитектуру сервера.

::: danger Не раскрывайте внутренние детали в 500-ошибках

Это вопрос безопасности. Если ваша 500-ошибка возвращает строки подключения к базе, SQL-выражения, пути файлов, stack trace — атакующие могут использовать эту информацию для поиска слабостей системы.

Правильный подход: 500-ошибки возвращают только generic-сообщения («Сервис временно недоступен»), детальная информация об ошибках идёт в серверные логи для вашего собственного разбора.
:::

### Единый формат ошибочных ответов

Консистентно с форматом ответов из введения, ошибочные ответы тоже должны иметь единую структуру:

<details>
<summary>Примеры ответов разных типов ошибок</summary>

**400 Ошибка параметров:**
```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Название не может быть пустым",
    "details": [
      { "field": "title", "message": "Название не может быть пустым" },
      { "field": "year", "message": "Год должен быть целым 1888–2030" }
    ]
  }
}
```

**404 Ресурс не найден:**
```json
{
  "success": false,
  "error": {
    "code": "NOT_FOUND",
    "message": "Не могу найти фильм с ID 999"
  }
}
```

**500 Ошибка сервера:**
```json
{
  "success": false,
  "error": {
    "code": "INTERNAL_ERROR",
    "message": "Сервис временно недоступен, попробуйте позже"
  }
}
```

Заметьте: 400-ошибки включают массив `details`, перечисляющий конкретные проблемы каждого поля. Так frontend может показать сообщения об ошибках у соответствующих полей ввода, а не просто generic «Ошибка параметров» вверху страницы.

</details>

Скажите AI:

> «Унифицируй обработку ошибок всех эндпоинтов. Провал валидации параметров — 400 с конкретными сообщениями по каждому полю. Ресурс не найден — 404. Дублирующиеся данные — 409. Внутренние ошибки сервера — 500 только с generic-сообщением, детальные ошибки — в лог. Все ошибочные ответы в едином формате `{ success: false, error: { code, message } }`».

## «Только что успешно добавил, но в списке не видно»

Друг Сяомина говорит: «Только что добавил фильм, API вернул успех, но на странице списка рефрешу несколько раз — не вижу. Через время появилось».

Это не баг — работает **кэш**.

У Next.js несколько слоёв кэширования, поведение зависит от способа получения данных. Если страница списка — Server Component, напрямую запрашивающий базу, Next.js может кэшировать результат рендера всей страницы. Если список зовёт API через `fetch`, сам `fetch` тоже имеет кэширование. Симптом один: записали новые данные, а чтение всё ещё даёт старые.

Проблема не в том, что AI написал неверный код, — в механизме кэширования фреймворка. Решение — **проактивно сказать Next.js «эти данные изменились, обновись»** после изменения данных:

- После успешных POST/PATCH/DELETE вызывайте `revalidatePath('/movies')` или `revalidateTag('movies')`, уведомляя Next.js очистить соответствующий кэш
- При следующем визите на страницу Next.js заново запросит базу и отдаст свежие данные

Скажите AI:

> «После добавления/изменения/удаления фильмов используй revalidatePath или revalidateTag для очистки кэша связанных страниц, чтобы юзеры видели свежие данные».

::: tip Кэш — хорошо, но требует активного управления
Кэш может сильно поднять производительность: одна и та же страница списка у 100 юзеров — один запрос к базе, следующие 99 раз — прямой возврат из кэша. Но без активной очистки юзеры видят устаревшие данные. Принцип: **чтения можно кэшировать, записи обязаны чистить кэш после себя**. Claude Code с загруженным Skill `next-best-practices` автоматически добавит вызовы revalidate при генерации write-кода, но знание этого механизма помогает быстро локализовать причину при проблемах.
:::

## Фильм добавлен успешно, но юзер ждал две секунды

Починив кэш, Сяомин добавляет фичу: после добавления фильма юзером отправлять уведомление всем, кто подписан на этот тег.

После запуска друзья репортят: «Добавлять фильмы стало медленнее: после клика "Отправить" жду две секунды до "Успешно добавлено". Раньше мгновенно».

Сяомин проверяет — проблема в логике уведомлений. API добавления теперь делает три вещи:

1. Записать фильм в базу (десятки миллисекунд)
2. Запросить всех юзеров, подписанных на теги (сотни миллисекунд)
3. Отправить уведомление каждому юзеру (одна-две секунды)

Три шага исполняются **сериально**: шаг 1 завершён, потом шаг 2, потом шаг 3 — и только после всего «Успешно добавлено». Юзеру приходится ждать отправки всех уведомлений.

Но юзера волнует только «добавился ли фильм». Отправились ли уведомления, кому — юзеру не нужно это ждать.

Это разница **блокирующего и неблокирующего**. Запись в базу — ключевая операция: дождавшись её, можно сказать юзеру «успех». А отправка уведомлений — побочная операция, её можно полностью сделать после возврата ответа: юзер сразу видит «Успешно добавлено», уведомления спокойно уходят в фоне.

Next.js даёт фичу `after()` именно для этого: отложить операции, не блокирующие ответ (отправка уведомлений, логи, обновление статистики), на исполнение после отправки ответа.

Скажите AI:

> «Для API добавления фильма возвращай успех сразу после завершения записи в базу. Операции вроде отправки уведомлений и обновления статистики исполняй через after() из Next.js после ответа — не блокируй юзера».

::: tip Критерий: должен ли результат этой операции сообщаться юзеру?
Если да (как «Успешно добавлено» или «Название не может быть пустым») — обязано завершиться до ответа. Если нет (отправка уведомлений, логирование, обновление кэша) — можно после ответа. Claude Code со Skill `next-best-practices` автоматически определит, какие операции подходят для `after()`, но при ревью AI-решений, если вы обнаружили, что «API стало медленнее», подумайте — не должны ли некоторые операции не блокировать ответ.
:::

## Однажды все API внезапно отдают 500

Приложение Сяомина месяц работало нормально. Однажды вечером он снова пошарил ссылку в чате — десятки людей зашли одновременно. И все API начали возвращать 500.

Он бросает ошибку в AI — тот говорит: «пул соединений базы исчерпан» — `too many connections`.

### Что такое пул соединений?

Концепция детально разбиралась в главе 6, разделе 6.4. Краткий рекап:

Каждый раз, когда API должен запросить базу, сначала устанавливается «соединение». Установление имеет цену: TCP-handshake, аутентификация, выделение памяти — обычно десятки миллисекунд. Если каждый запрос создаёт новое соединение и выбрасывает после использования — десятки конкурентных запросов могут задушить базу.

**Пул соединений** заранее создаёт партию соединений и кладёт их в «пул». Запрос пришёл — берёт одно; закончил — возвращает. Как шеринг велосипедов: не нужно каждому покупать свой — партия на улице, кому нужно — уехал, доехал — вернул.

Проблема Сяомина: он на бесплатном тарифе базы с максимумом 20 соединений. Десятки людей одновременно, каждый триггерит несколько запросов — соединения мгновенно исчерпаны. Последующие запросы в очереди, ждут слишком долго — timeout с 500-ошибкой.

### Как диагностировать и решать

**Шаг 1: Подтвердите, что это пул соединений.** Проверьте, содержат ли ошибки ключевые слова: `too many connections`, `connection pool exhausted`, `timeout waiting for connection`.

**Шаг 2: Проверьте конфигурацию пула.** Free tier баз обычно лимитирует 20–50 соединений. Сколько реально нужно вашему приложению? Обычно `ядра CPU × 2 + 1` — для большинства облачных серверов 5–10 соединений держат сотни конкурентных запросов (каждый занимает соединение очень коротко).

**Шаг 3: Проверьте утечки соединений.** Если в коде есть «взял соединение и не вернул» (например, ошибка запроса, но соединение не освобождено) — пул медленно истощается. Как кто-то уехал на шеринг-велосипеде и не вернул — велосипедов всё меньше.

Скажите AI:

> «Мой API репортит "too many connections" при конкурентном доступе. Проверь: 1) Разумна ли конфигурация пула соединений? 2) Есть ли утечки соединений (не освобождено после ошибки запроса)? 3) Используется ли адрес пула, а не прямое подключение?»

::: tip Claude Code с загруженными Skills обрабатывает автоматически
Если вы загрузили Skill `supabase-postgres-best-practices`, Claude Code автоматически сконфигурирует разумные параметры пула, добавит настройки timeout и обеспечит корректное освобождение соединений при генерации кода базы. Но понимание концепции всё равно полезно: при проблемах знаете, в какую сторону копать.
:::

## Шаблоны промптов для troubleshooting

При проблемах после запуска самый эффективный метод — бросить AI **полный контекст**. Расплывчатые описания дают расплывчатые ответы.

**При ошибках API:**
> «Мой `POST /api/movies` выдал ошибку: [вставьте полное сообщение ошибки со stack trace]. Тело запроса: [вставьте содержимое]. Помоги локализовать проблему и починить».

**При аномальных данных:**
> «В таблице movies базы есть записи с пустыми названиями (ID: 42, 43, 47). Названия не должны быть пустыми. Помоги найти, какой API не сделал валидацию, затем: 1) Добавь Zod-валидацию в этот API; 2) Почисти эти три грязные записи».

**При проблемах производительности:**
> «Мой API списка фильмов сильно замедлился после роста данных до 5000 записей: время ответа с 50 мс до 3 секунд. Помоги проанализировать причину — нехватка индексов, N+1-запросы или другое? Проверь через EXPLAIN ANALYZE».

**При intermittent-проблемах:**
> «Мой API в основном нормален, но изредка отдаёт 500 каждый день между 20:00 и 22:00. Сообщение: [вставьте]. Это пиковое время доступа юзеров. Помоги проверить, не пул ли соединений исчерпан».

Ключ — **давайте конкретные данные**. Не «API медленный», а «время ответа с 50 мс до 3 секунд». Не «иногда ошибки», а «каждый день 20:00–22:00, сообщение такое-то». С конкретикой AI даёт адресные решения; без — только кучу догадок «может это, может то».

---

::: tip Ключевые выводы

- **Backend-валидация — нижняя линия**: frontend-валидация не блокирует запросы в обход frontend, backend обязан валидировать снова
- **Идемпотентность предотвращает дубликаты**: unique constraint базы — простейший подход, idempotency key — самый универсальный
- **Статус-коды различают типы ошибок**: серия 400 — проблема вызывающего, серия 500 — проблема сервера
- **Кэш требует активного управления**: после write-операций обязателен сброс кэша, иначе юзеры видят устаревшие данные
- **Неключевые операции не блокируют ответ**: отправка уведомлений, логирование — после ответа
- **Пул соединений предотвращает падения**: десятки конкурентных запросов исчерпывают лимиты free tier — убедитесь, что используете пул
:::
