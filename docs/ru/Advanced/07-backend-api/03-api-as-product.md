# 7.3 Делаем API лучше

> **Цель раздела**: по мере роста вашего API и появления большего числа потребителей — узнать, как эволюционировать его от «функционального» до «отличного»: с документацией, управлением версиями, батч-операциями, загрузкой файлов и real-time.

---

## Новые головные боли Сяомина

«Личный Douban» Сяомина месяц работает гладко. Валидация ввода на месте, обработка ошибок унифицирована, пул соединений настроен. Он добавляет новые фичи — избранное, ссылки шеринга, комментарии юзеров.

Каждая новая фича — больше эндпоинтов. Избранное: добавить, убрать, получить список. Комментарии: опубликовать, удалить, получить список, лайкнуть. Шеринг: сгенерировать ссылку, получить статистику.

Сяомин посчитал — уже больше тридцати эндпоинтов.

И тут три головные боли.

## Все эндпоинты даже не запомнить

Каждый раз при написании frontend-кода Сяомину приходится открывать папку backend и копаться в файлах `route.ts`, чтобы вспомнить: «как называется этот эндпоинт, какие параметры нужны, какой формат возвращает?» Иногда он помнит неправильно — пишет `movieId` вместо `movie_id` — и полчаса дебажит, пока не понимает, что это опечатка.

Ещё неловче: его друг Лао Ван хочет построить на его кино-данных мини-программу «Итоги года». Лао Ван спрашивает: «Где твоя API-документация? Нужно знать, какие эндпоинты есть и как их вызывать».

Сяомин замер — документации не было. Пришлось открыть WeChat и перечислять Лао Вану по одному: «Список фильмов — GET /api/movies, поддерживает page, limit, tag, sort...» После двадцати с лишним сообщений Лао Ван сказал: «Не можешь просто дать ссылку на документацию?»

### Пусть AI генерирует API-документацию

Документацию не нужно писать руками. У индустрии есть стандартный формат — **OpenAPI** (раньше Swagger), специально созданный для описания API-эндпоинтов: URL каждого эндпоинта, HTTP-метод, параметры запроса, формат ответа, коды ошибок — всё в структурированном виде.

Сгенерировав OpenAPI-документацию, вы можете отрендерить её через **Swagger UI** в интерактивную web-страницу. Эта страница не только для чтения: можно заполнить параметры и кликнуть «Отправить» прямо на ней — протестировать каждый эндпоинт в real time. Как встроенный Postman.

Это полезно и вам: больше не нужно копаться в коде для деталей эндпоинтов — открыли страницу доков и видите всё разом.

Скажите AI:

> «Помоги мне сгенерировать документацию OpenAPI 3.0 на основе всех существующих API Routes. Затем добавь страницу `/api-docs` со Swagger UI для отображения, с возможностью тестировать эндпоинты прямо на странице в dev-окружении».

::: tip Держите доки и код в синкронизации
Худшее — написать документацию, потом поменять API и забыть обновить доки. Решение — автогенерация доков из кода: меняется код эндпоинта — доки обновляются сами. Скажите AI «используй next-swagger-doc или похожие инструменты для автогенерации OpenAPI-доков из файлов route.ts» — и он настроит автоматизацию.
:::

## Поменял одно имя поля — сломалось несколько страниц frontend

Сяомину показалось, что поле `score` в ответе API фильма недостаточно выразительно, и он хотел переименовать в `rating`. Он поручил AI заменить все `score` на `rating` в backend, запустил — главная сломалась, страница поиска сломалась, страница избранного сломалась. Код frontend всех трёх страниц использовал `movie.score`, и backend внезапно сменил его на `rating` — frontend не находил поле и падал.

Это классическая проблема **обратной совместимости**. Изменили API — старые потребители ломаются.

**Правило: добавлять поля безопасно, удалять и переименовывать — нет.**

| Изменение | Безопасно? | Почему |
|---------|--------|--------|
| Добавить новое поле | ✅ Безопасно | Старый код читает знакомые поля, новые просто игнорирует |
| Удалить старое поле | ❌ Ломает | Код, читающий это поле, падает |
| Переименовать поле | ❌ Ломает | Эквивалентно удалению старого + добавлению нового |
| Сменить тип поля | ❌ Ломает | Код, ожидающий строку, ломается на числе |
| Сменить URL-путь | ❌ Ломает | Все старые ссылки 404 |

Так что делать, когда изменение действительно нужно? Используйте **переходные периоды и версионирование**.

### Стратегия 1: Переходный период

Не удаляйте поле сразу. Вместо этого:

1. Добавьте новое поле `rating`, **одновременно** сохранив старое `score` (значения те же)
2. Дождитесь, пока все потребители перейдут на новое поле (если потребители — ваш frontend, обновите его в том же PR)
3. Через месяц или два удалите старое поле

### Стратегия 2: Версионирование

Если меняете слишком много, создайте новую версию API:

- `GET /api/v1/movies` — старая версия, поддерживается
- `GET /api/v2/movies` — новая версия, новые правила

Старые потребители используют v1 (без изменений, ничего не ломается), новые — v2. Когда все мигрируют, v1 можно плавно депрекейтить.

Скажите AI:

> «Я хочу переименовать score в rating в API фильмов. Не меняй всё разом. План: 1) В ответ API добавь поле rating с тем же значением, что score; 2) Оставь score для совместимости; 3) Помоги мне найти все места во frontend, использующие score, и обнови их на rating».

## Лао Ван хочет батч-операции

Лао Ван строит на данных Сяомина мини-программу «Итоги года» и обнаруживает проблему: для рендера годового отчёта нужны данные 50 фильмов. Он вызывает `GET /api/movies/1`... `GET /api/movies/50` по одному — 50 HTTP-запросов.

50 запросов — 50 сетевых round trip'ов. Даже на 100 мс каждый — 5 секунд ожидания. И на каждый запрос нужна проверка валидности и логи — накладные расходы удваиваются.

Он просит Сяомина: «Не можешь дать API, который вернёт несколько фильмов разом?»

### Как спроектировать батч-API?

Самый частый паттерн — **передача нескольких ID**:

- `GET /api/movies?ids=1,2,3,4,5` — query-параметр с разделёнными запятыми ID
- `POST /api/movies/batch` — body с массивом ID (для больших количеств query может не хватить длины URL)

Скажите AI:

> «Добавь батч-интерфейс для запроса фильмов: `POST /api/movies/batch`, принимающий массив ID в body, возвращающий несколько фильмов одним запросом. Максимум 100 ID за раз; при превышении — 400. Используй один SQL-запрос IN для базы — не циклом по одному».

::: warning Батч-операции имеют пределы
Не позволяйте батчам быть бесконечными. Если один запрос может передать 10 000 ID — любой может случайно или намеренно перегрузить ваш API и базу. Установите разумный лимит (100–500) и возвращайте 400 при превышении.
:::

### Батч-запись важнее батч-чтения

Выше — батч-чтение. Батч-запись чаще нужна в реальной работе. Например, Сяомин захотел за раз импортировать 200 фильмов из Excel.

Самый интуитивный подход — фронтовый цикл по одному POST на фильм. Очевидные проблемы:

1. 200 запросов — 200 round trip'ов — очень медленно
2. Если пункт 137-й провалился — первые 136 уже в базе, данные наполовину
3. Каждая вставка — отдельная транзакция — производительность ужасна

Правильный подход — **батч-API + транзакция**:

```
POST /api/movies/batch
{
  "movies": [ ...200 объектов фильмов... ]
}
```

Backend оборачивает все 200 вставок в **одну транзакцию**: либо все 200 успешно — commit, либо любой провал — откат всех, ничего наполовину. И одна транзакция с 200 вставками куда быстрее, чем 200 одиночных транзакций.

Скажите AI:

> «Добавь API пакетного импорта фильмов: `POST /api/movies/batch`, принимающий массив объектов фильмов (максимум 500). Используй Drizzle's db.insert + транзакцию для обеспечения "либо все, либо ничего". Один провалившийся элемент откатывает всё и возвращает список ошибок с индексами».

## Загрузка файлов: афиши фильмов

У Сяомина новая фича: юзеры загружают афиши фильмов. Текущий API принимает только текст — как обработать файлы?

Загрузка файлов — распространённое требование, и у неё свои особенности.

### Куда загружать?

**Вариант А: Локальное файловое хранилище (dev)**. Сохранить файл в папку проекта. Просто и прямо — но файлы исчезают при переразвёртывании (у большинства облачных платформ ephemeral-файловая система — новое развёртывание = чистый сервер). Годится только для разработки.

**Вариант Б: Облачное хранилище (production)**. Хранить файлы в выделенном облачном сервисе (вроде Supabase Storage, AWS S3, Cloudflare R2), в базе — только URL. Это стандарт для production: файлы персистентны, доступ через CDN, оплачивается только хранилище.

Скажите AI:

> «Добавь функцию загрузки афиш фильмов: юзер выбирает файл, frontend загружает его в Supabase Storage, получает URL, затем отправляет URL в API создания фильма. Лимит размера файла 5 МБ; разрешённые типы jpg, png, webp».

### Частые ловушки загрузки файлов

| Ловушка | Решение |
|------|------|
| Загружен слишком большой файл | Проверить размер на frontend и backend, отклонить с понятным сообщением |
| Загружен неверный тип файла | Разрешённые типы через белый список, не чёрный |
| Имя файла содержит спецсимволы | Использовать серверную генерацию имени (uuid + расширение), не оригинальное имя |
| Доступ к чужим файлам | Генерировать подписанные URL с временем жизни — публичные ссылки на приватные файлы не раздаются |

## Реальное время: очередь на обновление

У Сяомина последняя фича: юзеры, открывшие страницу фильма, видят обновление рейтинга в реальном времени — без рефреша.

Обычный HTTP — «запрос-ответ»: юзер спрашивает, сервер отвечает, разговор окончен. Для real-time нужны другие техники.

| Техника | Принцип | Когда использовать |
|------|------|---------|
| **Polling** | Frontend опрашивает сервер каждые N секунд | Простые сценарии, обновления не критичны по времени |
| **SSE** (Server-Sent Events) | Сервер держит соединение и пушит события | Односторонний пуш: нотификации, обновления статуса |
| **WebSocket** | Двунаправленный persistent-канал | Чаты, многопользовательская коллаборация, игры |

Для рейтинга фильмов достаточно SSE — рейтингом обновляется сервер, юзерам нужно только получать пуш, ничего не отправлять.

Скажите AI:

> «Добавь real-time обновление рейтинга фильма через SSE (Server-Sent Events). Когда рейтинг меняется, подключённые клиенты получают push-событие с новым значением. Не используй WebSocket — достаточно однонаправленного пуша».

::: tip Не переусложняйте
Если бы Сяомин хотел лишь «рейтинг обновляется при возврате на страницу» — polling раз в 30 секунд или даже рефетч по фокусу окна полностью достаточны, SSE излишен. Выбирайте технику по реальной потребности: **сначала заставьте работать, потом заставьте работать хорошо**.
:::

## Шаблоны промптов для общения с AI

Комбинируя изученное в этом разделе:

**При генерации документации:**
> «Сгенерируй OpenAPI 3.0 для всех API в этом проекте и создай интерактивную страницу документации со Swagger UI на /api-docs».

**При добавлении батч-операций:**
> «Добавь батч-интерфейс для API фильмов: `POST /api/movies/batch`, максимум 500 записей, одна транзакция "либо все, либо ничего", список ошибок с индексами».

**При загрузке файлов:**
> «Реализуй загрузку афиш через Supabase Storage: лимит 5 МБ, белый список jpg/png/webp, серверно-сгенерированные имена файлов, публичные URL после загрузки».

**При проектировании real-time:**
> «Фича real-time рейтинга: SSE-пуш при изменении, автоматический reconnect при обрыве соединения».

**При изменении API без ломки потребителей:**
> «Я хочу переименовать score в rating: добавь rating, сохранив score для совместимости, обнови frontend в том же PR, удали score через месяц».

::: tip Ключевые выводы раздела

- **Документация API**: автогенерация через OpenAPI/Swagger — удобно вам, референс другим
- **Обратная совместимость**: добавлять поля можно, удалять — с переходным периодом; большие изменения — через версии
- **Батч-операции**: цикл вызовов эндпоинтов → батч-эндпоинт, транзакции для консистентности
- **Загрузка файлов**: локальное хранилище для dev, облачное для продакшена; не забывайте лимиты размеров и типов
- **Real-time**: polling простейший, SSE хорош для одностороннего пуша, WebSocket — для двустороннего общения
:::
