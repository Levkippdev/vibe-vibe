# Глава 7: Backend API разработка

![img](/images/Advanced/mll04abe-1f408b85793aaf81.jpg)

## Введение

UI есть, база готова. Когда вы кликаете кнопку «Отправить», данные должны сохраниться в базу — но между frontend и базой всё ещё не хватает моста.

Этот мост — **API (Application Programming Interface)**. Frontend через HTTP-запросы говорит backend, что хочет юзер, а backend обрабатывает запрос и возвращает ответ.

---

### Что такое backend

Вы пробовали подключиться к базе прямо из frontend, но ветеран-разработчик остановил вас: «Frontend-код работает в браузере юзера. Если frontend подключается к базе напрямую, юзеры могут открыть F12, увидеть ваш пароль базы и даже удалять чужие данные». Тогда вы осознали: между frontend и базой обязан быть «посредник», принуждающий контроль доступа.

**Backend** — код, работающий на сервере и отвечающий за обработку запросов frontend, взаимодействие с базой и исполнение бизнес-логики.

| Слой | Ответственность |
|----|------|
| **Frontend** | Отобразить UI, собрать ввод юзера, отправить HTTP-запросы |
| **API** | Принять запросы, валидировать параметры, запросить базу, вернуть ответы |
| **База** | Хранить и выдавать данные |

Frontend не должен обращаться к базе напрямую — это exposes все данные и делает контроль прав невозможным. API — привратник базы, все операции с данными обязаны идти через него.

---

### Что такое API Route

Теперь вы понимаете, зачем нужен backend — но как именно его писать? Нужно ли самому поднимать Express-сервер? Ветеран говорит: нет — у Next.js встроенная поддержка API Route. Создали файл — получили эндпоинт, без поднятия отдельного сервера.

Но прежде чем говорить об API Route, разберём более фундаментальную концепцию: **роутинг (Route)**.

#### Роутинг: URL определяет, что вы видите

Вы имеете дело с роутингом каждый день — просто, возможно, не осознаёте. Откройте браузер и посмотрите на адресную строку:

- Зашли на `movie.douban.com/` → видите главную Douban Movies
- Зашли на `movie.douban.com/subject/37311135/` → видите страницу деталей *Pegasus 3*
- Зашли на `movie.douban.com/subject/37311135/comments?status=P` → видите короткие ревью этого фильма (`?status=P` значит «ревью от посмотревших»)
- Зашли на `movie.douban.com/chart` → видите страницу рейтингов

Разные URL — разные страницы. **В этом и есть роутинг: путь URL определяет, какой контент отображается.** Часть после `?` — query string, используется для дальнейшей фильтрации или контроля отображения.

В Next.js это соответствие отражено прямо в файловой структуре:

```
app/
├── page.tsx                    → yourdomain.com/
├── subject/
│   └── [id]/
│       ├── page.tsx            → yourdomain.com/subject/37311135
│       └── comments/
│           └── page.tsx        → yourdomain.com/subject/37311135/comments
└── chart/
    └── page.tsx                → yourdomain.com/chart
```

Структура папок — это структура URL. Создали файл — получили ещё одну страницу. `[id]` — динамический сегмент: `37311135` или любой другой ID фильма обрабатывается тем же `page.tsx`. Это **файл-системный роутинг** Next.js: не нужно писать конфиги «какой URL соответствует какой странице». Где файл — там и URL.

#### От страничных роутов к API-роутам

Роуты выше — для страниц, которые смотрят юзеры. **API Route** следует той же идее, только вместо страницы возвращает данные.

Создайте файл `route.ts` в каталоге `app/api/` — получите дата-эндпоинт:

- `app/api/movies/route.ts` → `yourdomain.com/api/movies` (возвращает JSON-данные списка фильмов)
- `app/api/movies/[id]/route.ts` → `yourdomain.com/api/movies/123` (возвращает JSON-данные конкретного фильма)

Разница одна: `page.tsx` возвращает страницу для юзеров, а `route.ts` — данные для программ.

#### Экспорт handler-функций

В файле `route.ts` вы экспортируете функции, соответствующие HTTP-методам. Например, экспорт функции `GET` обрабатывает GET-запросы, экспорт `POST` — POST-запросы.

Next.js автоматически вызывает подходящую функцию по методу запроса. Если экспортированы и `GET`, и `POST` — один URL поддерживает и получение, и создание.

::: tip Версии меняются быстро — пусть AI проверит доки

Next.js быстро релизит обновления, API могут меняться. Просите AI использовать Context7 для поиска свежей документации, чтобы сгенерированный код соответствовал текущей версии.

:::

### Перед разговором с AI о backend — несколько ключевых слов

Перед 7.0 — термины, которые будут встречаться постоянно. Не нужно заучивать — просто познакомьтесь. Каждый встретится в конкретных сценариях позже.

**RESTful** — конвенция именования API. Ключевая идея: URL представляют ресурсы, HTTP-методы — действия. Фактически вы уже каждый день отправляете HTTP-запросы: вводите URL в браузер и жмёте Enter — это GET-запрос; заполняете форму регистрации и кликаете «отправить» — это POST-запрос. RESTful просто систематизирует: `GET /api/movies` получает список фильмов, `POST /api/movies` создаёт новый фильм, `DELETE /api/movies/123` удаляет фильм с id=123. По пути видно, что он делает. Скажите AI «используй RESTful-стиль» — он автоматически будет следовать конвенции.

<FullStackFlow mode="rest" />

**Три источника параметров** — первые два вы уже видели в адресной строке браузера:

- **Path parameters**: в `movie.douban.com/subject/37311135` — `37311135` идентифицирует «какой фильм я хочу посмотреть»
- **Query parameters**: в `movie.douban.com/subject/37311135/comments?status=P` часть после `?` говорит backend «показывай только ревью посмотревших»
- **Request Body**: в адресной строке не видно — когда вы заполняете форму и кликаете «Отправить», данные формы (название, год, синопсис) пакуются в JSON и уходят в backend в теле запроса

Path parameters идентифицируют «какой ресурс», query parameters контролируют «как запрашивать», Body несёт «данные для создания или изменения».

<FullStackFlow mode="params" />

**Консистентный формат ответа** — в начале проекта договоритесь с AI о стандарте: успех — `{ success: true, data: ... }`, провал — `{ success: false, error: { message: "..." } }`. Это делает обработку frontend простой и единообразной: сначала проверяете `success`; если true — используете `data`; если false — показываете сообщение об ошибке.

::: tip REST — не единственный стиль API

Всё в этой главе использует RESTful API: URL представляют ресурсы, HTTP-методы — действия. Это самый частый подход, и обычно с ним вы столкнётесь первым.

Но в AI-сгенерированном коде может не быть файла `route.ts` или URL вроде `GET /api/movies`. Вместо этого — вызовы функций вроде `trpc.movie.list()`. Это значит, AI использовал **tRPC** — подход, позволяющий frontend вызывать backend-эндпоинты как локальные функции. Выгода: типы автоматически синхронизированы между frontend и backend — при смене сигнатуры интерфейса backend сразу получаете type error на frontend, без проблем вида «backend переименовал поле, frontend не узнал».

Не нужно указывать, какой подход использовать. Скажете AI «используй RESTful-стиль» — будет REST. Не укажете — AI выберет по контексту проекта, так что не удивляйтесь, увидев в коде tRPC. Он решает ту же проблему, что и REST, просто другим стилем: налаживает общение frontend и backend.
:::

### Ваша работа

Вам не нужно писать каждый эндпоинт руками. Достаточно сказать AI, что вы хотите, — и он сгенерирует полный код. Ваша работа — **верифицировать результат**:

1. **Работает?** — Запустите `pnpm dev` и убедитесь, что страница работает ожидаемо
2. **База корректна?** — Откройте Drizzle Studio и проверьте, правильно ли записались данные
3. **Есть ошибки?** — Скопируйте весь вывод ошибок терминала в AI и пусть исправит

Не нужно понимать каждую строку кода. Достаточно знать, за что отвечает каждый файл, — и при сбое уметь сказать AI, «какой файл менять».
