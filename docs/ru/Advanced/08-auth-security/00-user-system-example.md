# 8.0 Быстрый пример юзер-системы

> **Цель раздела**: понять, как работает полная система аутентификации юзеров — регистрация, логин, логаут и защищённые страницы.

В главе 7 вы изучили CRUD. Теперь перед вами новая проблема: любой может дёргать ваш API, и любой может удалять данные. Вам нужна **юзер-система**, чтобы различать «кто есть кто» и контролировать «кому что можно».

## Authentication vs Authorization

Вы можете сказать: «Просто добавим логин — и готово», но ветеран качает головой: «Логин — только первый шаг. После логина — обычные юзеры и админы могут делать одно и то же?» Тогда вы осознаёте: «доказать, кто ты» и «что тебе разрешено» — две разные проблемы.

Перед стартом ветеран хочет, чтобы вы чётко различали эти две концепции:

- **Authentication**: Кто ты? — верификация личности (логин)
- **Authorization**: Что ты можешь? — проверка прав (админ vs обычный юзер)

В этом разделе сначала решим authentication.

## Почему Better Auth

Auth-библиотек столько — NextAuth, Clerk, Auth0, Supabase Auth, Better Auth... — легко растеряться. Ветеран говорит: «Выбирая auth-библиотеку, смотри три вещи: кому принадлежат данные, насколько кастомизируема и активно ли сообщество».

Этот туториал использует **Better Auth** как решение для аутентификации. Вот почему ветеран выбрал его:

| Фича | Better Auth | NextAuth | Clerk |
|------|------------|----------|-------|
| Open source и бесплатно | ✅ | ✅ | ❌ (есть free tier) |
| Владение данными | ✅ Хранится в вашей базе | ⚠️ Требуется adapter | ❌ Хранится у третьей стороны |
| TypeScript-native | ✅ | ⚠️ Средняя поддержка типов | ✅ |
| Поддержка Drizzle | ✅ Нативная | ⚠️ Требуется adapter | ❌ |
| Кривая обучения | Средняя | Средняя | Низкая |

Ключевая причина: **ваши данные живут в вашей собственной базе**. Таблицы юзеров и сессий хранятся в вашем PostgreSQL-инстансе, без зависимости от сторонних сервисов и platform lock-in.

## Поручите AI настроить юзер-систему

Просто скажите AI:

> «Интегрируй Better Auth в мой Next.js проект с Drizzle ORM и PostgreSQL. Мне нужно: регистрация и логин по email/паролю, функция логаута и защищённая страница /dashboard (незалогиненных юзеров редиректить на /login)».

AI поможет сгенерировать такую структуру:

```
src/
├── lib/
│   ├── auth.ts            # Серверная конфигурация Better Auth
│   └── auth-client.ts     # Клиентская конфигурация Better Auth
├── app/
│   ├── api/auth/[...all]/
│   │   └── route.ts       # Auth API-роут (автоматически обрабатывает логин/регистрацию/логаут)
│   ├── login/
│   │   └── page.tsx        # Страница логина
│   ├── register/
│   │   └── page.tsx        # Страница регистрации
│   └── dashboard/
│       └── page.tsx        # Защищённая страница
```

## Понимание флоу аутентификации

### Флоу регистрации

Вы можете спросить: разве регистрация — не просто сохранение email и пароля в базу? Не совсем. Если хранить пароли в plain text, то при компрометации базы пароль каждого юзера раскрыт. Поэтому пароль сначала «шифруется» (точнее — хэшируется), и только потом сохраняется: даже если хакер получит базу, всё, что он увидит, — нечитаемая абракадабра.

После успешной регистрации сервер создаёт «сессию» — можно думать о ней как о временном пропуске. Когда вы логинитесь на Taobao, закрываете страницу и открываете снова позже, вы всё ещё залогинены — потому что браузер сохранил тот пропуск (Cookie) и автоматически предъявляет его серверу с каждым запросом.

```
Юзер вводит email + пароль → frontend вызывает auth.signUp() → Better Auth обрабатывает:
  1. Проверяет, существует ли уже email
  2. Хэширует пароль (bcrypt hash)
  3. Вставляет нового юзера в таблицу юзеров
  4. Создаёт сессию
  5. Возвращает session token → браузер сохраняет в Cookie
```

### Флоу логина

При логине сервер напрямую не сравнивает введённый пароль с паролем в базе — в базе хранится хэш. Он хэширует и введённый вами пароль, затем проверяет совпадение двух хэшей. Так даже подглядевший за сравнением процесс не получит настоящий пароль.

```
Юзер вводит email + пароль → frontend вызывает auth.signIn() → Better Auth обрабатывает:
  1. Ищет юзера по email
  2. Сравнивает хэши паролей
  3. Создаёт новую сессию
  4. Возвращает session token → браузер сохраняет в Cookie
```

### Защищённые роуты

Вы можете захотеть защитить страницу на frontend через `if (!loggedIn) redirect('/login')`. Но ветеран говорит: этого мало — юзеры могут отключить JavaScript в браузере или запросить вашу страницу напрямую через curl. По-настоящему безопасный подход — проверять на сервере: контент страницы вообще не должен отправляться незалогиненным юзерам.

```
Юзер visits /dashboard → сервер проверяет session token в Cookie:
  ✅ Валиден → нормально отображаем страницу
  ❌ Невалиден/истёк → редирект на /login
```

## Что сгенерировал AI

AI сгенерировал кучу файлов, но при открытии они полны незнакомых имён функций. Без паники — не нужно понимать синтаксис всего этого кода. Достаточно знать: `auth.ts` — серверная конфигурация, `auth-client.ts` — для вызовов из frontend, `dashboard/page.tsx` — защищённая страница. При сбое достаточно сказать AI: «У меня проблема с конфигурацией auth.ts».

### Серверная конфигурация (`auth.ts`)

Этот файл говорит Better Auth, какую базу использовать и какие методы логина включить.

<details>
<summary>Любопытно? Развернуть; смело пропускайте</summary>

```typescript
// src/lib/auth.ts
import { betterAuth } from 'better-auth'
import { drizzleAdapter } from 'better-auth/adapters/drizzle'
import { db } from '@/db'

export const auth = betterAuth({
  database: drizzleAdapter(db, { provider: 'pg' }),
  emailAndPassword: { enabled: true },
})
```

</details>

### Клиентские вызовы (`auth-client.ts`)

Этот файл позволяет страницам frontend получать текущее состояние логина — например, проверять, залогинен ли юзер, или отображать имя юзера.

<details>
<summary>Любопытно? Развернуть; смело пропускайте</summary>

```typescript
// src/lib/auth-client.ts
import { createAuthClient } from 'better-auth/react'

export const authClient = createAuthClient()

// Использование в компоненте:
const { data: session } = authClient.useSession()
```

</details>

### Защищённая страница (`dashboard/page.tsx`)

Этот файл проверяет на сервере, залогинен ли юзер: если нет — редирект на страницу логина, и контент страницы никогда не отправляется незалогиненным юзерам.

<details>
<summary>Любопытно? Развернуть; смело пропускайте</summary>

```typescript
// src/app/dashboard/page.tsx
import { auth } from '@/lib/auth'
import { headers } from 'next/headers'
import { redirect } from 'next/navigation'

export default async function Dashboard() {
  const session = await auth.api.getSession({
    headers: await headers(),
  })
  if (!session) redirect('/login')

  return <h1>С возвращением, {session.user.name}</h1>
}
```

</details>

## Частые вопросы

**Q: При регистрации ошибка «table does not exist»?**

Запустите `pnpm drizzle-kit push` для синхронизации схемы таблиц.

**Q: После логина Dashboard всё равно редиректит на логин?**

Проверьте, корректно ли ставится Cookie. В разработке убедитесь, что используете `http://localhost:3000`, а не `127.0.0.1`.

**Q: Хотите добавить сторонний логин GitHub/Google?**

Скажите AI: «Добавь GitHub OAuth логин в конфигурацию Better Auth». Сначала нужно создать OAuth App на GitHub, чтобы получить Client ID и Secret.

## Чему учит этот пример

Только что завершённая вами юзер-система включает ключевые строительные блоки аутентификации:

- **Безопасность паролей**: хранить хэши, не plain text
- **Управление сессиями**: состояние логина через Cookie + Session
- **Защита роутов**: проверки на сервере, чтобы незалогиненные не получали защищённый контент
- **Владение данными**: все данные юзеров живут в вашей собственной базе

Последующие разделы построятся на этом фундаменте и раскроют больше security-практик: управление переменными окружения, конфигурация CORS, Middleware и другое.
