# 8.1 Управление секретами и переменные окружения

> **Цель раздела**: научиться управлять секретами через переменные окружения, понять security-границу между Server и Client и гарантировать, что чувствительная информация никогда не появляется в вашем коде или истории Git.

---

## Урок Сяомина

В предисловии Сяомин запушил API-ключ на GitHub — и за 5 минут его сожгли на $127. Но история началась раньше.

Когда Сяомин впервые писал код, подключение к базе выглядело так:

```typescript
const db = drizzle('postgresql://ming:mypassword123@db.example.com:5432/moviedb')
```

А AI-ключ — так:

```typescript
const openai = new OpenAI({ apiKey: 'sk-proj-abc123...' })
```

Ему казалось это удобным — написал прямо в коде, не нужно искать в другом месте. Локально всё работало, ничего не случилось. Только запушив код на GitHub и лишившись ключа, он наконец понял: **код создан для того, чтобы делиться, секреты — нет**. Писать секреты прямо в коде — как писать PIN банковской карты на её обратной стороне: любой, увидевший карту, узнает PIN.

Речь о «секретах» включает многое: строки подключения к базе (`DATABASE_URL`) прячут имя юзера и пароль базы, сторонние API-ключи (`OPENAI_API_KEY`) — ваши креды для вызова AI-сервисов, OAuth-секреты (`GITHUB_CLIENT_SECRET`) — доверительные креды между вами и GitHub, платёжные ключи (`STRIPE_SECRET_KEY`) напрямую привязаны к вашему принимающему аккаунту, auth-секреты (`BETTER_AUTH_SECRET`) подписывают сессии юзеров. Общее у них одно: при утечке лучший случай — кто-то сожжёт вашу квоту; худший — все данные юзеров окажутся наружу. И секреты часто связаны между собой: утёк пароль базы — раскрыта таблица юзеров; раскрыта таблица юзеров — пропали все email и хэши паролей.

Решение — **переменные окружения**: вытащить секреты из кода в файл, который не коммитится. В коде вы говорите лишь «прочитай секрет отсюда», не записывая сам секрет.

## От хардкода к .env

Первое, чему ветеран-разработчик научил Сяомина: создайте в корне проекта файл `.env` и сложите все секреты в одно место:

```
DATABASE_URL=postgresql://user:password@host:5432/mydb
OPENAI_API_KEY=sk-proj-xxxxx
BETTER_AUTH_SECRET=your-random-secret-here
```

Затем вместо хардкода секретов читайте их через `process.env.DATABASE_URL` — как мобильное приложение не хардкодит яркость экрана, а читает текущее значение из «настроек системы». `process.env` — это «настройки системы» Node.js: автоматически читает все пары ключ-значение из `.env`. Это чисто разделяет секреты и код: код спокойно уезжает на GitHub, секреты остаются в локальном `.env`. Как перенести ключ от квартиры из-под коврика (записан в коде) в сейф (хранится в `.env`). Под ковриком может заглянуть кто угодно; сейф хотя бы требует пароль.

Но одного `.env` мало. Сяомин создал файл, перенёс все секреты — и решил, что проблема решена. Потом по привычке запустил `git add .` — а эта команда добавляет в staging **все файлы** текущего каталога, включая `.env`. Он не заметил и сразу `git commit` и `git push`. Секреты снова уехали наверх. Его реакция: «Я же вытащил секреты из кода — как они опять утекли?»

Ветеран указал на файл **`.gitignore`** в корне проекта и сказал: «Это последняя линия обороны, спасающая тебя от разорения». `.gitignore` — **игнор-лист** Git: всё, что в нём перечислено, автоматически пропускается при сканировании изменений, и `git add .` его не включит. Можете думать о нём как о чёрном списке: файл в списке — Git делает вид, что его не существует. Проверьте, есть ли в вашем `.gitignore` следующее:

```gitignore
# Чувствительные конфиги
.env
.env.local
.env.production

# Зависимости (слишком крупные, тиммейты ставят локально)
node_modules/

# Вывод сборки (временные файлы компиляции)
.next/
dist/

# Системный мусор
.DS_Store
Thumbs.db
```

::: danger Если файл уже закоммичен, добавление в .gitignore не поможет
Если `.env` уже отслеживается Git'ом (был закоммичен раньше), простое добавление в `.gitignore` его не уберёт. Сначала выполните `git rm --cached .env`, чтобы убрать его из индекса, и закоммитьте снова. Важнее: секрет всё ещё виден в истории Git — скажите AI: «Я случайно закоммитил секрет в историю Git. Помоги мне вычистить его». После чистки **обязательно ротируйте секрет на соответствующей платформе**.
:::

## .env.example — шаблон для себя будущего

Через месяц Сяомин перешёл на новый компьютер. Он спулил код с GitHub, запустил `pnpm install`, потом `pnpm dev` — и получил кучу ошибок. `DATABASE_URL` undefined, `OPENAI_API_KEY` undefined... Тут он вспомнил: `.env` игнорируется — на новой машине этого файла просто нет. Ещё неловче: он уже не мог точно вспомнить, какие переменные окружения нужны проекту. Проект стартовал три месяца назад; за это время добавились AI-фичи, аутентификация и сторонний OAuth. Каждый раз, что-то добавляя, он пихал новую переменную в `.env`, но ни одну не задокументировал. Искать в коде `process.env.`? Слишком муторно — и всё равно что-то упустишь.

Ветеран сказал: «В проекте должен быть файл `.env.example`». Он перечисляет все имена переменных, но значения оставляет пустыми:

```
DATABASE_URL=
OPENAI_API_KEY=
BETTER_AUTH_SECRET=
NEXT_PUBLIC_APP_URL=
```

`.env.example` **должен коммититься в Git**. Это как бланк: любой, получивший проект, может скопировать его, переименовать в `.env`, вписать свои значения и запустить проект. Если `.env` — сейф с настоящими ключами, то `.env.example` — пустой слепок ключа, говорящий, сколько ключей нужно и какие они.

> Скажите AI: «Сгенерируй мне файл .env.example на основе всех переменных окружения, используемых в проекте».

## Server vs Client — самая лёгкая ловушка

Сяомин положил `API_KEY=sk-proj-xxx` в `.env`. В API Route (серверный код) `console.log(process.env.API_KEY)` прекрасно печатался. Но он захотел показать на странице frontend бейдж «AI-фича включена» и попытался прочитать ту же переменную в React-компоненте — получил `undefined`. Трижды проверил написание, заподозрил баг. Потом сделал `console.log(process.env)` и обнаружил: в переменных окружения, доступных frontend'у, `API_KEY` вообще нет.

Он бросил вопрос AI, и тот объяснил: это не баг — это **security-механизм** Next.js.

Представьте: ваш backend-код работает на вашем сервере — как банковское хранилище, куда входят только сотрудники. Но frontend-код в итоге скачивается и работает в браузере юзера — как банковский холл, где видят все. Повесите пароль хранилища на стену холла — хранилище можно считать отсутствующим.

Код **Server** работает на облачном сервере или в вашем локальном Node.js-процессе. Юзеры видят только результат, возвращённый сервером (HTML, JSON); напрямую получить серверный код или переменные они не могут. Поэтому читать секреты там безопасно: по умолчанию переменные из `.env` доступны только на стороне сервера. Код **Client** работает в браузере юзера. Ваши React-компоненты, CSS и JavaScript в итоге бандлятся и отправляются в браузер юзера. Юзер может нажать F12, открыть DevTools и увидеть весь код и данные, отправленные в браузер. Если секрет ушёл на клиент — это то же самое, что приклеить код сейфа на входную дверь: увидит любой.

Правило Next.js простое: только переменные с префиксом `NEXT_PUBLIC_` бандлятся и отправляются в браузер. Этот префикс — как бирка «сдаваемый багаж» на чемодане: нет бирки — авиалиния не погрузит его в самолёт; нет префикса — Next.js не отправит его в браузер. Например, у `DATABASE_URL` префикса нет — она доступна только на Server, что подходит паролям базы, API-секретам и другой чувствительной информации. А `NEXT_PUBLIC_APP_URL` префикс имеет — её читают и Server, и Client, что подходит публичной информации вроде URL сайта или ID аналитики. Этот префикс — фактически декларация: «я подтверждаю, это значение может быть публичным» — только увидев его, Next.js вклеит значение переменной во frontend-код. Правило большого пальца тоже простое: спросите себя — увидит ли юзер это значение в браузере через F12, и есть ли риск? Если да — не добавляйте `NEXT_PUBLIC_`, держите серверным.

## Поменяли конфиг — ничего не произошло? Сначала перезапустите

Сяомин поменял пароль базы в `.env` (старый утёк, он сбросил), обновил страницу — всё ещё «connection failed». Поменял снова — безрезультатно. Он уже стал думать, что сломан сам `.env`. Ветеран спокойно спросил: «А ты перезапускал?»

Сяомин, сдерживая слёзы, нажал `Ctrl+C`, остановил dev-сервер, снова запустил `pnpm dev` — и всё заработало.

Причина проста: **переменные окружения загружаются в память при старте программы**. Пока программа работает, она читает старые значения из памяти и автоматически не проверяет, изменился ли `.env`. Это как посмотреть прогноз погоды перед выходом: солнечно — а погода изменилась после выхода, вы не узнаете, пока не проверите снова. В эту ловушку попадал каждый хотя бы раз. 90% проблем с `.env` лечится перезапуском.

## От локалки к облаку

Приложение Сяомина наконец готово к деплою. Он запушил код на Vercel, кликнул кнопку deploy и с нетерпением ждал. И всё сломалось: база не подключалась, AI API падал, аутентификация не работала. Только тогда он заметил упущенное: локальная разработка использовала файл `.env`, но `.env` игнорируется `.gitignore` — на GitHub он не уезжал. Значит, и на сервере Vercel его нет. Код там запускается — `process.env.DATABASE_URL` равно `undefined`.

У каждой deploy-платформы (Vercel, Railway, Cloudflare и т.д.) есть отдельная страница настройки переменных окружения. Туда нужно вручную внести всё из локального `.env` — и имена, и значения, как снова заполнять онлайн-форму. Это как переложить деньги из сейфа дома (локальный `.env`) в банковское хранилище (облачный конфиг): место меняется, суть та же — секреты живут в защищённом месте, код читает их через `process.env`. Один нюанс: некоторые значения различаются между локалкой и продакшеном. Например, `DATABASE_URL` локально указывает на `localhost`, в продакшене — на адрес облачной базы; `BETTER_AUTH_URL` локально `http://localhost:3000`, в продакшене — ваш домен.

Тот же принцип — для MCP-серверов (Supabase MCP, GitHub MCP и т.п.). Их информация подключения тоже содержит чувствительные креды, поэтому её тоже нужно управлять через переменные окружения, а не хардкодить в конфиг-файлах.

> Скажите AI: «Проверь мой проект: все ли секреты управляются через переменные окружения. Сгенерируй файлы .gitignore и .env.example. Если какие-то секреты захардкожены в коде — помоги перевести на чтение из переменных окружения».

---

::: tip Ключевые выводы раздела

- Секреты — в `.env`, чтение в коде через `process.env.XXX`
- `.gitignore` игнорирует `.env`, чтобы он не коммитился в Git
- `.env.example` перечисляет имена переменных без значений — коммитится в Git как шаблон
- Переменные без префикса `NEXT_PUBLIC_` доступны только на сервере — это security-механизм, не баг
- После изменения `.env` перезапустите сервис
- При деплое настраивайте переменные на странице платформы, а не загружайте файл `.env`
:::
