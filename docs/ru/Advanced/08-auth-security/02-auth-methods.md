# 8.2 Методы аутентификации и выбор решения

> **Цель раздела**: понять, как работают мейнстрим-методы аутентификации и где каждый уместен, выбрать подходящую auth-библиотеку для проекта и поручить AI доделать настройку.

---

## После логина — как сервер меня помнит?

В 8.0 Сяомин запустил юзер-систему — регистрация, логин и защищённые страницы функционировали. Но у него вопрос: каждый раз, когда он открывает `/dashboard`, откуда сервер знает, что «запрос от Сяомина, а не кого-то другого»? Не вводить же пароль каждый раз заново?

Это **управление сессиями**: после одного логина юзера — как последующие запросы доказывают «я всё ещё я»? Каждый раз, открывая новую страницу, кликая кнопку или отправляя форму, браузер шлёт новый HTTP-запрос серверу. Сам протокол HTTP «stateless»: обработав запрос, сервер о нём забывает. При следующем он не знает, тот ли это человек. Нужен механизм, позволяющий серверу «помнить» вас через несколько запросов. В индустрии два мейнстрим-подхода.

**Первый — Session.** Представьте выдачу книги в библиотеке. Первый раз вам выдают читательский билет с номером. Компьютерная система библиотеки хранит ваше имя, историю выдач и другую инфу, связанную с этим номером. Дальше при каждом визите вы показываете билет — стойка смотрит номер и узнаёт вас. Session работает так: после успешного логина сервер создаёт запись сессии в базе (как запись в компьютере библиотеки), затем отправляет session ID в браузер через Cookie (как читательский билет). С тех пор браузер автоматически прикладывает Cookie к каждому запросу — ничего вручную, браузер сам всё делает. Как наклейка члена клуба при входе в ТЦ: её видит каждая лавка на каждом этаже — не надо каждый раз показывать карту. Сервер, получив запрос, ищет юзера по session ID из Cookie — и знает: «это Сяомин». Преимущество — полный контроль на сервере: хотите выкинуть юзера немедленно — просто удалите запись сессии из базы. Следующий запрос ничего не найдёт — юзер выкинут. Недостаток: каждый запрос требует обращения к базе. При деплое на несколько серверов им нужно разделять хранилище сессий (иначе юзер залогинился на сервере A, следующий запрос ушёл на сервер B — сессия не найдена).

**Второй — Token (обычно JWT).** Другой сценарий: вы приходите в парк аттракционов, и на входе вам ставят штамп на тыльную сторону ладони. Штамп невидимыми чернилами кодирует ваше имя и тип билета (обычный/VIP). Сотрудники на каждом аттракционе светят УФ-фонариком и читают инфу — без звонка на главный вход для проверки. Token похож: после успешного логина сервер подписывает и шифрует информацию юзера (имя, роль, время истечения и т.д.) в строку токена и отправляет в браузер. Дальше браузер прикладывает токен к каждому запросу. Сервер, получив его, проверяет подпись, убеждается в отсутствии подделки и читает инфо юзера прямо из токена — обращения к базе не нужно. Преимущество: серверное хранилище не требуется — мультисерверность поддерживается естественно (вся инфо внутри токена, любой сервер может проверить). Недостаток: выпущенный токен нельзя отозвать — до истечения он валиден, как штамп парка: раз поставлен — сразу не смывается, сотрудники не могут удалённо его аннулировать. Даже при желании немедленно разлогинить юзера — не выйдет (разве что держать «чёрный список», но это снова серверное хранилище).

Для большинства web-приложений выбор делать не нужно — **auth-библиотека сделает его за вас**. Better Auth по умолчанию использует Session поверх базы (давая и безопасность, и контроль), так что Cookies и Tokens вручную не нужны. Смысл понимания этих подходов: увидев в AI-коде термины `session`, `token`, `JWT` или `Cookie`, вы будете знать, что они значат, а не теряться.

## Не только пароли: современные методы аутентификации

Парольный логин — базовая опция, но не единственная. Друзья Сяомина, тестируя «Личный Douban», первой реакцией сказали: «Опять регистрироваться? Я уже сбился, сколько паролей у меня. Нельзя залогиниться аккаунтом GitHub?» Эта потребность ведёт к нескольким мейнстрим-методам современной аутентификации.

<ModernAuthMethods />


**OAuth 2.0** — технология за кнопками «Войти через Google/GitHub» по всему вебу. Клик — вас перебрасывает на страницу Google для подтверждения, затем автоматически возвращает на исходный сайт — уже залогиненным. Идея как заселение в отель: вам не нужно доказывать отелю, что ваш паспорт настоящий — вы показываете паспорт, а отель сверяет его с государственной системой. В OAuth Google/GitHub — та «паспортная система», ваш сайт — «отель». Юзер не отдаёт пароль вашему сайту: Google за него ручается — «этот человек действительно владеет xxx@gmail.com». Для юзера — не нужно запоминать новый пароль, логин в один клик. Для разработчика — не нужно хранить и шифровать пароли: security-бремя переносится на Google/GitHub. После добавления GitHub OAuth в «Личный Douban» конверсия регистрации заметно выросла — друзьям больше не надо вводить email, придумывать пароль и ждать письмо подтверждения. Один клик — и внутри.

> Скажите AI: «Добавь GitHub OAuth логин в мою конфигурацию Better Auth». Сначала создайте OAuth App на GitHub, получите Client ID и Secret, положите их в `.env`.

**Passkeys** — будущее безпарольной аутентификации. Разблокируя телефон, вы касаетесь пальцем или смотрите на экран. Passkeys переносят этот опыт на логин на сайтах: вместо пароля — отпечаток, лицо или аппаратный ключ. Почему будущее? Они искореняют все парольные проблемы в корне: нет пароля — нет утечек паролей, нет фишинга (Passkey привязан к конкретному домену сайта — фейковый `g00gle.com` не триггернёт Passkey для `google.com`), и юзеру ничего не нужно запоминать. Better Auth имеет встроенную поддержку Passkeys. Если ваши юзеры в основном на современных устройствах (большинство телефонов и компьютеров после 2022 поддерживают), стоит рассмотреть.

**Magic Link** — ещё одна безпарольная опция: вводите email, получаете письмо, кликаете ссылку — залогинены. Не нужно запоминать пароль, не нужно проходить регистрацию. Позже Сяомин делал внутренний инструмент для нескольких друзей и использовал Magic Link — они могут заходить раз в несколько недель, забыть пароль — святое дело. Ввели email, кликнули ссылку — внутри; весь процесс меньше 30 секунд. Отлично подходит для низкочастотных инструментов и утилит. Недостаток — зависимость от почты: письмо задержится или упадёт в спам — страдает UX.

Есть ещё **SSO (Single Sign-On для энтерпрайза)** — один аккаунт для доступа ко всем системам компании. Залогинились в корпоративную почту — открываете OA, CRM и таск-трекер без повторного логина. Это стандарт enterprise-сценариев; личным проектам обычно не нужно.

## Почему не стоит писать аутентификацию самому

В 8.0 Сяомин запустил юзер-систему Better Auth, но задался вопросом: почему бы не написать самому? Разве логин — не «запросить базу и сравнить пароль»? Он попробовал реализовать простую версию: при регистрации класть пароли в базу, при логине — искать и сравнивать. Работало, код несложный — пара десятков строк. Он даже загордился: вроде просто — почему все говорят «не делай сам»?

Но опытный разработчик, глянув на код, перечислил вереницу неучтённых проблем: пароли в plain text? Компрометация базы — пароли всех юзеров раскрыты. Какой алгоритм хэширования? MD5 небезопасен уже годы, какой cost factor у bcrypt? Где хранится Session? Выставили ли Cookie-атрибуты `HttpOnly`, `Secure` и `SameSite`? Каждый защищает от своего класса рисков: `HttpOnly` запрещает JavaScript читать Cookie (останавливает XSS-кражу), `Secure` гарантирует отправку только по HTTPS (защита от прослушки), `SameSite` ограничивает отправку Cookie с кросс-сайтовыми запросами (помогает против CSRF). Пропустите один — дыра. Истекают ли ссылки сброса пароля? Одноразовые ли токены? Неистекающая ссылка сброса, единожды перехваченная, работает вечно. Есть ли лимит неудачных попыток логина? Без него атакующий скриптом подбирает тысячи паролей в секунду — brute force лишь вопрос времени. Сделали ли CSRF-защиту?

Выслушав всё, Сяомин отказался от самостоятельной реализации. Каждая из деталей — security-риск, и они взаимосвязаны: пропуск даже одной — компрометация. Его пара десятков строк «работала», но для security-эксперта была решето. **Не пишите свою auth-логику** — жесткое правило в разработке ПО. Не потому, что неспособны, а потому что в security «дьявол в деталях». Зрелые auth-библиотеки уже наступили на все мины за вас и прошли боевое тестирование в бесчисленных реальных проектах.

## Как выбрать auth-библиотеку

Несколько мейнстрим-опций: **Better Auth** — open source и бесплатна, хранит данные в вашей базе, нативный TypeScript, бесшовная интеграция с Drizzle, включает продвинутые фичи вроде 2FA, Passkeys и управления организациями — отлично для проектов, где нужен полный контроль. **NextAuth (Auth.js)** — тоже open source и бесплатна, но поддержка типов средняя и Drizzle требует дополнительного adapter'а — лучше для простых сценариев стороннего логина. **Clerk** — готовые UI-компоненты из коробки, но не open source (хотя есть free tier), данные у третьей стороны — подходит проектам, которым нужно быстро запуститься и не жалко стоимости. **Supabase Auth** глубоко интегрирован с Supabase и поддерживает RLS (row-level security), но не поддерживает Drizzle — лучше всего для проектов уже на Supabase.

Ключевая причина выбора Better Auth в этом туториале — **владение данными**: таблицы юзеров и сессий живут в вашем PostgreSQL, без зависимости от стороннего сервиса и привязки к платформе. К тому же команда Auth.js (NextAuth) теперь присоединилась к Better Auth, и Better Auth официально рекомендуется как первый выбор для новых проектов. Auth.js сейчас в maintenance-режиме: security-патчи ещё будут, крупных новых фич — нет. **Для новых проектов используйте Better Auth напрямую**. Если у вас уже стабильный Auth.js-проект в продакшене — спешить с миграцией не нужно.

Вам останется заполнить OAuth-ключи в `.env`. ## Ещё один вид аутентификации в разработке: публичные/приватные ключи

Помимо web-логина, в разработке встречается ещё один метод аутентификации: **публичные/приватные ключи**. Когда вы делаете `git push` на GitHub — откуда GitHub знает, что это вы? Через SSH-ключи: на вашем компьютере приватный ключ (известен только вам), на GitHub — соответствующий публичный. При пуше успешное совпадение ключей доказывает личность. Есть ещё GPG-подписи — «печать подлинности» для Git-коммитов. Другие, увидев бейдж `Verified` на вашем коммите, понимают: он действительно от вас, не подделан. С этим вы столкнётесь при настройке окружения разработки. Если ещё не настроили — скажите AI: «Помоги мне сгенерировать SSH-ключ и настроить его для GitHub».

::: tip Ключевые выводы раздела

- Session хранит данные на сервере и даёт сильнее контроль; Token не хранит ничего на сервере и лучше масштабируется — выбор обычно делает за вас auth-библиотека
- OAuth позволяет юзерам логиниться существующими аккаунтами, Passkeys — будущее безпарольной аутентификации
- Не пишите свою auth-логику — используйте зрелую библиотеку
- Для новых проектов Better Auth — выбор №1; загрузите Skill `better-auth-best-practices` для качества AI-вывода
