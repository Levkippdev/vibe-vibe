# 8.3 Защита роутов и контроль доступа

> **Цель раздела**: понять, почему скрытие точек входа на frontend не равно безопасности, и научиться защищать каждый роут через Middleware и контроль доступа.

---

## Скрыть на frontend — не значит защитить

Сяомин добавил в «Личный Douban» админ-панель `/admin`, где мог массово удалять фильмы и управлять комментариями юзеров. Ссылку на `/admin` в навигацию frontend он не положил и решил, что теперь безопасно: обычные юзеры не видят вход — естественно, и не войдут.

Пока однажды друг Лао Ван не написал в групповом чате: «Твоя админка удобная. Я помог удалить несколько фильмов-дублей».

Сяомин вздрогнул: «Как ты вошёл?»

Лао Ван: «Просто вбил `localhost:3000/admin` в адресную строку браузера — и открылось».

Тогда Сяомин понял: **скрытие точки входа на frontend — лишь security through obscurity**. Отсутствие ссылки в навигации лишь делает так, что юзеры «не видят» вход, но любой может вручную набрать URL в адресной строке. Хуже: атакующий может слать запросы через curl или скриптами дёргать ваш API батчами — frontend-«скрытие» против этих способов бессмысленно. Это как спрятать ключ от квартиры под цветочным горшком и накрыть горшок тканью. Вы думаете: не видят горшок — не найдут ключ; на деле любой может поднять ткань и взять его. Настоящая защита обязана быть на **стороне сервера**: не «спрятать вход», а «без ключа дверь не откроется».

## Middleware — привратник Next.js

В Next.js не нужно писать проверки прав на каждой странице. Достаточно положить файл `middleware.ts` в корень проекта — он работает как привратник сайта, и **каждый запрос** обязан пройти через него до страницы или API. Юзер запрашивает `/admin` — Middleware перехватывает и проверяет: залогинен ли, является ли админом. Не залогинен — редирект на `/login`; не админ — 403 (403 значит «я знаю, кто ты, но у тебя нет прав», в отличие от 401: «кто ты? Сначала залогинься»). Только после прохождения проверки запрос продолжается к странице `/admin`. Проверка происходит на сервере — браузер юзера вообще не получает контент страницы `/admin`: это не «страница загрузилась, а потом редирект», а «страницу вам вообще не отправляли».

> Скажите AI: «Создай middleware.ts, перехватывающий все пути, начинающиеся с /admin. Если юзер не залогинен или его роль не admin — редиректь на страницу логина. Также защити все API, начинающиеся с /api/admin».

<details>
<summary>Любопытно, как выглядит Middleware? Развернуть</summary>

```typescript
// middleware.ts (корень проекта)
import { betterFetch } from '@better-fetch/fetch'
import { NextRequest, NextResponse } from 'next/server'

export async function middleware(request: NextRequest) {
  // Проверяем, залогинен ли юзер
  const { data: session } = await betterFetch('/api/auth/get-session', {
    baseURL: request.nextUrl.origin,
    headers: { cookie: request.headers.get('cookie') || '' },
  })

  if (!session) {
    return NextResponse.redirect(new URL('/login', request.url))
  }

  return NextResponse.next()
}

// Указываем, какие пути требуют защиты
export const config = {
  matcher: ['/dashboard/:path*', '/admin/:path*'],
}
```

</details>

Middleware защищает не только страницы, но и API. Конфигурацией `matcher` можно точно контролировать, какие пути проверяются: `/dashboard/:path*` защищает все страницы дашборда, `/admin/:path*` — админ-панель, `/api/admin/:path*` — админ-API. `:path*` — wildcard «все подпути под этим путём»: `/admin/users` и `/admin/settings` будут защищены. Любой путь, который защищать не нужно (главная, логин, регистрация, публичные API), просто не включайте в `matcher` — Middleware перехватывает только указанные пути, остальные пропускает напрямую.

## Защита страниц и защита API нужны обе

Сяомин добавил Middleware для защиты страницы `/admin`. Он решил, что теперь безопасно: юзеры, пытающиеся открыть `/admin` в браузере, блокируются. Но опытный разработчик спросил: «А эндпоинт удаления фильма `/api/admin/delete-movie` ты тоже защитил?»

Сяомин: «Middleware же блокирует пути, начинающиеся с `/admin`?»

Опытный: «Middleware перехватывает запросы страниц. Но кто-то может напрямую вызвать `POST /api/admin/delete-movie` через curl с валидной Cookie юзера — Middleware может не остановить, это зависит от конфигурации matcher. А даже если Middleware блокирует, сам API всё равно должен иметь собственные проверки прав. Это принцип **defense in depth**».

Зачем два слоя? Middleware — «главный вход», но у каждой комнаты за ним должен быть свой замок. Даже защищённая страница не помешает атакующему обойти браузер и вызвать API напрямую через curl или Postman — как проскочить мимо главного входа ТЦ и пробраться на склад через вход для сотрудников. Проверка на главном входе там бессильна. Если у API нет собственных проверок, атакующему достаточно получить валидную Cookie юзера — и через curl можно удалять данные, менять настройки и даже эскалировать привилегии. Защита на уровне страниц — Middleware + серверные проверки; защита на уровне API — валидация внутри самого API Route; оба слоя контролируются сервером и не обходятся. Это и есть **defense in depth** из арсенала security-профессионалов: не класть все яйца в одну корзину и следить, чтобы у каждого слоя была своя защита.

<DefenseInDepth />

> Скажите AI: «Убедись, что все API, начинающиеся с /api/admin, проверяют права юзера внутри кода, а не полагаются только на Middleware».

## CORS — кросс-доменный security-механизм браузера

<CORSMechanism />

Позже Сяомин захотел добавить в «Личный Douban» фичу: тянуть постеры фильмов из публичного API Douban. Он написал во frontend вызов `fetch('https://api.douban.com/...')` — и консоль браузера немедленно выбросила красную ошибку: «Cross-origin request blocked (CORS policy)». Он в недоумении: в адресной строке API прекрасно возвращал данные — почему из JavaScript не работает?

Это не баг — это **security-механизм** браузера. Представьте: вы залогинены на сайте банка, и браузер хранит вашу логин-Cookie. Потом вы открываете злой сайт. Без кросс-доменных ограничений JavaScript злого сайта мог бы втихую слать запросы на сайт банка — браузер автоматически прикладывал бы вашу банковскую Cookie, и сервер банка считал бы, что это действительно вы. Атакующий переводил бы деньги от вашего имени. CORS (Cross-Origin Resource Sharing) — линия обороны браузера: **по умолчанию JavaScript на странице не может слать запросы на другой домен, если целевой сервер явно это не разрешил**. Прямой визит URL в адресной строке не ограничивается (это намеренное действие юзера), а запросы JavaScript-кода внутри страницы блокируются (потому что это может быть скрытно действующий злокод).

Когда вы столкнётесь с CORS? Если frontend и backend в одном Next.js-проекте (как в этом туториале) и frontend зовёт собственный API Route — CORS не будет, всё same-origin. Но если frontend и backend задеплоены раздельно — frontend на `app.example.com`, API на `api.example.com` — будет. Также вы упрётесь в него при вызове сторонних API напрямую из frontend. Если frontend и backend в одном Next.js-проекте, CORS настраивать обычно не нужно. Если кросс-доменный доступ действительно нужен — скажите AI: «Мой frontend на `https://app.example.com` должен вызывать API на `https://api.example.com`. Помоги настроить CORS так, чтобы разрешался только этот домен».

::: warning Не конфигурируйте `Access-Control-Allow-Origin: *`
Разрешение всех доменов фактически равно отсутствию CORS-защиты. Всегда указывайте конкретный домен.
:::

## Ролевой контроль доступа (RBAC)

<RBACMatrix />

Middleware решает проблему «залогинен ли юзер», но Сяомина быстро ждала новая: после логина Лао Ван всё ещё мог открыть `/admin` — Middleware проверял только логин, не админство. У приложения Сяомина два типа юзеров: он сам — админ, который может удалять фильмы и управлять комментариями; его друзья — обычные юзеры, которые могут только смотреть фильмы и писать комментарии. Здесь вступает **RBAC (role-based access control)** — разные роли могут разное.

Простейшая реализация — добавить поле `role` в таблицу `user`: роль Сяомина — `admin`, роль Лао Вана — `user`. Затем в Middleware или API проверять `session.user.role !== 'admin'` и возвращать 403 при истинности. Проверку можно положить в Middleware (централизованный перехват) или в каждый API Route (тонкий контроль), а лучше — в оба места: снова defense in depth.

С ростом сложности приложения только `admin` и `user` может не хватить. Например, «Личный Douban» Сяомина стал популярен, юзеров несколько сотен — и он хочет дать проверенным друзьям права модерации комментариев. Тогда нужны более гранулярные роли: `guest` может только смотреть публичный контент, `user` — смотреть, постить и править своё, `moderator` имеет все права `user` плюс удаление неуместного, `admin` — все права. Плагин управления организациями Better Auth поддерживает и более продвинутые модели прав, но для большинства личных проектов `admin` и `user` достаточно. Не переусложняйте — расширяйте, когда реально нужно. Когда придёт время, скажите AI, что нужно, — и он поможет скорректировать модель прав.

> Скажите AI: «Помоги реализовать полное решение защиты роутов: создай middleware.ts для защиты путей /dashboard и /admin, потребуй у обращающихся к /admin ещё и роль admin, заставь все API, начинающиеся с /api/admin, проверять права внутри кода, редиректь незалогиненных на /login, а залогиненных уводи с /login на /dashboard».

- Защита страниц и защита API нужны обе
