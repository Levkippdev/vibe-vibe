# 8.4 Security-проверки и troubleshooting

> **Цель раздела**: выработать security-осознанность для каждого этапа разработки, чтобы быстро локализовать и чинить проблемы при их появлении.

---

## Security-чек-лист

Пройдя через утечку ключа, раскрытую админку и ошибки CORS, Сяомин спросил ментора: «Есть ли чек-лист, которому я могу следовать при каждой разработке, чтобы не повторять ошибки?»

Ментор ответил: «Да. Безопасность — не то, что пробегают разок перед запуском и забывают. Она пронизывает весь жизненный цикл разработки — с самой первой секунды создания проекта».

**До разработки — заложите фундамент.** Сяомин оглянулся на свой опыт: настрой он `.gitignore` с самого начала — ключ бы не утёк; выбери он Better Auth сразу — и мысли бы не возникло писать аутентификацию самому. Корень многих security-проблем — «не сделали правильно с самого начала». Если ждать поломки и потом латать — стоимость куда выше, чем сразу сделать правильно. На этом этапе подтвердите три вещи: настроен ли `.gitignore`? Убедитесь, что `.env`, `node_modules/` и `.next/` в игнор-листе — это первое, что нужно сделать после создания проекта, до первой строки бизнес-кода. Создали ли `.env.example`? Перечислите все нужные имена переменных окружения, оставьте значения пустыми, закоммитьте в Git — это ориентир для себя будущего и возможных коллабораторов. Выбрали ли решение для аутентификации? Используйте зрелую библиотеку вроде Better Auth; не пишите свою — раздел 8.2 уже объяснил почему.

> Скажите AI: «Помоги проверить, полон ли .gitignore моего проекта и не отслеживает ли Git какие-то чувствительные файлы».

**Во время разработки — проверяйте на ходу.** Легче всего во время разработки ошибиться режимом «сначала пусть работает»: пока захардкодить ключ, пока пропустить защиту роутов, пока пропустить валидацию ввода. «Доработаю после готовности фичи» — и никогда не возвращаетесь. Именно так Сяомин постепенно накапливал security-долг, пока всё не взорвалось разом: утёкший ключ, незащищённая админка и невалидированный ввод юзеров. Каждая — ловушка, оставленная режимом «сначала пусть работает». На этом этапе стройте привычку проверять на ходу: все ли секреты в `.env`? Поищите в коде ключевые слова `sk-`, `password`, `secret` — не захардкожено ли что-то. Чётка ли граница Server/Client? Чувствительные данные — только на сервере; переменные для frontend — с префиксом `NEXT_PUBLIC_`. На месте ли защита роутов? Middleware плюс внутренняя перепроверка в API. Валидируется ли ввод юзеров? Zod на backend для всего ввода; никогда не доверяйте данным с frontend — frontend-валидация для UX, backend-валидация для security. Перезапустили ли после изменения `.env`? Переменные окружения грузятся только при старте — после изменений нужен рестарт.

> Скажите AI: «Проверь мой код и найди все захардкоженные секреты, API-эндпоинты без валидации ввода и роуты без проверок прав».

**Перед запуском — последняя линия обороны.** Приложение Сяомина готовилось к деплою. Он думал, достаточно запушить код, но ментор сказал: «Перед выходом в свет обязательно проверь ещё несколько вещей — иначе выставляешь приложение миру на растерзание». Есть ли уязвимости в зависимостях? Запустите `pnpm audit` и закройте high-severity проблемы — проект может косвенно зависеть от сотен пакетов, и в любом может быть известная уязвимость. Настроены ли продакшен-переменные окружения? Внесите их по одной на странице переменных deploy-платформы; учтите, что некоторые значения различаются между локалкой и продакшеном (например, `BETTER_AUTH_URL` локально `http://localhost:3000`, в продакшене — ваш домен). Включён ли HTTPS? Vercel и Railway включают по умолчанию, но self-hosted серверы требуют ручной настройки — без HTTPS пароли и cookie юзеров летят по сети plain text'ом, и перехватить их может любой. Безопасны ли сообщения об ошибках? В продакшене не возвращайте stack trace — только дружелюбные сообщения: stack trace раскрывает структуру кода, пути файлов и даже имена таблиц базы — всё это ценная разведка для атакующих.

**После запуска — постоянная поддержка.** Запуск — не финиш, а старт новой фазы. Приложение Сяомина проработало три месяца, когда однажды пришло security-уведомление GitHub: «Зависимость `lodash@4.17.20` вашего проекта имеет уязвимость prototype pollution». Он недоумевал — этот пакет он напрямую не ставил. Разобравшись, обнаружил: один из установленных им пакетов зависит от другого, который, в свою очередь, зависит от уязвимого. Так устроена экосистема npm: проект может косвенно зависеть от сотен пакетов, и любой может стать проблемой. На этом этапе: ротируйте секреты каждые 3–6 месяцев (даже без утечек регулярная ротация — хорошая привычка), запускайте `pnpm audit` ежемесячно для проверки уязвимостей зависимостей, следите за странными логинами (один аккаунт за короткое время из разных регионов), частыми неудачными запросами (возможно brute force) и внезапными всплесками вызовов API (возможно, кто-то злоупотребляет вашими эндпоинтами).

## Гайд по troubleshooting

Security-ошибки часто запутаны: сообщения неинтуитивны, а настоящая причина может быть там, где не ждёте. Каждая ловушка Сяомина стала пунктом этого гайда. Столкнулись с проблемой? Ищите по симптому.

**`.env` настроен, но не читается.** Симптом: `process.env.XXX` возвращает `undefined`. Сначала перезапустите — переменные грузятся только при старте: остановите сервис через `Ctrl+C` и запустите `pnpm dev` заново. В 90% случаев это решает. Если нет — проверьте точное совпадение имени переменной (включая регистр), убедитесь, что `.env` лежит в корне проекта (не внутри `src/`), проверьте лишние пробелы и кавычки: в `.env` кавычки не нужны; `DATABASE_URL=postgresql://...` — верно, а `DATABASE_URL="postgresql://..."` может создать проблемы.

**На Server читается, на Client — нет.** Симптом: переменная доступна в API Route, но в React-компоненте `undefined`. Причина — отсутствует префикс `NEXT_PUBLIC_`: это часть security-поведения Next.js, по умолчанию не отправляющего переменные окружения в браузер. Если значение действительно нужно на frontend и не чувствительно — переименуйте в `NEXT_PUBLIC_XXX`. Если чувствительно (как API Key) — на frontend ему вообще не место: вызывайте через API Route.

**Кросс-доменная ошибка (CORS).** Симптом: консоль браузера показывает `Access to fetch at 'xxx' has been blocked by CORS policy`. Если frontend и backend в одном Next.js-проекте, CORS-проблем быть не должно — проверьте, не ошибочен ли URL запроса (например, полный `http://localhost:3000/api/...` вместо относительного `/api/...`). Если вызываете внешний API — CORS нужно конфигурировать на его стороне, разрешив доступ с вашего домена. Иногда это специфика dev-окружения — проверьте конфигурацию `rewrites` в `next.config.js`.

**`.gitignore` настроен, но файлы всё ещё отслеживаются.** Симптом: `.env` добавлен в `.gitignore`, но `git status` его всё ещё показывает. Причина — файл уже отслеживался Git'ом до добавления в `.gitignore`: он применяется только к файлам, которые **никогда не отслеживались**. Фикс: выполните `git rm --cached .env`, чтобы убрать из индекса, затем закоммитьте снова.

**Секретный ключ уже утёк.** Симптом: ключ закоммичен на GitHub (публичный или приватный репозиторий — неважно). Четыре аварийных шага: немедленно на соответствующей платформе (OpenAI, Supabase, GitHub и т.д.) регенерируйте ключ; обновите `.env` новым ключом; скажите AI: «Мой файл .env закоммичен в историю Git. Помоги полностью вычистить его через git filter-branch или BFG»; проверьте биллинг на странные списания.

::: danger Удалить файл и закоммитить — недостаточно
`git rm .env` и коммит убирают файл только из последней версии. Каждая старая версия в истории Git всё ещё содержит файл. Любой найдёт его через `git log`. Нужно переписать историю.
:::

**После логина всё равно редиректит на страницу логина.** Симптом: логин успешен, но защищённая страница всё равно редиректит на `/login`. Сначала проверьте, корректно ли ставится cookie — откройте браузер F12 → Application → Cookies и посмотрите, существует ли session cookie. Затем убедитесь в одинаковости домена: в разработке используйте `http://localhost:3000`, а не `http://127.0.0.1:3000`. Cookie привязаны к доменам, разные домены их не разделяют. Наконец, проверьте `matcher` в Middleware — `/login` сам не должен быть защищён (страницу логина защищать не нужно).

Заучивать каждый пункт не нужно. Пусть AI регулярно ревьюит ваш проект:

> «Проверь security-позицию моего проекта: нет ли захардкоженных секретов, отслеживается ли .env в Git, есть ли в зависимостях известные уязвимости и есть ли у всех защищённых роутов проверки прав».

---

::: tip Ключевые выводы раздела

- Чек-лист исполняется по фазам: до разработки — настроить `.gitignore`; во время — проверять границы и валидацию; перед запуском — аудит зависимостей; после — регулярная ротация
- 90% проблем с `.env` лечится перезапуском
- `.gitignore` применяется только к неотслеживаемым файлам; для отслеживаемых сначала `git rm --cached`
- После утечки секрета обязательны сброс ключа + чистка истории Git; одного удаления файла мало
:::
