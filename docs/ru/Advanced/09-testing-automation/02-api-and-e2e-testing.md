# 9.2 API-тестирование и E2E-тестирование

> **Цель раздела**: освоить стратегию покрытия API-тестов и практические методы E2E-тестирования, научиться разбирать flaky-тесты и читать тестовые логи.

---

## Почему сначала тестируем API

Сяомин решил начать писать тесты. Но с чего начать? У приложения frontend-страницы, backend-API и операции базы — что тестировать?

Сеньор говорит: «Начни с фундамента — API-эндпоинтов».

Причины практичны. Страница рейтингов Сяомина выбрасывает ошибку. Он открыл браузер и видит «Отправка оценки не удалась». Где проблема? Может, кнопка frontend некорректно вызывает API; может, API возвращает битые данные; может, запись в базу падает. Без API-тестов ему придётся открывать браузер, логиниться, искать фильм, кликать оценку и смотреть результат — проходить полный флоу каждый раз, лишь бы определить «это проблема frontend или backend?»

А с API-тестами можно отправить запрос напрямую в `POST /api/movies/42/rate` и проверить ответ. API вернул 200 с корректными данными? Проблема во frontend. API вернул 500? Проблема в backend. **API-тесты помогают локализовать проблему до уровня «frontend или backend»**, не стартуя каждый раз с браузера.

Ещё одна важная причина: **API куда стабильнее UI**. Страница рейтингов Сяомина меняется часто: кнопка переехала, стиль другой, анимация добавлена. Каждое изменение UI рискует сломать тесты, зависящие от UI-элементов, — даже при рабочей функциональности. Но контракты API относительно стабильны: «отправь этот запрос — получи эти данные» не меняется от того, что кнопка перекрасилась. API-тесты, написанные раз, живут долго; UI-тесты, написанные раз, могут требовать правок уже на следующей неделе.

Как проверка машины: можно проверить, заводится ли двигатель (API-тесты), или выехать на трассу и посмотреть общую динамику (E2E-тесты). Тесты двигателя быстрые, стабильные, легко диагностируются; ходовые тесты комплексные, но долгие, и результат могут портить трафик или погода. Большинство проблем вскрывается на тестах двигателя.

## Что тестировать в одном эндпоинте

Эндпоинт рейтингов Сяомина — `POST /api/movies/:id/rate`: принимает тело запроса вида `{ rating: 4 }`, пишет оценку в базу, возвращает обновлённое среднее. Какие сценарии должен покрывать этот эндпоинт?

**Happy path**: залогиненный юзер отправляет валидную оценку (целое 1–5), ожидаем 200 и корректное среднее. Это база — работает ли фича вообще?

**Валидация параметров**: юзер отправляет 0 или 6 (вне диапазона 1–5) — ожидаем 400 с сообщением. Юзер отправляет строку `"abc"` вместо числа — ожидаем 400. Это проверка «может ли эндпоинт отвергнуть невалидный ввод»: без валидации грязные данные попадут в базу.

**Права**: незалогиненный юзер отправляет оценку — ожидаем 401. Проверка «проверяет ли эндпоинт личность»: аутентификацию вы добавили в главе 8 — теперь верифицируем, что она реально работает.

**Edge cases**: тот же юзер оценивает тот же фильм дважды — обновлять старую оценку или отклонять? ID фильма не существует (вроде `/api/movies/99999/rate`) — ожидаем 404. Это бизнес-специфичные сценарии. Если логика дубликатов оценок уже реализована в коде, AI увидит её при чтении и сгенерирует соответствующие тесты; но если правило живёт только у вас в голове (планируете, но ещё не написали) — упомянуть его должны вы.

**Минимум — покрыть эти четыре категории на каждый эндпоинт**: happy path, валидация, права, edge cases. Это не догма, а образ мысли: при написании тестов спрашивайте себя — работает ли нормальный случай? Блокируется ли невалидный ввод? Отклоняется ли неавторизованный? Есть ли особые случаи, которые знаю я, но не знает AI?

```typescript
import { describe, test, expect, beforeEach } from 'vitest'

describe('POST /api/movies/:id/rate', () => {
  // Happy path
  test('logged-in user submits valid rating', async () => {
    const res = await request(app)
      .post('/api/movies/42/rate')
      .set('Authorization', `Bearer ${userToken}`)
      .send({ rating: 4 })

    expect(res.status).toBe(200)
    expect(res.body.averageRating).toBeCloseTo(4.0)
  })

  // Валидация параметров
  test('rating out of range returns 400', async () => {
    const res = await request(app)
      .post('/api/movies/42/rate')
      .set('Authorization', `Bearer ${userToken}`)
      .send({ rating: 6 })

    expect(res.status).toBe(400)
  })

  // Права
  test('unauthenticated user returns 401', async () => {
    const res = await request(app)
      .post('/api/movies/42/rate')
      .send({ rating: 4 })

    expect(res.status).toBe(401)
  })

  // Edge cases
  test('duplicate rating updates old record', async () => {
    // Первая оценка
    await request(app)
      .post('/api/movies/42/rate')
      .set('Authorization', `Bearer ${userToken}`)
      .send({ rating: 3 })

    // Вторая оценка (тот же юзер, тот же фильм)
    const res = await request(app)
      .post('/api/movies/42/rate')
      .set('Authorization', `Bearer ${userToken}`)
      .send({ rating: 5 })

    expect(res.status).toBe(200)
    // Должна обновить, не добавить новую
    expect(res.body.averageRating).toBe(5)
  })

  test('non-existent movie returns 404', async () => {
    const res = await request(app)
      .post('/api/movies/99999/rate')
      .set('Authorization', `Bearer ${userToken}`)
      .send({ rating: 4 })

    expect(res.status).toBe(404)
  })
})
```

## Пусть AI сгенерирует API-тесты за вас

Вы привыкли, что Claude Code анализирует кодовую базу и генерирует код, — тестирование не исключение. Укажите на папку API и попросите сгенерировать тесты для каждого эндпоинта:

> Скажите AI: «Прочитай все роуты в папке `app/api` и сгенерируй Vitest-тесты для каждого API. Покрой на каждый эндпоинт: нормальный запрос (200), ошибку параметров (400), неавторизованный (401)».

Он обойдёт файлы эндпоинтов, анализируя параметры, возвращаемые значения и middleware каждого роута, и сгенерирует соответствующий тестовый код. Но результат нужно ревьюить — не синтаксис (AI редко ошибается), а покрытие. «Четыре категории» выше: AI обычно покрывает сценарии реализованной логики после чтения кода. Вам нужно смотреть: есть ли бизнес-правила, которые вы планируете, но ещё не написали? Есть ли edge cases, явно не обработанные в коде (конкурентные отправки, экстремальные объёмы данных)? Это то, что как бизнес-эксперт должны дополнить вы.

Ещё практичный приём: как проверить, что тесты реально «что-то тестируют», а не для галочки? Попробуйте вручную внести баг в бизнес-код (например, поменяв валидацию рейтингов с `1-5` на `1-10`) и запустите тесты. Не упали красным? Значит, они не проверяют это ограничение — нужно добавить assertion на границы диапазона. Этот метод «нарочно сломать код и посмотреть, поймут ли тесты» называется mutation testing — отличный способ верифицировать качество тестов.

## От эндпоинтов к UI: E2E-тестирование

API-тесты Сяомина все зелёные. Он выдохнул, решив, что с фичей рейтингов теперь всё в порядке. И друг репортит: «Кликнул кнопку оценки — ничего не произошло».

Он разбирается: сам API в порядке, прямые запросы возвращают норм. Проблема во frontend: клик-событие кнопки рейтинга вообще не вызывало API. Сяомин рефакторил компоненты и перенёс логику отправки в другой файл, забыв импортировать её в новом компоненте. TypeScript скомпилировался без ошибок (сигнатуры функций корректны, просто не вызывались), страница отрендерилась (кнопка есть, просто при клике ничего не делает). API-тесты это не поймали: они обходят frontend и шлют запросы напрямую.

В этом ценность E2E-тестирования: оно тестирует **полный опыт юзера** — от открытия страницы, кликов по кнопкам до увиденного результата. Ему не важно, «работает ли API» или «корректно ли возвращаемое значение функции», — важно «может ли юзер сделать то, что хочет».

**Playwright** — сейчас самый мейнстрим-инструмент E2E-тестирования, open source от Microsoft. Он умеет автоматически открывать браузеры (Chrome, Firefox, Safari — все поддержаны), симулировать клики, ввод, скролл юзера, даже делать скриншоты и записывать видео. Думайте о нём как о «роботе-юзере»: он по вашему скрипту, как живой человек, оперирует приложением и проверяет совпадение результата с ожиданием.

У Playwright особенно практичная фича: **режим записи**. Не нужно писать тест-скрипты с нуля — пусть Playwright записывает ваши операции: куда кликаете, что вводите, — и автоматически генерирует соответствующий тестовый код. Сгенерированный код может требовать правок (селекторы могут быть нестабильны), но как отправная точка это сильно быстрее нуля. Запустите `npx playwright codegen http://localhost:3000` для старта записи.

Первый E2E-тест Сяомина: юзер логинится и оценивает фильм.

<details>
<summary>Любопытно? Развернуть: код теста Playwright</summary>

```typescript
import { test, expect } from '@playwright/test'

test('user rates a movie', async ({ page }) => {
  // Логин
  await page.goto('/login')
  await page.fill('[name="email"]', 'ming@example.com')
  await page.fill('[name="password"]', 'password123')
  await page.click('button[type="submit"]')

  // Ждём завершения логина, редирект на главную
  await page.waitForURL('/')

  // Идём на страницу фильма
  await page.click('text=Interstellar')
  await page.waitForURL('/movies/**')

  // Кликаем 4 звезды
  await page.click('[data-testid="star-4"]')
  await page.click('[data-testid="submit-rating"]')

  // Проверяем обновление среднего рейтинга
  await expect(page.locator('.average-rating')).toContainText('4')
})
```

</details>

Обратите внимание на `waitForURL` и `waitForURL('/movies/**')` в коде — это **explicit waits**, говорящие Playwright «дождись завершения навигации, потом продолжай». Без ожидания скрипт может искать элементы до окончания загрузки страницы, не находить и падать. Это одна из самых частых ловушек E2E — детали ниже.

## Flaky-тесты — «мистика» тестирования

<FlakyTestAnalysis />

Сяомин написал первый E2E-тест, прогнал трижды: pass, pass, fail. Один и тот же код, та же среда — почему разные результаты?

Это **flaky-тест**: иногда проходит, иногда падает. Как автомат с напитками, изредка съедающий монеты без выдачи бутылки — дело не в монетах, машина сама нестабильна. Flaky-тесты — самая головная боль E2E-тестирования, с ними сталкивались все, кто писал E2E.

Почему flaky? Обычно эти причины:

**Тайминги async-операций**. Сяомин кликает «отправить оценку», тест-скрипт немедленно проверяет, обновился ли средний рейтинг на странице. Но отправка оценки асинхронна: запрос ушёл, сервер ещё не ответил, страница ещё не обновилась — тест уже assert'ит. Локальная сеть быстрая — запрос вернулся мгновенно, тест зелёный; сеть чуть медленнее — запрос не вернулся, тест красный. Решение — **явное ожидание**: не assert'ить сразу после операции, дождаться появления или обновления целевого элемента. `expect(locator).toContainText()` у Playwright ждёт по умолчанию (5 секунд), но при особенно медленных операциях (загрузки файлов, сложные вычисления) может понадобиться вручную увеличить timeout.

**Гонки данных**. Сяомин написал два теста: тест A ставит фильму 42 пять звёзд; тест B проверяет, что средний рейтинг фильма 42 равен 0 (в предположении, что никто не оценивал). Если A выполняется первым — B падает: остаточные данные A повлияли на B. Решение — **изоляция данных**: каждый тест независимо готовит нужные ему данные и подчищает за собой. Не позволяйте тестам разделять состояние.

**Различия окружений**. Локальная машина мощная, сеть быстрая — тесты бегут гладко. Но среда CI (виртуалки GitHub Actions) может быть слабее, с большей сетевой задержкой — то же время ожидания локально работает, в CI нет. Решение — задавать **разумные timeout** для assertions, не предполагая мгновенного исполнения операций.

Flaky-тесты нельзя игнорировать. «Иногда падает» означает: результатам теста никогда нельзя доверять — тест прошёл, он действительно в порядке или просто в этот раз не триггернул flake? Дыра в safety net лишает доверия ко всей сети. Встретив flaky-тест — либо чините (найдите и устраните причину нестабильности), либо временно скипайте (пометив `skip`) с документированием причины, но не оставляйте его «иногда красным» навсегда.

Как отличить flaky от реального бага? Простой способ: **прогоните 5 раз подряд**. Все 5 падают — вероятно, реальный баг; часть зелёные, часть красные — flaky. Playwright поддерживает параметр `--repeat-each=5`, прогоняя каждый тест 5 раз — легко быстро определить.

Ключевой принцип починки flaky-тестов: **не «подождать чуть-чуть» через `sleep`**. `await page.waitForTimeout(2000)` (ждать 2 секунды) кажется решением, но лишь прячет проблему: локально 2 секунды хватает, в CI может нет; сегодня хватает, при росте данных завтра — нет. Правильно — **условное ожидание**: `await page.waitForSelector('.average-rating')` (дождаться появления элемента), `await expect(locator).toContainText('4')` (дождаться, пока текст станет ожидаемым). Условное ожидание продолжается в момент выполнения условия — не слишком долго (трата времени) и не слишком коротко (причина flakiness).

> Скажите AI: «Этот E2E-тест иногда проходит, иногда падает, помоги проанализировать причину и починить. Сообщение об ошибке: [вставьте лог ошибки]»

## Чтение логов при падении тестов

E2E-тест Сяомина упал, терминал выдал кучу инфы. Он смотрит на экран, полный красного текста, и не знает, с чего начать. Сеньор говорит: «Без паники. Диагностика в три шага».

**Шаг 1: Смотрим тип ошибки**. Ошибки упавших тестов обычно таких типов:

`Timeout waiting for selector "[data-testid='submit-rating']"` — это **таймаут ожидания**: Playwright не нашёл элемент за лимит времени. Возможные причины: страница не догрузилась, `data-testid` элемента изменился, предыдущая операция (логин) провалилась, и страница остановилась не там.

`Expected "4.0" but received "3.5"` — это **провал assertion**: элемент найден, но значение неверное. Возможные причины: баг логики вычисления, тестовые данные плохо подготовлены (например, другие записи оценок уже в базе и влияют на среднее).

`Error: net::ERR_CONNECTION_REFUSED` — это **сетевая ошибка**: обычно backend-сервис не запущен или неверный порт.

**Шаг 2: Смотрим скриншот**. Playwright автоматически сохраняет скриншот страницы при падении теста, по умолчанию в каталоге `test-results/`. Откройте скриншот — увидите состояние страницы в тот момент: застряла на странице логина (логин не прошёл)? Показывает ошибку (API вернул ошибку)? Или полностью пустая (frontend-рендер рухнул)? Скриншоты куда интуитивнее логов — часто один скриншот локализует проблему.

**Шаг 3: Смотрим сетевые запросы**. Если скриншот не раскрыл проблему — смотрите сетевые запросы во время теста. Playwright умеет конфигурировать trace (трассировку), записывая каждый сетевой запрос и ответ. Откройте trace-файл, найдите запрос отправки оценки: вернул 200 или 500? Какие данные? API вернул 500 — проблема в backend; API вернул корректные данные, но страница не обновилась — проблема во frontend-логике рендера.

<details>
<summary>Любопытно? Развернуть: включение Playwright Trace</summary>

```typescript
// playwright.config.ts
export default defineConfig({
  use: {
    // Сохранять trace только при первом падении ретрая
    trace: 'on-first-retry',
    // Автоскриншот при падении
    screenshot: 'only-on-failure',
  },
})
```

Просмотр trace:

```bash
npx playwright show-trace test-results/xxx/trace.zip
```

Откроется визуальный интерфейс, где можно шаг за шагом прокручивать воспроизведение теста, видя состояние страницы, сетевые запросы и логи консоли на каждом шаге.

</details>

**Сообщение ошибки → скриншот → сетевые запросы** — три шага локализуют большинство упавших тестов. Если всё ещё не находится — бросьте логи ошибок и скриншоты в AI вместе, пусть поможет проанализировать.

## Когда E2E, а когда API-тесты

У Сяомина теперь есть и API-тесты, и E2E-тесты, но он не понимает, когда что использовать. Сеньор дал простые критерии решения:

**API-тесты покрывают «корректны ли данные»** — коды статусов, форматы данных, бизнес-логику, возвращаемую эндпоинтами. Большая часть ключевой логики фич верифицируется API-тестами. Быстрые в написании, быстрые в исполнении, дешёвые в поддержке.

**E2E-тесты покрывают «может ли юзер этим пользоваться»** — открываются ли страницы, кликаются ли кнопки, завершаются ли флоу. Использовать только для критичных юзер-флоу: регистрация/логин, ключевые бизнес-операции (оценки, поиск), платёжные флоу. Не пишите E2E на каждую страницу — стоимость поддержки взорвётся.

Для «личного Douban» Сяомина разумное распределение: все API-эндпоинты с integration-тестами (четыре категории), E2E-тестов всего два-три — «юзер регистрируется и логинится», «ищет фильм и смотрит детали», «оценивает фильм». Эти три флоу покрывают ключевой юзер-опыт, остальное — API-тестам.

Частое заблуждение: «E2E-тесты реалистичнее — значит, лучше». Реалистичность ≠ лучше: E2E ближе всего к опыту юзера, но и поддержка самая дорогая. Страница рейтингов Сяомина один раз поменяла раскладку — все E2E-тесты с рейтингами требуют обновления селекторов; API-тесты вообще не затронуты. Если вы тратите на поддержку E2E больше времени, чем на новые фичи, — E2E написано слишком много: спускайте часть логики на слой API-тестов.

Ещё критерий: **если баг можно найти только через E2E (кнопка не привязана к событию, неверная навигация страниц) — E2E-тест; если через API-тест (эндпоинт возвращает неверные данные, auth не проверяется) — API-тест**. Где можно — проверяйте легче, не применяйте тяжёлые методы.

---

::: tip Ключевые выводы раздела

- Тестируйте сначала API: быстро, стабильно, легко локализуются. Минимум четыре сценария на эндпоинт: happy path, валидация, права, edge cases
- E2E-тесты покрывают «юзер-опыт»: только критичные флоу, не злоупотребляйте
- Три главные причины flaky: тайминги async, гонки данных, различия сред. Решения: явные ожидания, изоляция данных, разумные timeout
- Трёхшаговая диагностика падений: сообщение ошибки → скриншот → сетевые запросы
:::
