# 9.3 Автоматизированные воркфлоу

> **Цель раздела**: настроить Git Hooks и GitHub Actions для автоматического запуска тестов; понять мышление TDD и области его применения.

---

## Тесты есть, но вы забываете их запускать

Сяомин потратил полдня на тесты ключевых API-эндпоинтов. При первом запуске всё зелёное — он доволен. Потом двинулся к новым фичам: добавление ревью фильмов, подкрутка ранжирования поиска, оптимизация загрузки страницы деталей. После каждого изменения он думал «тесты прогоню потом», но неизменно отвлекался на следующую фичу и забывал.

Через три дня он запушил код на GitHub. Друг спулил и прогнал тесты — два упали. Сяомин прошёлся по истории изменений и нашёл баг, внесённый при изменении ранжирования поиска в первый день. Прогони он тесты в тот день — поймал бы сразу. Но три дня спустя, с десятками изменений между, поиск коммита-виновника стоил в разы больше усилий.

Эта история вскрывает закономерность: **чем позже найден баг, тем дороже его чинить**. Поймали сразу после кодинга — вы ещё помните, что меняли, — починка за минуты. Подождали до завтра — придётся восстанавливать вчерашнюю работу в памяти. Подождали неделю — контекст потерян полностью; чтобы починить, нужно заново разбираться в коде. Ключевая ценность автоматизированного тестирования не «поиск багов» — руками вы тоже можете найти баги, — а **ранний поиск багов**, когда их чинить дешевле всего.

Ветеран говорит: «Люди забывают. Машины — нет. Пусть машина запоминает».

## Git Hooks — автоматические проверки перед коммитом

У Git есть встроенный механизм **Hooks** — скрипты, настроенные запускаться автоматически при определённых операциях Git. Например, hook `pre-commit` выполняется перед каждым `git commit`. Если скрипт падает (возвращает ненулевой код выхода), Git блокирует коммит.

<GitHooksWorkflow />

Представьте СКУД: вы прикладываете карту, система автоматически проверяет права — не нужно «помнить» о проверке. Каждый раз, когда Сяомин выполняет `git commit`, Git автоматически запускает `pnpm test`. Все тесты зелёные? Коммит проходит. Любой красный? Коммит заблокирован — сначала почини.

Психологический эффект важнее технического. Раньше Сяомин думал «тесты прогоню потом», но «потом» не наступало никогда. С pre-commit hook ему не нужно «помнить» — сам акт коммита триггерит тесты. Как не нужно «помнить» закрыть дверь, когда она закрывается автоматически. Превращение «надо бы, но легко забыть» в «случается само» — ключевая ценность автоматизации.

Самый популярный инструмент управления Git Hooks — **Husky**. Он берёт на себя скрипты хуков — без копания вручную в `.git/hooks/`. Скажите Claude Code, что нужно, — и он всё настроит:

> Скажите AI: «Помоги мне настроить Git pre-commit hook, автоматически запускающий `pnpm test` перед каждым коммитом. Блокируй коммит при падении тестов. Используй Husky».

<details>
<summary>Любопытно? Вот как выглядит конфигурация Husky</summary>

```bash
# Установка Husky
pnpm add -D husky

# Инициализация
npx husky init

# Содержимое файла .husky/pre-commit
pnpm test
```

Вот и всё. Теперь каждый `git commit` триггерит `pnpm test` через Husky. Тесты упали? Коммит заблокирован. Прошли? Обычный коммит.

Если хотите запускать только тесты, связанные с текущими изменениями (не все), можно использовать `lint-staged` — но для масштаба проекта Сяомина полный прогон занимает секунды, оптимизация не нужна.

</details>

Но у pre-commit hooks есть ограничение: **они работают только локально**. Кто-то может обойти hook через `git commit --no-verify` (спешит закоммитить, починить потом) — и плохой код всё равно пролезет. Плюс локальные среды различаются: у вас тесты зелёные, на другой машине могут упасть (локальные переменные окружения, устаревшие артефакты сборки и т.д.). Так что Git Hooks — первая линия обороны, не единственная.

Сяомин может спросить: «Когда можно использовать `--no-verify`?» Легитимные сценарии есть: WIP-коммиты (код не завершён, просто сохранение прогресса), изменения только в документации (тесты нерелевантны), или когда hook проверяет то, что явно не связано с вашими изменениями. Ключ — **осознанный пропуск**, не привычка: если вы постоянно обходите hooks, скорее всего, они слишком тяжёлые (полный прогон всех тестов, когда нужны только связанные). Оптимизируйте hook вместо обхода.

## GitHub Actions — автоматическая верификация после пуша

Код на GitHub — и **GitHub Actions** запускает ваши тесты на свежей, чистой виртуалке. Это вторая линия обороны: даже если кто-то скипнул локальный hook, CI поймает.

Как линия контроля качества на фабрике: каждый продукт проверяется перед отгрузкой. Рабочие могут скипнуть самопроверку (локальные hooks), но детекторы линии ловят всё (CI).

Ценность GitHub Actions не только в «прогоне тестов ещё раз». Он стартует с нуля в **чистой среде** — установка зависимостей, сборка, запуск тестов. Это ловит проблемы «у меня работает»: у вас есть переменная окружения, но вы забыли добавить её в `.env.example`; кэшированные артефакты сборки дают локально ложные зелёные тесты; глобально установленные инструменты не объявлены в `package.json`. Локально эти проблемы прячутся — в чистой среде CI они всплывают.

> Скажите AI: «Напиши мне GitHub Actions воркфлоу, автоматически запускающий тесты на каждый push и PR».

<details>
<summary>Любопытно? Вот как выглядит файл GitHub Actions воркфлоу</summary>

```yaml
# .github/workflows/test.yml
name: Test

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 20

      - name: Setup pnpm
        uses: pnpm/action-setup@v4

      - name: Install dependencies
        run: pnpm install

      - name: Run tests
        run: pnpm test
```

Каждый push или PR триггерит этот флоу на свежей виртуалке. Результат отображается на странице PR: зелёная галочка — прошёл, красный X — упал.

</details>

Две линии обороны работают вместе: Git Hooks ловят очевидное локально (быстрый фидбек, секунды), GitHub Actions делают финальную верификацию на удалёнке (комплексная проверка, возможно минуты). Большинство проблем ловится локально; в CI уходят лишь редкие «средо-специфичные».

Сяомин почувствовал облегчение, увидев зелёную галочку на своём PR — не «кажется, код в порядке», а «чистая среда с нуля верифицировала, что код в порядке». Эта определённость — то, чего локальное тестирование дать не может: у локальных сред всегда есть «только у меня» особенности.

Практический совет: если CI-тесты падают, а локально зелёные, — не гоняйте локально снова и снова. Сначала смотрите CI-логи: они точно говорят, какой тест упал и почему. Частые причины: отсутствующие переменные окружения (на CI нет `.env`, конфигурируйте в Settings → Secrets репозитория), ошибки подключения к базе (на CI нет локального инстанса), различия часовых поясов (CI по умолчанию UTC, у вас, возможно, UTC+8). Это «проблемы среды», не «проблемы кода» — чините выравниванием CI с локальной средой.

## TDD — сначала думаем, потом кодим

Сяомин хочет добавить в «Личный Douban» новую фичу: ревью фильмов. Юзеры могут писать текстовые отзывы до 500 символов. Ветеран предлагает: «В этот раз попробуй сначала написать тесты».

Сяомин в недоумении: «Как тестировать код, которого не существует?»

Ветеран: «Сначала чётко подумай, что эндпоинт принимает и возвращает — это и есть твой тест».

Сяомин думает: `POST /api/movies/42/reviews` принимает `{ content: "Amazing visuals, stunning effects" }`, возвращает `201` и объект ревью. Не залогинен? `401`. Пустой контент? `400`. Больше 500 символов? `400`.

Он записывает это как тестовый код. Тесты падают — естественно, эндпоинта ещё нет. Затем говорит Claude Code: «Вот мой тестовый файл, реализуй соответствующий API, чтобы все тесты прошли».

Закончив, он замечает интересное: потому что интерфейс-дизайн (параметры, коды статусов, отказы) был прояснён заранее, кодинг шёл гладко. Ни midway-смен интерфейса, ни «этот параметр лучше назвать по-другому» на середине. Тестовый файл сам — **спецификация интерфейса**: он точно описывает поведение, точнее документации и устных описаний, потому что исполняем. Поведение разошлось с тестом — немедленно красный.

Это ядро **TDD (Test-Driven Development)**: сначала тесты (определить «что правильно»), затем код (заставить тесты пройти), наконец рефакторинг (оптимизировать код, держа тесты зелёными). Как чертёж дома до стройки стен — не начинать стены, а потом думать, где дверь.

Три шага TDD имеют имена: **Red** (пишем тест, он падает, потому что кода нет) → **Green** (пишем минимальный код для прохождения) → **Refactor** (оптимизируем структуру, сохраняя зелёный). «Минимальный код» важно: это предотвращает over-engineering. Не нужно думать «а вдруг потом поддержим половинные звёзды?» — просто пройдите текущие тесты. Требования сменились — сначала обновите тесты (новое «правильно»), потом код.

Но TDD — не догма. Лучше всего подходит: **ключевой бизнес-логике** (расчёты рейтингов, проверки прав — ошибки дороги), **стабильным интерфейсам** (API-эндпоинтам — после дизайна их тяжело менять), **сложным ветвлениям условий** (много входов → много выходов: перечислить все случаи до кодинга — меньше шансов пропустить).

Неподходящие сценарии ясны: **правки UI-стилей** (цвет кнопки, отступы — тестировать бессмысленно), **исследовательские прототипы** (требования не устоялись, сегодняшние тесты завтра устарели), **одноразовые скрипты** (скрипты миграции данных выполняются раз и выбрасываются — тестировать не стоит).

Сяомину не нужен TDD для всего. Но для ключевых интерфейсов привычка «сначала тесты, потом код» стоит прокачки: она заставляет продумать «как это должно работать» до набора текста.

TDD исключительно хорошо сочетается с AI-кодингом. Боль традиционного TDD была «написание тестов занимает время», теперь вы описываете поведение интерфейса естественным языком, а AI генерирует тестовый код. Ваша работа смещается с «написания тестового кода» на «описания, как интерфейс должен работать» — а это дизайн. Затем тестовый файл передаётся AI для реализации. Тесты становятся «контрактом» между вами и AI: вы определяете поведение, AI реализует, тесты верифицируют. Этот воркфлоу бьёт «сначала код, потом тесты»: критерии приёмки определены заранее, AI не нужно гадать, чего вы хотите.

<details>
<summary>Любопытно? Полный флоу TDD</summary>

```typescript
// Шаг 1: Сначала тесты (RED — падают, эндпоинта нет)
describe('POST /api/movies/:id/reviews', () => {
  test('logged-in user submits review', async () => {
    const res = await request(app)
      .post('/api/movies/42/reviews')
      .set('Authorization', `Bearer ${userToken}`)
      .send({ content: 'Amazing visuals, stunning effects' })

    expect(res.status).toBe(201)
    expect(res.body.content).toBe('Amazing visuals, stunning effects')
    expect(res.body.movieId).toBe(42)
  })

  test('empty content returns 400', async () => {
    const res = await request(app)
      .post('/api/movies/42/reviews')
      .set('Authorization', `Bearer ${userToken}`)
      .send({ content: '' })

    expect(res.status).toBe(400)
  })

  test('content over 500 chars returns 400', async () => {
    const res = await request(app)
      .post('/api/movies/42/reviews')
      .set('Authorization', `Bearer ${userToken}`)
      .send({ content: 'a'.repeat(501) })

    expect(res.status).toBe(400)
  })

  test('no login returns 401', async () => {
    const res = await request(app)
      .post('/api/movies/42/reviews')
      .send({ content: 'Amazing' })

    expect(res.status).toBe(401)
  })
})

// Шаг 2: Код для прохождения тестов (GREEN)
// Скажите Claude Code: «Вот мой тестовый файл, реализуй соответствующий API»

// Шаг 3: Рефакторинг (REFACTOR)
// Все тесты зелёные — оптимизируем структуру кода. После каждого изменения гоняем тесты, подтверждая, что ничего не сломано.
```

</details>

## От «whack-a-mole» к «safety net»

Вернёмся к истории Сяомина. Месяц назад он кодил в страхе: каждый коммит — тревога «что я на этот раз сломал?». Репорты друзей были единственным фидбеком — всегда с опозданием.

Теперь иначе. Ключевые интерфейсы с API-тестами; ключевые флоу с E2E-тестами. Каждый `git commit` — Husky автоматически прогоняет тесты: всё зелёное — коммить с уверенностью. Код уехал на GitHub — Actions прогоняет снова: всё зелёное — мёржи с уверенностью. Тест покраснел? Он сразу знает, какое изменение виновато, — без ожидания баг-репортов.

Тесты — не груз, а **уверенность менять код**. Без тестов вы боитесь рефакторинга — вдруг сломается? С тестами рефакторите смело: прогнали — зелёное, значит нормально. Чем полнее покрытие — тем выше уверенность. Этот сдвиг постепенный: первый раз, когда тесты ловят для вас баг («слава тестам, это уехало бы в прод»), вы понимаете — ценность не теоретическая, она настоящая.

Это не строилось за ночь. Тесты Сяомина накапливались постепенно: начать с самых рискованных интерфейсов, добавить E2E для ключевых флоу, затем наслоить Git Hooks и CI. Каждый пойманный баг после починки получает тест — гарантию, что он никогда не вернётся. Эта стратегия — «bug-driven testing»: не предсказывать все возможные баги, а латать оборону после каждого укуса. Набор тестов растёт медленно, safety net затягивается.

Не гонитесь за идеальным покрытием. 80% риска закрывается 20% тестов. Сначала защитите критичное, остальное заполняйте со временем. Важно **начать**: даже один тест лучше нуля. Начните сегодня: в следующий раз, чиня баг, напишите тест, закрепляющий фикс. Это ваш первый шаг.

---

::: tip Ключевые выводы

- Git Hooks (Husky): автоматический прогон тестов перед коммитом, блок при падении — первая линия обороны
- GitHub Actions: тесты в чистой среде после пуша, ловят «у меня работает» — вторая линия обороны
- TDD подходит ключевой бизнес-логике и стабильным интерфейсам: сначала определить поведение тестами, потом реализовать код — не догма, а инструмент
- Тесты накапливаются постепенно: сначала защитить критичное, добавлять тесты при починке багов, safety net затягивается со временем
:::
