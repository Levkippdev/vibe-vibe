# 10.1 От localhost к интернету

> **Цель раздела**: понять, почему другие не могут открыть ваш localhost, научиться тестировать на телефоне через локальную сеть и разобраться в способах «показать проект другим людям».

## Localhost: каждое устройство «говорит само с собой»

Сяомин думал, что `localhost` значит «адрес моего компьютера». Не совсем: localhost значит «устройство, отправляющее запрос, само».

Когда Сяомин вводит `localhost:3000` в своём браузере, браузер обращается к компьютеру Сяомина. На компьютере Сяомина работает Next.js-сервер — страница отображается нормально.

Когда друг вводит `localhost:3000` в своём браузере, браузер обращается к компьютеру друга. На компьютере друга ничего не запущено — браузер показывает ошибку «connection refused».

Интуитивная проверка: введите `localhost` в браузере телефона — он обратится к самому телефону, не к компьютеру. localhost каждого устройства указывает на него самого.

Технически localhost отображается на IP-адрес `127.0.0.1`, называемый **loopback-адресом**. Пакеты покидают ваш компьютер и сразу же возвращаются в него, никогда не проходя через сетевой кабель или Wi-Fi. Поэтому localhost по своей природе безопасен: внешние устройства до него просто не достучатся.

::: info Почему dev-серверы по умолчанию используют localhost?
Именно потому, что localhost доступен только с самой машины, это самая безопасная среда разработки. В вашем коде могут быть баги, security-уязвимости или тестовые данные в базе — и это нормально, потому что видеть это можете только вы. Фреймворки разработки по умолчанию биндятся на localhost, чтобы случайно не выставить work-in-progress другим устройствам локальной сети.
:::

## Локальная сеть: устройства на одном Wi-Fi видят друг друга

Сяомин разобрался с localhost, но у него осталась потребность: тестировать тач-жесты и адаптивные раскладки на телефоне. Неужели ради этого каждый раз деплоиться в публичный интернет?

Не нужно. Если телефон и компьютер подключены к одному Wi-Fi, они в одной **локальной сети (LAN)**. Устройства в одной LAN могут обращаться друг к другу напрямую.

Представьте устройства на одном Wi-Fi как людей в одном офисе — они могут напрямую окликнуть друг друга. Разные Wi-Fi — как разные города: перекричать не выйдет.

Локальная сеть — ключевой метод real-device-отладки в full-stack-разработке. Не нужно каждый раз деплоиться в интернет только чтобы посмотреть, как выглядит на телефоне: если телефон и компьютер на одном Wi-Fi, можно зайти напрямую.

### Найдите свой локальный IP-адрес

У компьютера есть внутренний IP-адрес в локальной сети, обычно формата `192.168.x.x` или `10.x.x.x`. Найти его:

::: code-group

```bash [Windows]
ipconfig
```

```bash [macOS]
ifconfig
```

```bash [Linux]
ip addr
```

:::

В выводе ищите адрес вида `192.168.1.105` (не `127.0.0.1` — это localhost).

### Зайдите в проект на компьютере с телефона

1. Убедитесь, что телефон и компьютер подключены к одному Wi-Fi
2. Убедитесь, что проект запущен (например, `pnpm dev` на порту 3000)
3. Введите `http://192.168.x.x:3000` в браузере телефона (подставьте свой реальный IP)

Если всё гладко, вы увидите проект на телефоне. Можно тестировать тач-жесты, проверять адаптивные раскладки и верифицировать мобильный интерактивный опыт — без деплоя и без лишних инструментов.

::: tip Адрес привязки Next.js
Некоторые фреймворки по умолчанию слушают только `127.0.0.1` (localhost) и не принимают запросы от других устройств локальной сети. Если телефон не может зайти, попробуйте указать в команде запуска слушать на всех сетевых интерфейсах:

```bash
# Next.js
pnpm dev --hostname 0.0.0.0

# Vite
pnpm dev --host
```

`0.0.0.0` значит «принимать запросы с любого сетевого интерфейса», включая локальную сеть.
:::

## Firewall: почему телефон всё ещё не открывает?

Сяомин следовал шагам, но телефон показывал «Unable to connect».

В 90% случаев это **firewall** блокирует.

Firewall защищает компьютер от свободного доступа других устройств локальной сети. Это как режим «Не беспокоить» на телефоне: не то чтобы звонков нет — вы просто решили их блокировать.

Когда вы запускаете `pnpm dev`, Node.js слушает запросы на порту 3000. Но firewall может не разрешать внешним устройствам доступ к этому порту — запрос телефона останавливается у двери.

Порядок разбора:

1. **Убедитесь, что телефон и компьютер на одном Wi-Fi** (звучит очевидно, но это самое частое упущение)
2. **Убедитесь, что dev-сервер слушает на `0.0.0.0`** (см. tip выше)
3. **Проверьте настройки firewall** — финальное и самое частое препятствие

### Пусть AI поможет разобрать

Конфигурация firewall различается по ОС, и вручную легко ошибиться. Просто скажите Claude Code:

> «Мой телефон и компьютер подключены к одному Wi-Fi, но с телефона не открывается IP моего компьютера. Помоги проверить настройки firewall и разрешить порт 3000 для Node.js».

Claude Code сгенерирует подходящие команды под вашу ОС.

::: details Пример: разрешение в Windows Firewall

```powershell
# Разрешить входящий TCP-трафик на порт 3000
New-NetFirewallRule -DisplayName "Node.js Dev Server" -Direction Inbound -Protocol TCP -LocalPort 3000 -Action Allow
```

:::

::: details Разрешение в macOS Firewall

Управление firewall в macOS по умолчанию построено на приложениях. В «System Settings → Network → Firewall → Options» убедитесь, что Node.js разрешено принимать входящие соединения.

:::

::: tip Не забудьте вернуть как было
Завершив real-device-отладку, хорошо бы отключить это firewall-правило. Долго держать dev-порты открытыми в локальной сети — не лучшая привычка.
:::

## Глобальная сеть: другой Wi-Fi — и до вас не достучаться

Сяомин наладил отладку на телефоне. Но его друг в другом городе, подключён к другому Wi-Fi. Локальный IP `192.168.x.x` валиден только внутри сети вашего роутера. Сеть друга никак не найдёт этот адрес.

Здесь вступает **глобальная сеть (WAN)** — собственно интернет.

Чтобы люди из других сетей могли получать ваш сервис, нужен **публичный IP**. Но у обычного домашнего широкополосного интернета обычно нет независимого публичного IP. Провайдеры используют технологию NAT, позволяющую многим юзерам делить один публичный IP.

Аналогия: публичный IP — как адрес многоквартирного дома на улице. Курьер доезжает только до парадной внизу (публичный IP провайдера), но не до двери вашей квартиры (вашего устройства). Ваш компьютер спрятан за NAT провайдера — внешние запросы его не найдут.

Проверьте сами: поищите в браузере «мой IP» — увиденный публичный IP будет полностью отличаться от локального IP из `ipconfig`. Публичный IP назначается провайдером вашему домашнему роутеру (и может делиться несколькими домохозяйствами), а локальный IP назначается роутером вашему компьютеру.

Так что, чтобы люди из интернета получали доступ к проекту, нужно деплоить код на сервер с публичным IP. Это тема главы 12.

## Три пути: от «вижу только я» к «видят другие»

Сяомин разложил всю картину. Если вы хотите, чтобы другие увидели проект, есть три пути, каждый под свой сценарий:

### 1. Прямой доступ по LAN

**Лучше всего для**: тестирования на собственном телефоне или чтобы друг рядом быстро глянул.

**Требование**: устройства на одном Wi-Fi.

**Как**: ввести в браузере телефона локальный IP компьютера + порт.

**Ограничение**: перестаёт работать, как только вы уходите с этого Wi-Fi.

### 2. Туннелирование

**Лучше всего для**: друг в другом городе, и вы хотите временно дать ему посмотреть без полного процесса деплоя.

**Как**: инструментом создать туннель между компьютером и публичным сервером, получив временную ссылку.

**Ограничение**: ссылка меняется каждый раз, компьютер должен оставаться включённым, скорость может плавать.

Следующий раздел расскажет, как именно это делается.

### 3. Формальный деплой

**Лучше всего для**: чтобы любой мог пользоваться продуктом в любое время.

**Как**: деплоить код на платформы вроде Vercel или Tencent Cloud и получить стабильный публичный URL.

**Пререквизит**: сначала код в Git (глава 11), потом деплой (глава 12).
