# 11.1 Зачем нужен Git

> **Цель раздела**: понять ключевую ценность Git — какую проблему он решает и почему вы, возможно, уже им пользуетесь.

---

## Дилемма «финальной версии»

Вы точно переживали этот сценарий.

Пишете дипломную — и на рабочем столе появляются файлы вроде:

```
thesis.docx
thesis-revised.docx
thesis-final.docx
thesis-final2.docx
thesis-final-final.docx
thesis-advisor-wants-changes.docx
```

Презентации, правки дизайнов, написание предложений — любая работа с «многократными ревизиями» ведёт к инстинктивной маркировке версий именами файлов. Метод работает, но проблемы очевидны: какой из них последний? Имена файлов врут. Нужно вернуться к версии трёхдневной давности? Возможно, уже перезаписана. Что именно изменилось между версиями? Сравнивать вручную. Несколько человек правят один файл? Полный хаос.

Вы можете думать: «У меня хорошая память, я знаю, какой свежий». Но этой уверенности обычно хватает дня на три. Что вы меняли три дня назад, зачем, как это выглядело до — у этих деталей в мозге очень короткий срок хранения. Имена файлов несут крайне ограниченную информацию. Чем именно «final2» отличается от «final»? Придётся открыть оба файла и сверять построчно.

А когда действительно нужно вернуться к исторической версии — например, научрук говорит «версия прошлой недели была лучше», — вы обнаружите: версия прошлой недели, возможно, уже перезаписана, или вы вообще не уверены, какой файл соответствует состоянию прошлой недели.

При написании дипломной эти проблемы терпимы — файлов всего несколько, десяток страниц максимум. С кодом всё совсем иначе.

У web-проекта могут быть сотни файлов, и изменение одной фичи может затронуть согласованную правку дюжины файлов. Добавление поиска на главную может потребовать изменений в компонентах страницы, API-эндпоинтах, конфигурации роутов и файлах стилей. Управлять версиями именами файлов? Пришлось бы копировать всю папку проекта. Сравнивать различия руками? С сотнями файлов — сколько времени это займёт?

Хуже: файлы кода имеют зависимости — файл A вызывает функцию файла B, файл B читает конфиг из файла C. Один файл не откатить — нужно вернуть все связанные файлы в одну точку времени, иначе программа не запустится.

У Сяомина однажды в каталоге проекта лежали папки `project-backup`, `project-v2` и `project-works`. Он день кодил, понял, что идёт в неверном направлении, и захотел вернуться ко вчерашнему состоянию — но вчерашний код уже был перезаписан сегодняшним.

Ещё хуже: он не был уверен, как именно выглядело «вчерашнее состояние» — ведь он не записывал каждый шаг изменений, помня только «вчера работало, сегодня нет». Он попытался восстановить вчерашний код по памяти, потратил два часа — и внёс новые баги. Будь у него инструмент, записывающий каждое состояние, как game save, он мог бы просто «load game» для возврата ко вчера — вместо ручной реконструкции по памяти.

Это и есть проблема, которую решает Git: **надёжный способ записывать каждую модификацию, позволяющий в любой момент вернуться к любой исторической версии**.

Никакой маркировки версий именами, никакого ручного копирования для бэкапа, никакого ручного сравнения различий. Git помнит всё это за вас. Он записывает не «определённую версию определённого файла», а «полный снапшот всего проекта в определённый момент времени» — состояние всех файлов сохраняется вместе и откатывается вместе, исключая рассинхрон «файл A вернулся ко вчера, а файл B всё ещё сегодняшний».

## Вы, возможно, уже используете Git

Интересный факт: если вы шли по этой книге и разрабатывали проекты с Claude Code, в каталоге вашего проекта, скорее всего, уже есть папка `.git`.

При создании нового проекта Claude Code обычно автоматически запускает `git init` для инициализации репозитория и помогает коммитить код в процессе разработки. Иными словами, вы всё время использовали Git — просто не осознавали.

Откройте терминал, перейдите в каталог проекта и выполните `git log --oneline -5`. Увидите серию записей коммитов — вот и всё: Claude Code всё это время «сейвил вашу игру». Само это открытие — момент прозрения: **инструментом, которым вы давно пользуетесь, пора понять**.

Это как функция автобэкапа телефона: фото синхронизируются в облако по умолчанию, но вы никогда не открывали облачный альбом. Однажды телефон ломается — и вы обнаруживаете: все фото в облаке, ни одно не потеряно. Git делает похожее для вашего кода, только записывает не «последнюю версию», а полную историю каждой модификации.

Если в проекте ещё нет Git-репозитория — не проблема: просто попросите Claude Code инициализировать. Пользователям Windows: `.git` — скрытая папка; если её не видно в Проводнике, выполните `git status` — есть вывод, значит репозиторий существует.

## Commit: сохраните свой код

Ключевая операция Git — **commit**. Каждый commit как ручной сейв в игре: записывает текущее состояние всех файлов с описанием и меткой времени. Save — это commit, load — rollback, список сейвов — `git log`.

В отличие от игровых сейвов, сейвы Git **инкрементальны**: записываются только изменённые части, не весь проект. У проекта могут быть сотни коммитов, но папка `.git` обычно занимает десятки МБ — куда меньше, чем копировать сотни папок проекта. Поэтому можно коммитить часто, не переживая за место.

В этом Git превосходит «копирование папок»: полная история при минимальной стоимости хранения.

Сяомин поручил Claude Code коммитить код. Ему не нужно помнить синтаксис `git add` и `git commit` — достаточно сказать AI «закоммить это» после завершения фичи или починки бага. Claude Code автоматически стейджит изменения, генерирует commit message и завершает commit. Для Сяомина весь процесс — одно предложение, но за кулисами Git сохраняет полный снапшот проекта, к которому можно вернуться в любой момент.

Когда коммитить? Жёсткого правила нет, но простая рекомендация: **когда завершено что-то, «описываемое одним предложением», — стоит закоммитить**.

Например: «добавил компонент рейтингов», «починил баг пустого поиска», «подправил раскладку главной». Не накапливайте изменения за день и не коммитьте всё разом — откат станет слишком грубым, как сейвы только на «уровне 1» и «финальном уровне», с потерей всего между. Представьте сложный уровень игры без сейва посередине: умерли — начинаете заново. Вы бы ругали себя за редкие сейвы. С кодом так же.

## Модель трёх зон: где ваши изменения

Git управляет кодом в трёх областях. Понимание помогает ответить на ключевой вопрос: **«где мои изменения прямо сейчас?»**

<GitFlowDiagram />

Аналогия: **рабочий каталог** — ваш стол: файлы разложены, вы активно правите. **Staging area** — аккуратно сложенная стопка бумаг: «вот это я подаю». **Локальный репозиторий** — архивный шкаф: поданное хранится навсегда. Вы черкаете на столе (рабочий каталог), удовлетворившись — собираете бумаги в стопку рядом (staging area), наконец кладёте стопку в шкаф (локальный репозиторий). Три шага соответствуют «правка файлов → git add → git commit».

В повседневной разработке эти шаги за вас делает Claude Code — вручную запускать `git add` и `git commit` не нужно. Но при путанице вроде «куда делись мои изменения» или «почему этого файла нет в коммите» модель трёх зон помогает локализовать проблему.

Файлы изменены, но `git status` показывает «not staged» — изменения всё ещё в рабочем каталоге, не `add`нуты. `add`нуты, но не `commit`чены — изменения в staging area, ещё не сохранены. `commit`чены, но не запушены — сейв локальный, ещё не синхронизирован с облаком — об этом следующий раздел.

Команды запоминать не нужно. Важно построить ментальную модель: изменения стартуют в рабочем каталоге, проходят staging area и наконец попадают в локальный репозиторий. Каждый шаг контролируем — в любой момент можно спросить Claude Code «на какой стадии мои изменения».

Как взглянуть на зарядку телефона перед выходом: не всегда нужно зарядить, но проверка даёт спокойствие. `git status` — тот самый взгляд: он говорит, какие файлы изменены, но не застейджены, какие застейджены, но не закоммичены, и на какой вы ветке. Claude Code обычно проверяет статус автоматически перед Git-операциями, но в замешательстве знание, что инструмент существует, помогает локализовать проблемы.

## Rollback: безграничный Ctrl+Z

Когда вы делаете Ctrl+Z, есть неявное ограничение: **закрыли файл и открыли снова — Ctrl+Z больше не работает**. Он отменяет операции только текущей сессии редактирования. Правили файл в VS Code, сохранили, закрыли, открыли на следующий день — Ctrl+Z не вернёт назад. Не говоря о состоянии трёхдневной или недельной давности. У Git этого ограничения нет: пока вы закоммитили, вы можете вернуться в ту точку времени — даже версия месячной давности. Это Ctrl+Z без срока годности и с безграничными слоями.

Три частых сценария отката — три разных подхода.

**Правил какое-то время, понял, что направление неверное, ещё не коммитил.** Простейший случай. Скажите Claude Code, изменения каких файлов хотите отменить, — и он восстановит их до последнего закоммиченного состояния. Изменения рабочего каталога отбрасываются; staging area и локальный репозиторий не затронуты. Как почеркать на столе, потом смять черновик и выбросить — архив в шкафу остаётся нетронутым. Операция безрисковая: вы отбрасываете только несохранённые черновики.

**Уже закоммитил, хочу вернуться к предыдущей версии.** Скажите Claude Code «верни к последней работающей версии». Он использует `git reset`, сдвигая указатель локального репозитория назад. Это переписывает историю коммитов — «неверный коммит» исчезает из истории. Если код не запушен на remote, это чистейший подход: как вытащить из шкафа последний лист и порвать, сделав вид, что его не существовало. Но учтите: порванный лист исчезает по-настоящему — захотев позже контент того коммита, вернуть его не сможете. Поэтому перед reset убедитесь, что код вам действительно не нужен.

**Уже запушено на remote.** Тут нельзя просто «удалить» коммит: тиммейты, возможно, уже спулили ваш код. Удалите — их история разойдётся с вашей, сея путаницу. Правильный подход — `git revert`: он не удаляет историю, а создаёт новый коммит, «разворачивающий» изменения и отменяющий эффект той модификации. История ясно показывает «коммит 10 сделал X, коммит 11 отменил X». Это как ошибочная запись в бухгалтерской книге: не замазывать корректором, а написать следующей строкой «сторно». Оригинальная запись остаётся, итог верен.

Сяомин столкнулся именно с этим. Он полдня добавлял сложный алгоритм сортировки в фичу рекомендаций, закоммитил и запушил. На следующий день обнаружил фундаментальные изъяны логики — всё направление было неверным. Он сказал Claude Code «верни к состоянию до добавления алгоритма сортировки». Claude Code через `revert` создал новый коммит, чисто отменив модификацию, не задев тиммейтов при их следующем pull.

Ключевой инсайт Git-отката: **осознание, что можно вернуться**. Первая реакция многих при поломке кода — продолжать чинить, делая всё хуже. Зная, что Git вернёт к любой исторической версии в любой момент, вы смеете экспериментировать смело: сломалось — откатились, не страшно.

## Просмотр истории: что реально изменил AI?

При разработке с Claude Code AI часто модифицирует файлы. Иногда хочется знать «что именно он только что поменял» или «как выглядел вчерашний код». История коммитов Git — ваш ответ. Каждая запись содержит: кто, когда, какие файлы менял и какие именно строки в каждом файле.

Различия между `git log`, `git diff` и `git show` помнить не нужно. Скажите Claude Code, что хотите увидеть — «что менялось недавно», «что было в последнем коммите», «история изменений этого файла» — и он подберёт подходящую команду и объяснит результат.

Особенно полезно в AI-программировании. Иногда Claude Code меняет несколько файлов разом, и вы хотите проверить корректность: беглый взгляд на diff куда быстрее перечитывания целых файлов. Вы наверняка пользовались «Рецензированием» в Word: удалённый текст зачёркнут красным, новый — синим. Diff — то же для кода: зелёное — добавленные строки, красное — удалённые, всё видно с одного взгляда. Привычка «проверять diff после изменений» помогает лучше понимать, что сделал AI, и рано ловить неожиданные модификации.

У просмотра истории есть и менее очевидное, но важное применение: **понимание того, как код эволюционировал**. Видя кусок кода и не понимая, почему он так написан, загляните в историю коммитов файла — ответ часто там. Возможно, три коммита назад код был проще и стал таким для починки бага. Commit message может гласить «fix: handle null pointer exception when user not logged in» — и вы сразу понимаете, от чего защищает эта кажущаяся избыточной проверка. Сам код говорит «что», история коммитов — «почему».

## Commit messages: улики для себя будущего

Называя папки, вы пишете «2024-налоговые-счета», а не «Новая папка (3)». Commit messages следуют тому же принципу: их читаете вы сами будущий (и ваши коллабораторы).

Хорошие commit messages следуют простому формату: префикс типа + краткое описание. `feat: add movie rating feature` — новая фича, `fix: fix empty search results issue` — починка бага, `docs: update API documentation` — изменения документации, `refactor: refactor user authentication module` — рефакторинг. Другие частые: `style` (правки стилей) и `chore` (рутинные задачи вроде апгрейда зависимостей).

Это не жёсткое правило, а конвенция, делающая историю коммитов **сканируемой**. Просматривая десятки записей, префиксы помогают мгновенно находить «где тот коммит, добавлявший фичу рейтингов». История без префиксов — куча папок без наклеек: чтобы узнать содержимое, открывать каждую. Представьте почтовый ящик: если каждая тема — «обновление» или «правка», сколько займёт поиск конкретного письма? А темы «[Возмещение] Мартовские командировочные» или «[Встреча] Пятничное продуктовое ревью» находятся с первого взгляда.

Claude Code обычно генерирует стандартные commit messages автоматически, помогая вам коммитить. Он анализирует, какие файлы и что вы поменяли, и генерирует точное описание. Большую часть времени его тексты достаточно хороши. Если описание кажется неточным — например, написал «update components», а вы хотите конкретики, — попросите скорректировать. Хорошему commit message не нужно быть длинным: одного предложения, чётко говорящего «что сделано», достаточно.
