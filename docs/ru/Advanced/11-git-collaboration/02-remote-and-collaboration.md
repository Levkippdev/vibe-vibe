# 11.2 Пушим в облако, начинаем коллаборацию

> **Цель раздела**: понять ценность remote-репозиториев, запушить код на GitHub, дать другу склонировать и разрешать конфликты и security-вопросы коллаборации.

---

## Все яйца в одной корзине

Код Сяомина существует только на его компьютере. Это значит: умер диск — код ушёл; украли компьютер — код ушёл; слетела система и требуется переустановка — код ушёл. Техническим языком это называется **Single Point of Failure**: вся система зависит от одного узла, и когда узел падает, всё обнуляется.

Вы наверняка испытывали похожую тревогу — потерять телефон со всеми фото. Или хотя бы слышали чужие страшные истории. Сейчас люди синхронизируют фото с облачными альбомами, и логика та же: **важное не должно существовать только в одном месте**. Вы не держите все деньги в одном кармане, не прячете единственный ключ под ковриком — и ваш код не должен жить на одном диске.

Помните главу 6? Вы разместили базу в облаке Neon, а не локально. Причина: локальная база исчезает при переустановке системы, облачная — нет. Код следует той же логике: запушьте в облако, не зависите от одного устройства. «Облачный альбом» для кода называется **платформой хостинга кода**, самый мейнстрим — GitHub; Gitee и CNB быстрее из Китая.

Помимо бэкапа, remote-репозитории решают ещё одну проблему: **коллаборацию**. Друг Сяомина хочет контрибьютить, но код на компьютере Сяомина — друг не достанет. Отправить zip? Предисловие уже показало, куда это ведёт: два человека правят один файл, потом мучительно сверяют построчно в WeChat. С GitHub Сяомин пушит код наверх, друг спулит с GitHub — оба разрабатывают независимо, оставаясь в синке. GitHub работает «перевалочной станцией» посередине, гарантируя, что обе стороны видят одну и ту же версию одной кодовой базы.

## Выбор платформы и регистрация

GitHub — международный стандарт с богатейшей экосистемой, первый выбор open source-проектов. Gitee быстрее из Китая с русским— нет, с китайским интерфейсом. CNB — более новая отечественная платформа с хорошими скоростями доступа. Подойдёт любая — эта глава использует GitHub как пример, но остальные платформы работают похоже. Если GitHub из вашей точки в Китае медленный, начните с Gitee или CNB, мигрируете позже.

Если у вас ещё нет аккаунта GitHub, зайдите на [github.com](https://github.com) и зарегистрируйтесь. Процесс как на любом сайте: email, username, пароль. Ваш username появится в URL репозитория (вроде `github.com/your-username/project-name`) — выбирайте тот, о котором не пожалеете.

## SSH-аутентификация: настройте раз — навсегда без паролей

Зарегистрировав аккаунт GitHub, установите доверие между компьютером и GitHub. GitHub отключил логин по паролю для терминального доступа — пуши вводом username и пароля, как на сайте, не работают. Вместо этого используется **SSH-ключ аутентификации**.

SSH-ключи — по сути замок и ключ. **Публичный ключ** — замочная скважина, размещается на GitHub, сообщая: «обладатель этого ключа — я». **Приватный ключ** — сам ключ, хранится на компьютере, доказывая: «я тот, за кого себя выдаю».

Каждый пуш на GitHub сопровождается сверкой приватного ключа с публичным: личность подтверждена — проходите. Весь процесс происходит автоматически, вы его не чувствуете, как разблокировку телефона пальцем без ввода пароля каждый раз.

Настройка разовая. Скажите Claude Code, что хотите настроить SSH для GitHub, — он сгенерирует пару ключей (если её нет), затем покажет содержимое публичного ключа. Скопируйте его на страницу GitHub Settings → SSH and GPG keys, протестируйте соединение — готово.

С этого дня каждый push и pull — без кредов. Как замок на входной двери: установили раз — дальше просто носите ключ с собой, не переустанавливая замок. Вся настройка может потребовать несколько переключений между сайтом GitHub и терминалом, но делается один раз.

Если SSH-настройка встретит трудности (например, корпоративная сеть блокирует SSH-порты), фоллбеком служит HTTPS + Personal Access Token. В GitHub Settings → Developer settings → Personal access tokens сгенерируйте Token — это не заданный вами пароль, а временный пропуск, выданный платформой. Используйте Token вместо пароля при пуше. Однако SSH — рекомендуемое долгосрочное решение: Token'ы истекают, SSH-ключи — нет. И Token нужно где-то хранить: забыли где — регенерируйте. SSH-ключи живут в фиксированном месте на компьютере, ничего запоминать не нужно.

## Первый пуш

SSH настроен — теперь пушим код на GitHub.

Сяомин говорит Claude Code: «Создай репозиторий на GitHub и запушь мой проект». Claude Code помогает создать remote-репозиторий, связать локальный и запушить код. При первом пуше выполняются команды, похожие на эти (запоминать не нужно, просто понять):

```bash
git remote add origin git@github.com:xiaoming/personal-douban.git
git push -u origin main
```

`origin` — ник, который вы даёте remote-репозиторию: как записать адрес GitHub в контакты телефона под именем «origin», чтобы пушить и спулить по нику, не набирая полный адрес каждый раз. `-u` делает ник контактом по умолчанию: в следующий раз просто жмёте «вызов». Команды запоминать не нужно — Claude Code всё делает. Но знание, что они существуют, помогает понимать, что происходит в терминале, не ослепнув от потока вывода команд.

После пуша откройте страницу репозитория GitHub — здесь все файлы проекта, идентичные локальной копии. Если есть README.md, он автоматически рендерится под списком файлов. Клик по «commits» показывает всю историю — то же, что локальный `git log`, только в браузере. Ваш код теперь существует в двух местах: локально и на GitHub. Смерть диска больше не страшна.

![GitHub repository page showing pushed project files](/images/Advanced/image-20260227003017220.png)

При создании репозитория можно выбрать Public или Private. Для личных проектов рекомендуется Private — коду необязательно быть видимым миру. Позже, захотев open source, поменяете на Public.

## Push и pull: оставаясь в синке

С кодом на GitHub повседневный ритм разработки: вы правите код локально, коммитите и **push'ите** для синка с GitHub; другие пушат новый код на GitHub, и вы **pull'ите** обновления к себе.

Это как два человека, правящие документ каждый на своём компьютере и периодически синкащиеся в общий облачный диск. Облако (GitHub) — перевалочная станция, гарантирующая всем одну и ту же последнюю версию.

Отношения push и pull просты: push — «я закончил, выгружаю»; pull — «кто-то обновил, скачиваю». Два направления — вверх и вниз, GitHub посередине. Постоянно синкаться не нужно: Git спроектирован для свободной локальной разработки с синком по вашему выбору. Это отличается от реального времени Google Docs; Git даёт больше автономии — ценой ручного триггера синков.

Claude Code коммитит код в процессе разработки, но push обычно требует вашего активного действия — пуш на remote это «публикация», и вы, возможно, захотите накопить несколько коммитов перед ней.

Хорошая привычка: **делайте push после завершения каждого этапа работы**. Не нужно пушить каждый коммит, но и не затягивайте: откажет компьютер — незапушенные коммиты потеряны. Представьте: пишете документ весь день без сохранения в облако, а вечером — синий экран. Дважды это переживать не хочется.

## Clone: первое получение кода другом

Сяомин отправляет другу ссылку на GitHub-репозиторий. Для первого раза друг использует **clone**.

Чем clone отличается от «скачать zip»? Zip даёт текущие файлы; clone даёт **весь проект плюс всю историю коммитов**. Склонированный каталог содержит папку `.git`, готовую к push и pull, — это полная копия Git-репозитория, а не просто груда файлов.

Поэтому рассылка zip в предисловии и была ненадёжной: у zip нет истории версий, информации о ветках, связи с remote-репозиторием — только изолированные файлы. Получив zip и поменяв код, друг для обратной синхронизации мог снова зиповать и отправлять, потом сверять построчно в WeChat. Clone за один раз устанавливает двусторонний канал; все будущие синки — через push и pull.

После клонирования другу нужно установить зависимости проекта. Для Node.js-проектов это `npm install` (или `pnpm install`) в каталоге проекта.

Поэтому `node_modules` не нужно коммитить в репозиторий: каждый устанавливает сам после клона, а пакеты зависимостей могут компилировать разные бинарные файлы на разных системах. Файл `.node`, скомпилированный на Windows, не запустится на Mac. `package.json` записывает, какие зависимости нужны, а `npm install` скачивает их автоматически — как отношение рецепта и ингредиентов. Вы делитесь рецептом (`package.json`), не пересылая ингредиенты почтой (`node_modules`).

По умолчанию пушить может только создатель репозитория. Сяомину нужно пригласить друга в GitHub Settings → Collaborators; после принятия приглашения друг сможет пушить. Приглашённый — оба разрабатывают независимо.

<PushPullSync />

Сяомин и друг разрабатывают раздельно, в основном без проблем: ты правишь свои файлы, я свои — Git мержит автоматически. При мерже Git очень умён: двое правят разные файлы — просто совмещает оба изменения; правят один файл в разных местах — тоже разрулит. Только когда двое правят одну и ту же строку одного файла, Git «поднимает руки» — он не знает, чью версию оставить.

## Конфликты: двое отредактировали одну строку

Сяомин и друг попали ровно в это. Сяомин поменял максимум рейтинга фильма с 5 на 10; друг — с 5 на 100. Оба закоммитили; Сяомин успел запушить первым, а у друга push отклонили — Git сказал: «remote обновлён, сначала pull».

<ConflictResolution />

Друг делает pull, и Git находит две разные правки одной строки. Не зная, чью слушать, он помечает файл в формате «множественного выбора», предлагая решить, какую версию оставить:

```
<<<<<<< HEAD
const MAX_SCORE = 100  // правка друга (текущая ветка)
=======
const MAX_SCORE = 10   // правка Сяомина (remote-ветка)
>>>>>>> origin/main
```

Между `<<<<<<< HEAD` и `=======` — ваша локальная версия; между `=======` и `>>>>>>> origin/main` — remote-версия. Вы решаете, какую оставить (или обе, или пишете совсем новую), затем удаляете маркеры.

Если вы пользовались Google Docs или Feishu, видели индикаторы реального времени «кто-то редактирует». У Git таких уведомлений нет — он обнаруживает конфликты только при синке кода. Это не изъян Git, а его философия: **каждый свободно разрабатывает локально, разногласия решаются в момент синка**.

При конфликте без паники. Скажите Claude Code «помоги разрешить конфликт», поясните, какую логику оставить (или обе) — он всё смержит. Затем commit и push — конфликт закрыт.

На практике конфликты в маленьких командах нечасты. Большую часть времени люди правят разные файлы, и Git мержит автоматически, вы даже не замечаете. Конфликт возникает, только когда двое случайно правят один и тот же кусок одного файла.

Так что не избегайте коллаборации из «страха конфликтов» — конфликты нормальны и несложно решаются. Самый эффективный способ снижения конфликтов — **чёткое разделение труда**: ты — frontend-страницы, друг — backend-API, каждый правит свои файлы, конфликты естественно убывают. Механизм «ветвления» из следующего раздела ещё сильнее изолирует работу каждого.

## .gitignore: список уборки перед сборами

При первом пуше Сяомин запушил и `node_modules`. Друг склонировал и обнаружил: репозиторий весит 500 МБ — 490 из которых `node_modules`.

Это как отправить другу zip с горой системных временных файлов, кэшей и мусора из корзины. `.gitignore` — «список уборки перед сборами»: файлы и папки в нём автоматически игнорируются Git'ом и не коммитятся в репозиторий.

Типичный `.gitignore` должен исключать: `node_modules/` — пакеты зависимостей, огромные (сотни МБ — норма), друг после клона сделает `npm install` сам; `.env` и `.env.local` — файлы переменных окружения с вашими API-ключами и паролями баз, подробнее ниже; `.DS_Store` и `Thumbs.db` — скрытые файлы, автоматически генерируемые macOS и Windows, проекту бесполезные; `dist/`, `.next/`, `build/` — артефакты сборки, восстанавливаемые из исходников, хранить в репозитории незачем.

Claude Code обычно автогенерирует `.gitignore` при инициализации проектов. Если в репозитории оказались лишние файлы — попросите помочь вычистить и обновить `.gitignore`. Тут лёгкая ловушка: если `node_modules` уже закоммичен, простое добавление строки в `.gitignore` не поможет — он влияет только на **неотслеживаемые** файлы. Уже отслеживаемое Git продолжает отслеживать. Сначала уберите из репозитория (сохранив локально), потом коммитьте. Скажите Claude Code «удали node_modules из Git-репозитория, сохранив локальные файлы, и добавь в .gitignore» — он использует `git rm --cached`: как убрать книгу из реестра выдач библиотеки, оставив её у вас в руках. Git больше не отслеживает папку, локальные файлы не тронуты.

## Security-предупреждение: что коммитить категорически нельзя

Большинство исключений `.gitignore` — просто «незачем коммитить». Но одна категория — **строго запрещена к коммиту**: не из-за размера, а потому что закоммитить её — как повесить ключи на общедоску.

Однажды попав в историю Git, они остаются там, даже если позже удалить файл, — Git спроектирован «помнить всё». Вы добавили `.env` в третьем коммите, удалили в четвёртом — но любой, открыв третий коммит, всё ещё видит ваши API-ключи. Это не баг Git, а ключевая фича — полная история. Кроме этого сценария, где фича становится security-риском.

Публичный репозиторий виден каждому — включая случайно закоммиченные API-ключи. У GitHub есть специализированные краулеры, сканирующие публичные репозитории на API-ключи: найдя — используют. Даже в приватных репозиториях ключам не место в коде: вдруг позже сделаете публичным? Вдруг пригласите коллаборатора, которому не полностью доверяете?

Правильный подход — ключи в `.env`, а `.env` — в `.gitignore`. Глава 8 упоминала этот security-принцип; здесь он подчёркнут снова, потому что Git усугубляет проблему: утечка локального файла ограничена, а пуш на GitHub делает его видимым всему миру. Категорически нельзя коммитить: API-ключи и Access Token'ы (OpenAI, Stripe, ключи сторонних сервисов); строки подключения к базе (`DATABASE_URL` с паролями); файлы приватных ключей (`.pem`, `.key`, `id_rsa`); файлы переменных окружения (`.env`, `.env.local`, `.env.production`).

::: danger Что если чувствительное уже закоммичено
Если вы случайно закоммитили и запушили `.env` на GitHub, **простого удаления файла и нового коммита недостаточно** — история Git всё ещё содержит тот коммит, доступный каждому. Нужно полностью вычистить файл из истории Git. Скажите Claude Code «полностью удали файл .env из истории Git» — он использует `git filter-branch` или BFG Repo-Cleaner. Одновременно **немедленно ротируйте все утёкшие ключи**: идите на соответствующие платформы и регенерируйте API-ключи, инвалидировав старые. Не пропускайте этот шаг: вы не можете определить, не увидел ли кто-то ключи до очистки истории.
:::

Впервые открыв страницу репозитория GitHub, вы можете не понимать, на что смотрите. Краткий обзор частей, которыми будете пользоваться.

**Главная репозитория** — первая страница, вкладка Code. Сверху список файлов, идентичный локальному каталогу проекта; ниже — рендер README.md. Справа от списка — последний commit message и время для каждого файла. Страница особенно полезна для «что я менял на прошлой неделе» или «какой коммит внёс этот баг».

Наверху репозитория — вкладки **Issues** и **Pull Requests**. Issues трекают баги и задачи; Pull Request — для ревью и мержа кода (подробно в следующем разделе). Пока просто знайте, где они.

**Settings → Collaborators** — место приглашения друзей. Добавьте username друга GitHub; после принятия приглашения он сможет пушить.

## Первая коллаборация после присоединения друга

Сяомин пригласил друга; тот склонировал репозиторий, установил зависимости и запустил проект. Теперь нужно разделить труд.

Простое разделение: Сяомин продолжает оптимизировать рейтинги; друг занимается алгоритмом рекомендаций. Они правят разные файлы — конфликты редки. Повседневный ритм: pull перед стартом работы, чтобы получить свежий код друг друга; разработка раздельно, commit по завершении; push на GitHub, второй спулит.

Ритм поначалу непривычен: нужно помнить про pull до работы и push после. Но за пару дней это мышечная память, как проверка «телефон, ключи, кошелёк» перед выходом. Забыли pull перед правками — не страшно: при push Git напомнит «remote обновлён, сначала pull», вы спулите и смержите.

Цикл «pull → разработка → commit → push» — базовый ритм Git-коллаборации. Простой, прямой, работает для двоих. Но с ростом сложности проекта Сяомин открывает новую проблему: он хочет попробовать смелую новую фичу, но боится сломать существующий код. Следующий раздел вводит «ветвление», делающее этот ритм безопаснее и организованнее.

---

::: tip Ключевые выводы раздела
Запушите код на GitHub — и получите облачный бэкап и фундамент коллаборации. SSH — разовая настройка; push/pull — ежедневные синки; clone — способ первого получения кода другом. Конфликты не страшны — это просто Git говорит «здесь я не уверен, реши ты». Важнейшее security-правило: ключи и пароли никогда не должны появляться в Git-репозиториях.
:::
