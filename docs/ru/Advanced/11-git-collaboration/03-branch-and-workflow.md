# 11.3 Ветки, PR и командные воркфлоу

> **Цель раздела**: понять ценность веток, освоить воркфлоу Pull Request и установить повседневный ритм совместной разработки.

---

## Инстинкт «сначала скопируй, потом меняй»

Сяомин хочет добавить фичу рекомендаций «Вам может понравиться» в «Личный Douban». Но колеблется: система рейтингов наконец-то работает гладко, и он боится, что ковыряние рекомендаций случайно сломает код рейтингов — и придётся тратить время на починку.

Первая реакция: скопировать всю папку проекта и экспериментировать в копии. Получится — заменить оригинал копией; сломается — просто удалить копию.

У вас, вероятно, был тот же инстинкт: хочется попробовать новое, но страшно сломать работающее — сначала копия. Рассуждение здравое — примитивно только исполнение. У Git для этого есть более элегантный механизм: **ветки**.

---

## Ветки: версия Git для «копирования папки»

Ветка — по сути «сначала скопируй, потом меняй», но куда изощрённее дублирования папок. Файлы реально не копируются: Git записывает только различия, поэтому создание ветки почти не занимает места. Переключаться между «оригиналом» и «копией» можно в любой момент, а изменения мержатся обратно точно тогда, когда готовы, — без замены целых папок.

Проблема копирования папок: в копии вы поменяли 10 файлов, кто-то другой починил срочный баг в 3 файлах оригинала, и теперь хотите влить свои изменения — вручную сравнить 13 файлов, ничего не упустив и не перезаписав. Ветки Git автоматизируют это.

Проект начинается с дефолтной основной ветки, обычно `main` (в старых репозиториях `master`). Она означает «текущая стабильная, работающая версия». Разрабатывая новую фичу, создайте ветку от `main` — например, `feature/recommend` — и экспериментируйте свободно. Сломали? Вернулись на `main` — всё как было. Закончили? Влили в `main` — фича в продакшене.

Думайте о `main` как об «официальном релизе», а о фича-ветках — как о «черновых тетрадях»: в черновиках можно черкать сколько угодно, не затрагивая официальный релиз, пока не удовлетворитесь и не перепишете набело.

<BranchDiagram />

Когда Сяомин говорит Claude Code «создай ветку для разработки фичи рекомендаций», Claude Code создаёт и переключается на `feature/recommend`. С этого момента все изменения Сяомина — на этой ветке; `main` не тронут. Имена веток обычно `feature/xxx` для новых фич, `fix/xxx` для багфиксов, `refactor/xxx` для рефакторинга — не обязательно, но помогает вам и коллабораторам мгновенно понимать назначение ветки.

## Полный веточный воркфлоу

Пройдём с Сяомином полный процесс. Это самый частый паттерн коллаборации на GitHub, называемый **GitHub Flow**. Как в готовке много школ, а домашней кухне хватает одного простого порядка — так и GitHub Flow — простейший паттерн. Дальше вы увидите всё, что в нём есть.

<BranchWorkflow />

Сяомин создаёт `feature/recommend` от `main` и начинает разработку алгоритма рекомендаций. С Claude Code он пишет логику, добавляет API-эндпоинты, правит frontend. Коммит после каждого маленького шага: «Добавить модель данных для алгоритма рекомендаций», «Реализовать логику рекомендаций на основе рейтингов», «Показать рекомендации на frontend».

В это же время друг работает над профилями юзеров в другой ветке `feature/user-profile`. Каждый работает независимо в своей ветке, не мешая. Сломанные рекомендации Сяомина не затрагивают страницу профиля друга; баги профиля друга не затрагивают рекомендации Сяомина. В этом ключевая ценность веток — **изоляция**.

В определённый момент Сяомин пушит ветку на GitHub. Две цели: облачный бэкап кода и видимость прогресса для друга. Даже при отказе компьютера Сяомина код на ветке не потеряется.

Почувствовав, что фича рекомендаций почти готова, но не желая мержить напрямую в `main` — сначала ревью друга — он создаёт **Pull Request (PR)** на GitHub.

---

## Pull Request: ревью перед мержем

Почему просто не влить ветку в `main`?

Вспомните написанные вами документы: как бы вы отнеслись к тому, что кто-то правил ваш основной текст, не показав вам? PR — это «я сделал изменения, пожалуйста, проверьте перед слиянием». Процесс «проверки» называется **Code Review** — критически важная командная практика предотвращения инцидентов.

Вы можете думать: «Нас всего двое — нужны ли такие формальности?» Да. Не потому, что важен сам процесс, а потому, что вторая пара глаз реально ловит то, чего вы не видите. После трёх дней погружения в детали реализации у вас выработались слепые зоны: логика кажется нормальной — а друг мгновенно замечает пропущенный edge case.

PR дают больше, чем «дополнительные глаза». Друг может поймать граничные условия или потенциальные баги — например, алгоритм не обрабатывает юзеров без истории оценок. Ревьюя ваш код, он заодно изучает, как фича устроена, — происходит шаринг знаний: однажды Сяомин будет недоступен, а друг сможет поддерживать фичу, ведь он уже читал код на ревью.

Все обсуждения этого кода живут на странице PR, прослеживаемые позже для «почему это написано так». Через три месяца, встретив непонятный код, можно открыть обсуждение PR за ответом.

Для личных проектов PR тоже добавляют ценность: «пауза и рефлексия» перед мержем. После дней непрерывной разработки diff-вью PR помогает охватить изменения целиком, ловя проблемы, потерянные в деталях. Перед сабмитом можно попросить Claude Code провести self-review: проверить логические ошибки, security-риски, проблемы производительности. Это даёт более качественный код на ревью друга — и большее желание помогать.

Друг открывает страницу PR: какие файлы изменены и какие именно строки в каждом. Может комментировать конкретные строки: «Этот алгоритм рекомендаций не обрабатывает юзеров без истории оценок». Сяомин видит коммент, правит код, пушит снова. PR обновляется автоматически; друг видит новые изменения. Пинг-понг может продолжаться несколько раундов: вопросы — правки — повторное ревью — пока оба не удовлетворены. Это не потраченное время, а улучшение качества кода. Многие баги ловятся здесь, а не юзерами после деплоя.

<!-- 📸 Screenshot placeholder: GitHub PR page showing code diff and inline comments -->

Друг подтверждает: всё выглядит хорошо — кликает **Merge pull request**. Код фичи рекомендаций вливается в `main` и выходит в свет. После мержа GitHub спрашивает, удалить ли ветку. Кликните **Delete branch** — ветка послужила, все её изменения теперь в `main`. Не бойтесь удалять: ветки дешёвые и одноразовые. Страница PR сохраняет все изменения кода и историю обсуждений даже после удаления ветки. Позже, для «как была реализована фича рекомендаций», откройте этот PR.

![image-20260227003046255](/images/Advanced/image-20260227003046255.png)

Полная диаграмма флоу:

```
main ──────────────────────────────────────── main (включая рекомендации)
  │                                            ↑
  └── feature/recommend ──→ Разработка ──→ PR ──→ Ревью ──→ Merge
```

## Экскурсия по странице GitHub PR

Создаёте PR впервые — вот что нужно знать о странице.

![image-20260227003217565](/images/Advanced/image-20260227003217565.png)

![image-20260227003224983](/images/Advanced/image-20260227003224983.png)

При создании PR вы заполняете заголовок (краткое описание, что делает PR) и описание (подробное, что и зачем менялось), затем выбираете, в какую ветку мержить (обычно `main`). Заголовки делайте ясными: «Добавить фичу рекомендаций на основе рейтингов». Описания — подробнее: какие модули менялись, почему выбран этот подход, известные ограничения. Хорошее описание PR помогает ревьюеру быстрее понять намерение, повышая эффективность ревью. Можно поручить PR и Claude Code: скажите «создай PR на GitHub для мержа feature/recommend в main» — он использует GitHub CLI, включая заполнение заголовка и описания.

На детальной странице PR несколько вкладок: **Conversation** — описание PR и все обсуждения; **Commits** — все коммиты этого PR; **Files changed** — diff'ы всех изменённых файлов: главное рабочее место ревью, где видна каждая строка изменения. Строки с зелёной подсветкой — добавления, красной — удаления, без подсветки — контекст (помогает понять, где в коде происходят изменения). После прохождения ревью внизу появляется зелёная кнопка **Merge** — клик — и мерж.

Если вы настроили CI/CD (глава 12), страница PR показывает и результаты автоматических проверок: проходят ли тесты, собирается ли билд. При провале проверок кнопка Merge серая — проблемный код не вольётся, как дизейблится кнопка сабмита при пустых обязательных полях. Это автоматический safety net без человеческого надзора. Даже без CI/CD знание, что это возможно, полезно: когда проекту понадобится строже качество — оно бесценно.

## Нужны ли ветки личным проектам?

Вы можете спросить: я разрабатываю один, ревьюить некому — нужны ли мне ветки и PR?

Ответ: зависит. В маленьких проектах разработка прямо на `main` — commit и push — совершенно нормальна. Многие личные проекты всю жизнь живут на одном `main`.

С ростом сложности — когда хочется пробовать два подхода одновременно или делать большой рефакторинг, не затрагивая задеплоенную версию, — ветки становятся полезны.

Сценарий: проект задеплоен и живёт (глава 12), юзеры активно пользуются. Вы хотите добавить фичу, которая займёт несколько дней. Разрабатывая прямо на `main`, вы рискуете задеплоить наполовину готовый код — неполные фичи у юзеров, плохой опыт. Разработка на ветке держит `main` всегда стабильным и готовым к деплою; новые фичи вливаются только после завершения и тестирования — юзеры всегда видят полную функциональность.

Золотая середина: маленькие ежедневные правки — прямо в `main`; крупные фичи и эксперименты — в ветки. Не обязательно с самого начала строго внедрять полные PR-воркфлоу — вводите их при коллаборации с другими.

Git-воркфлоу постепенны: сначала привычки частых коммитов и своевременных пушей; когда устоятся — ветки и PR. Не пытайтесь всё сразу — так Git только покажется громоздким.

## Кроссплатформенная коллаборация: Windows встречает Mac

Сяомин на Windows; друг на Mac. Их коллаборация наступает на классические грабли.

Если вы когда-нибудь переносили файлы между Windows и Mac, вы встречали проблемы кодировки, кракозябр в именах или отображения. Кроссплатформенные проблемы Git-коллаборации в своей основе те же: у разных ОС разные «диалекты», нуждающиеся в стандартизации.

**Различия концов строк** — самый частый капкан. Windows использует CRLF (два символа) для переводов строк; Mac/Linux — LF (один символ). На экране выглядят одинаково — оба дают разрыв строки, — но на бинаровом уровне различаются.

Без стандартизации Git считает изменёнными целые файлы: поменяли одну строку кода, а diff показывает изменение каждой строки, потому что концы строк сместились с LF на CRLF (или наоборот). Этот «ложный diff» делает code review мучительным, скрывая реальные изменения.

Решение: скажите Claude Code «настрой Git на повсеместное использование LF». Он создаст в корне проекта файл `.gitattributes` со строкой `* text=auto eol=lf`, автоматически конвертируя все текстовые файлы в LF при коммите. Настроили раз — выигрывает вся команда: на какой бы системе никто ни разрабатывал, концы строк в коммитах едины.

**Регистр имён файлов** — другой тонкий капкан. Windows нечувствителен к регистру: `Button.tsx` и `button.tsx` — один файл; на Mac/Linux — разные.

Сяомин пишет `import Button from './button'` при файле `Button.tsx` — на его Windows работает, а Mac друга бросает «file not found». Баг особенно коварен: у Сяомина-то всё работает, он будет твердить «но у меня-то запускается!».

Хуже: Git на Windows по умолчанию не отслеживает изменение регистра — переименование `Button.tsx` в `button.tsx` может пройти незамеченным. Решение: стандартизуйте имена файлов на lowercase или PascalCase — договоритесь в команде.

**Разделители путей** проще: Windows использует обратные слэши `\`, Mac/Linux — прямые `/`. В коде всегда используйте прямые. `import { Button } from './components/Button'` работает везде; `import { Button } from '.\\components\\Button'` — только на Windows. К счастью, большинство современных фреймворков и бандлеров сами обрабатывают разделители — просто пишите прямые слэши, лишних забот нет.

Каждый капкан запоминать не нужно. Важно **знать, что они существуют**: коллаборируя между системами и встретив «один код — разные результаты», первой мыслью должно быть «возможная кроссплатформенная проблема», затем попросить Claude Code разобрать. Claude Code хорошо знает эти проблемы и обычно быстро определяет: концы строк, регистр или пути. Ранняя настройка `.gitattributes` и конвенций имён файлов избавляет от множества бед позже.

## Повседневный ритм разработки

Когда коллаборация с другом войдёт в колею, ежедневная разработка оседает в стабильный ритм. День начинается с pull последнего кода — локальная копия актуальна. Затем фича-ветка для изоляции работы. Разработка на ветке — быстро, маленькими шагами, частые коммиты. Push на GitHub на милстоунах — и бэкап, и видимость прогресса. По завершении — PR с просьбой о ревью. После ревью — мерж в main и удаление фича-ветки для чистоты.

<DailyRhythm />

Ритм — не жёсткие правила. Личные проекты упрощают: не обязательно ветвиться и PR'ить каждый раз. Но при коллаборации этот воркфлоу предотвращает большинство «конфликтов кода». Поначалу шагов много, но после нескольких повторений — привычка. Как вождение: сначала ошеломляет руль, газ, тормоз и зеркала одновременно; осваиваешься — и действия автоматичны, почти не замечаются. Git-воркфлоу те же: с практикой «pull → ветка → разработка → PR → мерж» становится мышечной памятью.

## Быстрый справочник

| Что вы хотите сделать | Скажите Claude Code |
|---------------------|------------------|
| Начать новую фичу | «Создай ветку от main для разработки фичи xxx» |
| Сохранить прогресс | «Закоммить текущие изменения» |
| Синхронизировать в облако | «Запушь на GitHub» |
| Получить свежий код | «Спули свежий код из ветки main» |
| Создать PR | «Создай Pull Request на GitHub» |
| Разрешить конфликты | «Помоги разрешить Git-конфликты» |
| Отменить изменения | «Отменяй изменения файла xxx» |
| Откатить версию | «Верни к последней работающей версии» |
| Удалить ветку | «Удали ветку feature/xxx» |

---

::: tip Ключевые выводы
Ветки позволяют безопасно экспериментировать с новыми фичами; PR дают ревью перед мержем; кроссплатформенная настройка — гладкую коллаборацию между разными системами. Ядро этого воркфлоу не в запоминании команд, а в привычке: **ветка перед изменением, ревью перед мержем**.
:::
