# 12.3 CI/CD и автоматизация

> **Цель раздела**: понять ключевые концепции CI/CD, чтобы сборка, тесты и деплой происходили автоматически после пуша кода.

На следующий день после успешного деплоя Сяомин починил баг и запушил изменение на GitHub. Через несколько минут открыл сайт — баг уже исправлен.

«Я не кликал деплой?» — Сяомин слегка озадачен.

Фактически с момента подключения GitHub в 12.1 Сяомин уже пользовался CI/CD — просто не осознавал.

## Вы уже используете CI/CD

CI/CD звучит продвинуто, но по сути значит всего две вещи:

- **CI (Continuous Integration)**: при каждом пуше кода автоматически запускаются проверки и сборка — убедиться, что всё в порядке
- **CD (Continuous Deployment)**: после прохождения проверок код автоматически релизится в продакшен

<CIWorkflow />

Вам нужно только писать код и пушить; всё между — автоматизировано.

Когда вы подключали GitHub-репозиторий к EdgeOne Pages в 12.1, платформа зарегистрировала на GitHub **webhook**. Это как оформить заказ на Taobao — и логистика сама шлёт SMS «отправлено»: не нужно рефрешить страницу трекинга каждые пять минут. Webhook работает так же: это механизм «уведоми меня, когда случится». При каждом `git push` GitHub сам говорит EdgeOne: «Эй, новый код». EdgeOne получает уведомление и автоматически спулит код, ставит зависимости, запускает сборку и деплоит онлайн.

Это «push-to-deploy» — простейшая форма CI/CD.

## Встроенный CI/CD на платформе

На платформах вроде EdgeOne Pages, Vercel или Cloudflare Pages CI/CD уже встроен и не требует дополнительной настройки. После подключения GitHub платформа автоматически реагирует на три вида событий:

- **Push в ветку `main`** → автоматический деплой в продакшен-окружение (версия, к которой ходят юзеры)
- **Создание Pull Request** → автоматическая сборка и генерация preview-ссылки

**Preview-ссылка — самый интуитивный результат CI/CD.**

## Когда нужен кастомный пайплайн

Встроенного в платформу «push-to-deploy» личным проектам уже достаточно. Но с усложнением проекта вы можете захотеть делать перед деплоем больше:

- Автоматически гонять тесты — убеждаться, что новый код не сломал существующую функциональность
- Автоматически проверять стиль кода — держать кодовую базу чистой
- Автоматически проверять type-ошибки — не пускать простые баги в продакшен

Один друг Сяомина предложил: «Давайте добавим автоматическое тестирование, чтобы багованный код не мержился». Это прямое продолжение раздела о тестировании из главы 9: тесты вы написали, но гонять их вручную каждый раз легко забыть. Если тесты запускаются автоматически при каждом пуше — ничего не пропущено.

Вот тут и нужен **GitHub Actions** — встроенный CI/CD-инструмент GitHub.

## GitHub Actions: рецепт автоматизации

<DeploymentPipeline />

GitHub Actions конфигурируется YAML-файлами в каталоге `.github/workflows/`. Думайте о нём как о «рецепте», говорящем GitHub: когда что делать, в каком порядке и что именно.

Типичная конфигурация состоит из трёх частей:

**Условия триггера (`on`)**: определяют, когда запускать. Например, при пуше в `main` или создании PR.

**Runtime-окружение (`runs-on`)**: указывает, на какой системе исполнять (обычно `ubuntu-latest`). GitHub поднимает временную виртуалку, исполняет ваш воркфлоу и уничтожает её по завершении. Место, где исполняются ваши шаги.

**Шаги (`steps`)**: конкретные задачи — спулить код, поставить зависимости, запустить тесты, задеплоить. Каждый шаг — отдельное действие, выполняющееся по порядку.

Файл конфигурации — «рецепт» GitHub Actions, описывающий, какие шаги исполняются при каких условиях. Как мануал для кухонного комбайна: положите ингредиенты — он исполняет по шагам и выдаёт результат.

Скажите Claude Code:

> «Помоги создать GitHub Actions воркфлоу: при пуше в main автоматически запускать тесты; деплой — только после прохождения тестов».

AI сгенерирует конфигурационный файл, объяснит назначение каждой части и положит его в правильный каталог.

### Пример: тесты перед каждым деплоем

<details>
<summary>Развернуть: полный пример YAML-конфигурации</summary>

```yaml
name: Test and Deploy

# Триггер: запускать при пуше в main или PR в main
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      # Шаг 1: спулить код
      - uses: actions/checkout@v4

      # Шаг 2: настроить Node.js
      - uses: actions/setup-node@v4
        with:
          node-version: '20'

      # Шаг 3: поставить зависимости
      - run: npm ci

      # Шаг 4: запустить тесты
      - run: npm test

  deploy:
    needs: test  # Деплой ждёт завершения тестов
    if: github.ref == 'refs/heads/main'  # Только при пуше в main (не на PR)
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm ci
      - run: npx vercel deploy --prod --token=${{ secrets.VERCEL_TOKEN }}
```

</details>

Эта конфигурация делает две вещи: сначала запускает тесты; при провале любого деплой не стартует. Прошли — задеплоит. Это и есть автоматизация CI/CD: не «запустил и запомнил», а «плохой код не пройдёт физически».

Это соответствует концепции мержа PR из главы 11: PR мержится только после прохождения проверок. Теперь с CI/CD «проверка» — это не просто просмотр глазами: машинная верификация — куда строже людей.

## Продвинутый пример: multi-environment деплой

С ростом проекта может понадобиться деплоить в разные окружения: dev-ветка — в тестовое, main — в продакшен. GitHub Actions легко справляется.

<details>
<summary>Развернуть: пример multi-environment CI/CD</summary>

```yaml
name: Multi-Environment Deploy

on:
  push:
    branches: [main, develop]

jobs:
  test:
    uses: ./.github/workflows/reusable-test.yml  # Переиспользуемый тестовый воркфлоу

  deploy-production:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Deploy to production
        run: ./scripts/deploy-production.sh
        env:
          DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}

  deploy-staging:
    needs: test
    if: github.ref == 'refs/heads/develop'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Deploy to staging
        run: ./scripts/deploy-staging.sh
        env:
          DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}
```

**Пара деталей конфигурации:**

**Переиспользуемые воркфлоу (`uses: ./.github/workflows/...`):** тестовые шаги можно вынести в отдельный файл и переиспользовать в нескольких воркфлоу — не дублируя.

**Хранение секретов (`secrets`):** чувствительные данные (токены, ключи) не храните в YAML напрямую — используйте GitHub Secrets: Settings → Secrets and variables → Actions. В конфигурации обращайтесь через `${{ secrets.VERCEL_TOKEN }}` — GitHub автоматически подставит и не покажет в логах.

**YAML-якоря:** определите флоу деплоя один раз через `&docs_deploy_pipeline`, затем переиспользуйте в нескольких местах через `<<: *docs_deploy_pipeline` — без дублирования конфигурации.

Эта конфигурация демонстрирует полный multi-environment CI/CD: dev-ветки автоматически деплоятся в тестовое, main — в продакшен, PR автоматически валидируются и мержатся. Личному проекту такая сложность не нужна, но при росте до нескольких окружений это полезный шаблон.
