# Глава 12: Serverless-деплой и автоматизация CI/CD

![img](/images/Advanced/mll089oi-6566edafa4114ef0.jpg)

## Предисловие

Сяомин уже запушил код «Личного Douban» на GitHub и несколько раз поработал с друзьями через ветки и PR. Всё шло гладко — пока друг не прислал сообщение: «Та ссылка, что ты мне показывал через Tunnel, больше не работает. Можешь сделать постоянную? Хочу отправить девушке».

Сяомин на секунду замер. Временная ссылка Cloudflare Tunnel из главы 10 перестала работать, как только закрылся терминал. Ему нужен **постоянно доступный** адрес — такой, чтобы любой мог открыть в любой момент.

Именно эту проблему и решает «деплой».

### Деплой с нулевой стоимостью

Опытный эксперт рекомендует стартовый сетап без затрат: выберите **платформу деплоя** + **сервис хостинга базы**.

**Платформа деплоя** отвечает за запуск вашего frontend- и backend-кода, предоставляя **Serverless**-окружение. Заметьте: Serverless не значит «серверов нет» — значит, **серверы не нужно администрировать вам**. Вы просто пишете код, а платформа берёт на себя масштабирование и обслуживание.

Мейнстрим-платформы деплоя:

- **Tencent Cloud EdgeOne Pages**: доступен из материкового Китая, построен на глобальной edge-сети Tencent, поддерживает автодеплой после подключения GitHub и отлично работает с Next.js
- **Alibaba Cloud ESA Functions и Pages**: комплексная full-stack платформа Alibaba Cloud с глубокой интеграцией Git-воркфлоу и быстрым доступом внутри страны
- **Vercel**: официальная платформа деплоя Next.js с превосходным developer experience, но из материкового Китая медленнее; лучше для зарубежных юзеров или проектов с кастомными доменами
- **Cloudflare Pages**: ускорение глобальным CDN, щедрый free tier, поддержка edge-функций
- **GitHub Pages**: простейший хостинг статических сайтов, идеален для чисто frontend-проектов

<DeploymentComparison />

**Хостинг базы** отвечает за хранение ваших данных. Эксперт рекомендует **Neon** — облачный сервис, сфокусированный именно на PostgreSQL, с serverless-архитектурой и автоматическим масштабированием по требованию. Самое важное: это стандартный PostgreSQL. Вы подключаетесь через **Drizzle ORM** со стандартной строкой подключения, без vendor lock-in. Захотите сменить провайдера базы — поменяете только `DATABASE_URL`. Это и значит **держать архитектуру независимой**.

Если нужно больше backend-фич (Auth, Storage, Realtime-подписки), можно рассмотреть и **Supabase**. По сути это **облачный PostgreSQL** плюс набор backend-сервисов. Но эксперт напоминает: по возможности подключайтесь к базе напрямую через Drizzle ORM, а не полагайтесь сильно на проприетарный JS SDK Supabase — так вы сохраните гибкость миграции.



### Автоматизация CI/CD

Эксперт упомянул и звучащий продвинуто термин: **CI/CD (Continuous Integration / Continuous Deployment)**. Звучит сложно, но в современных воркфлоу разработки это просто **«автоматизация»**.

Раньше деплой сайта выглядел так: `ручная сборка -> загрузка на сервер -> SSH на сервер -> рестарт сервиса`. Теперь процесс такой:

1. Вы локально выполняете `git push`, отправляя код на GitHub.
2. GitHub автоматически уведомляет платформу деплоя: «Эй, есть новый код!»
3. Платформа получает сигнал, автоматически спулит свежий код, ставит зависимости, запускает сборку и публикует.

Больше не нужно разбираться в сложных ops-командах — **сохранил и опубликовал**.

CI/CD превращает деплой в «сохранил и опубликовал». Эксперт говорит: идея **автоматически триггерить действия при изменении кода** — та же концепция, что и **Hooks** из разработки. Локально Hooks автоматически гоняют тесты и форматирование; в облаке CI/CD автоматически гоняет сборку и деплой. Вместе они образуют полный автоматический цикл.

**Жизненный цикл деплоя**: полный флоу включает несколько стадий — вы пишете код локально, пуш в GitHub автоматически триггерит сборку, после успеха генерируется preview-ссылка (на отечественных платформах обычно валидна 3 часа). Подтвердив, что всё в порядке, мёржите в основную ветку — и проект официально онлайн. Когда число записей деплоя превышает лимит, старые помечаются невалидными — это экономит место на хранении.



### Конфигурация деплоя

Перед стартом деплоя эксперт советует сначала понять несколько ключевых параметров конфигурации. Современные платформы автоматически детектят многие настройки проекта, но понимание параметров поможет разбираться при сбоях.

**Настройки сборки**:

- **Framework preset**: выберите используемый фреймворк (например, Next.js) — платформа автоматически заполнит рекомендуемые настройки
- **Root directory**: где находится код в репозитории; обычно по умолчанию корень, `./`
- **Build command**: обычно `npm run build` или `pnpm build`
- **Output directory**: где хранятся артефакты сборки; для Next.js это обычно `.next` или `out`
- **Node version**: платформа имеет предустановленные версии Node (18, 20, 22, 24); этот туториал использует мажорную версию 24

**Переменные окружения**: их нужно конфигурировать отдельно после деплоя. Отечественные платформы обычно поддерживают bulk import — можно вставить содержимое файла `.env` напрямую, и платформа распознаёт автоматически. Учтите: изменения переменных вступают в силу только для новых деплоев и не затрагивают существующие.

### Ловушки деплоя

Вы научились подключать GitHub-проект к платформе деплоя, кликнули «Deploy» — первая сборка пошла.

**Ловушка 1: Несовпадение версий Node.js**

Красный **Failed** бьёт по голове. В логах видно: проблема в устаревшей версии Node. Дефолтная версия Node платформы может быть старой, а проекту Next.js нужна свежее. Зайдите в настройки платформы, поменяйте Node.js Version под локальное окружение (в этом туториале 24) и передеплойте.

**Ловушка 2: Отсутствующие переменные окружения**

Версию починили — сборка успешна, но сайт при визите сыпет ошибками. И тут вы вспоминаете главу 6: **файл `.env` заблокирован `.gitignore`!** У GitHub вовсе нет вашего пароля базы и API Key. Зайдите на страницу «Environment Variables» платформы и перенесите туда всё из локального `.env` построчно.

Отечественные платформы обычно поддерживают bulk import — просто вставьте полное содержимое `.env`, и платформа распознаёт автоматически.

Переменные настроены — вы полны предвкушения снова открываете сайт, и страница наконец отображается корректно. Вы всё время использовали облачную базу — код и данные уже там; деплой лишь меняет место, где выполняется код.

**Деплой успешен**

Когда всё настроено, платформа генерирует ссылку доступа. Вы с волнением кликаете — сайт работает в публичном интернете: наконец-то у вас есть шерабельная ссылка для друзей.

### Постепенный rollout — снижение риска

После успешного деплоя эксперт упоминает более продвинутую стратегию: «Если у продукта много юзеров, выкатывать новые фичи сразу всем — рискованно. Серьёзный баг заденет всех».

Идея **постепенного rollout**: сначала выкатить новую версию 10% юзеров, несколько дней понаблюдать, расширить до 50% и лишь затем — всем. Как дегустация для маленькой группы перед массовым продвижением.

Это позволяет быстро обрезать убытки при появлении проблем, а не выставлять сразу всех юзеров под риск. Хорошая новость: некоторые платформы это поддерживают, и можно поручить AI настройку.

Личным проектам такая сложность пока не нужна, но понимание концепции помогает понять, как работают крупные компании — почему иногда вам доступна новая фича, а иногда нет: вы можете быть в разных партиях rollout.



### Автоматическая оптимизация платформы

После успеха деплоя эксперт сообщает хорошую новость: **эти платформы уже сделали для вас массу оптимизаций производительности**.

Например, картинки автоматически сжимаются в более эффективные форматы, код автоматически режется на меньшие чанки для загрузки по требованию, а статические ассеты распределяются по глобальным узлам ускорения. Ничего из этого конфигурировать самим не нужно — платформа делает по умолчанию.

Конечно, если продукт вырастет до большой аудитории, дефолтных оптимизаций может не хватить. Тогда можно думать о более продвинутых стратегиях. Но на ранней стадии дефолтов платформы более чем достаточно.

### CDN

Эксперт мимоходом затрагивает важную концепцию: **CDN (Content Delivery Network)**. После деплоя сайта в публичный интернет вы можете заметить: из материкового Китая доступ быстрый, за рубежом медленнее. Физическая дистанция ограничивает скорость передачи: когда данным нужно облететь полмира — это время.

Принцип CDN — разместить «серверы-кэши» по всему миру. Юзер заходит на сайт — CDN автоматически отдаёт контент с ближайшего к нему сервера, вместо того чтобы каждый раз тянуть с origin-сервера. Как открыть филиалы везде: юзеры ходят в ближайший, а не в штаб-квартиру.

Современные платформы деплоя (EdgeOne, ESA, Vercel, Cloudflare и т.д.) имеют встроенную поддержку CDN — дополнительная настройка не нужна. Поняв принцип, вы поймёте, почему сайты открываются быстро по всему миру.

### Три слоя кэш-защиты

Эксперт говорит: «Кэширование повсюду, и оно делает сайты быстрее». Вы встретите три вида кэша:

1. **Кэш браузера**: ранее посещённые ресурсы хранятся локально — в следующий раз скачивать не нужно. Вы уже сталкивались в главе 4: поменяли код, рефрешнули страницу — а видите старую версию, потому что она из кэша.
2. **Кэш CDN**: глобальный кэш edge-узлов, о котором мы только что говорили, — ближайший к юзеру.
3. **Серверный кэш**: сервер кэширует результаты вычислений или запросов к базе в памяти, чтобы не делать одну работу повторно. Вы могли заметить: первая загрузка страницы медленнее, повторная — заметно быстрее, даже если вы почистили кэш браузера. Часто это серверный кэш в деле.

Большая часть кэширования автоматична. Его идея проста: **сохранить часто используемое, чтобы в следующий раз взять готовое**. Иногда сайт обновлён, а юзеры не видят изменений — возможно, просто кэш не обновился. Очистка кэша или hard refresh (Ctrl+Shift+R) обычно решает.

### Оптимизация стоимости

Продукт поработал в онлайне — вы открываете страницу биллинга, и цифры заставляют сердце колотиться. Эксперт говорит: пора строить осознанность **оптимизации стоимости**.

В решениях о деплое эксперт советует думать по стадиям. На стадии MVP (<1000 юзеров) стартуйте с бесплатного Serverless и не оптимизируйте слишком рано. На стадии роста (1000–10 000 юзеров) оценивайте гибридную архитектуру и переходите к self-hosting, только если расходы растут слишком быстро. На энтерпрайз-стадии (>10 000 юзеров) собственные серверы нужны лишь для комплаенса или оптимизации производительности. **Преждевременная оптимизация — корень всех зол**: не решайте проблемы третьей стадии, находясь на первой.

Стоимость AI-моделей тоже стоит оптимизировать. Простые задачи отправляйте более дешёвым отечественным моделям (GLM, DeepSeek), глубокие рассуждения — Claude. Можно добавить слой принятия решений в коде: простые переводы и суммаризацию — дешёвым моделям, запросы с глубоким рассуждением — только Claude. Это называется «intelligent routing». Одно AI-приложение через intelligent routing снизило расходы на API на 80% (70% GLM + 30% Claude). Ключ — соответствие сложности задачи возможностям модели: не стреляйте из пушки по комарам.

Эксперт также напоминает про **ловушку free tier**: бесплатные квоты многих платформ хватает только на тестирование. С реальными юзерами расходы могут расти экспоненциально. Обязательно настройте биллинг-алерты (например, «прислать email при превышении ¥70»), регулярно проверяйте usage и держите руку на пульсе. Free tier — для проб, не для долгого продакшена.

SRE-практики вроде операций мониторинга и анализа логов мы детально разберём позже в разделе об операциях облачных серверов.
