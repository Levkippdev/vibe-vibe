# 14.3.4 Деплой приложений с разделённым frontend и backend

> **Цель раздела**: освоить общий воркфлоу деплоя для архитектур с разделённым frontend/backend, научиться использовать Claude Code для помощи с настройкой reverse proxy; применимо к любому стеку (Node.js / Python / PHP / Java / Go / .NET и т.д.).

::: tip Отличие от 14.3.2
- **14.3.2**: подходит для «full-stack»-фреймворков вроде Next.js, где frontend и backend в одном проекте, обслуживаются одним контейнером
- **Этот раздел (14.3.4)**: подходит для «разделённых» архитектур, где frontend и backend — независимые проекты, требующие раздельного деплоя

Если ваш проект на Next.js/Nuxt или похожих full-stack-фреймворках — идите прямо в 14.3.2. Если frontend у вас на React/Vue, а backend — отдельный API-сервис (Node.js/Python/Java и т.д.), вам нужен подход из этого раздела.
:::

Full-stack проект Сяомина состоит из трёх частей: frontend, backend API и база. «Раньше на Vercel это был один проект, который делал всё, — а теперь мне нужно деплоить их по отдельности?»

Ветеран сказал: «Vercel связал их для вас в один пучок, а на своём сервере вам нужно понять роль каждой части. Плюс в том, что вы получаете полный контроль над каждым слоем».

Он нарисовал диаграмму: «Разделённая frontend-backend-архитектура выглядит так —»

## Архитектура с разделённым frontend и backend

```
Браузер юзера
    │
    ▼
  OpenResty (Reverse Proxy) :80
    │
    ├── /          → Статика frontend (HTML/CSS/JS)
    ├── /api/*     → Backend-сервис (порт контейнера 3000/8000/8080...)
    │
    └── Backend-сервис
            │
            ▼
        База (PostgreSQL/MySQL/MongoDB...)
```

Три сервиса, каждый со своей зоной ответственности:

- **OpenResty**: единственная точка входа для внешнего трафика, отвечает за маршрутизацию запросов
- **Backend-сервис**: обрабатывает бизнес-логику и операции с базой (Node.js / Python / Java / Go и т.д.)
- **База**: хранит данные

::: tip Что такое reverse proxy?
**Reverse proxy** — как «ресепшионист»:
- Все запросы юзеров сначала попадают на ресепшн (OpenResty)
- Ресепшн смотрит на путь запроса и решает, кто его обработает:
   - Заход на `/` → возвращает страницу frontend
   - Заход на `/api/users` → форвардит в backend-сервис
- Юзер ощущает, что имеет дело с одним сервером, хотя за кулисами могут работать несколько сервисов

**Выгоды**:
1. Единая точка входа: юзерам нужно запомнить один домен
2. Избегаем CORS: frontend и API живут под одним доменом
3. Безопасность: backend-сервисы не выставлены напрямую в публичный интернет
:::

Сяомин нарисовал простую диаграмму: запросы юзеров сначала идут в OpenResty, который проверяет путь — если начинается с `/api`, форвард в backend; иначе вернуть страницу frontend. «Так вот, Vercel делал это за кулисами — просто прятал от меня всё».

Все они работают в Docker-контейнерах и общаются между собой через container network.

## Общий воркфлоу деплоя

Каким бы ни был ваш backend-стек, воркфлоу деплоя похож:

### Шаг 1: Деплой базы

Исходя из задач проекта, поставьте нужную базу из магазина 1Panel:

- **PostgreSQL**: подходит для реляционных данных, сложных запросов
- **MySQL**: подходит для традиционных web-приложений
- **MongoDB**: подходит для документо-ориентированных данных
- **Redis**: подходит для кэширования, хранения сессий

После установки создайте базу и юзера под приложение и зафиксируйте данные подключения (hostname, порт, имя, пароль).

::: tip Конвенция имён контейнеров баз 1Panel
Контейнеры баз, созданные 1Panel, следуют формату `1Panel-{тип_базы}-{4_случайных_буквы}`:
- PostgreSQL: `1Panel-postgresql-ukow`
- Redis: `1Panel-redis-w94p`
- MySQL: `1Panel-mysql-abcd`
- MongoDB: `1Panel-mongodb-xyz1`

**Как узнать фактическое имя контейнера**:
На странице «Containers» в 1Panel имя контейнера — первая колонка списка. Также можно кликнуть «Details» у нужной базы на странице «Database» и посмотреть информацию о подключении.

Backend-приложения подключаются к базе по **имени контейнера** (не `localhost`).
:::

::: details Частые примеры connection strings

**PostgreSQL**:
```bash
DATABASE_URL="postgresql://username:password@1Panel-postgresql-ukow:5432/database_name"
```

**MySQL**:
```bash
DATABASE_URL="mysql://username:password@1Panel-mysql-abcd:3306/database_name"
```

**Redis (с паролем)**:
```bash
REDIS_URL="redis://:password@1Panel-redis-w94p:6379"
```

**Redis (без пароля)**:
```bash
REDIS_URL="redis://1Panel-redis-w94p:6379"
```

**MongoDB**:
```bash
MONGODB_URI="mongodb://username:password@1Panel-mongodb-xyz1:27017/database_name"
```
:::

### Шаг 2: Деплой backend-сервиса

Способ деплоя выбирайте по вашему backend-стеку:

| Стек | Runtime 1Panel (язык) | Референс startup command |
|--------|---------|-------------|
| Node.js / Next.js | Node.js | `git pull && pnpm build && pnpm start` |
| Python / FastAPI | Python | `git pull && pip install -r requirements.txt && uvicorn main:app --host 0.0.0.0` |
| PHP / Laravel | PHP | PHP-FPM стартует автоматически, доступ через reverse proxy OpenResty |
| Java / Spring Boot | Java | `java -jar app.jar` |
| Go | Go | `./app` |
| .NET / ASP.NET Core | .NET | `dotnet run --urls http://0.0.0.0:5000` |

::: tip Runtime = Docker-контейнер
«Runtime» 1Panel — по сути Docker-контейнер. Каждому языку (Node.js, Python, PHP, Java, Go, .NET) соответствует преднастроенный базовый образ. Выбрав язык и версию, 1Panel через docker-compose управляет созданием и запуском контейнера.
:::

**Ключевые конфигурации**:

1. **Переменные окружения**: строки подключения к базам, секреты и т.д.
2. **Port mapping**: в расширенных настройках замапьте внутренний порт контейнера (например, 3000) на внешний порт сервера (например, 3001)
3. **Startup command**: обеспечьте автоматический пуллинг свежего кода при каждом рестарте
4. **Имя контейнера**: используется для коммуникации между контейнерами (например, reverse proxy форвардит запросы по имени контейнера)

Проект Сяомина на Node.js. Он создал контейнер в «Runtime», заполнил каталог проекта, startup command и переменные окружения. Через несколько минут backend API заработал. Он зашёл на `http://serverIP:3001/api/health` в браузере и увидел JSON-ответ.

### Шаг 3: Сборка и деплой frontend

Frontend обычно нужно сначала собрать локально, затем загрузить на сервер:

```bash
# На локальной машине
cd your-project

# Задать переменную окружения (указывающую на backend API на сервере)
echo "VITE_API_URL=http://your-server-ip:3001" > .env.production

# Сборка frontend
npm run build  # или pnpm build / yarn build

# Результат сборки обычно в dist/ или build/ или out/
```

Загрузка на сервер:

```bash
# Способ 1: через scp
scp -r dist/* root@your-server-ip:/opt/your-frontend/

# Способ 2: drag-and-drop загрузка через FinalShell
```

Создайте статический сайт в 1Panel:

1. Перейдите в «Website > Websites», кликните «Create Website»
2. Выберите «Static Website»
3. Primary Domain: `yourdomain.com` (или сначала потестируйте с IP)
4. Website Directory: `/opt/your-frontend`
5. Кликните Confirm

Сяомин перетащил собранные frontend-файлы на сервер через FinalShell, затем создал статический сайт в 1Panel. Заход по IP сервера в браузере показал страницу frontend — но при попытке логина выскочила ошибка: «Cross-origin request blocked».

### Шаг 4: Настройка reverse proxy (критический шаг)

Теперь frontend и backend разделены: frontend на порту 80, backend на 3001. API-запросы с frontend упрутся в CORS-проблемы. Решение — настроить reverse proxy, чтобы frontend и backend жили под одним доменом.

#### Рекомендуемый воркфлоу: пусть Claude Code напишет конфигурацию за вас

1. **Возьмите дефолтную конфигурацию 1Panel**

В 1Panel откройте настройки только что созданного статического сайта, вкладку «Configuration File» и скопируйте всё содержимое конфигурации.

2. **Локально уточните конфигурацию с Claude Code**

Откройте Claude Code локально и отправьте промпт:

```
Мне нужно настроить OpenResty reverse proxy для деплоя с разделённым frontend/backend.

Текущая дефолтная конфигурация 1Panel:
[вставьте скопированную конфигурацию]

Мои требования:
- Статика frontend лежит в /opt/your-frontend
- Контейнер backend API называется your-backend, порт 3000
- Все запросы /api/* должны форвардиться в backend
- Остальные запросы должны возвращать страницу frontend (с поддержкой SPA-роутинга)

Пожалуйста, доработай эту конфигурацию.
```

Claude Code сгенерирует полную конфигурацию под вашу ситуацию, включая:
- Корректные адреса `proxy_pass`
- Необходимые настройки заголовков
- Конфигурации timeout
- Поддержку SPA-роутинга (`try_files`)

3. **Скопируйте обратно на сервер**

Скопируйте сгенерированную Claude Code конфигурацию обратно в редактор «Configuration File» 1Panel и кликните «Save and Reload».

Сяомин скопировал дефолтную конфигурацию 1Panel в локальный Claude Code и описал требования. Claude Code быстро сгенерировал полную конфигурацию: правила reverse proxy, настройки заголовков и timeout. Сяомин вернул её в 1Panel, кликнул сохранение — рефрешнул браузер, и на этот раз логин прошёл!

::: tip Почему рекомендуем этот воркфлоу?

1. **Claude Code понимает ваш проект**: он знает имена ваших контейнеров, порты и структуру роутинга
2. **Избежание ручных ошибок**: опечатки в имени контейнера и ошибки в путях — частые проблемы
3. **Автодополнение деталей**: настройки timeout, заголовки, обработка ошибок и прочее, что легко упустить
4. **Итеративность**: если конфигурация не подошла, можно продолжать править с Claude Code

:::

::: warning А если у конфигурации Claude Code проблемы?

1. **Смотрите error-логи**: error-логи в «App Store → Installed → OpenResty»
2. **Отправьте ошибки в Claude Code**: скопируйте error-логи и скажите Claude Code «У моего reverse proxy проблемы, error-логи такие...»
3. **Claude Code поможет починить**: он разберёт причину ошибки и сгенерирует исправленную конфигурацию
4. **Частые ошибки**:
   - Опечатка в имени контейнера → проверьте корректность имени
   - Неверный номер порта → проверьте фактический порт backend-сервиса
   - Ошибка в конфигурации пути → проверьте правильность пути `proxy_pass`

Если после нескольких попыток всё равно не работает, сверьтесь с «Типовым примером конфигурации reverse proxy» в конце раздела и поправьте вручную.
:::

#### Типовой пример конфигурации reverse proxy

Сгенерированные Claude Code конфигурации обычно выглядят так:

```nginx
server {
    listen 80;
    server_name yourdomain.com;

    # Статика frontend
    location / {
        root /opt/your-frontend;
        try_files $uri $uri/ /index.html;  # поддержка SPA-роутинга
    }

    # Reverse proxy backend API
    location /api/ {
        proxy_pass http://your-backend:3000/api/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # Настройки timeout
        proxy_connect_timeout 60s;
        proxy_send_timeout 60s;
        proxy_read_timeout 60s;
    }
}
```

### Шаг 5: Обновление API-адреса frontend

После настройки reverse proxy API-адрес frontend стоит сменить на относительный путь (frontend и backend теперь под одним доменом):

```bash
# На локальной машине
echo "VITE_API_URL=/api" > .env.production  # или NEXT_PUBLIC_API_URL=/api

# Пересборка
npm run build

# Повторная загрузка на сервер
scp -r dist/* root@your-server-ip:/opt/your-frontend/
```

Сяомин пересобрал и перезалил frontend. Рефреш браузера — все функции работают: «Frontend, backend и база — три части работают сообща на моём собственном сервере».

## Различия между стеками

Хотя воркфлоу деплоя похож, у разных стеков есть детали:

### Node.js / Next.js

- **Язык runtime**: Node.js
- **Выбор версии**: берите версию Node.js, совпадающую с локальной (свежая — 24.10.0)
- **Startup command**: `pnpm build && pnpm start`
- **Порт**: обычно 3000
- **Переменные окружения**: `DATABASE_URL`, `NODE_ENV=production`

### Python / FastAPI

- **Язык runtime**: Python
- **Выбор версии**: берите версию Python, совпадающую с локальной (свежая — 3.14.0)
- **Startup command**: `pip install -r requirements.txt && uvicorn main:app --host 0.0.0.0 --port 8000`
- **Порт**: обычно 8000
- **Переменные окружения**: `DATABASE_URL`, `PYTHONUNBUFFERED=1`

### PHP / Laravel

- **Язык runtime**: PHP
- **Выбор версии**: берите версию PHP по требованиям проекта (свежая — 8.5.2)
- **Способ деплоя**: PHP runtime даёт сервис PHP-FPM (дефолтный порт 9000), используется в связке с OpenResty
- **Startup command**: PHP-FPM стартует сам, настройка startup command не нужна
- **Переменные окружения**: `DB_CONNECTION`, `DB_HOST` (имя контейнера), `APP_ENV=production`
- **Замечание**: PHP-проекты обычно доступны через reverse proxy OpenResty в PHP-FPM, а не запускают собственный HTTP-сервер

### Java / Spring Boot

- **Язык runtime**: Java
- **Выбор версии**: берите версию JDK по проекту (свежая — 22)
- **Startup command**: `java -jar app.jar`
- **Порт**: обычно 8080
- **Переменные окружения**: `SPRING_DATASOURCE_URL`, `SPRING_PROFILES_ACTIVE=prod`

### Go

- **Язык runtime**: Go
- **Выбор версии**: берите версию Go по проекту (свежая — 1.25)
- **Startup command**: `./app`
- **Порт**: кастомный (например, 8080)
- **Переменные окружения**: по проекту

### .NET / ASP.NET Core

- **Язык runtime**: .NET
- **Выбор версии**: берите версию .NET по проекту (свежая — 10.0)
- **Startup command**: `dotnet run --urls http://0.0.0.0:5000`
- **Порт**: обычно 5000
- **Переменные окружения**: `ConnectionStrings__DefaultConnection`, `ASPNETCORE_ENVIRONMENT=Production`

## Тестирование полного воркфлоу

После деплоя проверьте следующие функции:

1. **Визит главной**: `http://your-server-ip` → видна страница frontend
2. **API-запросы**: API-запросы из frontend возвращают данные нормально
3. **Персистентность данных**: данные переживают рефреш страницы
4. **Аутентификация юзеров**: логин, логаут и проверка прав работают нормально

Сяомин прогнал все проверки — всё в норме. Он открыл devtools Network и увидел, что страница frontend загружена с `/`, а API-запросы уходят на `/api/xxx`: «Юзеры совершенно не чувствуют, что за кулисами работают три сервиса».

## Разбор частых проблем

| Симптом | Возможная причина | Решение |
|------|---------|---------|
| Frontend не открывается | Security group не открыла порт 80 | Откройте порт 80 в консоли провайдера |
| API-запрос — 404 | Ошибка конфигурации reverse proxy | Проверьте имя контейнера и путь в `proxy_pass` |
| API-запрос — 502 | Backend-контейнер не запущен | Проверьте логи в «Runtime», рестартните контейнер |
| Провал подключения к базе | Неверный hostname в `DATABASE_URL` | Используйте имя контейнера (например, `postgresql`) вместо `localhost` |
| Ошибка CORS | Reverse proxy не вступил в силу | Убедитесь, что конфиг OpenResty сохранён и перегружен |
| SPA-роутинг — 404 | Нет конфигурации `try_files` | Попросите Claude Code добавить поддержку SPA-роутинга |

::: tip Воркфлоу дебага при проблемах

1. **Сначала логи**: логи в «Containers» или «Runtime» — у 90% проблем ответы в логах
2. **Проверьте статусы контейнеров**: убедитесь, что все контейнеры работают
3. **Протестируйте связь между контейнерами**: войдите в терминал backend-контейнера, `ping postgresql` для проверки сети
4. **Позовите Claude Code**: отправьте error-логи в Claude Code и попросите разобрать

:::

## Итоги преимуществ архитектуры

Разделённый деплой frontend/backend даёт вам:

1. **Единая точка входа**: юзеры запоминают один домен, им не нужно знать порт backend
2. **Избежание CORS**: frontend и API под одним доменом, без CORS-проблем
3. **Безопасность**: backend-сервисы не торчат в публичном интернете, внешний трафик встречает только OpenResty
4. **Гибкое масштабирование**: frontend, backend и базу можно апгрейдить и масштабировать независимо
5. **Полный контроль**: вы управляете каждым слоем, не ограничены платформами

Сяомин вспомнил деплой на Vercel, где один `vercel deploy` делал всё. Теперь шагов больше, но он понимает, что делает каждый: «То, что Vercel делал за меня, я теперь могу сам. А с Claude Code, помогающим писать конфиги, — не так уж сложно».
