> ## Резюме

> Вместо построения сложных retrieval-пайплайнов и кастомных тулчейнов Vercel обнаружил: организация данных в файлы и выдача агентам bash-доступа даёт лучшие результаты на 75% дешевле. LLM от природы сильны в навигации файловых систем — используйте это себе на пользу.

## Ключевая находка: 75% снижения стоимости

Заголовочная цифра поразительна: заменив кастомные retrieval-пайплайны простым подходом «файловая система + bash», Vercel снизил стоимость агента с примерно **$1 до $0.25 за API-вызов** — минус 75%.

Но стоимость — только часть истории. Файловый подход также улучшил надёжность, снизил сложность разработки и сделал систему проще в дебаге и поддержке. Это кейс того, как простейшая архитектура часто побеждает.

## Почему LLM от природы сильны в навигации файловых систем

Подход работает из-за фундаментального инсайта о том, как обучаются большие языковые модели:

### Совпадение с обучающими данными

LLM обучались на огромных количествах данных кодовых репозиториев и логов терминальных взаимодействий. Они видели миллионы примеров:

- Навигации по структурам директорий с `ls`, `cd` и `find`
- Поиска по содержимому файлов с `grep`, `awk` и `sed`
- Чтения файлов с `cat`, `head` и `tail`
- Пайпинга вывода между командами
- Написания скриптов для автоматизации многошаговых операций

Это значит: навигация по файловой системе — не то, чему нужно учить модель; это то, что модель уже глубоко знает. Выдавая агенту bash-доступ, вы задействуете её сильнейшие существующие способности вместо просьбы учить новые абстракции.

### Структурное совпадение

Бизнес-данные естественно мапятся на иерархии директорий. Возьмём отдел продаж:

```
/data/
├── customers/
│   ├── acme-corp/
│   │   ├── profile.json
│   │   ├── contracts/
│   │   └── communications/
│   └── globex/
│       ├── profile.json
│       └── contracts/
├── products/
│   ├── enterprise-plan.md
│   └── starter-plan.md
└── reports/
    ├── q1-2024.csv
    └── q2-2024.csv
```

Эта структура немедленно навигируема. Модель может `ls /data/customers/` для списка всех клиентов, `cat /data/customers/acme-corp/profile.json` для чтения конкретного профиля и `grep -r "renewal" /data/customers/` для поиска всей информации о продлениях. Никакого кастомного языка запросов, никакой документации API, никаких специальных инструментов.

## Технические преимущества

### Точный retrieval против семантической близости

Традиционные RAG-подходы (Retrieval Augmented Generation) полагаются на поиск по семантической близости — превращение запросов в векторы и поиск ближайших совпадений. Это работает, но размыто. Вы получаете «похожие» результаты, не точные совпадения.

Поиск по файловой системе с инструментами вроде `grep` даёт точные совпадения:

```bash
# Find all files mentioning a specific customer ID
grep -rl "CUST-12345" /data/

# Find all contracts expiring this quarter
grep -l "expires.*2024-Q3" /data/customers/*/contracts/

# Count total revenue by product
awk -F',' '{sum += $4} END {print sum}' /data/reports/q2-2024.csv
```

Эти операции детерминистичны. Вы получаете ровно то, что просили, каждый раз. Никакого скоринга релевантности, пропущенных результатов и галлюцинированных совпадений.

### Минимальная загрузка контекста

Один из главных вызовов дизайна агентов — управление контекстным окном. Кастомные retrieval-системы часто грузят слишком много или слишком мало информации.

Файловый подход решает это естественно:

- **Ленивая загрузка**: агент читает файлы только когда нужны
- **Селективное чтение**: `head -20 file.csv` читает только заголовок и первые строки
- **Таргетный поиск**: `grep` находит ровно те строки, что важны
- **Прогрессивное исследование**: агент может сначала `ls` директорию, затем нырнуть в конкретные файлы

Этот паттерн «по требованию» держит контекстное окно сфокусированным на релевантном, снижая расход токенов и повышая качество ответов.

### Безопасность через изоляцию в песочнице

Файловые агенты тривиально песочатся:

- Смонтировать read-only файловую систему для данных, которые агент должен опрашивать, но не менять
- Использовать изоляцию контейнеров для предотвращения доступа вне директории данных
- Выставить лимиты ресурсов (CPU, память, время исполнения) на bash-команды
- Логировать каждую команду для аудируемости

Это драматически проще, чем встраивать контроль доступа в кастомные API-инструменты. Модель прав ОС делает тяжёлую работу.

## Устраняет кастомные retrieval-пайплайны

Подумайте, чего требует традиционный подход:

1. **Ingestion данных**: парсить документы, извлекать текст, обрабатывать разные форматы
2. **Генерация эмбеддингов**: превращать чанки текста в векторы
3. **Векторное хранение**: поддерживать векторную базу с индексацией
4. **Обработка запросов**: превращать запросы юзера в векторы, искать ближайших соседей
5. **Ререйтинг**: скорить и фильтровать результаты по релевантности
6. **Сборка контекста**: комбинировать извлечённые чанки в связный контекст

Файловый подход заменяет всё это на:

1. **Организовать данные в файлы и директории**
2. **Дать агенту bash-доступ**

Вот и всё. Никаких моделей эмбеддингов, векторных баз, настройки retrieval. Снижение сложности системы — колоссальное.

## Реальный пример: агент по sales-звонкам

Команда Vercel продемонстрировала это на агенте анализа продажных звонков. Задача: помочь отделам продаж анализировать взаимодействия с клиентами и извлекать инсайты.

### Организация данных

Данные продаж были организованы в естественную структуру директорий:

```
/sales-data/
├── calls/
│   ├── 2024-01-15-acme/
│   │   ├── transcript.txt
│   │   ├── summary.json
│   │   └── action-items.md
│   └── 2024-01-16-globex/
│       ├── transcript.txt
│       ├── summary.json
│       └── action-items.md
├── playbooks/
│   ├── discovery-call.md
│   ├── demo-script.md
│   └── objection-handling.md
└── metrics/
    ├── conversion-rates.csv
    └── pipeline-status.json
```

### Взаимодействие агента

На вопрос «Какие возражения всплывали в недавних звонках с энтерпрайз-проспектами?» агент:

1. Листает директории звонков, определяя недавние
2. Читает summary-файлы, отбирая энтерпрайз-проспектов
3. Ищет в транскриптах паттерны, связанные с возражениями
4. Сверяется с плейбуком обработки возражений
5. Синтезирует находки в действенный отчёт

Каждый шаг — стандартные bash-команды. Никаких кастомных инструментов. Никакого retrieval-пайплайна. Модель навигирует данные так же, как человек навигировал бы свою файловую систему.

## Паттерн: организовать → дать доступ → навигировать

Обобщаемый паттерн прост:

### 1. Организуйте данные

Структурируйте доменные данные в логичную иерархию директорий. Подумайте, как человек хотел бы browsить и искать эту информацию:

- Используйте осмысленные имена директорий и файлов
- Храните связанную информацию вместе
- Используйте стандартные форматы (JSON, CSV, Markdown), лёгкие для чтения и парсинга
- Включайте метаданные в имена файлов или metadata-файлы

### 2. Выдайте bash-доступ

Дайте агенту доступ к песочнице bash со смонтированными организованными данными:

- Read-only доступ для кейсов «только запросы»
- Соответствующие права записи, если агенту нужно создавать отчёты или обновлять записи
- Лимиты ресурсов против runaway-команд

### 3. Пусть модель навигирует

Модель использует знакомые терминальные идиомы для исследования и анализа данных:

- `ls` и `find` для обнаружения
- `cat`, `head`, `tail` для чтения
- `grep`, `awk`, `sort` для поиска и фильтрации
- `wc`, `uniq`, `jq` для агрегации и трансформации
- Shell-скрипты для сложных многошаговых операций

## Когда использовать этот подход

Паттерн «файловая система + bash» работает лучше всего, когда:

- **Данные документо-ориентированы**: файлы, отчёты, логи, транскрипты
- **Запросы исследовательские**: агент не знает точно, что ему понадобится upfront
- **Стоимость важна**: хотите минимизировать расход токенов и стоимость API
- **Ценится простота**: хотите избежать поддержки сложной инфраструктуры
- **Важен дебаг**: нужно понимать точно, что агент сделал

Менее подходит, когда:

- Данные требуют сложных JOIN'ов через многие связи (используйте SQL)
- Вовлечены realtime-данные с высокой пропускной записью
- Нужны транзакционные гарантии на модификациях данных
- Объём данных слишком велик для практической организации в файлы

## Ключевой вывод

Подход «файловая система + bash» — не просто хитрый хак; это признание, что у LLM уже есть мощный, хорошо обученный интерфейс для исследования данных. Вместо построения новых абстракций поверх этой способности используйте её напрямую. Организуйте данные так, чтобы это совпадало с тем, что модель уже умеет, — и пусть она работает так, как её обучали работать.

Снижение стоимости на 75% впечатляет, но настоящий выигрыш — архитектурная простота. Меньше движущихся частей — меньше режимов отказа, легче дебаг и быстрее итерации.
