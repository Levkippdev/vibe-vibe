# Тестирование: достаточно ли bash — сравнение агентов SQL и Bash

**Авторы: Ankur Goyal, Andrew Qu (Vercel & Braintrust)**

**Оригинал: [Читать полную статью](https://vercel.com/blog/testing-if-bash-is-all-you-need)**

<div class="article-meta">
</div>

> ## Резюме
>
> Когда Vercel заявил, что агенты могут эффективно работать с одной файловой системой и bash, возник естественный вопрос: как это сравнивается со специализированными инструментами вроде SQL? Это эмпирическое исследование даёт ответ — и главный вывод не о том, какой инструмент побеждает.

## Вопрос

После исследования Vercel файлово-bash-агентов возник естественный follow-up: если bash так хорош для общей разведки данных, как он сравнивается с SQL — языком, специально созданным для запросов к структурированным данным?

Чтобы узнать, Vercel объединился с Braintrust для строгого эмпирического сравнения. Эксперимент тестировал разные конфигурации агентных инструментов на стандартизированном наборе задач анализа данных, измеряя точность, стоимость и надёжность.

## Сетап эксперимента

### Бенчмарк

Команда разработала набор задач анализа данных, требующих запросов к структурированным данным — та работа, где SQL традиционно очевидный выбор. Задачи варьировались от простых поисков («Какова была общая выручка в Q3?») до сложных агрегаций («Какая категория продуктов имела самый высокий рост месяц-к-месяцу за последние 6 месяцев?»).

### Конфигурации агентов

Тестировались три конфигурации:

1. **Чистый SQL-агент**: доступ только к SQL-базе и инструменту исполнения SQL-запросов
2. **Чистый Bash-агент**: доступ только к данным как CSV/JSON-файлам и bash-терминалу
3. **Гибрид SQL+Bash-агент**: доступ и к SQL, и к bash, плюс шаг самоверификации

Каждый агент получал одну и ту же базовую языковую модель и одни данные. Единственной переменной был набор инструментов и паттерн взаимодействия.

## Результаты

### Чистый SQL-агент: 100% точность

SQL-агент работал безупречно на задачах со структурированными данными. Неудивительно — SQL создан именно для такой работы. Агент мог:

- Писать точные запросы, извлекающие ровно нужные данные
- Естественно использовать JOIN'ы, GROUP BY и оконные функции
- Обрабатывать сложные агрегации одним запросом
- Задействовать индексацию базы для эффективного исполнения

Декларативная природа SQL идеально совпадает с анализом данных: вы описываете, *что* хотите, а не *как* получить. Обширное обучение модели на SQL означает стабильно точные запросы.

### Чистый Bash-агент: хорошо, но не идеально

Bash-агент достиг высокой точности, но недотянул до SQL на структурированных данных. Хотя он корректно обрабатывал многие запросы инструментами вроде `awk`, `sort`, `uniq` и `jq`, некоторые операции были громоздки:

- Сложные мульти-табличные JOIN'ы требовали многошаговых пайплайнов, склонных к ошибкам
- Агрегации с несколькими уровнями группировки было труднее выразить
- Edge cases парсинга CSV (квотированные поля, экранированные запятые) иногда спотыкали шелл-подход
- Некоторые вычисления требовали написания мини-скриптов, добавляя сложность

Bash-агент сиял на задачах текстового поиска, матчинга паттернов и исследования структуры данных — областях, где файловый подход силён. Но для чистого анализа структурированных данных специализированные абстракции SQL давали явное преимущество.

### Гибрид SQL+Bash с самоверификацией: 100% точность

Самый интересный результат — у гибридной конфигурации. С доступом и к SQL, и к bash, плюс явный шаг самоверификации, этот агент тоже достиг 100% точности.

Шаг самоверификации был ключом: после генерации ответа агента инструктировали верифицировать результат альтернативным методом. Например:

1. Прогнать SQL-запрос для получения ответа
2. Экспортировать результат
3. Bash'ем независимо верифицировать вычисление
4. Сравнить результаты перед отчётом

Или наоборот:

1. Bash'ем исследовать данные и вычислить ответ
2. Написать SQL-запрос для проверки
3. Разрешить расхождения

Такая перекрёстная проверка ловила ошибки, которые любой инструмент поодиночке мог бы упустить.

## Ключевой инсайт: верификация важнее выбора инструмента

Главный вывод — не «SQL бьёт bash» и не «bash достаточно хорош». Он такой: **самоверификация важнее, какой инструмент вы используете**.

И чистый SQL-агент (100%), и гибрид с верификацией (100%) достигли идеальной точности. Гибрид добился этого, несмотря на использование bash для операций, где он менее уместен, — потому что шаг верификации ловил и исправлял любые ошибки.

Это имеет глубокие импликации для дизайна агентов:

### Верификация как первоклассная задача

Большинство агентных фреймворков фокусируются на выборе и оркестрации инструментов. Этот эксперимент показывает: шаг верификации — когда агент проверяет свою работу — минимум так же важен, как сами инструменты. Посредственный инструмент с хорошей верификацией может сравняться с идеальным инструментом без верификации.

### Паттерн самоверификации

Паттерн самоверификации прост в имплементации:

```
1. Agent performs the task using its preferred method
2. Agent independently verifies the result
   - Using a different tool or approach
   - Using a different query that should produce the same answer
   - Using sanity checks (totals should sum, counts should be positive, etc.)
3. If verification fails, agent corrects and re-verifies
4. Agent reports the verified result with confidence
```

Паттерн применим за пределами анализа данных. Кодинг-агенты могут гонять тесты после написания кода. Агенты документации могут сверять точность с исходным кодом. Любой агент выигрывает от проверки собственной работы перед отчётом.

## Практические импликации

### Выбор инструментов для агента

Результаты подсказывают практическую рамку выбора:

| Тип данных | Лучший инструмент | Обоснование |
|-----------|-----------|-----------|
| Структурированные данные (таблицы, базы) | SQL | Специализирован, декларативен, точен |
| Неструктурированный текст (логи, документы) | Bash | grep, awk и пайпы здесь превосходны |
| Смешанные данные | Гибрид | Правильный инструмент на каждую подзадачу |
| Любая критичная задача | + Верификация | Всегда верифицируйте, независимо от инструмента |

### Не переусложняйте выбор инструментов

Соблазнительный вывод: давать агентам все возможные инструменты. Но есть trade-off: больше инструментов — больше сложность решений для модели. Эксперимент подсказывает, что **сфокусированный набор инструментов плюс верификация** обходит **широкий набор без верификации**.

Строите агента для структурированных данных — дайте SQL и добавьте верификацию. Для исследования документов — bash и верификацию. Не стройте оба, если ваш кейс не охватывает оба домена.

### Соображения стоимости

Bash-подход остаётся значительно дешевле для исследовательских задач:

- SQL требует поддержки сервера базы
- Bash работает прямо на файлах, устраняя стоимость инфраструктуры
- Для read-heavy исследовательских workload'ов файловый подход тратит меньше токенов
- Но для сложных аналитических запросов эффективность одного SQL-запроса может тратить меньше токенов, чем многошаговые bash-пайплайны

Оптимум зависит от вашего паттерна workload'ов.

## За пределами анализа данных

Эксперимент фокусировался на анализе данных, но принцип самоверификации обобщается широко:

### Генерация кода

Агент, пишущий код, может:
1. Написать код
2. Прогнать тест-сьют
3. При падении проанализировать и починить
4. Перегнать тесты для верификации

Это уже стандартная практика кодинг-агентов — эксперимент квантифицирует, почему это работает.

### Генерация контента

Агент, пишущий документацию, может:
1. Сгенерировать документацию
2. Проверить, что примеры кода реально компилируются и запускаются
3. Сверить, что ссылки на API совпадают с реальным API
4. Убедиться, что кросс-ссылки валидны

### Принятие решений

Агент, делающий рекомендации, может:
1. Проанализировать данные и сформировать рекомендацию
2. Проверить рекомендацию на ограничения
3. Верифицировать вычисления, использованные в анализе
4. Презентовать рекомендацию с доказательствами верификации

## Ключевые выводы

1. **Соответствуйте инструментам типы данных**: SQL для структурированных, bash для неструктурированной разведки
2. **Всегда добавляйте самоверификацию**: это самое impactful решение в дизайне агента
3. **Верификация компенсирует ограничения инструментов**: слабее инструмент + верификация может сравняться с сильным инструментом в одиночку
4. **Держите набор инструментов сфокусированным**: больше инструментов — больше сложность; лучше овладеть меньшим числом с верификацией
5. **Кросс-инструментальная верификация сильнейшая**: проверка результатов другим подходом ловит систематические ошибки, которые same-tool-верификация может упустить

Эксперимент даёт эмпирический фундамент принципу, который многие практики интуитивно знали: в дизайне агентов способность проверить свою работу значит столько же, сколько способность сделать работу.
