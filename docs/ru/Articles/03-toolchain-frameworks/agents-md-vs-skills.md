# AGENTS.md vs Skills: почему пассивный контекст обходит активный retrieval

**Автор: Vercel Team**

**Оригинал: [Читать полную статью](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)**

<div class="article-meta">
</div>

> **Источник:** [официальный блог Vercel](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)

## Проблема

AI-кодинг-ассистенты полагаются на обучающие данные, которые устаревают. Next.js 16 ввёл новые API вроде `'use cache'`, `connection()` и `forbidden()`, которых нет в текущих обучающих данных моделей. Когда агенты не знают об этих API, они генерируют некорректный код или откатываются к устаревшим паттернам.

Верно и обратное: если вы на старой версии Next.js, модели могут предлагать новые API, которых в вашем проекте ещё нет. Команда Vercel хотела решить это, дав агентам доступ к документации, совпадающей с версией.

## Два метода обучения

До результатов — быстрое объяснение двух протестированных подходов:

### Skills

[Skills](https://agentskills.io/) — открытый стандарт упаковки доменных знаний для кодинг-агентов. Skill бандлит промпты, инструменты и документацию, которую агенты могут вызывать по требованию. Идея: агенты распознают, когда им нужна помощь по фреймворку, вызывают Skill и получают доступ к релевантной документации.

### AGENTS.md

[AGENTS.md](https://agents.md/) — Markdown-файл в корне проекта, дающий персистентный контекст для кодинг-агентов. Что бы вы ни положили в `AGENTS.md`, агент имеет к этому доступ на каждом ходу — без решения агента загружать. Claude Code использует `CLAUDE.md` с той же целью.

Команда Vercel построила Skill с документацией Next.js и индекс документации в `AGENTS.md`, затем прогнала их через evaluation-сьют, чтобы увидеть, что работает лучше.

## Первоначальная ставка на Skills

Skills казались правильной абстракцией. Упаковываете документацию фреймворка в Skill, агент вызывает её при работе с задачами Next.js — и получаете корректный код. Чистое разделение забот, минимальный оверхед контекста — агент грузит только нужное. Есть даже растущий каталог переиспользуемых Skills на [skills.sh](https://skills.sh/).

Команда ожидала: встретив задачу Next.js, агент вызовет Skill, прочитает документацию совпадающей версии и сгенерирует корректный код.

Затем они запустили оценки.

## Skills не срабатывали надёжно

В 56% оценочных кейсов Skill вообще не вызывался. Агент имел доступ к документации — но не использовал. Добавление Skill дало ноль улучшений к baseline:

| Конфигурация | Pass Rate | vs. Baseline |
| --- | --- | --- |
| Baseline (без доков) | 53% | — |
| Skill (дефолтное поведение) | 53% | +0pp |

Ноль улучшений. Skill существовал, агент мог его использовать — но решил не использовать. В детальном разбивке build/check/test Skill местами работал хуже baseline (test 58% против 63%), что намекает: неиспользуемый Skill в окружении может вносить шум или интерференцию.

Это не уникально для их сетапа. Агенты ненадёжно используют доступные инструменты — задокументированная проблема, с которой сталкивались все, кто экспериментировал с tool-using-агентами.

## Принудительный вызов помог, но недостаточно

Команда попробовала жёстче указывать агенту использовать Skill. Это улучшило вызовы, но результат был неустойчив: вызванный Skill работал нормально, но общий pass rate остался ниже ожиданий. Агенты иногда вызывали Skill для несвязанных задач или игнорировали его содержимое после вызова.

Даже с идеальными вызовами Skills столкнулись с потолком: лучший результат Skills — 79% pass rate против 100% у AGENTS.md.

## AGENTS.md: подход через индекс

Команда переключилась на подход через `AGENTS.md`. Вместо Skill с полной документацией — компактный индекс ключевых API, паттернов и gotcha в файле, всегда доступном агенту.

Проблема: полная документация Next.js огромна. Поместить всё в `AGENTS.md` означало бы раздуть контекст каждого хода. Решение — 8KB сжатого индекса:

```markdown
# Next.js 16 Documentation Index

## New APIs
- `'use cache'` — Server Component caching directive (v16)
  Usage: add at top of server component file
  Common mistakes: using inside client components
- `connection()` — runtime connection state (v16)
  Usage: import from 'next/server' in server components
- `forbidden()` / `unauthorized()` — auth guards (v16)

## Changed in v16
- `middleware.ts` → `proxy.ts` (renamed)
- Default cache behavior changed — verify before assuming

## Common Errors
- "use cache" without Suspense boundary → hydration errors
- connection() in client components → build error
```

Индекс содержит не документацию — а карту документации: какие API существуют, когда их использовать, типичные ошибки. Достаточно для агента, чтобы писать корректный код и знать, когда копать глубже.

## Результаты: AGENTS.md доминирует

| Конфигурация | Pass Rate |
| --- | --- |
| Baseline (без доков) | 53% |
| Skill (дефолтное поведение) | 53% |
| Skill (принудительный вызов) | 79% |
| AGENTS.md (8KB индекс) | **100%** |

AGENTS.md достиг идеального pass rate с компактным индексом. Каждый кейс — build, check, test — прошёл с правильным использованием новых API.

## Почему пассивный контекст бьёт активный retrieval

Результаты выявляют фундаментальный инсайт о том, как агенты используют информацию.

### Проблема точки решения

Skills требуют, чтобы агент решил: «Мне нужно проверить документацию?» Это решение — точка отказа. Агент должен:

1. Распознать, что текущая задача может выиграть от документации
2. Вспомнить, что Skill существует
3. Решить, что вызов стоит усилия
4. Правильно интерпретировать возвращённую документацию

Каждый шаг — шанс на провал. Устав от сложности, модели часто пропускают вызов инструментов, особенно в потоке сложной задачи.

AGENTS.md устраняет решение. Информация просто есть — каждый ход, без решения. Нет «проверить ли доки?», нет «загружать ли Skill?» — знание уже в контексте.

### Видимость против вспоминаемости

Есть когнитивная разница между информацией, которую нужно вспомнить, и информацией, которая перед глазами.

Skills требуют вспоминаемости: агент должен помнить, что Skill существует, и активно его вызывать. Это как инженер, который должен помнить, что где-то есть внутренняя вики — и сходить поискать.

AGENTS.md дают видимость: знание присутствует в каждом промпте. Это как стикер на мониторе — вы не можете его не видеть.

Для моделей, обученных на next-token-предсказании, информация в текущем контексте радикально доступнее, чем информация, требующая tool-вызова.

### Паттерн interleaved-знаний

Команда также обнаружила, что лучше всего работает интерливинг документации с кодом в контексте, а не отдельный блок:

```markdown
## Task
Implement user profile caching

## Relevant API
`'use cache'` — add at top of server component
Common mistake: missing Suspense boundary

## Implementation
...
```

Когда знание расположено рядом с задачей, модели используют его надёжнее, чем при отдельном справочном блоке.

## Компрессия — ключ

Важнейшая находка: не нужна полная документация. 8KB сжатого индекса обошли полные доки и в форме Skill, и в загружаемом блоке.

Почему компрессия работает:

1. **Меньше контекста — лучше фокус.** Раздутый контекст деградирует производительность модели на всех задачах, не только связанных с лишней информацией.
2. **Индексы достаточно для большинства задач.** Агенту редко нужна полная спецификация — ему нужно знать, что API существует, базовый паттерн использования и главные gotcha.
3. **Сжатие фильтрует шум.** Команда, кураторно отбирающая индекс, включает только проверенные, актуальные паттерны — не всё.

Правило Vercel: если документация не помещается в ~8KB, найдите, что можно вырезать. Если нельзя — возможно, вам нужен не индекс, а рефакторинг документации.

## Ограничения подхода

Честность требует оговорок:

**AGENTS.md не масштабируется бесконечно.** 8KB работает для одного фреймворка. Проект с 10 фреймворками потребует компромиссов — возможно, иерархической организации или возврата к selective-загрузке.

**Skills остаются ценными для вертикальных воркфлоу.** AGENTS.md силён для горизонтальных знаний (применимо к каждой задаче). Skills лучше для вертикальных процессов (конкретные последовательности шагов для конкретных операций — деплой, релиз, миграции).

**Команды, отличные от Vercel, могут увидеть иные результаты.** Ваш пробег может варьироваться в зависимости от моделей, задач и качества вашей документации.

## Рекомендации

1. **Для знаний фреймворка используйте AGENTS.md.** Пишите сжатый индекс (цель ~8KB) критичных API, паттернов и gotcha вашей версии.

2. **Для повторяемых воркфлоу используйте Skills.** Процессные знания (как деплоить, как релизить) подходят Skills — им нужна последовательная структура, а не фрагментарный индекс.

3. **Тестируйте с собственными оценками.** Стройте evaluation-сьюты для вашего домена. Не доверяйте чужим результатам вслепую.

4. **Версионная специфичность важна.** Убедитесь, что ваша документация совпадает с версией фреймворка, которую вы реально используете.

5. **Компрессируйте агрессивно.** Каждый килобайт контекста должен заслуживать место. Если что-то не используется агентами — удаляйте.

## Заключение

Оценка Vercel даёт ясный ответ для знаний фреймворка: пассивный, всегда доступный контекст через AGENTS.md радикально обходит on-demand Skills. При текущих способностях моделей удаление точки решения «загружать ли документацию?» — самый большой рычаг улучшения производительности агентов.

Будущее может измениться: модели, лучше замечающие доступные инструменты, сделают Skills надёжнее. Но сегодня работайте с реальностью: пассивный контекст побеждает.

Для команд это означает смену мышления: не «как заставить агентов искать информацию?», а «какая информация должна быть всегда перед ними?». Это сдвиг от претрейн-ведомого рассуждения к retrieval-ведомому. `AGENTS.md` оказался самым надёжным способом этого достичь.

## Ключевые выводы

1. **Пассивный контекст > активный retrieval:** При текущих способностях моделей всегда доступный контекст надёжнее Skills по требованию.

2. **Компрессия — ключ:** 8KB-сжатый индекс достигает 100% pass rate — полная документация не нужна.

3. **Устраняйте точки решения:** Не заставляйте агента решать «проверить ли доки?» — сделайте доки всегда доступными.

4. **Совпадение версий важно:** Убедитесь, что агент обращается к документации, совпадающей с реальной версией фреймворка проекта.

5. **Два подхода дополняют друг друга:** AGENTS.md для горизонтальных знаний фреймворка, Skills для вертикальных специфичных воркфлоу.
