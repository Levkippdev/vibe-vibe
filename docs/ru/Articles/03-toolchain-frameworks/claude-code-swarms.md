# Claude Code Swarms: мульти-агентная коллаборативная разработка

**Автор: Addy Osmani**

**Оригинал: [Читать полную статью](https://addyosmani.com/blog/claude-code-agent-teams/)**

<div class="article-meta">
</div>

> ## Резюме
>
> Claude Code теперь поддерживает [команды агентов](https://code.claude.com/docs/en/agent-teams) (swarms) — больше не один агент, работающий последовательно, а ведущий агент, делегирующий нескольким тиммейтам, работающим параллельно. Включите agent teams в `settings.json`, чтобы попробовать. Если вы исследовали мульти-агентную оркестрацию через Conductor, Gas Town или похожие инструменты — вот где эти идеи становятся нативными.

Комьюнити называет эти паттерны **swarms** — скоординированные команды AI-агентов, каждый со специализированной ролью, работающие параллельно через структурированную коммуникацию. То, что началось с разработчиков, находящих feature flag'и в бинарнике Claude Code и строящих workaround'ы через суб-агентов и bash-скрипты, теперь first-class-фича. TeammateTool, коммуникация через inbox, tmux-сплит-скрин — всё здесь.

Это важно, потому что архитектура фундаментально отличается от одноагентной модели, которой большинство из нас пользовалось. Если вы следили за [сдвигом от командира к оркестратору](https://addyosmani.com/blog/future-agentic-coding/) или экспериментировали с [параллельными агентными воркфлоу](https://addyosmani.com/blog/coding-agents-manager/), команды агентов — вот где эти идеи становятся реальностью.

## Почему мульти-агентная координация важна

У одноагентной модели известный режим отказа. Вы просите Claude о чём-то сложном — например, отрефакторить аутентификацию через три сервиса — и он может пройти 60%, прежде чем контекст начнёт деградировать. Детали шага 2 размываются в шаг 5. Вы делаете `/clear` и начинаете заново. Повторяете до фрустрации.

Ключевой инсайт swarms прост: **LLM работают хуже по мере расширения контекста**. Дело не только в лимитах токенов — чем больше информации в контекстном окне, тем труднее модели фокусироваться на текуще важном. Добавление стратегических заметок продакт-менеджера в контекст агента, чинящего CSS-баг, реально вредит производительности.

Человеческие команды работают так же. Мы не сажаем backend-инженеров в ревью frontend-кода. Мы не CC'им всю компанию в каждый Slack-тред. Специализация — про фокус.

Мульти-агентный паттерн формализует это. Давая каждому агенту узкий scope и чистый контекст, вы получаете лучшее рассуждение внутри каждого домена, независимые проверки качества, естественные чекпоинты между фазами и грациозную деградацию при провале одного агента. Тест-агент имеет тесты в контексте — не три часа обсуждения планирования. Security-ревьюеру не нужно продираться через заметки об оптимизации производительности.

Одна оговорка: это работает только при правильном скопинге задач. «Построй мне приложение» сожжёт токены в мучениях агентов. «Имплементируй эти пять чётко определённых API-эндпоинтов по этой спеке» даёт хорошие результаты.

## Что такое команды агентов

Архитектура проста. Одна сессия Claude Code становится **тимлидом**. Она порождает **тиммейтов** — каждый полноценный независимый инстанс Claude Code со своим большим токен-контекстным окном. Есть shared-лист задач с трекингом зависимостей, коммуникация на inbox между агентами и параллельное исполнение через tmux-сплиты.

### Ключевые компоненты

**TeammateTool** — новый инструмент, позволяющий ведущему агенту порождать тиммейтов. Каждый тиммейт получает:
- Собственное контекстное окно (не разделяет контекст с ведущим)
- Определённую роль/специализацию
- Доступ к тем же инструментам и файлам проекта

**Общий список задач** — структурированный таск-трекер:
- Задачи с зависимостями (задача B требует завершения A)
- Статус: pending/in_progress/completed/blocked
- Видимость для всех агентов — никто не дублирует работу

**Inbox-коммуникация** — агенты не болтают свободно; они отправляют структурированные сообщения:
- Запросы на ревью («проверь мою имплементацию X»)
- Отчёты о статусе («завершил API-эндпоинт, тесты проходят»)
- Блокировки («не могу продолжить, пока Y не решён»)
- Эскалации («это архитектурное решение выше моего уровня»)

**Параллельное исполнение через tmux** — каждый агент работает в своём tmux-пейне. Вы буквально смотрите, как несколько Claude Code работают одновременно, каждый в собственном терминальном окне.

### Как это выглядит

Ведущий агент получает вашу задачу, создаёт план, разбивает на подзадачи и порождает тиммейтов:

```
You: "Refactor the auth system across the three services"

Lead Agent:
  1. Analyzes the current architecture
  2. Creates task list:
     - Task 1: Extract shared auth utilities (no dependencies)
     - Task 2: Refactor service-a to use new utilities (depends on Task 1)
     - Task 3: Refactor service-b (depends on Task 1)
     - Task 4: Refactor service-c (depends on Task 1)
     - Task 5: Integration tests (depends on Tasks 2-4)
  3. Spawns teammates:
     - Teammate A: "You're handling Tasks 2-3. Service-a first,
       then service-b. Read the shared utilities first."
     - Teammate B: "You're handling Task 4, service-c."
  4. Monitors progress, reviews completed work
  5. Spawns self for Task 5 when dependencies complete
```

Тиммейты работают параллельно. Timmate A рефакторит service-a, пока Teammate B работает над service-c. Они не наступают друг другу на ноги, потому что задачи имеют явные зависимости.

## Практические паттерны

### Паттерн 1: Исследование → исполнение

Самый частый паттерн — разделить исследование и имплементацию:

**Ведущий агент** (или выделенный исследовательский агент):
- Читает кодовую базу, документацию, требования
- Понимает конвенции проекта
- Формирует план имплементации
- НЕ пишет код

**Тиммейт(ы)** (исполнители):
- Получают план от ведущего
- Каждый берёт конкретную задачу из списка
- Пишут код в собственном чистом контексте
- Докладывают о завершении, передают на ревью

Почему это работает: исследовательский контекст (требования, конвенции, архитектура) загрязняет имплементационный контекст. Их разделение держит каждое контекстное окно сфокусированным.

### Паттерн 2: Исполнение плюс ревью

Другой паттерн — выделенный ревью-агент:

- **Имплементатор** пишет фичу
- **Ревьюер** проверяет код на: корректность, конвенции проекта, проблемы безопасности, покрытие тестами
- Ревьюер НЕ имеет контекста имплементации — только код, спеку и конвенции

Почему это работает: ревьюер без знания «почему код такой» ловит проблемы, которые имплементатор, ослепленный собственным контекстом, упустит. Это то же самое, почему люди ценят ревью свежим взглядом.

### Паттерн 3: Специализация по доменам

Для больших задач агенты специализируются:

- **Frontend-агент**: UI-компоненты, стили, клиентская логика
- **Backend-агент**: API-эндпоинты, логика базы, серверные операции
- **Тест-агент**: юнит-тесты, интеграционные тесты, e2e-покрытие
- **Док-агент**: документация API, README, комментарии

Каждый получает только релевантный контекст. Backend-агент не грузит CSS-дизайн-токены. Тест-агент видит спеку и код, но не разговор о выборе фреймворка.

## Соображения стоимости и токенов

Мульти-агентность не бесплатна. Каждый агент — отдельное контекстное окно, потребляющее токены.

### Математика токенов

Один агент с большим контекстом:
- Один полный проход через контекст
- Стоимость масштабируется с размером контекста

Три агента со специализированным контекстом:
- Три меньших контекстных окна
- Общий объём может быть меньше одного раздутого контекста
- Плюс оверхед координации (сообщения, обновления задач)

Практическое правило: если задача помещается в один контекст без деградации, один агент проще и дешевле. Мульти-агенты сияют, когда контекст в противном случае разросся бы до неуправляемости.

### Когда мульти-агенты дешевле

Контринтуитивно мульти-агенты могут быть дешевле:

- **Деградация контекста стоит дорого.** Когда одноагентный контекст разрастается, модель начинает делать ошибки, требующие повторных попыток, уточнений и переделок. Каждая переделка — токены.
- **Параллелизм сжимает wall-clock время.** Три агента, работающие 10 минут, завершают за 10 минут, а не 30.
- **Чистый контекст = меньше промпт-фиксов.** Агент со специализированным контекстом делает меньше ошибок, чем генералист с перегруженным контекстом.

### Мониторинг стоимости

Отслеживайте:
- Токены на агента
- Общие токены на задачу
- Оверхед координации (токены, потраченные только на сообщения)
- Сравнение одноагентного baseline

Если мульти-агентная версия стабильно дороже на 30%+ без прироста качества — паттерн вам не подходит.

## Ограничения и реальность

### Что всё ещё тяжело

**Сквозной контекст между агентами.** Тиммейты не разделяют живой контекст. Если Timmate A обнаруживает, что паттерн, который использует Teammate B, сломан, передача этого знания требует явных сообщений. Ведущий агент должен активно фасилитировать обмен знаниями.

**Merge-конфликты.** Два агента, редактирующие один файл, — реальность. Список задач с зависимостями помогает, но не гарантирует. Нужны соглашения о владении файлами или серийное редактирование горячих файлов.

**Сложность дебага.** Когда мульти-агентный прогон идёт не так, диагностировать сложнее. Что делал каждый агент? В каком порядке? Кто внёс баг? tmux-история помогает, но это не то же, что единый трейс.

**Разброс качества.** Разные тиммейты — разное качество вывода. Ведущий должен ревьюить всё, что делает каждый, иначе несогласованная работа будет мержиться.

### Когда НЕ использовать

- Небольшие задачи, помещающиеся в один контекст
- Задачи с жёсткими последовательными зависимостями (нет параллелизируемых частей)
- Highly exploratory работа, где план эволюционирует каждую минуту
- Когда стоимость токенов важнее скорости

## Начало работы

Включите agent teams в настройках Claude Code (см. [документацию](https://code.claude.com/docs/en/agent-teams)). Затем попробуйте на своей задаче:

1. Начните с задачи с параллелизируемыми компонентами
2. Пусть ведущий создаст план и список задач
3. Пусть порождает 2 тиммейтов для независимых задач
4. Наблюдайте tmux-пейны и координацию
5. Ревьюьте результаты ведущего

Продвинитесь к более амбициозным мульти-агентным сетапам, когда освоите координацию.

## Куда это движется

Команды агентов — естественная эволюция [agentic engineering](https://addyosmani.com/blog/agentic-engineering/). По мере того как модели улучшаются в следовании инструкциям и координации, мы увидим:

- Больше нативных паттернов мульти-агентности в инструментах
- Стандартизированные протоколы агент-агент-коммуникации
- Лучшую обработку shared-состояния между агентами
- Гибриды «человек + флот агентов» как норму продакшн-разработки

Архитектура координации AI-агентных систем уже здесь. Используйте её мудро.

Полная [документация Claude Code agent teams](https://code.claude.com/docs/en/agent-teams) содержит полные гайды по настройке и использованию.
