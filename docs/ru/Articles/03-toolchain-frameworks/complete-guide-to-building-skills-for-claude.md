## Введение

Skill — набор инструкций, упакованных в простую папку, который учит Claude обращаться с конкретными задачами или воркфлоу. Skills — один из мощнейших способов кастомизировать Claude под нужные задачи. Вместо того чтобы заново объяснять свои предпочтения, процессы и доменную экспертизу в каждом разговоре, skills позволяют обучить Claude один раз — и выигрывать каждый раз.

Skills особенно сильны при повторяемых воркфлоу: генерация frontend-дизайна из спецификаций, исследования по консистентной методологии, создание документации по стайл-гайду команды или оркестрация многошаговых процессов. Они хорошо работают вместе со встроенными способностями Claude вроде исполнения кода и создания документов. Тем, кто строит MCP-интеграции, skills добавляют ещё один мощный слой, помогающий превращать сырой доступ к инструментам в надёжные, оптимизированные воркфлоу.

Этот гайд покрывает всё, что нужно знать для построения эффективных skills — от планирования и структуры до тестирования и дистрибуции. Строите ли вы skill для себя, команды или комьюнити — по ходу найдёте практические паттерны и примеры из реальной жизни.

- Power-юзеры, желающие, чтобы Claude придерживался определённых процессов

## Основы

### Что такое Skill?

Skill — папка, содержащая:

- **SKILL.md** (обязательно): Markdown-инструкции с YAML frontmatter
- **scripts/** (опционально): исполняемый код (Python, Bash и т.д.)
- **references/** (опционально): документация, загружаемая по требованию
- **assets/** (опционально): шаблоны, шрифты, иконки, используемые в выводе

### Ключевые принципы дизайна

#### Прогрессивное раскрытие

Skills используют трёхуровневую систему:

- **Уровень 1 (YAML frontmatter):** всегда загружается в системный промпт Claude. Достаточно информации, чтобы Claude знал, когда использовать каждый skill — без загрузки всего содержимого в контекст.

- **Уровень 2 (тело SKILL.md):** загружается, когда Claude определяет релевантность skill'а для текущей задачи. Содержит полные инструкции и руководство.

- **Уровень 3 (связанные файлы):** дополнительные файлы в директории skill'а, к которым Claude может опционально обратиться и открыть только по необходимости.

Такое прогрессивное раскрытие минимизирует расход токенов, сохраняя доступность экспертизы.

#### Композируемость

Claude может загружать несколько skills одновременно. Ваш skill должен хорошо работать с другими, не предполагая, что он — единственная доступная способность.

#### Портативность

Skills работают одинаково на Claude.ai, Claude Code и API. Создайте skill один раз — и он работает на всех платформах без модификаций (при условии, что окружение поддерживает зависимости skill'а).

### Для строителей MCP: Skills + коннекторы

> 💡 Строите standalone-скиллы без MCP? Переходите к разделу «Планирование и дизайн» — сюда можно вернуться позже.

Если у вас уже есть работающий MCP-сервер — сложную часть вы сделали. Skills — это верхний слой знаний: они фиксируют уже известные вам воркфлоу и best practices, чтобы Claude применял их консистентно.

#### Кухонная аналогия

- **MCP даёт профессиональную кухню**: доступ к инструментам, ингредиентам и оборудованию
- **Skills дают рецепты**: пошаговые инструкции, как создать нечто ценное

Вместе они позволяют пользователю выполнять сложные задачи, не разбираясь самостоятельно в каждом шаге.

#### Как они работают вместе

| MCP (связность) | Skills (знания) |
| --- | --- |
| Подключает Claude к вашим сервисам (Notion, Asana, Linear и т.д.) | Учит Claude эффективно использовать ваши сервисы |
| Даёт доступ к данным в реальном времени и вызовы инструментов | Фиксирует воркфлоу и best practices |
| Что Claude **может** делать | Как Claude **должен** делать |

#### Почему это важно для ваших MCP-пользователей

**Без skills**:

- пользователь подключает ваш MCP и не знает, что делать дальше
- тикеты поддержки: «как сделать X через вашу интеграцию?»
- каждый разговор начинается с нуля
- неконсистентные результаты, потому что каждый промпт разный
- пользователи винят ваш коннектор, а реальная проблема — отсутствие руководства по воркфлоу

**С skills**:

- предустановленные воркфлоу активируются автоматически, когда нужны
- консистентное, надёжное использование инструментов
- best practices встроены в каждое взаимодействие
- ниже порог входа в интеграцию

## Планирование и дизайн

### Начните с юзкейсов

До написания любого кода определите 2–3 конкретных юзкейса, которые ваш skill должен включать.

#### Пример хорошего определения юзкейса

**Юзкейс: планирование спринта проекта**

- **Триггер**: пользователь говорит «помоги спланировать спринт» или «создай задачи спринта»
- **Шаги**:
  1. Получить текущее состояние проекта из Linear (через MCP)
  2. Проанализировать скорость и ёмкость команды
  3. Предложить приоритеты задач
  4. Создать в Linear задачи с подходящими лейблами и оценками
- **Результат**: полностью спланированный спринт с созданными задачами

#### Спросите себя

- Что пользователь хочет получить?
- Какие многошаговые воркфлоу для этого нужны?
- Какие инструменты нужны (встроенные или MCP)?
- Какие доменные знания или best practices стоит встроить?

### Три категории Skills

В Anthropic мы наблюдаем три типовых юзкейса:

#### Категория 1: Создание документов и ассетов

**Назначение**: создание консистентного качественного вывода — документация, презентации, приложения, дизайны, код и т.д.

**Реальный пример: skill frontend-design** (см. также skills для docx, pptx, xlsx и pdf)

> «Создавай уникальные продакшн-уровня frontend-интерфейсы с высоким качеством дизайна. Использовать при построении веб-компонентов, страниц, артефактов, постеров или приложений».

**Ключевые техники**:

- встроенные стайл-гайды и бренд-стандарты
- шаблонные структуры для консистентного вывода
- чеклисты контроля качества перед финализацией
- внешние инструменты не нужны — используются встроенные способности Claude

*Паттерн дизайна (из en-версии): задайте ясные спецификации вывода, включите примеры хорошего результата, укажите критерии качества и постройте чекпоинты самооценки.*

#### Категория 2: Автоматизация воркфлоу

**Назначение**: многошаговые процессы, выигрывающие от консистентного подхода, включая координацию между несколькими MCP-серверами.

**Реальный пример: skill skill-creator**

> «Интерактивный гайд по созданию новых skills. Ведёт пользователя через определение юзкейса, генерацию frontmatter, написание инструкций и валидацию».

**Ключевые техники**:

- пошаговый воркфлоу с гейтами валидации
- шаблоны типовых структур
- встроенное ревью и предложения по улучшению
- циклы итеративного улучшения

*Паттерн дизайна: смаппируйте полный воркфлоу с точками решений, определите критерии входа/выхода каждого шага и обрабатывайте ошибки на каждой стадии.*

#### Категория 3: Усиление MCP

**Назначение**: руководство по воркфлоу поверх доступа к инструментам, который даёт MCP-сервер.

**Реальный пример: skill sentry-code-review (от Sentry)**

> «Анализируй и автоматически чини ошибки, найденные в GitHub Pull Requests, используя данные мониторинга ошибок Sentry через его MCP-сервер».

**Ключевые техники**:

- координация нескольких MCP-вызовов в определённом порядке
- встроенная доменная экспертиза
- предоставление контекста, который пользователю пришлось бы указывать вручную
- обработка типовых проблем MCP

*Паттерн дизайна: задокументируйте оптимальную последовательность использования инструментов и гейты качества между шагами.*

### Определите критерии успеха

#### Как понять, что ваш skill работает?

Это идеальные ориентиры — грубые бенчмарки, а не точные пороги. Стремитесь к строгости, но принимайте элемент оценки «на глаз». Мы активно работаем над более мощными инструментами измерения.

#### Количественные метрики

**Skill триггерится на 90% релевантных запросов**

- Как измерить: прогоните 10–20 тестовых запросов, которые должны триггерить skill. Считайте, сколько раз он загрузился автоматически против явного вызова.

**Воркфлоу завершается за X вызовов инструментов**

- Как измерить: сравните одну и ту же задачу с включённым и выключенным skill'ом. Считайте вызовы инструментов и суммарный расход токенов.

**0 проваленных API-вызовов на воркфлоу**

- Как измерить: мониторьте логи MCP-сервера во время тестовых прогонов. Трекайте частоту ретраев и коды ошибок.

#### Качественные метрики

**Пользователю не нужно подсказывать Claude следующие шаги**

- Как оценить: во время тестов отмечайте, как часто вам приходилось перенаправлять или уточнять. Собирайте feedback бета-юзеров.

**Воркфлоу завершается без пользовательских правок**

- Как оценить: выполните один и тот же запрос 3–5 раз. Сравните структурную консистентность и качество вывода.

**Консистентные результаты между сессиями**

- Как оценить: сможет ли новый пользователь пройти задачу с первого раза с минимальными подсказками?

### Технические требования

#### Структура файлов

```
your-skill-name/
├── SKILL.md              # обязательно — главный файл skill'а
├── scripts/              # опционально — исполняемый код
│   ├── process_data.py   # пример
│   └── validate.sh       # пример
├── references/           # опционально — документация
│   ├── api-guide.md      # пример
│   └── examples/         # пример
└── assets/               # опционально — шаблоны и т.д.
    └── report-template.md # пример
```

#### Ключевые правила

**Именование SKILL.md**:

- файл должен называться ровно `SKILL.md` (регистр важен)
- варианты не принимаются (SKILL.MD, skill.md и т.д.)

**Именование папки skill'а**:

- kebab-case: `notion-project-setup` ✅
- без пробелов: `Notion Project Setup` ❌
- без подчёркиваний: `notion_project_setup` ❌
- без заглавных: `NotionProjectSetup` ❌

**Никакого README.md**:

- не кладите README.md внутрь папки skill'а
- вся документация — в SKILL.md или references/
- примечание: при дистрибуции через GitHub вам всё ещё нужен репо-уровневый README для людей — см. «Дистрибуция и шеринг»

### YAML Frontmatter: важнейшая часть

YAML frontmatter — то, как Claude решает, загружать ли ваш skill. Сделайте это правильно.

#### Минимальный обязательный формат

```yaml
---
name: your-skill-name
description: [Что делает skill + когда использовать]
---
```

Это всё, что нужно для старта.

#### Требования к полям

**name (обязательно)**:

- только kebab-case
- без пробелов и заглавных букв
- должно совпадать с именем папки

**description (обязательно)**:

- обязана включать и то, и другое:
  - что делает skill
  - когда его использовать (условия триггера)
- менее 1024 символов
- без XML-тегов (< или >)
- включает конкретные задачи, которые может озвучить пользователь
- если уместно — упоминает типы файлов

**license (опционально)**:

- если skill опенсорсный
- типовые: MIT, Apache-2.0

**compatibility (опционально)**:

- 1–500 символов
- указывает требования к окружению: ожидаемый продукт, нужные системные пакеты, требования к сетевому доступу и т.д.

**metadata (опционально)**:

- любые кастомные пары ключ-значение
- рекомендации: author, version, mcp-server
- пример:

```yaml
metadata:
  author: ProjectHub
  version: 1.0.0
  mcp-server: projecthub
```

#### Ограничения безопасности

**Запрещено во frontmatter**:

- XML-угловые скобки (< >)
- skills с «claude» или «anthropic» в имени (зарезервировано)

Почему: frontmatter попадает в системный промпт Claude. Вредоносный контент мог бы инъецировать инструкции.

### Написание эффективных Skills

#### Поле Description

По инженерному блогу Anthropic: «Эта метадата… даёт достаточно информации, чтобы Claude знал, когда использовать каждый skill, не загружая всё содержимое в контекст». Это первый уровень прогрессивного раскрытия.

**Структура**:

```
[Что делает] + [Когда использовать] + [Ключевые возможности]
```

**Примеры хороших описаний**:

✅ **Хорошо — конкретно и действенно**

```yaml
description: Анализирует файлы Figma-дизайнов и генерирует документацию для передачи разработчикам. Использовать, когда пользователь загружает .fig-файл, спрашивает про «спеки дизайна», «документацию компонентов» или «передачу дизайна в код».
```

✅ **Хорошо — содержит триггерные фразы**

```yaml
description: Управляет воркфлоу проекта в Linear, включая планирование спринтов, создание задач и трекинг статусов. Использовать, когда пользователь упоминает «спринт», «задачи Linear», «планирование проекта» или просит «создать тикет».
```

✅ **Хорошо — ясное ценностное предложение**

```yaml
description: Сквозной воркфлоу клиентского онбординга PayFlow. Обрабатывает создание аккаунтов, настройку платежей и управление подписками. Использовать, когда пользователь говорит «заведи нового клиента», «настрой подписку» или «создай аккаунт PayFlow».
```

**Примеры плохих описаний**:

❌ **Слишком расплывчато**

```yaml
description: Помогает с проектами.
```

❌ **Нет триггеров**

```yaml
description: Создаёт сложные многораничные документные системы.
```

❌ **Слишком технично, без пользовательских триггеров**

```yaml
description: Имплементирует модель сущности Project с иерархическими связями.
```

#### Написание основных инструкций

После frontmatter пишутся сами инструкции в Markdown.

**Рекомендуемая структура**: адаптируйте этот шаблон под свой skill, заменив скобочные фрагменты своим контентом.

````markdown
---
name: your-skill
description: [Что делает skill + когда использовать]
---

# Your Skill Name

## Instructions

### Step 1: [Первый основной шаг]

Ясно объясни, что происходит.

Пример:

```bash
python scripts/fetch_data.py --project-id PROJECT_ID
```

Ожидаемый вывод: [опишите, как выглядит успех]

### Step 2: [Второй основной шаг]

(Добавьте шаги по необходимости)

## Examples

### Example 1: [Типовой сценарий]

Пользователь говорит: «Настрой новую маркетинговую кампанию»

Действия:

1. Получить существующие кампании через MCP
2. Создать новую кампанию с данными параметрами

Результат: кампания создана, с подтверждением-ссылкой

(Добавьте примеры по необходимости)

## Troubleshooting

### Error: [Типовое сообщение об ошибке]

Причина: [почему это происходит]

Решение: [как чинить]

(Добавьте ошибочные кейсы по необходимости)
````

#### Best practices для инструкций

**Конкретность и действенность**

✅ **Хорошо**:

```markdown
Запусти `python scripts/validate.py --input {filename}` для проверки формата данных.
Если валидация упала, частые причины:
- отсутствуют обязательные поля (добавьте их в CSV)
- неверный формат дат (используйте YYYY-MM-DD)
```

❌ **Плохо**:

```markdown
Валидируй данные перед продолжением.
```

**Включайте обработку ошибок**

```markdown
## Common Issues

### MCP connection failed

Если видите «connection refused»:

1. Проверьте, что MCP-сервер запущен: Settings > Extensions
2. Убедитесь, что API-ключ валиден
3. Попробуйте переподключиться: Settings > Extensions > [ваш сервис] > Reconnect
```

**Явно ссылайтесь на бандл-ресурсы**

```markdown
Перед написанием запроса сверься с `references/api-patterns.md`:

- правила rate limiting
- паттерны пагинации
- коды ошибок и обработка
```

**Используйте прогрессивное раскрытие**

Держите SKILL.md сфокусированным на ключевых инструкциях. Подробную документацию переносите в `references/` и линкуйте. (Как работает трёхуровневая система — см. «Ключевые принципы дизайна».)

## Тестирование и итерация

Skills можно тестировать с разной степенью строгости:

- **Ручное тестирование в Claude.ai** — запускайте запросы и наблюдайте поведение. Быстрая итерация без сетапа.
- **Скриптовое тестирование в Claude Code** — автоматизируйте тест-кейсы для воспроизводимой верификации между изменениями.
- **Программное тестирование через skills API** — стройте evaluation-сьюты, прогоняемые по определённым тест-сетам.

Выбирайте метод под ваши требования к качеству и видимость skill'а. Skill для внутреннего пользования маленькой команды и skill, разворачиваемый тысячам корпоративных юзеров, требуют разного тестирования.

> 💡 **Про-тип: итерируйте одну задачу до масштабирования**
>
> Мы обнаружили: самые эффективные авторы skills итерируют одну сложную задачу, пока Claude не справится, а затем экстрагируют выигравший подход в skill. Это эксплуатирует in-context learning Claude и даёт более быстрый сигнал, чем широкое тестирование. Как только есть рабочий базис — расширяйтесь на несколько тест-кейсов ради покрытия.

### Рекомендуемый подход к тестированию

На основе раннего опыта эффективное тестирование skills обычно покрывает три области:

#### 1. Тесты триггеров

**Цель**: убедиться, что skill загружается в правильный момент.

**Тест-кейсы**:

- ✅ триггерится на очевидных задачах
- ✅ триггерится на перефразированных запросах
- ❌ не триггерится на нерелевантных темах

**Пример тест-сьюта**:

Должен триггериться:

- «Помоги настроить новый workspace в ProjectHub»
- «Мне нужно создать проект в ProjectHub»
- «Инициализируй ProjectHub-проект для планирования Q4»

Не должен триггериться:

- «Какая погода в Сан-Франциско?»
- «Помоги написать код на Python»
- «Создай таблицу» (если только ProjectHub-скилл не работает с таблицами)

#### 2. Функциональные тесты

**Цель**: убедиться, что skill производит корректный вывод.

**Тест-кейсы**:

- генерирует валидный вывод
- API-вызовы успешны
- обработка ошибок работает
- edge cases покрыты

**Пример**:

```
Тест: создать проект с 5 задачами
Дано: имя проекта «Q4 Planning», 5 описаний задач
Когда: skill выполняет воркфлоу
Тогда:
- проект создан в ProjectHub
- 5 задач созданы с корректными атрибутами
- все задачи привязаны к проекту
- нет API-ошибок
```

#### 3. Сравнение производительности

**Цель**: доказать, что skill улучшает результат относительно базовой линии.

Используйте метрики из раздела «Определите критерии успеха». Вот как может выглядеть сравнение.

**Сравнение с базой**:

```
Без skill:
- пользователь каждый раз даёт инструкции вручную
- 15 сообщений туда-обратно
- 3 проваленных API-вызова, потребовавших ретраев
- потрачено 12 000 токенов
```

```
С skill:
- автоматическое выполнение воркфлоу
- всего 2 уточняющих вопроса
- 0 проваленных API-вызовов
- потрачено 6 000 токенов
```

### Использование skill skill-creator

skill-creator — доступен в каталоге плагинов Claude.ai или для скачивания в Claude Code — помогает строить и итерировать skills. Если у вас есть MCP-сервер и вы знаете свои топовые 2–3 воркфлоу, функциональный skill можно построить и протестировать за одну сессию — обычно за 15–30 минут.

**Создание skills**:

- генерирует skills из описаний на естественном языке
- создаёт корректный SKILL.md с frontmatter
- предлагает триггерные фразы и структуру

**Ревью skills**:

- помечает частые проблемы (расплывчатые описания, отсутствующие триггеры, структурные проблемы)
- выявляет риски избыточного/недостающего триггера
- предлагает тест-кейсы по заявленной цели skill'а

**Итеративное улучшение**:

- после использования skill'а, если встретили edge cases или сбои, верните эти примеры в skill-creator
- пример: «Используя найденные в этом чате проблемы и решения, улучши обработку skill'ом [конкретного edge case]»

**Как использовать**:

```
«Используй skill skill-creator, чтобы помочь мне построить skill для [ваш юзкейс]»
```

Примечание: skill-creator помогает проектировать и шлифовать skills, но не выполняет автоматизированные тест-сьюты и не выдаёт количественных результатов оценки.

### Итерация на основе фидбека

Skills — живые документы. Планируйте итерации по следующим сигналам:

**Сигналы недотриггера**:

- skill не загружается, когда должен
- пользователи включают его вручную
- вопросы поддержки «когда его использовать?»

Решение: добавьте в description больше деталей и нюансов — включая ключевые слова, особенно технические термины.

**Сигналы перетриггера**:

- skill загружается для нерелевантных запросов
- пользователи его отключают
- путаница с назначением

Решение: добавьте негативные триггеры, повысьте специфичность.

**Проблемы исполнения**:

- неконсистентные результаты
- сбои API-вызовов
- нужны пользовательские правки

Решение: улучшите инструкции, добавьте обработку ошибок.

1. скачайте папку skill'а
2. заархивируйте её (при необходимости)
3. загрузите в Claude.ai через Settings > Capabilities > Skills

### Открытый стандарт

Мы выпустили Agent Skills как открытый стандарт. Как и с MCP, мы верим, что skills должны быть переносимы между инструментами и платформами — один и тот же skill должен работать и на Claude, и на других AI-платформах. При этом некоторые skills рассчитаны на фичи конкретной платформы; авторы могут отметить это в поле compatibility. Мы сотрудничаем с участниками экосистемы по стандарту и рады раннему принятию.

Для программных кейсов — приложений, агентов, автоматизированных воркфлоу, использующих skills, — API даёт прямой контроль над управлением и исполнением skills.

- версионирование и управление через Claude Console
- совместимость с Claude Agent SDK для построения кастомных агентов

**Когда skills через API против Claude.ai**:

| Юзкейс | Лучшая платформа |

| Ручное тестирование и итерация при разработке | Claude.ai / Claude Code |
| Личные разовые воркфлоу | Claude.ai / Claude Code |

| Продакшн-деплои в масштабе | API |
| Автоматизированные пайплайны и агентные системы | API |

Примечание: Skills в API требуют беты инструмента исполнения кода (code execution tool) — она даёт безопасное окружение, необходимое skills для работы.

## Паттерны и траблшутинг

Эти паттерны собраны у ранних адоптеров и внутренних команд. Они описывают подходы, которые мы видим работающими, а не предписывающие шаблоны.

### Выбор подхода: проблема-первая vs инструмент-первая

Представьте строительный гипермаркет. Можно зайти с проблемой — «мне починить кухонный шкаф» — и сотрудник укажет правильный инструмент. А можно выбрать новую дрель и спросить, как применить её к вашей задаче.

Skills работают так же:

- **Проблема-первая**: «Мне нужно настроить project workspace». Ваш skill оркестрирует нужные MCP-вызовы в правильном порядке. Пользователь описывает результат; skill управляет инструментами.
- **Инструмент-первая**: «Я подключил Notion MCP». Ваш skill обучает Claude лучшим воркфлоу и практикам. У пользователя есть доступ; skill даёт экспертизу.

Большинство skills тяготеет к одному направлению. Понимание, какой фреймворк подходит вашему юзкейсу, помогает выбрать правильный паттерн ниже.

### Паттерн 1: Оркестрация последовательного воркфлоу

**Когда использовать**: пользователю нужно выполнять многошаговый процесс в определённом порядке.

**Пример структуры**:

```markdown
## Workflow: Онбординг нового клиента

### Step 1: Создать аккаунт

MCP-инструмент: `create_customer`
Параметры: name, email, company

### Step 2: Настроить платежи

MCP-инструмент: `setup_payment_method`
Дождаться: валидации способа оплаты

### Step 3: Создать подписку

MCP-инструмент: `create_subscription`
Параметры: plan_id, customer_id (из Step 1)

### Step 4: Отправить welcome-письмо

MCP-инструмент: `send_email`
Шаблон: welcome_email_template
```

**Ключевые техники**:

- явная последовательность шагов
- зависимости между шагами
- валидация на каждой стадии
- инструкции отката при сбоях

### Паттерн 2: Координация нескольких MCP

**Когда использовать**: воркфлоу пересекает несколько сервисов.

**Пример: передача из дизайна в разработку**

```markdown
## Фаза 1: Экспорт дизайна (Figma MCP)

1. Экспортировать дизайн-ассеты из Figma
2. Сгенерировать дизайн-спеки
3. Создать манифест ассетов

## Фаза 2: Хранение ассетов (Drive MCP)

1. Создать проектную папку в Drive
2. Загрузить все ассеты
3. Сгенерировать шареные ссылки

## Фаза 3: Создание задач (Linear MCP)

1. Создать задачи для разработки
2. Приложить ссылки на ассеты к задачам
3. Назначить инженерную команду

## Фаза 4: Уведомление (Slack MCP)

1. Постить handoff-резюме в #engineering
2. Включить ссылки на ассеты и референсы задач
```

**Ключевые техники**:

- чёткое разделение фаз
- передача данных между MCP
- валидация перед переходом к следующей фазе
- централизованная обработка ошибок

### Паттерн 3: Итеративное улучшение

**Когда использовать**: качество вывода растёт через итерации.

**Пример: генерация отчётов**

```markdown
## Итеративное создание отчёта

### Черновик

1. Получить данные через MCP
2. Сгенерировать первый черновик отчёта
3. Сохранить во временный файл

### Проверка качества

1. Запустить валидационный скрипт: `scripts/check_report.py`
2. Выявить проблемы:
   - отсутствующие секции
   - неконсистентное форматирование
   - ошибки валидации данных

### Цикл улучшения

1. Исправить каждую выявленную проблему
2. Перегенерировать затронутые секции
3. Ревалидировать
4. Повторять до достижения порога качества

### Финализация

1. Применить финальное форматирование
2. Сгенерировать резюме
3. Сохранить финальную версию
```

**Ключевые техники**:

- явные критерии качества
- итеративное улучшение
- валидационные скрипты
- понимание, когда остановить итерацию

### Паттерн 4: Контекст-осведомлённый выбор инструментов

**Когда использовать**: один и тот же результат, но инструменты различаются по контексту.

**Пример: хранение файлов**

```markdown
## Умное хранение файлов

### Дерево решений

1. Проверить тип и размер файла
2. Определить лучшее место хранения:
   - большие файлы (>10 МБ): cloud storage MCP
   - коллаборативные документы: Notion/Docs MCP
   - файлы кода: GitHub MCP
   - временные файлы: локальное хранилище

### Выполнение хранения

По решению:

- вызвать подходящий MCP-инструмент
- применить специфичные для сервиса метаданные
- сгенерировать ссылку доступа

### Контекст для пользователя

Объяснить, почему выбрано это хранилище
```

**Ключевые техники**:

- ясные критерии решений
- fallback-опции
- прозрачность выбора

### Паттерн 5: Домен-специфический интеллект

**Когда использовать**: skill добавляет экспертизу сверх доступа к инструментам.

**Пример: финансовый комплаенс**

```markdown
## Комплаенс-обработка платежей

### До обработки (комплаенс-проверка)

1. Получить детали транзакции через MCP
2. Применить комплаенс-правила:
   - проверить санкционные списки
   - валидировать юрисдикционное лицензирование
   - оценить уровень риска
3. Залогировать комплаенс-решение

### Обработка

Если комплаенс пройден:

- вызвать MCP-инструмент обработки платежа
- применить надлежащие антифрод-проверки
- обработать транзакцию

Иначе:

- пометить для ручного ревью
- создать комплаенс-кейс

### Аудит-трейл

- залогировать все комплаенс-проверки
- залогировать решения по обработке
- сгенерировать аудит-отчёт
```

**Ключевые техники**:

- доменная экспертиза, встроенная в логику
- комплаенс до действия
- исчерпывающая документация
- ясное управление (governance)

### Траблшутинг

#### Skill не загружается

**Ошибка: «SKILL.md not found in uploaded folder»**

Причина: имя файла не ровно SKILL.md.

Решение:

- переименуйте в SKILL.md (регистр важен)
- проверка: `ls -la` должен показывать SKILL.md

**Ошибка: «Invalid frontmatter»**

Причина: проблемы YAML-формата.

Частые ошибки:

```yaml
# Ошибка — нет разделителя
name: my-skill
description: [описание skill]

# Ошибка — незакрытая кавычка
name: my-skill
description: "[описание skill

# Правильно
---
name: my-skill
description: [описание skill]
---
```

**Ошибка: «Invalid skill name»**

Причина: имя содержит пробелы или заглавные.

```yaml
# Ошибка
name: My Cool Skill

# Правильно
name: my-cool-skill
```

#### Skill не триггерится

**Симптом**: skill никогда не загружается автоматически.

Фикс: измените поле description. Примеры хороших/плохих — в разделе «Поле Description».

**Быстрый чеклист**:

- слишком общий? («помогает с проектами» не работает)
- содержит триггерные фразы, которые пользователь реально скажет?
- упоминает релевантные типы файлов, если применимо?

**Метод дебага**: спросите Claude: «Когда ты использовал бы skill [имя]?» Claude процитирует description. Правьте по тому, чего не хватает.

#### Skill триггерится слишком часто

**Симптом**: skill загружается для нерелевантных запросов.

**Решения**:

1. **Добавьте негативные триггеры**

```yaml
description: Продвинутый анализ данных CSV-файлов. Для статистического моделирования, регрессий, кластеризации. Не использовать для простого исследования данных (вместо этого — data-viz skill).
```

2. **Повысьте специфичность**

```yaml
# Слишком широко
description: Обрабатывает документы

# Конкретнее
description: Обрабатывает PDF-юридические документы для контрактного ревью
```

3. **Уточните охват**

```yaml
description: Обработка платежей PayFlow для e-commerce. Специально для онлайн-платёжных воркфлоу, а не общих финансовых запросов.
```

#### Проблемы MCP-подключения

**Симптом**: skill загружается, но MCP-вызовы падают.

**Чеклист**:

1. Проверьте, что MCP-сервер подключён
   - Claude.ai: Settings > Extensions > [ваш сервис]
   - должен быть статус «connected»

2. Проверьте аутентификацию
   - API-ключ валиден и не истёк
   - выданы подходящие permissions/scopes
   - OAuth-токены обновлены

3. Протестируйте MCP отдельно
   - попросите Claude вызвать MCP напрямую, без skill
   - «получи мои проекты через MCP [сервиса]»
   - если падает — проблема в MCP, а не в skill

4. Валидируйте имена инструментов
   - skill ссылается на корректные имена MCP-инструментов
   - сверьтесь с документацией MCP-сервера
   - имена инструментов чувствительны к регистру

#### Инструкции не соблюдаются

**Симптом**: skill загружается, но Claude не следует инструкциям.

**Частые причины**:

1. **Инструкции слишком многословны**
   - держите инструкции сжатыми
   - используйте буллеты и нумерованные списки
   - детальный справочник вынесите в отдельные файлы

2. **Инструкции «похоронены»**
   - ключевые инструкции — наверх
   - заголовки ## Important или ## Critical
   - при необходимости повторяйте критичные пункты

3. **Расплывчатый язык**

❌ **Плохо**:

```
Убедись, что всё правильно валидировано
```

✅ **Хорошо**:

```
КРИТИЧНО: перед вызовом create_project проверь:
- имя проекта непустое
- назначен минимум один член команды
- дата старта не в прошлом
```

Продвинутая техника: для критичной валидации рассмотрите бандл-скрипт, выполняющий проверки программно, а не языковые инструкции. Код детерминирован; интерпретация языка — нет. Пример паттерна — в Office skills.

4. **Модель «ленится»** — добавьте явные побуждения:

```markdown
## Performance Notes

- потрать время и сделай основательно
- качество важнее скорости
- не пропускай шаги валидации
```

Примечание: добавление этого в пользовательский промпт эффективнее, чем в SKILL.md.

#### Проблемы большого контекста

**Симптом**: skill выглядит медленным или качество ответов деградирует.

**Причины**:

- содержимое skill'а слишком большое
- слишком много skills включено одновременно
- всё загружается вместо прогрессивного раскрытия

**Решения**:

1. **Оптимизируйте размер SKILL.md**
   - детальную документацию перенесите в references/
   - линкуйте референсы вместо инлайна
   - держите SKILL.md менее 5 000 слов

2. **Сократите число включённых skills**
   - оцените, не включено ли у вас одновременно 20–50+ skills
   - практикуйте выборочное включение
   - рассмотрите skill-«паки» по тематикам

### Приложение B: YAML Frontmatter

**Обязательные поля**

```yaml
---
name: skill-name-in-kebab-case
description: [Что делает skill + когда использовать]
---
```

**Все опциональные поля**

```yaml
---
name: skill-name
description: [Что делает + когда использовать + ключевые возможности]
license: MIT # опционально: опенсорс-лицензия
allowed-tools: 'Bash(python:*) Bash(npm:*) WebFetch' # опционально: ограничение доступа к инструментам
metadata: # опционально: кастомные поля
  author: Company Name
  version: 1.0.0
  mcp-server: server-name
  category: productivity
  tags: [project-management, automation]
  documentation: https://example.com/docs
  support: support@example.com
---
```

**Замечания по безопасности**

Разрешено:

- любые стандартные YAML-типы (строки, числа, булевы, списки, объекты)
- кастомные metadata-поля
- длинные описания (до 1024 символов)

Запрещено:

- XML-угловые скобки (< >) — security-ограничение
- исполнение кода в YAML (используется safe YAML-парсинг)
- skills с префиксами «claude» или «anthropic» в имени (зарезервировано)

### Паттерн синергии MCP + Skill

| Компонент | Даёт | Пример |
| --- | --- | --- |
| MCP-сервер | Сырой доступ к инструментам | `create_issue()`, `query_database()` |
| Skill | Интеллект воркфлоу | «При создании баг-репорта сначала проверь дубликаты, затем собери системную информацию, затем создай с правильными лейблами» |
| Вместе | Надёжные автоматизированные воркфлоу | Баг-филинг одним промптом, консистентный каждый раз |

Skills решают частые боли MCP: неконсистентное использование инструментов, пропущенные шаги в воркфлоу, слабую обработку ошибок и необходимость юзеров помнить сложные последовательности. Они превращают «вот некоторые инструменты» в «вот экспертный ассистент».

### Когда использовать Skills против AGENTS.md — или оба

| Подход | Лучше всего для | Как работает |
| --- | --- | --- |
| **Skills** | Конкретные повторяемые воркфлоу | Загружаются по требованию при релевантности |
| **AGENTS.md** | Широкие конвенции и контекст проекта | Всегда присутствует в системном промпте |
| **Оба** | Сложные проекты с конвенциями и воркфлоу | AGENTS.md для горизонтальных знаний, Skills для вертикальных воркфлоу |

AGENTS.md даёт персистентный, всегда доступный контекст о проекте (тех-стек, конвенции кодинга, архитектурные решения). Skills дают экспертизу по требованию для конкретных задач (воркфлоу code review, процедуры деплоя, паттерны тестирования). Для максимальной эффективности используйте AGENTS.md для информации, нужной агенту на каждой задаче, и Skills — для специализированных воркфлоу конкретных операций.

### Пятишаговый цикл итерации (из en-версии)

1. **Протестируйте** skill репрезентативными промптами
2. **Выявите**, где Claude отклоняется от ожидаемого поведения
3. **Диагностируйте**, проблема ли в условиях триггера, инструкциях или примерах
4. **Уточните** конкретную секцию, вызывающую проблемы
5. **Перетестируйте** для проверки фикса и регрессий
