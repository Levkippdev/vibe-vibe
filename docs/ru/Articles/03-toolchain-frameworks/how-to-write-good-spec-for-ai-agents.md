# Как писать хорошие спецификации для AI-агентов

**Автор: Addy Osmani**

**Оригинал: [Читать полную статью](https://addyosmani.com/blog/good-spec/)**

<div class="article-meta">
</div>

> ## Резюме
>
> **TL;DR:** Цель написания спек — дать AI ясный, достаточно детальный, но не перегруженный базлайн исполнения. Нужно специфицировать структуру, стиль, тесты и границы; разбивать большие задачи на меньшие; планировать сначала в read-only режиме, затем исполнять — и непрерывно итерировать по всему процессу.

_«Я видел много дискуссий о спеках AI-агентов, но никогда не находил по-настоящему стабильной, переиспользуемой рамки. Я могу писать спеки, приближающиеся к RFC-уровню детализации, но когда контекст разрастается, модель начинает терять фокус»._

Многие разработчики делят эту фрустрацию: вы пишете то, что выглядит как спека RFC-качества, а модель постепенно дрейфует с ростом контекста. Проблема часто не в «недописании» — а в том, действительно ли спека спроектирована для потребления агентом. Хорошая спека должна ясно ограничивать направление, контролировать нагрузку контекста и эволюционировать по ходу проекта. Статья дистиллирует практики из инструментов вроде Claude Code и Gemini CLI в более переиспользуемую рамку написания спек.

Разберём пять принципов отличных спецификаций для AI-агентов, каждый начиная с ключевого тезиса.

## 1. Начните с высокоуровневого видения, пусть AI детализирует

**Запускайте проект с лаконичной высокоуровневой спеки, затем пусть AI разворачивает её в детальный план.**

Не пытайтесь зафиксировать каждую деталь со старта. Начните с ясных формулировок целей и пары ключевых требований. Относитесь к этому как к «продакт-брифу» и пусть агент драфтит более полную спецификацию. Это задействует силу AI в расширении и дополнении, удерживая руль в ваших руках. Если у проекта нет жёстких технических ограничений с самого начала, такой подход обычно эффективнее.

**Почему работает:** Агенты на LLM великолепны в заполнении деталей, когда высокоуровневые цели ясны — но только когда они действительно знают границы задачи. Дайте короткий, но надёжный план — пусть развернёт в полную спеку (например, `spec.md`). Вы, по сути, строите устойчиво референсируемый «source of truth» для последующей имплементации. Для агентов upfront-планирование часто даже важнее, чем для людей: сначала выровняйте план — и последующий код будет стабильнее.

**Практика:** Начните новую сессию с: «You are an AI software engineer. Draft a detailed specification for [Project X], covering goals, features, constraints, and a step-by-step plan». Держите первый промпт высокоуровневым: «Build a web app that lets users manage to-dos, with accounts, a database, and simple UI». Агент выдаст структурированный драфт: обзор, список фич, предложения тех-стека, модели данных и т.д. Драфт становится общей референсной базой. Отревьюйте его до любого кода — исправьте расхождения, закройте пробелы.

**Используйте plan mode для принуждения к upfront-планированию:** Инструменты вроде Claude Code предлагают plan mode, ограничивающий агента read-only — он может читать код, анализировать контекст и генерировать планы, но не модифицировать файлы. Эта фаза идеальна для рафинирования спек: вы описываете, что построить, агент исследует кодовую базу и выдаёт план — до единой строчки изменений.

## 2. Дайте структуру: шесть доменов, которые покрывают почти всё

**Хорошая спека покрывает шесть ключевых доменов, а не только «что построить».**

Одна из причин, по которым спеки проваливаются: они фокусируются на функциональности, но пропускают операционный контекст, в котором агент работает. Проверенная структура:

**1. Команды и воркфлоу:** Какие команды запускает проект (build, test, lint, dev)? Какие соглашения о коммитах? Какой flow веток?

```markdown
## Commands
- Build: `npm run build`
- Test all: `npm test`
- Test single file: `npm test -- path/to/file.test.ts`
- Lint: `npm run lint`
- Dev server: `npm run dev` (NOT `npm start`)
```

**2. Тестирование:** Какой фреймворк? Как добавлять тесты? Что покрывать тестами? Что НЕ тестировать?

```markdown
## Testing
- Framework: Vitest
- New features require tests before implementation is considered done
- Test files live alongside source: `foo.ts` → `foo.test.ts`
- Use the existing test helpers in `src/test/utils.ts`
```

**3. Структура:** Где живут файлы? Какова архитектура? Какие паттерны использует кодовая база?

**4. Стиль кода:** Конвенции, которым должен следовать агент. Не только linting-правила, но и паттерны: именованные экспорты, обработка ошибок, стратегия импортов.

**5. Git-воркфлоу:** Формат сообщений коммитов, стратегия веток, размер коммитов.

**6. Границы:** Что агент может менять автоматически против того, что требует явного человеческого апрува (подробнее в принципе 4).

**Почему работает:** Агенты принимают лучшие решения, когда контекст операции явно предоставлен. Знание, как запускать тесты, где живут файлы и какие паттерны приемлемы, устраняет класс ошибок с самого начала.

## 3. Модуляризуйте агрессивно

**Разбивайте большие задачи на сфокусированные куски; свежий контекст на задачу бьёт накопленный контекст.**

Когда спека становится большой, не скармливайте её целиком. Разбейте имплементацию на модульные задачи:

**Против одного мега-промпта:**

```
"Implement the entire user management system: registration,
login, password reset, profile editing, avatar upload,
email verification, and admin panel."
```

**За модульный подход:**

```
Task 1: "Implement user registration with email/password,
including Zod validation and duplicate email checks."

Task 2: "Implement login with session management.
Reference the auth patterns in src/auth/existing-pattern.ts"

Task 3: "Implement password reset flow with email tokens."
```

Каждая задача становится свежей сессией (или, по крайней мере, свежим контекстным окном). Агент на задаче 3 не тащит весом проблем задачи 1.

**Почему работает:** Компрессия контекста деградирует качество. К тому времени, как агент добирается до задачи 8 мега-промпта, ранние инструкции были сжаты, суммаризированы или потеряны. Модульные задачи держат каждую единицу работы в свежем, сфокусированном контексте.

**Практика:** Разбивайте проекты на задачи, которые: завершаемы за одну сессию; имеют чёткие критерии успеха; затрагивают управляемое число файлов; зависят максимум от 1–2 других задач.

## 4. Трёхуровневые границы

**Определите чёткие границы: что агент делает всегда, что требует вопроса, что запрещено.**

Агенты без границ либо слишком осторожны (спрашивают перед каждым шагом), либо слишком агрессивны (мержат в main, деплоят в продакшн, удаляют данные). Хорошая спека определяет границы явно:

**✅ Всегда (без вопросов):**

```markdown
## Always
- Fix failing tests that you caused
- Update imports when moving files
- Run the relevant test file after changes to it
- Follow existing code patterns in the codebase
- Create new files for new functionality (don't force into existing files)
```

**⚠️ Сначала спросить:**

```markdown
## Ask First
- Any change to database schema or migrations
- Adding new dependencies to package.json
- Changes to CI/CD pipeline configuration
- Deleting more than 20 lines of existing code
- Changes to authentication or authorization logic
```

**🚫 Никогда:**

```markdown
## Never
- Never deploy to production
- Never merge to main branch
- Never modify files in `config/` directory
- Never expose secrets or API keys in code
- Never disable or skip existing tests
```

**Почему работает:** Трёхуровневая структура устраняет двусмысленность. Агенту не нужно гадать, «достаточно ли это важно, чтобы спросить» — спека решает за него. Это также делает ревью проще: вы знаете, что любые изменения в категориях ✅ безопасны для автоприменения, а всё в ⚠️ требует вашего внимания.

## 5. Итерируйте спеку, а не только код

**Когда агент неправильно понимает, обновлять нужно спеку — не только промпт.**

Провал агента — часто симптом спеки. Вместо перепромптинга в моменте:

1. **Диагностируйте корневую причину:** Агент не понял требования? Спека была двусмысленной? Контекст был разбавлен?
2. **Обновите спеку:** Превратите полученный урок в постоянное правило, пример или ограничение
3. **Перепроверьте с обновлённой спекой:** Убедитесь, что улучшение работает

**Пример итерации:**

```
# Агент постоянно использует `npm start` вместо `npm run dev`
# ВМЕСТО перепромптинга "use npm run dev" в каждой сессии:

## Commands (updated)
- Dev server: `npm run dev`
- IMPORTANT: `npm start` runs production mode — do NOT use for development
```

Спека теперь документирует готчу для всех будущих сессий.

**Почему работает:** Каждая итерация спеки — инвестиция в каждую будущую сессию. Агенты имеют совершенную память о том, что в спеке, но нулевую память между сессиями. Фиксация уроков в спеке накапливает знание.

## Практический шаблон

Вот компактный шаблон спеки, покрывающий пять принципов:

```markdown
# Project Spec: [Name]

## Vision
[1-3 предложения: что это и зачем]

## Commands
- Build: [команда]
- Test: [команда]
- Dev: [команда]
- Lint: [команда]

## Structure
- [Ключевые директории и что в них живёт]
- [Паттерны архитектуры]

## Style
- [Конвенции кодирования]
- [Паттерны обработки ошибок]
- [Предпочтения импортов]

## Testing
- [Фреймворк и структура]
- [Что тестировать всегда]
- [Что не тестировать]

## Git
- [Формат коммитов]
- [Стратегия веток]

## Boundaries
### ✅ Always
- [Автоматические действия]
### ⚠️ Ask First
- [Требуют человеческого апрува]
### 🚫 Never
- [Запрещено]
```

## Синтаксис спек: тонкие моменты

**Пишите требованиям, а не решениям.** «Система должна аутентифицировать юзеров до доступа к профилям» оставляет гибкость имплементации. «Используй middleware X с конфигом Y» может быть устаревшим к следующей неделе.

**Используйте «должно/не должно» для ясности.** «Функция должна возвращать ошибку для невалидного ввода» ясно. «Функция обрабатывает ошибки» двусмысленно.

**Различайте «should» и «may».** «Should» — сильная рекомендация; «may» — опционально. «Система должна логировать ошибки, но может включать стек-трейсы» передаёт интент, оставляя гибкость имплементации.

## Ключевые выводы

1. **Начинайте высокоуровнево, расширяйте итеративно:** Пусть AI драфтит детали из вашего видения. Ревью, рафинируйте, исполняйте.

2. **Структура важна:** Шесть ключевых доменов (команды, тесты, структура, стиль, git-воркфлоу, границы) покрывают то, что агентам нужнее всего.

3. **Модуляризуйте агрессивно:** Разбивайте большие задачи на сфокусированные куски. Свежий контекст на задачу бьёт накопленный контекст.

4. **Трёхуровневые границы:** ✅ Всегда / ⚠️ Сначала спросить / 🚫 Никогда дают ясное, однозначное руководство агенту.

5. **Итерируйте спеку, а не только код:** Когда агенты неправильно понимают, обновлять нужно спеку — не только промпт.

Хорошие спеки + строгая итерация + правильные границы = драматически ниже ставки переделок и дрейфа контекста. Spec-driven development относится к спецификациям как к исполняемым инженерным артефактам, а не одноразовым документам.
