# Мы убрали 80% инструментов нашего агента

**Автор: Andrew Qu (Vercel)**

**Оригинал: [Читать полную статью](https://vercel.com/blog/we-removed-80-percent-of-our-agents-tools)**

<div class="article-meta">
</div>

> Vercel месяцами строил сложный text-to-SQL-агент — и обнаружил: иногда проще — просто лучше. Дача ему способности исполнять произвольные bash-команды обошла каждый тщательно спроектированный инструмент.

Результаты стали лучше.

Мы месяцами строили сложный внутренний text-to-SQL-агент под названием d0, оснащённый специализированными инструментами, обширным промпт-инжинирингом и аккуратным управлением контекстом. Он работал... впритык. И был хрупким, медленным и требовал постоянной поддержки.

Мы попробовали иначе. Вырезали большую часть кода и упростили агента до одного инструмента: **исполнять произвольные bash-команды**. Назвали его файловым агентом. Claude напрямую работает с вашими файлами, используя `grep`, `cat` и `ls`, чтобы разобраться самому.

Агент стал проще — и стал лучше. Success rate вырос с 80% до 100%. Меньше шагов, меньше токенов, быстрее ответы. Всё — делая меньше.

## Что такое d0

Если [v0](https://v0.app/) — наш AI для строительства UI, d0 — наш AI для понимания данных.

d0 переводит вопросы на естественном языке в SQL-запросы к нашей аналитической инфраструктуре, позволяя любому в команде получать ответы без написания кода или ожидания data-команды.

Когда d0 работает хорошо, он демократизирует доступ к данным по всей компании. Когда нет — люди теряют доверие и возвращаются к вопросам аналитикам в Slack. Нам нужен был d0 быстрым, точным и надёжным.

## Не мешайте модели

Оглядываясь, мы решали проблемы, с которыми модель справилась бы сама. Мы предполагали, что она заплутает в сложных схемах, сделает неверные JOIN'ы или галлюцинирует несуществующие таблицы. Так что строили ограждения. Мы префильтровали контекст, ограничивали опции, оборачивали каждое взаимодействие логикой валидации. Мы думали за модель:

- Построили множество специализированных инструментов (поиск схемы, валидация запросов, восстановление ошибок и т.д.)
- Добавили обширный промпт-инжиниринг для ограничения рассуждений
- Использовали аккуратное управление контекстом, чтобы не перегружать модель
- Писали ручной retrieval-код для поверхностной «релевантной» информации схемы

Каждый edge case означал новый патч, каждый апдейт модели — перекалибровку ограничений. Мы тратили больше времени на поддержку скаффолдинга, чем на улучшение самого агента.

**Старая архитектура** (на ToolLoopAgent из AI SDK):

```typescript
import { ToolLoopAgent } from 'ai'
import { GetEntityJoins, LoadCatalog /*...*/ } from '@/lib/tools'

const agent = new ToolLoopAgent({
  model: 'anthropic/claude-opus-4.5',
  instructions: '',
  tools: {
    GetEntityJoins,
    LoadCatalog,
    RecallContext,
    LoadEntityDetails,
    SearchCatalog,
    ClarifyIntent,
    SearchSchema,
    GenerateAnalysisPlan,
    FinalizeQueryPlan,
    FinalizeNoData,
    JoinPathFinder,
    SyntaxValidator,
    FinalizeBuild,
    ExecuteSQL,
    FormatResults,
    VisualizeData,
    ExplainResults
  }
})
```

17 инструментов. Каждый — промпт, схема, обработка ошибок, edge cases. Каждый — то, что нужно поддерживать, отлаживать и калибровать.

## Файловый агент

Вместо этого мы дали Claude ровно один инструмент и полное право исследовать:

```typescript
import { ToolLoopAgent } from 'ai'

const agent = new ToolLoopAgent({
  model: 'anthropic/claude-opus-4.5',
  instructions: `Use bash to explore the files and answer questions.`,
  tools: {
    execute_bash
  }
})
```

Один инструмент. Ноль кастомной логики. Просто модель, файловая система и цель.

Результаты поразили нас:

| Метрика | Старый d0 (17 инструментов) | Файловый агент (1 инструмент) |
|---|---|---|
| **Success rate** | 80% | **100%** |
| **Среднее число шагов** | 14 | **4** |
| **Средние токены** | 45k | **~28k (−37%)** |
| **Задержка** | Медленная (30s+) | **В 3.5 раза быстрее (~9s)** |

Лучше по всем метрикам. Меньше инструментов, меньше сложности, лучше производительность.

## Почему это работает

### 1. Обучающие данные — суперсила

Модели вроде Claude обучались на огромных корпусах реального использования терминала. Комбинации `grep`, `cat`, `ls`, `awk`, `sed`, `sort` и пайпов — паттерны, которые модель видела миллиарды раз. Это как родной язык.

Наши кастомные инструменты (`GetEntityJoins`, `JoinPathFinder`) не имели такого покрытия в обучении. Каждое использование — небольшое усилие: модель должна понять, что делает инструмент, когда его звать, как интерпретировать вывод. Мы боролись с градиентом обучающих данных вместо того, чтобы ехать по нему.

### 2. Bash универсален

Bash-команда — инструмент, который не нужно проектировать, документировать или поддерживать. `grep` уже знает, как искать. `cat` уже умеет читать. `awk` уже агрегирует. Всё, что мы строили — обёртки над способностями, которые уже были у модели.

### 3. Больше инструментов = больше решений = больше ошибок

Каждый инструмент добавляет точку решения. С 17 инструментами модель должна на каждом шаге решать: «Какой из 17 инструментов мне использовать?» Каждое решение — шанс на ошибку. С одним инструментом решений нет — просто используй bash.

### 4. Каскадные ошибки против изолированных

Со сложными пайплайнами инструментов ошибка на раннем шаге (неверный выбор инструмента) каскадирует — последующие инструменты строят на неправильном основании. С bash'ем каждая команда независима: провал на одной команде не заражает следующую.

## Но подождите — а безопасность?

Да, давать агенту произвольный bash — страшно. Вот что мы сделали:

**Песочница**: команды исполняются в изолированном окружении без сетевого доступа (кроме read-only API-эндпоинтов, которые агенту нужны)

**Read-only**: у агентного юзера нет прав записи. Модифицировать файлы агент не может — только читать

**Allowlist команд**: полный доступ к чтению, но опасные команды (`rm`, `sudo`, `chmod`) запрещены на уровне песочницы

**Логирование**: каждая команда и вывод логируются для аудита

Философия: ограничивайте на уровне окружения, не уровне промпта. Модель может попытаться сделать что-то плохое — окружение не даст.

## Что мы узнали о данных

Файловый агент подчеркнул кое-что важное о наших данных: структура имела значение больше, чем мы думали.

Мы реорганизовали аналитические данные из сложной схемы в плоскую файловую структуру:

```
/analytics/
├── schemas/
│   ├── users.json       # таблица, колонки, типы
│   ├── events.json
│   └── sessions.json
├── dims/
│   ├── countries.csv
│   └── plans.csv
├── README.md             # обзор: как связаны сущности
└── examples/
    ├── common-queries.sql
    └── joins-map.md
```

Чем лучше организованы файлы, тем меньше работы агенту — и меньше вероятность ошибок. Ясные имена файлов, последовательные конвенции, README с обзором — всё помогает модели ориентироваться без кастомных инструментов.

**Следствие**: качество вашего агента ограничено качеством вашей организации данных. Прежде чем строить сложных агентов, инвестируйте в простую структуру.

## Когда НЕ упрощать

Наш вывод не «инструменты плохи». Есть случаи, где специализированные инструменты — правильный выбор:

**Когда нужны транзакционные гарантии**: бронирование, платежи, инвентарь — операции, где нужен явный контракт и атомарность

**Когда у вас compliance-требования**: audit trail на уровне операций, SOC2, HIPAA — вам нужны чёткие логи каждого вызова инструмента

**Когда модель слабая**: если модель не может надёжно исполнять bash (меньшие модели), специализированные инструменты с жёсткими схемами надёжнее

**Когда среда hostile**: внешние юзеры, недоверенные входы — вам нужны явные ограничения

Правило: специализированные инструменты покупают надёжность ценой гибкости. Покупайте их, когда надёжность некондициональна. Не покупайте, когда решаете гипотетические проблемы.

## Как применить это к своим агентам

1. **Начните с минимального набора инструментов.** Один инструмент (bash), одна способность. Добавляйте больше только при измеряемой необходимости.

2. **Измеряйте baseline.** Прежде чем добавлять инструменты, зафиксируйте success rate, шаги, токены, задержку. Каждый инструмент должен улучшать эти числа или уходить.

3. **Доверяйте модели.** Современные модели лучше, чем вы думаете, в самостоятельном ориентировании. Дайте им цель и свободу, а не путь пошаговых инструментов.

4. **Структурируйте данные.** Хорошо организованные файлы и README бьют сложные retrieval-системы. Это самое дешёвое улучшение производительности агента.

5. **Ограничивайте окружением, не промптом.** Песочницы, права, allowlist'ы — механические ограничения надёжнее инструкций в промпте.

## Ключевые уроки

1. **Меньше — больше.** Один инструмент (bash) обошёл 17 специализированных. Простота — фича, не компромисс.

2. **Работайте с обучающими данными, не против.** Bash, grep, cat — паттерны из обучающих данных. Не абстрагируйте то, что уже работает.

3. **Хорошие данные > умные инструменты.** Хорошо структурированные, ясно названные файлы с консистентными конвенциями позволяют модели рассуждать эффективно без руководства.

4. **Перестаньте сомневаться в модели.** Современные модели (особенно Claude 4.5+) принимают лучшие решения без ограничений, чем когда вы строите ограждения вокруг их рассуждений.

5. **Измеряйте всё.** Скорость, расход токенов, success rate, шаги — квантифицируйте влияние каждого инструмента, который добавляете или убираете.

Иногда лучшая архитектура агента — почти отсутствие архитектуры. Модель + файлы + цель = оптимум.
