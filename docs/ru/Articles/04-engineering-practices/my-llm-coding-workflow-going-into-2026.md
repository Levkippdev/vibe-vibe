# Мой LLM-кодинг-воркфлоу на 2026 год

**Оригинал: [My LLM Coding Workflow Going Into 2026](https://addyosmani.com/blog/ai-coding-workflow/) (Addy Osmani)**

## Воркфлоу, который выкристаллизовался

После года ежедневного AI-ассистированного кодинга стало ясно: разработчики, выжимающие максимум из LLM, — не те, кто использует самые навороченные инструменты, а те, у кого самая дисциплинированная структура работы. AI-ассистенты — force multipliers, но как любой мощный инструмент, они усиливают и хорошие привычки, и плохие.

Далее — воркфлоу, который я рафинировал через 2025-й и планирую нести в 2026-й. Он построен вокруг трёх фаз: **планирование**, **имплементация** и **ревью**. У каждой фазы — свои AI-точки и, критично, свои места, где человеческое суждение не подлежит компромиссу.

## Фаза 1: Планирование

Фаза планирования — где AI даёт максимальный ROI на потраченный токен. До единой строчки кода используйте AI для исследования пространства решений:

- **Генерация требований**: Опишите фичу на высоком уровне и попросите AI перечислить edge cases, потенциальные режимы отказа и неочевидные требования. Это вскрывает слепые зоны мышления, которые иначе стали бы багами позже.
- **Драфтинг архитектуры**: Попросите AI предложить 2–3 архитектурных подхода с trade-off'ами. Вы ищете не «правильный» ответ — вы ищете структурированное сравнение, помогающее решить быстрее.
- **Исследование зависимостей**: Пусть AI проанализирует потенциальные библиотеки, статус их поддержки, влияние на bundle size и совместимость с вашим стеком.

Ключевой инсайт: планирование с AI — это разговор, а не запрос. Начните широко, потом сужайте. Каждый обмен должен рафинировать ваше понимание и производить артефакты (доки требований, architecture decision records), питающие следующую фазу.

## Фаза 2: Имплементация

Здесь выбор инструмента важнее всего. Разные инструменты сильны на разных уровнях гранулярности:

### Claude Code для сложных задач

Когда нужно построить фичу end-to-end, отрефакторить несколько файлов или рассуждать о системных изменениях — agentic-воркфлоу Claude Code сияет. Он может читать вашу кодовую базу, понимать контекст, планировать многошаговые изменения и исполнять их. Ключ — давать ему ясные, скоупленные задачи с чётко определёнными критериями приёмки.

### Cursor для inline-редактирования

Для сфокусированной работы уровня файла — рефакторинг функции, добавление обработки ошибок в существующий модуль, имплементация чётко определённого интерфейса — inline-редактирование Cursor даёт плотные петли фидбека. Вы видите изменения в контексте, принимаете или отклоняете отдельные правки и быстро итерируете.

### GitHub Copilot для автодополнения

Для мелочей — заполнение boilerplate, завершение паттернов, написание тест-ассертов — tab-completion-модель Copilot непревзойдённа по скорости. Лучше всего, когда интент очевиден из контекста, а дополнение короткое.

### Соответствие инструмента задаче

Самая частая ошибка — использование одного инструмента для всего. Copilot ужасен в мультифайловых рефакторингах. Claude Code — оверкилл для добавления log-стейтмента. Cursor неуклюж для greenfield-архитектуры. Подбирайте инструмент под сложность и scope задачи.

## Фаза 3: Ревью

Фаза, которую большинство разработчиков пропускает — и именно она определяет, шипится AI-код чистым или сломанным.

**Всегда читайте вывод.** Каждую строку. AI-код — это предложение, не deliverable. Вы — engineer of record. Чтение кода не опционально — это способ поддерживать понимание собственной системы.

**Тестируйте до коммита.** AI-код проходит тест «выглядит правильно» гораздо чаще, чем тест «работает правильно». Запустите тесты. Проверьте edge cases. Хитните по эндпоинту. Кликните кнопку. Верификация не подлежит обсуждению.

**Проверяйте когерентность.** У AI нет ментальной модели инвариантов вашей системы. Он может сгенерить функцию, идеально работающую изолированно, но нарушающую предположение, сделанное в другом месте. Ревьюйте с целой системой в голове.

## Управление сессиями

Один из самых недооценённых аспектов AI-кодинга — гигиена сессий:

- **Свежие сессии для чистого контекста**: Переключая задачу — начинайте новую сессию. Протухший контекст предыдущего разговора смещает ответы AI тонкими, трудноотлаживаемыми способами.
- **Разговоры, скоупленные на задачу**: Держите каждый разговор сфокусированным на одной чётко определённой задаче. Сессия, начавшаяся с «имплементируй аутентификацию» и сплывшая к «ещё поправь CSS сайдбара», даст худший результат в обоих направлениях.
- **Загрузка контекста**: В начале сессии явно дайте AI нужный контекст — релевантные файлы, архитектурные ограничения, конвенции кодинга. Не предполагайте, что он знает вашу кодовую базу лишь потому, что вы в IDE.

## Выбор модели

Разные модели — разные сильные стороны. К 2025-му прагматичная стратегия выглядела так:

- **Модели с высоким reasoning** (Claude 3.5 Sonnet, GPT-4) для архитектурных решений, сложного дебага и code review
- **Быстрые модели** (Claude Haiku, GPT-4o-mini) для автодополнений, простых трансформаций и массовых операций
- **Специализированные модели** для доменных задач (code-tuned для чистой генерации кода, instruction-tuned для документации)

Trade-off стоимость-качество реален. Гонять frontier-модель на каждом автодополнении — расточительно. Дешёвая модель на security-чувствительном ревью — безрассудно.

## Промпт-паттерны, которые работают

После тысяч взаимодействий с AI эти паттерны стабильно дают лучшие результаты:

1. **Constraint-first prompting**: Сначала заявите, чего код НЕ должен делать, потом что должен. «Не модифицируй public API. Не добавляй новых зависимостей. В этих ограничениях отрефактори слой данных под repository pattern».
2. **Example-driven specification**: Вместо абстрактного описания поведения покажите конкретный пример входа и ожидаемого выхода.
3. **Инкрементальное рафинирование**: Начните с happy path, проверьте, затем слоями добавляйте обработку ошибок, edge cases и оптимизации отдельными проходами.
4. **Role framing**: «Вы ревьюите этот код как сеньор backend-инженер с фокусом на безопасность» даёт другой (и часто лучший) результат, чем общее «поревьюте код».

## Интеграция AI в существующие воркфлоу

AI не заменяет ваш воркфлоу — он усиливает отдельные шаги внутри него:

- **Описания pull request'ов**: AI может надрафтить из diff'а, но редактируйте для ясности нарратива.
- **Commit-сообщения**: AI-генерация из diff'ов удивительно хороша. Добавьте человеческий контекст про «почему», не только «что».
- **Документация**: AI силён в генерации API-доков из кода. Посредственен в архитектурных доках, требующих системного понимания.
- **Code review**: AI быстро ловит механические проблемы, освобождая людей-ревьюеров для дизайна и логики.

## Дневной ритм

Продуктивный AI-ассистированный день следует ритму:

1. **Утро**: Планируйте день с AI. Генерируйте разбивку задач, выявляйте блокеры, драфтите подходы для сложных задач.
2. **Блоки сфокусированной работы**: Чередуйте AI-имплементацию и ручной кодинг. Используйте AI там, где он добавляет скорости. Кодите вручную, когда нужно глубокое понимание.
3. **Блоки ревью**: Выделяйте время на ревью AI-вывода, запуск тестов и проверку поведения. Никогда не мержите AI-код, который лично не валидировали.
4. **Конец дня**: Используйте AI для документирования сделанного, генерации пропущенных тест-кейсов и планирования завтрашней работы.

## Взгляд в 2026-й

Инструменты будут лучше. Модели — быстрее и дешевле. Контекстные окна — расти. Но фундаментальный воркфлоу — планируй, имплементируй, ревьюить — не изменится. Процветать будут те, кто относится к AI как к мощному, но несовершенному коллаборатору, а не оракулу. Структурируйте воркфлоу, держите планку — остальное пусть делает AI.
