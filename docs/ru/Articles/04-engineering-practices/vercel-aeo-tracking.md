# Как Vercel построил AEO-трекинг для кодинг-агентов

**Авторы: Eric Dodds, Allen Zhou**

**Оригинал: [How We Built AEO Tracking for Coding Agents](https://vercel.com/blog/how-we-built-aeo-tracking-for-coding-agents)**

![Конечный пользователь маркетинговой команды видит консистентный ответ по формату в разных кодинг-агентах](/images/articles/2026-03/vercel-aeo-tracking.png)

AI изменил то, как люди ищут информацию. Для бизнеса критично понимать, как LLM ищут и пересказывают контент их сайта.

Мы строим систему AI Engine Optimization (AEO), которая трекает, как модели находят, интерпретируют и цитируют Vercel и наши сайты.

Поначалу это был прототип только для стандартных чат-моделей, но мы быстро поняли: этого мало. Чтобы реально увидеть visibility, в трекинг нужно включить и кодинг-агентов.

Для стандартных моделей трекинг относительно прост. Мы используем [AI Gateway](https://vercel.com/ai-gateway), чтобы отправлять промпты десяткам популярных моделей (GPT, Gemini, Claude и др.), и анализируем их ответы, поисковое поведение и цитируемые источники.

Но кодинг-агенты ведут себя совершенно иначе. Многие пользователи Vercel взаимодействуют с AI через терминал или IDE во время активной разработки проекта. В ранних сэмплах мы обнаружили: кодинг-агенты выполняют веб-поиск примерно в 20% промптов. Поскольку эти поиски происходят инлайн с реальной дев-работой, оценка качества ответов и точности источников особенно важна.

Измерение AEO кодинг-агентов требует другого подхода, чем тестирование чистых моделей. Кодинг-агенты не спроектированы отвечать на одиночный API-вызов. Они созданы работать внутри проекта и ожидают полноценную dev-среду: файловую систему, shell-доступ и пакетный менеджер.

Это приносит новый набор вызовов:

1. **Изоляция исполнения**: как безопасно запускать автономных агентов, исполняющих произвольный код?
2. **Наблюдаемость**: как захватывать поведение агентов, когда у каждого свой формат логов, конвенции tool-вызовов и структура вывода?

## Жизненный цикл AEO для кодинг-агентов

Кодинг-агенты обычно доступны через CLI, а не API. Даже если вы просто шлёте промпт и захватываете ответ, CLI нужно установить и исполнить в полноценном runtime-окружении.

[Vercel Sandbox](https://vercel.com/sandbox) решает это, предоставляя временные Linux MicroVM, поднимающиеся за секунды. Каждый запуск агента получает собственный sandbox и проходит один и тот же шестишаговый жизненный цикл — независимо от того, какой CLI используется.

1. **Создание sandbox**: поднимаем новый MicroVM с правильным runtime (Node 24, Python 3.13 и т.д.) и таймаутом. Таймаут — жёсткий потолок: если агент завис или зациклился, sandbox его остановит.

2. **Установка CLI агента**: каждый агент публикуется как npm-пакет (`@anthropic-ai/claude-code`, `@openai/codex` и т.д.). Sandbox ставит его глобально, чтобы он был доступен как shell-команда.

3. **Инъекция кредов**: вместо выдачи каждому агенту API-ключа мы задаём переменные окружения, роутящие все LLM-вызовы через Vercel AI Gateway. Это даёт единое логирование, rate limiting и трекинг затрат, даже если агенты используют разных underlying-провайдеров (система также позволяет прямые провайдерские ключи).

4. **Запуск агента с промптом**: единственный шаг, отличающийся от агента к агенту. У каждого CLI свои паттерны вызова, флаги и форматы конфигурации. Но с точки зрения sandbox это просто shell-команда.

5. **Захват транскрипта**: после завершения агента мы извлекаем запись того, что он делал — какие инструменты вызывал, искал ли в вебе и что рекомендовал в ответе. Это агенто-специфично (см. ниже).

6. **Очистка**: останавливаем sandbox. Блок `catch` гарантирует остановку sandbox при любых проблемах — чтобы не течь ресурсами.

В коде жизненный цикл выглядит так:

```typescript
import { Sandbox } from '@vercel/sandbox'

// Шаг 1: создать sandbox
sandbox = await Sandbox.create({
  resources: { vcpus: 2 },
  timeout: 10 * 60 * 1000
})

// Шаг 2: установить CLI агента
for (const setupCmd of agent.setupCommands) {
  await sandbox.runCommand('sh', ['-c', setupCmd])
}

// Шаг 3: инъекция кредов AI Gateway (через env-переменные в шаге 4)

// Шаг 4: запустить агента
const fullCommand = `AI_GATEWAY_API_KEY='${aiGatewayKey}' ${agent.command}`
const result = await sandbox.runCommand('sh', ['-c', fullCommand])

// Шаг 5: захватить транскрипт (агенто-специфично — см. следующий раздел)

// Шаг 6: очистка
await sandbox.stop()
```

### Агент как конфиг

Раз жизненный цикл унифицирован, каждый агент определяется простым конфиг-объектом. Добавить нового агента в систему = добавить новую запись; sandbox-оркестрация делает всё остальное.

```typescript
export const AGENTS: Agent[] = [
  {
    id: 'anthropic/claude-code',
    name: 'Claude Code',
    setupCommands: ['npm install -g @anthropic-ai/claude-code'],
    buildCommand: prompt => `echo '${prompt}' | claude --print`
  },
  {
    id: 'openai/codex',
    name: 'OpenAI Codex',
    setupCommands: ['npm install -g @openai/codex'],
    buildCommand: prompt => `codex exec -y -S '${prompt}'`
  }
]
```

`runtime` определяет базовый образ MicroVM. Большинство агентов работает на Node, но система поддерживает и Python-runtime.

`setupCommands` — массив, потому что некоторым агентам мало глобальной установки. Например, Codex требует записать TOML-конфиг в `~/.codex/config.toml`.

`buildCommand` — функция, принимающая промпт и возвращающая shell-команду для запуска. У CLI каждого агента свои флаги и стиль вызова.

## Роутинг через AI Gateway

Мы хотели централизованно управлять затратами и логами через AI Gateway. Для этого базовый URL провайдера переопределяется env-переменными внутри sandbox. Сам агент не знает об этом и работает так, будто общается с провайдером напрямую.

Вот имплементация для Claude Code:

```typescript
const claudeResult = await sandbox.runCommand('claude', ['-p', '-m', options.model, '-y', options.prompt], {
  env: {
    ANTHROPIC_BASE_URL: AI_GATEWAY.baseUrl,
    ANTHROPIC_AUTH_TOKEN: options.apiKey,
    ANTHROPIC_API_KEY: '' // намеренно пусто — аутентификацию обрабатывает AI Gateway
  }
})
```

`ANTHROPIC_BASE_URL` указывает на AI Gateway вместо `api.anthropic.com`. HTTP-вызовы агента уходят в Gateway, который проксирует их в Anthropic.

`ANTHROPIC_API_KEY` намеренно установлен в пустую строку — Gateway аутентифицируется собственным токеном, поэтому агенту прямой провайдерский ключ не нужен (его и нет).

Тот же паттерн работает для Codex (переопределение `OPENAI_BASE_URL`) и любого другого агента, следующего convention базового URL в env-переменных. Можно и напрямую использовать провайдерские API-креды.

## Проблема форматов транскриптов

После завершения прогона агента в sandbox у нас есть сырой транскрипт — запись всего, что сделал агент.

Проблема: каждый агент генерирует его в своём формате. Claude Code пишет JSONL-файл на диск. Codex стримит JSON в stdout. OpenCode тоже использует stdout, но с другой схемой. Разные имена для одних и тех же инструментов, разная вложенность сообщений, разные конвенции.

Нам нужно было пропустить всё это через единую брендовую пайплайн, поэтому мы построили четырёхфазный слой нормализации:

1. **Захват транскрипта**: каждый агент хранит транскрипт по-своему, поэтому шаг агенто-специфичен.

2. **Парсинг**: у каждого агента свой парсер, нормализующий имена инструментов и расплющивающий агенто-специфичные структуры сообщений в единый тип событий.

3. **Обогащение**: общий пост-процессинг, извлекающий структурированные метаданные из аргументов инструментов (URL, команды) и нормализующий различия в именовании аргументов.

4. **Суммаризация и бренд-экстракция**: унифицированные события агрегируются в статистику и попадают в ту же пайплайн бренд-экстракции, что используется для ответов стандартных моделей.

### Фаза 1: захват транскрипта

Происходит, пока sandbox ещё жив (шаг 5 из жизненного цикла выше).

**Claude Code** пишет транскрипт как JSONL-файл в файловую систему sandbox. Нужно найти и прочитать его после завершения агента:

```typescript
async function captureTranscript(sandbox) {
  const workdir = sandbox.getWorkingDirectory()
  const projectPath = workdir.replace(/\//g, '-')
  const claudeProjectDir = `~/.claude/projects/${projectPath}`

  // найти самый свежий .jsonl-файл
  const findResult = await sandbox.runShell(`ls -t ${claudeProjectDir}/*.jsonl 2>/dev/null | head -1`)

  const transcriptPath = findResult.stdout.trim()
  return await sandbox.readFile(transcriptPath)
}
```

**Codex и OpenCode** выводят транскрипт в stdout, поэтому захват проще — фильтруем JSON-строки из вывода:

```typescript
function extractTranscriptFromOutput(output: string) {
  const lines = output.split('\n').filter(line => {
    const trimmed = line.trim()
    return trimmed.startsWith('{') && trimmed.endsWith('}')
  })
  return lines.join('\n')
}
```

Выход этой фазы одинаков для всех агентов: сырая JSONL-строка. Но структура каждой JSON-строки всё ещё совершенно разная — этим занимается следующая фаза.

### Фаза 2: парсинг имён инструментов и форм сообщений

Мы построили по выделенному парсеру на каждого агента, каждый делает две вещи: нормализует имена инструментов и расплющивает агенто-специфичные структуры сообщений в единый формат событий.

**Нормализация имён инструментов**

Одна и та же операция в разных агентах называется по-разному:

| Операция | Claude Code | Codex | OpenCode |
| --- | --- | --- | --- |
| Прочитать файл | `Read` | `read_file` | `read` |
| Записать файл | `Write` | `write_file` | `write` |
| Отредактировать файл | `StrReplace` | `patch_file` | `patch` |
| Запустить команду | `Bash` | `shell` | `bash` |
| Поиск в вебе | `WebFetch` | _(varies)_ | _(varies)_ |

Каждый парсер держит lookup-таблицу, мапящую агенто-специфичные имена в ~10 канонических:

```typescript
export type ToolName =
  | 'file_read'
  | 'file_write'
  | 'file_edit'
  | 'shell'
  | 'web_fetch'
  | 'web_search'
  | 'glob'
  | 'grep'
  | 'list_dir'
  | 'agent_task'
  | 'unknown'

const claudeToolMap = {
  Read: 'file_read',
  Write: 'file_write',
  Bash: 'shell',
  WebFetch: 'web_fetch',
  Glob: 'glob',
  Grep: 'grep' /* ... */
}

const codexToolMap = {
  read_file: 'file_read',
  write_file: 'file_write',
  shell: 'shell',
  patch_file: 'file_edit' /* ... */
}

const opencodeToolMap = {
  read: 'file_read',
  write: 'file_write',
  bash: 'shell',
  rg: 'grep',
  patch: 'file_edit' /* ... */
}
```

**Расплющивание форм сообщений**

Помимо имён, структура событий различается между агентами:

- **Claude Code** вкладывает сообщения в свойство `message` и смешивает блоки `tool_use` в content-массиве.
- **Codex** имеет lifecycle-события Responses API (`thread.started`, `turn.completed`, `output_text.delta`) плюс события инструментов.
- **OpenCode** бандлит tool-вызов + результат в одном событии через `part.tool` и `part.state`.

Парсер каждого агента обрабатывает эти структурные различия и сворачивает всё в единый тип `TranscriptEvent`:

```typescript
export interface TranscriptEvent {
  timestamp?: string
  type: 'message' | 'tool_call' | 'tool_result' | 'thinking' | 'error'
  role?: 'user' | 'assistant' | 'system'
  content?: string
  tool?: {
    name: ToolName // каноническое имя
    originalName: string // агенто-специфичное имя (для дебага)
    args?: Record<string, unknown>
    result?: unknown
  }
}
```

Выход фазы — плоский массив `TranscriptEvent[]` одной формы, каким бы агентом он ни был сгенерирован.

### Фаза 3: обогащение

После парсинга по всем событиям проходит общий пост-процессинг. Он извлекает структурированные метаданные из аргументов инструментов, чтобы downstream-коду не нужно было знать, что Claude Code кладёт путь к файлу в `args.path`, а Codex — в `args.file`:

```typescript
if (['file_read', 'file_write', 'file_edit'].includes(event.tool.name)) {
  const path = extractFilePath(args)
  if (path) event.tool.args = { ...args, _extractedPath: path }
}

if (event.tool.name === 'web_fetch') {
  const url = extractUrl(args)
  if (url) event.tool.args = { ...args, _extractedUrl: url }
}
```

### Фаза 4: суммаризация и бренд-экстракция

Обогащённый массив `TranscriptEvent[]` сворачивается в агрегированную статистику (суммарные tool-вызовы по типам, web fetch, ошибки) и подаётся в ту же пайплайн бренд-экстракции, что обслуживает ответы стандартных моделей. С этой точки система не знает и не волнуется, пришли данные от кодинг-агента или из API-вызова модели.

## Оркестрация через Vercel Workflow

Вся пайплайн работает как [Vercel Workflow](https://vercel.com/workflow). Когда промпт помечен типом «agents», workflow параллельно fan-out'ится на все сконфигурированные агенты, у каждого свой sandbox:

```typescript
export async function probeTopicWorkflow(topicId: string) {
  'use workflow'

  const agentPromises = AGENTS.map((agent, index) => {
    const command = agent.buildCommand(topicData.text)
    return queryAgentAndSave(
      topicData.text,
      run.id,
      {
        id: agent.id,
        name: agent.name,
        setupCommands: agent.setupCommands,
        command
      },
      index + 1,
      totalQueries
    )
  })

  const results = await Promise.all(agentPromises)
}
```

## Что мы узнали

- **Кодинг-агенты приносят значительный трафик из веб-поиска**. Ранние тесты на случайной выборке промптов показали: кодинг-агенты ищут в вебе примерно в 20% случаев. По мере сбора данных мы выстроим более полную картину поискового поведения агентов, но эти результаты ясно говорят: оптимизировать контент под кодинг-агентов важно.

- **Форма рекомендаций агентов отличается от ответов моделей**. Когда кодинг-агент рекомендует инструмент, он склонен генерировать рабочий код этого инструмента — import-стейтменты, конфиги или деплой-скрипты. Рекомендация встроена в вывод, а не просто упомянута текстом.

- **Форматы транскриптов — бардак**. По мере быстрых обновлений агентных CLI их становится только больше. Ранняя постройка слоя нормализации спасла нас от постоянных поломок.

- **Одна и та же пайплайн бренд-экстракции работает и для моделей, и для агентов**. Сложная часть — всё, что выше по потоку: заставить агента работать, захватить, что он сделал, и нормализовать это в структуру, которую можно скорить.

### Что такое AEO

Если SEO (Search Engine Optimization) — про то, чтобы ваш контент находили поисковики, то **AEO (Agent Experience Optimization)** — про то, чтобы ваша инфраструктура, API и документация хорошо работали для AI-агентов. Кодинг-агенты становятся основным потребителем дев-инструментов и платформ — понимание того, как они взаимодействуют с вашими системами, уже не опция, а конкурентная необходимость.

### Почему агенты «невидимы» для традиционной аналитики

Традиционные аналитические инструменты построены вокруг паттернов человеческого взаимодействия: просмотры страниц, CTR, длительность сессий. AI-агенты взаимодействуют с инфраструктурой принципиально иначе:

- **Нет сессий**: агент делает дискретные API-вызовы, не «бродит» по сайту
- **Нет UI**: агенты не видят ваш дашборд — они потребляют API-ответы и документацию
- **Много объёма, мало разнообразия**: агенты часто делают много похожих запросов подряд
- **Успех бинарен**: агент либо завершил задачу, либо нет. Поведения «просто посмотреть» нет

### Ключевые метрики

- **Task Completion Rate** — процент инициированных агентами воркфлоу, достигающих целевого конечного состояния. North star метрика AEO: если агенты не завершают задачи на вашей платформе, они (и их юзеры) уйдут в другое место.
- **Токен-эффективность** — сколько токенов потребляет агент на конкретную задачу. Высокое потребление обычно означает, что агент мучается: перечитывает документацию, ретраит провалы, исследует тупики.
- **Паттерны ошибок** — не просто rate ошибок, но кластеризация. Один эндпоинт, вызывающий 80% агентных провалов, — ясная цель оптимизации; стабильно неверное использование параметра API — сигнал, что его документация требует улучшения.
- **Time to Completion** — сколько времени агент тратит на стандартную задачу; вместе с токен-эффективностью отделяет сложность (легитимно длинные задачи) от трения (ненужные ретраи и блуждания).

### Как AEO-инсайты улучшают продукт

AEO-трекинг — не просто мониторинг, а продуктовая петля фидбека:

- **Дизайн API**: когда агенты мучаются с API — это часто вскрывает проблемы дизайна, которые люди молча обходят. Фиксы улучшают опыт всех.
- **Документация**: страницы, которые агенты посещают раз за разом без успеха в задаче, нужно переписывать.
- **Сообщения об ошибках**: генерические ошибки, которые люди интерпретируют по контексту, для агентов бесполезны — AEO-данные ведут инвестиции в структурированные, машино-парсабельные ответы.
- **Rate limiting**: традиционные лимиты под человеческие паттерны не учитывают агентное burst-поведение — AEO-данные формируют агентно-осведомлённые политики.

### Большая картина

AEO-трекинг — фундаментальный сдвиг в том, как платформы думают о юзерах. AI-агенты становятся основным интерфейсом между разработчиками и инструментами — оптимизация опыта агентов есть оптимизация опыта разработчиков. Инвестиция Vercel в AEO — не только понимание текущего поведения агентов, но строительство инфраструктуры под будущее, где агенты — first-class граждане платформы.
