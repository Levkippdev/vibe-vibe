# 6.2 Отправляем код в удалённый repository и делаем deploy через EdgeOne Pages

Deploy выглядит пугающе из-за того, что на поверхности тянет за собой много терминов: repository, remote, build, платформа, переменные окружения, логи. Но для базовой версии достаточно сначала просто запустить цикл. Начните с push кода в удалённый repository — он служит одновременно бэкапом и источником, из которого читает платформа deploy; затем подключите этот repository к платформе deploy и опубликуйте проект, используя вариант по умолчанию, более доступный из Китая — например, EdgeOne Pages.

## Сначала запомните этот путь

Базовая версия не требует сразу полностью понять принципы deploy. Пока достаточно запомнить этот минимальный путь:

```text
Локальный проект
-> Удалённый repository
-> Платформа deploy
-> Публичный URL
```

Когда эта цепочка работает, ваш проект больше не существует только на вашем компьютере.

## Почему сначала нужен push в удалённый repository

Многие новички спрашивают: если код уже есть локально, зачем ещё сначала идти на GitHub или Gitee? Причина проста: здесь удалённый repository выполняет сразу две роли:

- Это бэкап вашего кода
- Это источник, из которого читает платформа deploy

Так что этот шаг не избыточен — он часть pipeline релиза.

## Для первого deployа — просто заставьте его работать

Здесь важнее не понимать каждую деталь под капотом, а не загнать себя в мышление «сделаю deploy, только когда во всём разберусь». Цель первого deploy — просто заставить его работать, а не понять каждую настройку за один заход. Многие значения по умолчанию поначалу вполне годятся. Базовая версия также не требует входить в workflow коллаборации. Branch-стратегии, PR и командные процессы пока учить не нужно.

Достаточно пройти минимальный путь:

1. Создать удалённый repository
2. Запушить туда локальный код
3. Подключить repository в EdgeOne Pages
4. Один раз прогнать с конфигурацией build по умолчанию
5. Получить первый доступный URL

В этот момент проект по-настоящему покинул ваш компьютер.

## Если deploy упал — сначала смотрите логи, потом отдавайте их AI

Если что-то по пути упало, не начинайте сразу сомневаться, а вдруг вы в принципе не знаете, что делаете. Сначала посмотрите логи, потом вставьте их в AI и пусть он поможет определить: проблема в команде build, в переменных окружения или в настройках платформы.

Можно спросить прямо так:

```text
Это build-логи, которые я вижу на платформе deploy.
Сначала помоги определить наиболее вероятную причину падения.
Скажи мне только одно, что менять следующим, — не выкладывай сразу много вариантов.
```

Это, по сути, тот же подход, что и в главе 2 при локальном запуске проекта: сначала смотрим на симптомы, потом сужаем scope.
